아키텍처 케이스 · 7

트래픽 급증에 스케일아웃이 못 따라갔다

Auto Scaling은 설정되어 있었고 정책도 있었습니다. 그런데도 10분 동안 오류를 냈습니다. 원인은 정책의 유무가 아니라 반응이 완료되기까지의 지연 구간입니다. 지표를 모으고, 알람을 평가하고, 인스턴스를 시작하고, 초기화가 끝나기까지의 시간이 급증 속도보다 느리면 부족 구간이 생깁니다.

주 도메인: 복원력 있는 아키텍처 설계(26%) · 과제 진술 2.1 확장 가능하고 느슨하게 결합된 아키텍처 설계

학습 목표

  • 스케일아웃 반응이 완료되기까지의 지연 구간을 단계별로 분해할 수 있습니다.
  • 대상 추적 · 단계 조정 · 단순 · 예측 스케일링 정책의 성격을 구분해 고를 수 있습니다.
  • 워밍업과 쿨다운이 어떤 오작동을 막는지 설명할 수 있습니다.
  • 예측 가능한 급증에 예약 스케일링을 적용하는 판단을 할 수 있습니다.
  • 큐로 요청을 완충해 처리 속도와 유입 속도를 분리하는 설계를 설명할 수 있습니다.

상황

티켓 예매 서비스가 Application Load Balancer 뒤에서 Auto Scaling 그룹으로 운영됩니다. 평상시 인스턴스는 4대이고, 다음과 같이 설정되어 있습니다.

  • 스케일링 정책은 평균 CPU 사용률 70% 기준의 단순 조정 정책 하나입니다. 한 번에 1대를 추가합니다.
  • 인스턴스는 부팅 후 애플리케이션 초기화와 캐시 예열에 수 분이 걸립니다.
  • 워밍업과 쿨다운 값은 기본 상태로 두었습니다.
  • 공연 티켓 오픈 시각은 매주 화요일 오후 2시로 정해져 있습니다.

오픈 시각에 다음이 일어났습니다.

  1. 요청이 수십 배로 뛰었고 4대의 CPU가 곧바로 포화됐습니다.
  2. 지표가 집계되고 알람이 임계값 위반을 확정하기까지 시간이 걸렸습니다.
  3. 정책이 발동했지만 한 번에 1대만 추가했습니다.
  4. 새 인스턴스가 준비되기 전에 상태 확인이 실패해 일부가 비정상으로 판정되어 교체됐습니다.
  5. 쿨다운이 끝날 때까지 다음 추가가 지연됐습니다.
  6. 결국 필요한 대수에 도달했을 때는 피크가 지나간 뒤였습니다.

"Auto Scaling을 켜 두었다"는 것은 대비가 되었다는 뜻이 아닙니다. 스케일아웃은 반드시 사후 반응이고, 반응에는 시간이 듭니다. 급증 속도가 반응 속도보다 빠르면 부족 구간은 반드시 생깁니다. 설계에서 정할 것은 "부족 구간을 없앨 수 있는가"가 아니라 "부족 구간을 얼마나 줄이고, 남는 구간을 무엇으로 견딜 것인가"입니다.

지연 구간을 나눈다

스케일아웃이 완료되기까지의 구간과 각각을 줄이는 수단
구간 무슨 일이 일어나는가 줄이는 수단
1. 지표 집계 부하 변화가 지표에 반영되기까지 시간이 걸린다 세부 모니터링 사용, 반응이 빠른 지표 선택
2. 알람 평가 임계값 위반이 확정되어야 정책이 발동한다 평가 기간 조정, 대상 추적 정책 사용
3. 용량 계산 몇 대를 늘릴지 결정한다 단계 조정으로 위반 크기에 비례해 늘린다
4. 인스턴스 시작 인스턴스가 시작되고 부팅한다 가벼운 AMI, 예열 풀(warm pool)
5. 애플리케이션 초기화 런타임 기동, 의존성 연결, 캐시 예열 이미지에 미리 굽기, 워밍업 값 정확히 설정
6. 트래픽 수용 상태 확인 통과 후 대상 그룹에 들어간다 상태 확인 간격과 임계 횟수 조정

이 케이스에서 가장 큰 구간은 3(한 번에 1대)과 5(초기화 시간을 워밍업에 반영하지 않음)입니다. 그리고 급증 시각이 정해져 있다는 사실이, 반응을 빠르게 하는 것보다 더 좋은 답을 가능하게 합니다.

선택과 근거

D안을 고릅니다. 예측 가능한 급증은 예약 스케일링으로 미리 세우고, 예측하지 못한 급증은 대상 추적 정책으로 따라가며, 그래도 남는 부족 구간은 큐로 견딥니다. 세 수단이 서로 다른 문제를 담당합니다.

이 케이스의 원래 설정이 SimpleScaling이었다는 점이 문제의 절반입니다. 한 번 조정한 뒤 쿨다운을 기다리므로 급증을 따라갈 수 없습니다.

대상 추적 정책이 쓸 수 있는 사전 정의 지표는 ASGAverageCPUUtilization, ASGAverageNetworkIn, ASGAverageNetworkOut, ALBRequestCountPerTarget입니다. 웹 티어에서는 CPU보다 대상당 요청 수가 부하를 더 직접적으로 반영하는 경우가 많습니다. CPU는 요청이 몰린 뒤에야 올라가므로 한 박자 늦습니다.

워밍업과 쿨다운

새 인스턴스가 아직 준비되지 않았는데 지표에 포함되면 평균이 왜곡되어 필요 이상으로 인스턴스를 늘리거나, 준비 중인 인스턴스가 비정상으로 판정되어 교체됩니다. 이 케이스에서 4번 증상이 정확히 그것입니다.

워밍업과 쿨다운의 역할 구분
설정 무엇을 막는가 값을 정하는 근거
기본 인스턴스 워밍업 준비 중인 인스턴스가 지표에 포함되어 과잉 확장이 일어나는 것 실제 초기화 완료까지의 시간을 측정해 넣는다
상태 확인 유예 기간 준비 중인 인스턴스가 비정상으로 판정되어 교체되는 것 워밍업보다 넉넉하게
쿨다운 연속된 조정이 겹쳐 널뛰는 것 단순 조정 정책에서만 중요하다. 대상 추적에서는 워밍업이 그 역할을 한다

예약 스케일링 — 정해진 시각에는 미리 세운다

오픈 시각이 정해져 있다면 반응을 빠르게 만들 이유가 없습니다. 미리 세워 두면 반응이 필요 없습니다. 예약 스케일링은 최소·최대·희망 용량을 시각에 맞춰 바꿉니다.

--recurrence는 UTC 기준으로 해석되는 것이 기본입니다. 현지 시각으로 지정하려면 시간대를 명시해야 하고, 그러지 않으면 서머타임이나 시차 때문에 엉뚱한 시각에 확장됩니다. 위 예시의 04:30 UTC는 한국 표준시 13:30에 해당합니다.

또한 예약 스케일링으로 최소 용량을 올린 뒤 되돌리는 작업을 반드시 짝으로 만들어야 합니다. 되돌리지 않으면 대상 추적 정책이 축소하려 해도 최소 용량에 막혀 비용이 계속 발생합니다.

예열 풀 — 시작과 초기화 구간을 미리 끝내 둔다

초기화 시간을 당장 줄일 수 없다면(제약 3), 인스턴스를 미리 시작해 초기화까지 끝낸 뒤 중지 상태로 대기시킬 수 있습니다. 확장이 필요할 때 이 인스턴스를 깨우면 부팅과 초기화 구간이 사라집니다.

중지 상태로 두면 인스턴스 사용 요금은 발생하지 않지만 볼륨 요금은 계속됩니다. 예열 풀의 크기를 정할 때는 이 점을 고려합니다.

큐로 유입과 처리를 분리한다

제약 1(결제 요청 유실 불가)과 요구 2(예측 못 한 급증)를 함께 만족시키는 것은 완충 계층입니다. 웹 계층은 요청을 검증하고 큐에 넣은 뒤 즉시 응답하고, 처리 계층이 자기 속도로 큐를 소비합니다.

웹 인스턴스가 결제 처리를 동기로 수행합니다. 처리 속도가 유입 속도보다 느리면 요청이 대기하다가 타임아웃으로 실패하고, 사용자는 결제가 됐는지 알 수 없습니다. 부하가 그대로 데이터베이스까지 전달됩니다.

웹 인스턴스는 요청을 큐에 넣고 접수 번호를 즉시 돌려줍니다. 처리 계층은 큐 적체량을 기준으로 확장하며, 확장이 늦어도 요청은 큐에 남아 있으므로 유실되지 않습니다. 데이터베이스는 처리 계층의 속도만큼만 부하를 받습니다.

큐 완충을 도입할 때 정해야 하는 것
항목 결정 근거
큐 유형 순서와 중복 제거가 필요하면 FIFO, 아니면 표준 표준 큐는 처리량이 훨씬 크고, FIFO는 메시지 그룹 안에서 순서를 보장한다
확장 지표 큐의 대기 메시지 수를 인스턴스 수로 나눈 값 CPU보다 적체를 직접 반영한다
가시성 제한 시간 한 건 처리에 걸리는 최대 시간보다 길게 짧으면 처리 중인 메시지가 다시 전달되어 중복 처리된다
배달 못한 편지 큐(DLQ) 최대 수신 횟수를 정하고 별도 큐로 보낸다 독이 든 메시지가 큐를 막는 것을 방지한다
사용자 경험 접수 확인과 완료 알림을 나눈다 비동기 처리는 화면 흐름 변경을 동반한다

큐 유형과 속성의 세부 사항은 12장 서버리스와 애플리케이션 통합에서 다루고, 직접 만들어 보려면 실습 7 · SQS + Lambda 비동기 처리를 따라 합니다.

좌석 조회처럼 즉시 응답해야 하는 경로(제약 2)는 큐로 바꾸지 않습니다. 대신 읽기 경로는 캐시로, 쓰기 경로는 큐로 나누는 것이 이 유형의 표준 처방입니다. 읽기 부하 처리는 케이스 2 · 읽기 부하로 데이터베이스가 죽었다에서 다룹니다.
