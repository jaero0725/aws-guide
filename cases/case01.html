EC2에 액세스 키를 심어 배포했다

시험에서 가장 자주 나오는 안티패턴이자, 실무에서 가장 자주 일어나는 사고입니다. 핵심은 "키를 어디에 숨길 것인가"가 아니라 애초에 회수해야 할 키를 만들지 않는 것입니다. 이 케이스는 장기 자격 증명이 어떻게 통제 불가능한 상태로 번지는지 경로를 추적하고, 세 가지 후보 설계를 비교해 IAM 역할로 넘어가는 판단을 정리합니다.

주 도메인: 보안 아키텍처 설계(30%) · 과제 진술 1.1 AWS 리소스에 대한 보안 액세스 설계

학습 목표

  • 장기 액세스 키가 이미지·저장소·로그로 번지는 확산 경로를 설명할 수 있습니다.
  • 키 정기 교체, 비밀 관리 서비스 조회, IAM 역할 세 후보를 회수 가능성 기준으로 비교할 수 있습니다.
  • 인스턴스 프로파일을 붙이는 것만으로는 부족하고 기존 자격 증명 파일을 함께 제거해야 하는 이유를 설명할 수 있습니다.
  • IMDSv2를 강제하고 홉 제한을 조정해 서버 측 요청 위조(SSRF)로 자격 증명이 새는 경로를 차단할 수 있습니다.
  • 시험 문항에서 "액세스 키" 선택지를 소거하고 역할 기반 선택지를 고를 수 있습니다.

상황

사내 이미지 변환 서비스가 Amazon EC2 Auto Scaling 그룹에서 12대로 운영되고 있습니다. 각 인스턴스는 원본을 Amazon S3에서 읽고 변환 결과를 다른 버킷에 씁니다. 2년 전 첫 배포 때 담당자가 IAM 사용자를 하나 만들고 액세스 키를 발급해 AMI 안의 공유 자격 증명 파일(~/.aws/credentials)에 적어 두었습니다. 그 뒤로 배포는 이 AMI를 복제하는 방식으로 이어졌습니다.

문제는 그 IAM 사용자에게 AmazonS3FullAccess가 붙어 있고, 같은 키가 다음 네 곳에 동시에 존재한다는 점입니다.

  • 현재 운영 중인 인스턴스 12대의 디스크
  • Auto Scaling 그룹이 참조하는 AMI, 그리고 그 AMI를 복제해 만든 개발용 AMI 3개
  • 사내 저장소에 커밋된 배포 스크립트의 환경 변수 예시 파일
  • 2년 전 장애 대응 때 캡처해 사내 위키에 붙인 셸 출력

이번 주 AWS CloudTrail 이벤트에서 그 액세스 키 ID로 평소 쓰지 않는 리전의 s3:ListAllMyBuckets 호출이 관측되었습니다. 보안 담당자는 즉시 키를 비활성화하려 하지만, 키를 끄는 순간 운영 중인 12대의 변환 작업이 전부 실패한다는 것도 알고 있습니다.

이 사고의 본질은 키가 유출된 것이 아니라 어디까지 퍼졌는지 셀 수 없다는 것입니다. 장기 자격 증명은 복사되어도 아무 흔적을 남기지 않으므로, 유출 범위를 확정할 방법이 없습니다. 그래서 "키를 잘 숨기는" 모든 대책은 이 문제를 풀지 못합니다.

B안이 왜 정답이 아닌가

AWS Secrets Manager는 좋은 서비스이고 자동 교체까지 지원합니다. 그러나 이 시나리오에서는 부트스트랩 문제를 만듭니다. 인스턴스가 비밀을 읽으려면 그 자체로 자격 증명이 필요한데, 그 자격 증명을 인스턴스에 주는 올바른 방법이 결국 IAM 역할입니다. 역할을 붙일 수 있다면 처음부터 S3 권한을 역할에 주면 되고, 중간에 액세스 키를 둘 이유가 사라집니다.

Secrets Manager가 정답이 되는 자리는 따로 있습니다 — AWS가 발급하지 않는 자격 증명, 예를 들어 데이터베이스 사용자 비밀번호나 외부 서비스의 API 키입니다. 그 구분은 16장 보안 · 암호화 · 거버넌스에서 다룹니다.

선택과 근거

C안 — IAM 역할을 만들어 인스턴스 프로파일로 연결합니다. 근거는 세 가지입니다.

  • 회수 지점이 한 곳으로 모입니다. 역할이 발급하는 자격 증명은 만료되므로, 역할의 권한 정책을 줄이거나 신뢰 정책을 끊으면 그 시점 이후 호출이 전부 막힙니다. 디스크에 흩어진 복사본을 찾아다닐 필요가 없습니다.
  • 사람이 키를 옮기는 절차가 사라집니다. 재발 방지는 절차를 잘 지키게 만드는 것이 아니라 절차를 없애는 것으로 달성됩니다.
  • 코드를 고치지 않습니다. AWS SDK와 AWS CLI의 기본 자격 증명 체인이 인스턴스 메타데이터를 조회하므로, 애플리케이션은 자격 증명을 명시적으로 다루지 않아도 됩니다.

전환 순서 — 순서를 틀리면 서비스가 멈춘다

제약 2(무중단) 때문에 순서가 설계의 일부입니다. 키 비활성화는 마지막이고, 자격 증명 파일 제거는 역할 연결 다음입니다.

무중단 전환 순서와 각 단계의 확인 지점
순서 작업 무엇을 확인하고 다음으로 넘어가는가
1 필요한 버킷과 동작만 허용하는 권한 정책으로 역할을 만든다 정책 시뮬레이터나 스테이징에서 필요한 동작이 전부 허용되는지
2 인스턴스 프로파일을 만들어 역할을 넣고, 실행 중인 인스턴스에 연결한다 인스턴스 안에서 역할 자격 증명이 조회되는지
3 AMI와 인스턴스에서 공유 자격 증명 파일과 환경 변수를 제거한다 호출 주체가 IAM 사용자가 아니라 수임한 역할로 바뀌었는지
4 시작 템플릿을 새 AMI로 갱신하고 인스턴스를 교체한다 새로 뜬 인스턴스가 키 없이 정상 동작하는지
5 액세스 키를 먼저 비활성화하고, 관측 기간을 둔 뒤 삭제한다 비활성화 후에도 실패한 호출이 없는지 CloudTrail로 확인

3단계를 건너뛰면 전환이 완료되지 않습니다. SDK와 CLI의 기본 자격 증명 체인은 환경 변수와 공유 자격 증명 파일을 인스턴스 메타데이터보다 먼저 확인합니다. 역할을 붙여도 파일이 남아 있으면 여전히 옛 키로 호출하며, 겉보기에는 아무 문제가 없어 보입니다. 그래서 5단계에서 키를 끄는 순간 장애가 납니다.

전환이 실제로 끝났는지는 호출 주체를 직접 확인하는 것이 유일하게 확실한 방법입니다.

역할과 인스턴스 프로파일 구성

권한 정책은 요구된 버킷과 동작만 남깁니다. AmazonS3FullAccess를 그대로 옮겨 붙이면 사고 범위가 그대로 유지됩니다.

메타데이터 경로 잠그기 — IMDSv2 강제

역할로 바꾸면 자격 증명이 인스턴스 메타데이터 서비스(IMDS)를 통해 전달됩니다. 즉 메타데이터 엔드포인트가 새로운 회수 대상이 됩니다. 애플리케이션에 서버 측 요청 위조(SSRF) 취약점이 있으면 공격자가 애플리케이션을 시켜 메타데이터를 읽게 만들 수 있기 때문입니다.

IMDSv2는 먼저 PUT으로 세션 토큰을 받고, 그 토큰을 헤더에 실은 요청만 응답하는 방식입니다. 단순히 URL을 대신 호출하게 만드는 전형적인 SSRF로는 토큰 발급 단계를 통과할 수 없습니다. 여기에 홉 제한을 1로 두면 컨테이너처럼 한 단계 더 떨어진 곳에서의 접근도 막힙니다.

2024년 3월부터 계정 수준에서 신규 인스턴스 시작의 IMDS 기본값을 지정할 수 있습니다. 그전에는 인스턴스마다 또는 시작 템플릿마다 설정해야 했습니다. 또한 2024년 중반 이후 출시된 신규 인스턴스 타입은 IMDSv2 전용입니다. "IMDSv1으로 메타데이터를 읽는다"고 서술한 자료는 현행 기준이 아닙니다.

비용과 운영에 미치는 영향

이 전환은 아키텍처를 바꾸지 않으므로 컴퓨팅이나 스토리지 사용량은 그대로입니다. 달라지는 것은 운영 항목의 개수입니다.

전환 전후의 비용 항목과 운영 항목 변화 — 금액이 아니라 항목의 증감입니다
항목 전환 전 전환 후
추가되는 과금 리소스 없음 없음 — 역할과 인스턴스 프로파일은 리소스를 새로 띄우지 않는다
B안을 골랐다면 — 비밀 저장과 조회 API 호출이 새로운 과금 항목이 된다. 얻는 것 없이 항목만 늘어난다
정기 작업 키 교체, 배포 파이프라인 갱신, 교체 실패 대응 없음 — 자격 증명 교체를 AWS가 처리한다
사고 대응 시간 복사본 추적에 상한이 없다 역할 권한 변경 한 번으로 종료된다
감사 공유 키 하나 — 주체 구분 불가 역할 세션 이름으로 인스턴스까지 좁혀진다

권한을 좁히는 작업(제약 3)은 비용에도 간접적으로 기여합니다. s3:GetObject와 s3:PutObject만 남기면 잘못된 코드가 대량의 목록 조회나 교차 리전 복사를 일으키는 경로가 사라집니다. 데이터 전송 요금 구조는 케이스 6 · 데이터 전송 요금이 예산을 넘겼다에서 다룹니다.

예방 체크리스트

새 워크로드를 설계할 때와, 기존 워크로드를 점검할 때 각각 확인합니다. 체크 상태는 저장되지 않으므로 점검용으로만 씁니다.

점검할 때

조직 수준에서 이 실수를 구조적으로 막고 싶다면 서비스 제어 정책(SCP)으로 iam:CreateAccessKey를 거부하는 방법이 있습니다. 예외가 필요한 계정만 별도 OU로 분리하면 "정책을 잘 지키자"는 합의를 기술적 상한으로 바꿀 수 있습니다. SCP의 성질은 2장 IAM과 자격 증명과 17장 모니터링 · 운영 · 계정 관리에서 다룹니다.

관련 시험 포인트

EC2 인스턴스에 IAM 사용자와 액세스 키를 둔다는 선택지는 SAA에서 거의 항상 오답입니다. 문제문이 MOST secure든 LEAST operational overhead든 결론이 같으므로, 이 선택지는 문제를 다 읽기 전에 소거해도 됩니다.

정답 선택지의 형태는 "IAM 역할을 만들어 인스턴스 프로파일로 연결한다"입니다. 컴퓨팅 서비스가 바뀌면 이름만 바뀝니다 — AWS Lambda는 실행 역할, Amazon ECS는 태스크 역할입니다.

이 케이스에서 뽑아내는 문항 판별 규칙
문제문의 신호 고르는 것 소거하는 것
EC2가 다른 AWS 서비스를 호출해야 한다 IAM 역할 + 인스턴스 프로파일 액세스 키를 사용자 데이터·환경 변수·AMI에 넣는 안
교차 계정으로 접근해야 한다 대상 계정에 역할을 만들고 sts:AssumeRole 대상 계정의 IAM 사용자 키를 발급해 전달하는 안
자격 증명을 주기적으로 교체해야 한다 가능하면 역할. 데이터베이스 비밀번호 등은 Secrets Manager 자체 교체 스크립트를 만드는 안(운영 부담 한정어와 충돌)
SSRF로 메타데이터가 노출된다 IMDSv2 필수화, 홉 제한 조정 메타데이터 엔드포인트를 보안 그룹으로 차단하는 안(링크 로컬 주소라 성립하지 않는다)
모바일 앱이 AWS 리소스를 직접 호출해야 한다 Amazon Cognito 자격 증명 풀로 임시 자격 증명 교환 앱에 액세스 키를 포함하는 안

한정어별 선호 선택지는 한정어 키워드 사전에, 헷갈리는 쌍은 함정 사전에 모여 있습니다.
