퍼블릭 서브넷에 데이터베이스를 뒀다

"보안 그룹으로 내 IP만 열어 뒀으니 괜찮다"는 판단이 왜 부족한지 분해합니다. 노출은 라우팅 테이블 · 퍼블릭 주소 · 보안 그룹 세 조건이 동시에 성립할 때 생기고, 그중 하나만 실수로 넓어져도 즉시 인터넷에 열립니다. 이 케이스는 세 조건을 하나씩 제거하면서 무엇이 남는지 확인합니다.

주 도메인: 보안 아키텍처 설계(30%) · 과제 진술 1.2 보안 워크로드·애플리케이션 설계

학습 목표

  • 퍼블릭 서브넷을 정의하는 것이 이름이 아니라 라우팅 테이블이라는 점을 설명할 수 있습니다.
  • 노출이 성립하는 세 조건을 분리하고, 각각을 어떻게 제거하는지 설계할 수 있습니다.
  • 보안 그룹과 네트워크 ACL의 적용 계층과 상태 저장 여부를 구분해 배치할 수 있습니다.
  • Amazon RDS의 퍼블릭 액세스 설정과 DB 서브넷 그룹의 관계를 설명할 수 있습니다.
  • 시험 문항에서 "보안 그룹으로 특정 IP를 차단한다"류 선택지를 즉시 소거할 수 있습니다.

상황

스타트업의 초기 인프라를 그대로 쓰고 있는 서비스입니다. VPC에 서브넷이 두 개뿐이고, 둘 다 라우팅 테이블에 인터넷 게이트웨이로 향하는 기본 경로가 있습니다. 애플리케이션 서버와 Amazon RDS 인스턴스가 같은 서브넷에 있습니다.

RDS 인스턴스는 퍼블릭 액세스가 켜진 상태로 만들어졌습니다. 당시 개발자가 사무실 노트북에서 직접 접속해 스키마를 만들어야 했기 때문입니다. 보안 그룹은 데이터베이스 포트에 대해 사무실 고정 IP 하나만 허용하고 있었고, 여기까지는 팀도 알고 있었습니다.

문제는 지난 분기에 생겼습니다.

  • 재택근무가 늘면서 "임시로" 보안 그룹에 0.0.0.0/0 규칙이 추가되었고, 그 규칙이 지워지지 않았습니다.
  • 서브넷의 MapPublicIpOnLaunch가 켜져 있어 새로 만든 인스턴스마다 퍼블릭 주소가 붙습니다.
  • 데이터베이스 사용자 하나가 여전히 초기 설정 비밀번호를 쓰고 있었습니다.

보안 점검에서 데이터베이스 엔드포인트가 인터넷에서 조회 가능한 주소로 해석된다는 사실이 확인되었습니다. 유출 여부는 아직 확인되지 않았습니다.

서브넷 이름은 아무것도 결정하지 않습니다. private-subnet-1이라고 이름 붙여도 라우팅 테이블에 인터넷 게이트웨이 경로가 있으면 그것은 퍼블릭 서브넷입니다. 점검할 때는 이름이 아니라 연결된 라우팅 테이블의 경로를 봅니다.

노출은 세 조건의 결합이다

인터넷에서 데이터베이스에 도달하려면 아래 셋이 모두 성립해야 합니다. 하나만 끊어도 경로는 성립하지 않습니다. 그래서 처방을 고를 때 "어느 조건을 끊는가"로 이야기하면 논의가 명확해집니다.

노출 성립 조건 3종과 각각의 확인·제거 방법
조건 무엇을 의미하는가 어떻게 확인하는가 어떻게 제거하는가
1. 경로 서브넷의 라우팅 테이블에 인터넷 게이트웨이로 가는 경로가 있다 라우팅 테이블의 0.0.0.0/0 대상이 igw-인지 인터넷 게이트웨이 경로가 없는 서브넷으로 옮긴다
2. 주소 리소스에 퍼블릭 IP 또는 퍼블릭으로 해석되는 엔드포인트가 있다 RDS의 퍼블릭 액세스 설정, 서브넷의 MapPublicIpOnLaunch 퍼블릭 액세스를 끄고, 자동 퍼블릭 IP 할당을 끈다
3. 허용 보안 그룹이 그 출발지에서의 접속을 허용한다 인바운드 규칙의 소스가 CIDR인지 보안 그룹인지 소스를 애플리케이션 계층의 보안 그룹 ID로 바꾼다

Amazon RDS의 퍼블릭 액세스 설정은 주소가 어떻게 해석되는가를 정합니다. API 문서는 이렇게 설명합니다 — 퍼블릭 액세스가 켜져 있으면 VPC 밖에서 접속할 때 엔드포인트가 퍼블릭 IP로 해석되고, 같은 VPC 안에서 접속하면 프라이빗 IP로 해석됩니다. 퍼블릭 액세스가 꺼져 있으면 그 인스턴스는 내부 전용이며 엔드포인트가 항상 프라이빗 IP로 해석됩니다.

기본값도 함정입니다. DB 서브넷 그룹을 지정하지 않으면 Aurora가 아닌 인스턴스에서 퍼블릭 액세스가 켜진 것이 기본입니다. DB 서브넷 그룹을 지정하면 기본이 꺼짐으로 바뀝니다 (단 그 그룹의 이름이 default이면 다시 켜짐이 기본입니다). "명시하지 않으면 안전하겠지"라는 가정이 성립하지 않습니다.

보안 그룹과 네트워크 ACL의 역할 구분

B안이 왜 단독 해법이 아닌지는 두 통제의 성질 차이에서 나옵니다.

보안 그룹과 네트워크 ACL 비교
항목 보안 그룹 네트워크 ACL
적용 계층 인스턴스(네트워크 인터페이스) 서브넷
적용 범위 연결된 리소스에만 서브넷 안의 모든 리소스에

평가 방식 모든 규칙을 평가 번호가 낮은 규칙부터 순서대로
상태 상태 저장 — 반환 트래픽 자동 허용 상태 비저장 — 반환 트래픽을 명시 허용해야 함

보안 그룹에는 거부 규칙이 없습니다. 그러므로 "보안 그룹으로 특정 IP를 차단한다"는 선택지는 항상 오답입니다. 차단이 필요하면 네트워크 ACL이거나, 상위 계층의 AWS WAF입니다.

반대로 네트워크 ACL은 상태 비저장이라 아웃바운드만 허용하고 인바운드 임시 포트 범위를 열지 않으면 응답이 돌아오지 못합니다. "요청은 나가는데 응답이 안 온다"는 시나리오의 전형적인 원인입니다.

선택과 근거

D안 — 프라이빗 서브넷으로 옮기고, 퍼블릭 액세스를 끄고, 개발자 접속은 세션 기반 경로로 제공합니다.

근거는 하나로 요약됩니다. A안과 B안은 규칙에 의존하고, C·D안은 구조에 의존합니다. 규칙은 사람이 바꿀 수 있고 실제로 이 케이스에서 바뀌었습니다. 경로 자체가 없으면 규칙이 잘못 열려도 인터넷에서 도달할 수 없습니다.

목표 구성

계층별 서브넷 배치와 라우팅
계층 서브넷 아웃바운드 경로 인바운드 허용 소스
로드 밸런서 퍼블릭 (가용 영역마다 하나) 인터넷 게이트웨이 인터넷 (HTTPS)
애플리케이션 프라이빗 NAT 게이트웨이 (가용 영역마다 하나) 로드 밸런서의 보안 그룹
데이터베이스 프라이빗 (인터넷 경로 없음) 없음 애플리케이션의 보안 그룹

데이터베이스 계층 서브넷에는 NAT 게이트웨이 경로조차 두지 않는 것이 기본입니다. 데이터베이스가 인터넷으로 나갈 이유가 없기 때문입니다. 패치는 관리형 서비스가 처리하고, 백업은 서비스 내부 경로로 갑니다.

NAT 게이트웨이는 지정한 서브넷의 가용 영역 안에서만 동작합니다. 관리형이라는 이유로 다중 가용 영역을 자동으로 커버하지 않습니다. 가용 영역마다 하나씩 만들고, 각 가용 영역의 프라이빗 라우팅 테이블이 자기 가용 영역의 NAT를 가리키게 해야 합니다. 그러지 않으면 가용 영역 장애 시 전면 중단이 나고, 평상시에도 가용 영역을 넘는 데이터 전송 요금이 붙습니다.

또한 NAT 게이트웨이에는 보안 그룹을 연결할 수 없습니다. 통제가 필요하면 라우팅과 대상 측 보안 그룹으로 설계합니다.

보안 그룹을 CIDR이 아니라 보안 그룹으로 참조한다

데이터베이스 보안 그룹의 인바운드 소스를 애플리케이션 서버의 CIDR로 적으면, 서브넷을 늘리거나 인스턴스를 옮길 때마다 규칙을 고쳐야 합니다. 소스를 보안 그룹 ID로 지정하면 그 보안 그룹에 속한 리소스가 늘어나도 규칙은 그대로입니다.

프라이빗 서브넷으로 옮기기

개발자 접속 경로 (요구 3)

"임시로 열어 두는" 규칙이 재발의 원인이므로, 규칙을 열지 않고도 접속할 수 있는 경로를 미리 제공합니다.

개발자 접속 경로 후보 비교
방법 인바운드 포트 개방 감사 비고
퍼블릭 배스천 호스트(SSH) 필요 — 22번 포트를 인터넷에 연다 호스트 로그에 의존 관리 대상 인스턴스가 하나 늘어난다
AWS Systems Manager 세션 기반 접속 불필요 — 아웃바운드만으로 동작 세션 기록과 API 호출 기록이 남는다 포트 전달로 데이터베이스까지 연결할 수 있다
Site-to-Site VPN 또는 Client VPN 불필요 연결 로그 사내망 연동이 이미 있으면 자연스럽다

어느 쪽을 고르든 원칙은 같습니다 — 사람이 접속하기 위해 인터넷 인바운드 포트를 열지 않습니다.

재발 방지 (요구 4)

  • 탐지 — AWS Config 규칙으로 퍼블릭 액세스가 켜진 데이터베이스와 0.0.0.0/0이 허용된 보안 그룹을 상시 감시합니다.
  • 차단 — 조직 수준에서 서비스 제어 정책으로 퍼블릭 액세스를 켜는 변경을 막는 것도 가능합니다.
  • 가시성 — VPC 흐름 로그로 데이터베이스 인터페이스에 대한 거부·수락 기록을 남겨 둡니다. 다만 흐름 로그는 5-튜플과 수락·거부만 기록하고 페이로드는 남기지 않습니다. "통신 내용을 감사하라"는 요구에는 답이 되지 않습니다.

비용과 운영에 미치는 영향

구조 변경이 만드는 비용·운영 항목의 변화
항목 변화 설명
NAT 게이트웨이 늘어난다 애플리케이션 계층의 아웃바운드용으로 가용 영역마다 필요하다. 시간과 처리량 모두 과금 항목이다
VPC 엔드포인트 선택적으로 늘어난다 Amazon S3·DynamoDB 트래픽을 NAT에서 걷어내면 NAT 처리량이 줄어든다. 게이트웨이 엔드포인트 경로가 자주 유리하다
배스천 호스트 줄어들거나 사라진다 세션 기반 접속을 쓰면 상시 인스턴스가 필요 없다
가용 영역 간 전송 설계에 따라 달라진다 NAT를 하나만 두고 다중 가용 영역에서 쓰면 가용 영역을 넘는 전송이 발생한다
사고 대응 시간 줄어든다 노출 경로가 구조적으로 없으므로 규칙 감사 범위가 좁아진다

공식 문서 출처

  • Amazon VPC 사용 설명서 — VPC의 보안 — 보안 그룹과 네트워크 ACL의 적용 계층, 허용·거부 규칙 지원 여부, 상태 저장 여부 비교표
  • Amazon VPC 사용 설명서 — 네트워크 ACL — 규칙이 번호 순서로 평가되고 반환 트래픽을 명시 허용해야 한다는 서술
  • Amazon VPC 사용 설명서 — NAT 게이트웨이 — 지정한 서브넷에 네트워크 인터페이스를 만든다는 동작과 퍼블릭·프라이빗 NAT의 구분
  • Amazon VPC 사용 설명서 — VPC 흐름 로그 — 기록되는 필드와 수락·거부 표시, 페이로드가 포함되지 않는다는 범위
  • Amazon RDS 사용 설명서 — VPC의 DB 인스턴스 — DB 서브넷 그룹이 서로 다른 가용 영역의 서브넷을 포함해야 한다는 요건
  • Amazon RDS API 레퍼런스 — CreateDBInstance — PubliclyAccessible의 엔드포인트 해석 동작과 DB 서브넷 그룹에 따른 기본값
  • Amazon EC2 API 레퍼런스 — ModifySubnetAttribute — MapPublicIpOnLaunch 속성의 의미
  • Amazon EC2 API 레퍼런스 — AuthorizeSecurityGroupIngress — 인바운드 소스를 CIDR 대신 보안 그룹으로 지정하는 방법
