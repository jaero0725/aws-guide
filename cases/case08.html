리전 장애에 대비한 DR을 설계하라

재해 복구 설계는 서비스를 고르는 문제가 아니라 RTO와 RPO를 먼저 정하는 문제입니다. 두 값이 정해지면 전략이 좁혀지고, 전략이 정해지면 데이터 복제 · DNS 전환 · 용량 확보 세 가지 결정이 따라옵니다. 이 케이스는 그 순서를 그대로 밟습니다.

주 도메인: 복원력 있는 아키텍처 설계(26%) · 비용 최적화 아키텍처 설계(20%)

학습 목표

  • RTO와 RPO를 정의하고 요구사항에서 두 값을 뽑아낼 수 있습니다.
  • DR 4전략의 차이를 평상시에 무엇이 켜져 있는가로 설명할 수 있습니다.
  • 데이터 계층별 복제 수단을 고르고 각각의 RPO 성격을 설명할 수 있습니다.
  • DNS 장애 조치와 상태 확인으로 전환 경로를 설계할 수 있습니다.
  • 대상 리전의 용량 확보 위험과 정기 훈련의 필요성을 설명할 수 있습니다.

상황

결제 중개 서비스가 단일 리전에서 다중 가용 영역으로 운영되고 있습니다. 가용 영역 장애에는 대비되어 있지만, 리전 전체가 손상되는 경우에는 복구 계획이 없습니다. 경영진은 다음을 요구했습니다.

  • 리전 장애가 나도 결제 기록이 유실되면 안 됩니다.
  • 서비스는 수십 분 안에 다른 리전에서 재개되어야 합니다.
  • 평상시 비용은 현재의 두 배가 되어서는 안 됩니다.
  • 규정상 데이터는 국내 리전 안에서만 처리되어야 합니다.

현재 구성은 이렇습니다.

현재 구성 요소와 리전 장애 시 상태
구성 요소 현재 리전 장애 시
웹·애플리케이션 Auto Scaling 그룹, 다중 가용 영역 전부 소실
관계형 데이터베이스 Amazon RDS Multi-AZ 대기 인스턴스도 같은 리전이라 함께 소실
주문 이력 Amazon DynamoDB 단일 리전 테이블 소실
영수증 파일 Amazon S3 버킷, 복제 없음 접근 불가
DNS Amazon Route 53, 단순 라우팅 계속 죽은 리전을 가리킨다
인프라 정의 일부만 CloudFormation, 나머지는 수동 다른 리전에 재구축하는 데 시간이 오래 걸린다

Multi-AZ는 리전 장애 대비가 아닙니다. 대기 인스턴스는 같은 리전의 다른 가용 영역에 있으므로, 리전이 손상되면 함께 사라집니다. 리전 경계를 넘는 것은 교차 리전 복제 · 교차 리전 읽기 전용 복제본 · 글로벌 테이블 · 스냅샷 복사처럼 명시적으로 리전 간 동작을 하는 기능뿐입니다.

먼저 RTO와 RPO를 숫자로 만든다

RTO와 RPO의 정의와 이 케이스의 요구
지표 무엇을 묻는가 이 케이스의 요구 무엇을 결정하는가
RTO (Recovery Time Objective) 장애 발생부터 서비스 재개까지 허용되는 시간 수십 분 대상 리전에 무엇이 미리 서 있어야 하는가
RPO (Recovery Point Objective) 장애로 잃어도 되는 데이터의 시간 폭 결제 기록은 사실상 0에 가깝게 데이터를 어떤 방식으로 복제하는가

두 값은 서로 독립적으로 정해집니다. RPO는 데이터 복제 방식이 결정하고, RTO는 대상 리전의 준비 수준이 결정합니다. RPO를 0에 가깝게 만들면서 RTO는 몇 시간을 허용하는 설계도 가능하고, 그 반대도 가능합니다.

이 케이스에서는 요구가 갈립니다 — 결제 기록은 RPO가 매우 작아야 하지만, 서비스 재개는 수십 분을 허용합니다. 그래서 데이터는 상시 복제하되 컴퓨팅은 최소만 켜 두는 구성이 자연스럽게 나옵니다.

후보 설계안 비교 — DR 4전략

네 전략의 차이는 한 문장으로 요약됩니다 — 평상시에 대상 리전에서 무엇이 켜져 있는가.

DR 4전략 비교 — 평상시 대상 리전의 상태를 기준으로
항목 A · 백업과 복원 B · 파일럿 라이트 C · 웜 스탠바이 D · 다중 사이트 액티브-액티브
평상시 데이터 백업이 복사되어 있다 상시 복제된다 상시 복제된다 양방향 복제
평상시 컴퓨팅 없음 최소 코어만 (또는 꺼진 상태로 정의만) 축소된 규모로 실제 가동 운영 규모로 가동, 트래픽도 받는다
복구 시 할 일 인프라 생성 + 데이터 복원 + 전환 컴퓨팅 시작 + 확장 + 전환 확장 + 전환 전환만 (또는 자동)
RTO 성격 가장 길다 중간 짧다 가장 짧다
RPO 성격 백업 주기에 묶인다 복제 지연 수준 복제 지연 수준 복제 지연 수준
평상시 비용 가장 낮다 낮다 중간 가장 높다
이 케이스 판정 RTO 요구 미달 경계선 — 확장 시간이 변수 선택 비용 제약 위반

문제문에서 전략을 고를 때 보는 것은 두 문장입니다.

  • "몇 시간의 중단을 허용한다" + "비용을 최소화" → 백업과 복원
  • "수 분 안에 복구" + "데이터 손실 최소" → 웜 스탠바이 이상
  • "중단이 전혀 없어야 한다" → 다중 사이트 액티브-액티브
  • "핵심 데이터베이스만 미리 띄워 둔다" → 파일럿 라이트

네 전략의 이름을 외우는 것보다 "평상시 무엇이 켜져 있는가"로 구분하는 편이 문항을 빠르게 풉니다.

선택과 근거

C · 웜 스탠바이를 고릅니다. RTO 요구(수십 분)는 인프라를 새로 만들 여유가 없다는 뜻이고, 비용 제약은 운영 규모를 그대로 두 벌 유지할 수 없다는 뜻입니다. 축소된 규모로 상시 가동하되 장애 시 확장하는 구성이 두 요구 사이에 정확히 놓입니다.

규정 제약(국내 리전)은 대상 리전 후보를 좁힙니다. 데이터가 국경을 넘어서는 안 된다면, 다른 나라의 리전은 아무리 가깝고 싸도 선택지가 아닙니다. 국내에 사용 가능한 리전이 하나뿐이라면 DR 전략 자체를 다시 논의해야 하며, 이 사실을 먼저 확인합니다.

결정 1 · 데이터 복제

데이터 계층별 리전 간 복제 수단과 RPO 성격
데이터 수단 RPO 성격 주의
관계형 데이터베이스 교차 리전 읽기 전용 복제본 비동기 — 복제 지연만큼 손실 가능 장애 시 수동 승격이 필요하다. 자동 장애 조치가 아니다
관계형(Aurora) 글로벌 데이터베이스 비동기지만 지연이 작다 보조 리전에서 쓰기가 필요하면 승격해야 한다
주문 이력(DynamoDB) 글로벌 테이블 다중 리전 복제. 리전 간 최종 일관성 같은 항목을 두 리전에서 동시에 쓰면 충돌 해결 규칙이 적용된다
영수증 파일(S3) 교차 리전 복제(CRR) 객체 단위 비동기 버전 관리가 필수이고, 규칙 생성 이전 객체는 자동 복제되지 않는다
머신 이미지·볼륨 AMI·스냅샷 리전 간 복사 복사 주기에 묶인다 암호화된 스냅샷은 대상 리전의 키 설정이 필요하다
백업 전반 AWS Backup의 리전 간 복사 백업 계획 주기 복원 절차를 실제로 시험해 두어야 한다

S3 교차 리전 복제에는 세 가지 전제가 있습니다.

  • 원본과 대상 버킷 모두 버전 관리가 켜져 있어야 합니다.
  • 규칙을 만들기 이전에 존재하던 객체는 자동으로 복제되지 않습니다. 기존 객체를 옮기려면 별도의 일괄 복제 작업이 필요합니다.
  • 삭제 마커 복제는 선택 사항입니다. 한쪽에서 지운 것이 다른 쪽에도 지워질지를 의도적으로 정해야 합니다.

위 예시의 리전 코드는 명령 형태를 보이기 위한 값입니다. 실제 대상 리전은 규정 제약(데이터 레지던시)을 먼저 확인해 정합니다.

결정 2 · 전환 경로

데이터가 대상 리전에 있어도 사용자를 그쪽으로 보내지 못하면 복구가 아닙니다. Amazon Route 53의 장애 조치 라우팅은 상태 확인 결과에 따라 기본(primary) 레코드에서 보조(secondary) 레코드로 응답을 바꿉니다.

전환 수단 비교
수단 전환 방식 전환 속도에 영향을 주는 것
Route 53 장애 조치 라우팅 상태 확인 실패 시 보조 레코드로 응답 상태 확인 주기와 임계 횟수, 레코드 TTL, 클라이언트 캐시
Route 53 가중치 기반 가중치를 조정해 트래픽을 옮긴다 수동 조작 시점, TTL
AWS Global Accelerator 고정 IP를 유지한 채 엔드포인트 그룹을 전환 DNS 캐시의 영향을 받지 않는다

DNS 기반 전환은 TTL만큼 늦습니다. 평상시 TTL이 길면 전환 후에도 상당 시간 동안 옛 주소로 요청이 갑니다. DR을 전제한 레코드는 TTL을 짧게 유지하고, 그 대가로 질의 수가 늘어난다는 점을 감수합니다.

클라이언트나 중간 리졸버가 TTL을 무시하는 경우도 있으므로, DNS 전환만으로 RTO를 보장한다고 가정하지 않습니다. 고정 IP가 필요한 요구에는 Global Accelerator가 답이 됩니다.

결정 3 · 대상 리전의 용량

웜 스탠바이에서 가장 자주 간과되는 위험이 여기 있습니다. 장애가 나면 우리만 확장하는 것이 아닙니다. 같은 리전을 DR 대상으로 삼은 다른 조직들도 동시에 확장을 시도하므로, 필요한 만큼의 인스턴스를 즉시 얻지 못할 수 있습니다.

  • 축소된 규모라도 실제로 가동해 두면 그만큼은 이미 확보된 것입니다. 이것이 파일럿 라이트보다 웜 스탠바이의 RTO가 짧은 이유이기도 합니다.
  • 중요한 워크로드는 용량 예약을 검토합니다.
  • 인스턴스 타입을 하나로 고정하지 말고 대체 가능한 타입 목록을 시작 템플릿에 넣어 둡니다.

결정 4 · 인프라를 코드로

현재 인프라의 일부만 CloudFormation으로 정의되어 있다는 점은 그 자체로 위험입니다. 수동으로 만든 리소스는 대상 리전에 재현할 방법이 사람의 기억뿐입니다.

  • 모든 계층을 템플릿으로 정의하고, 리전에 따라 달라지는 값은 파라미터로 뺍니다.
  • 템플릿을 대상 리전에도 실제로 배포해 봅니다. 배포해 보지 않은 템플릿은 검증되지 않은 계획입니다.
  • AWS CloudFormation은 시험 범위 안이며, 이 사이트도 정식으로 다룹니다.

인프라를 코드로 정의하는 다른 도구들도 있지만, AWS CDK는 SAA-C03 시험 범위 밖입니다. 학습 시간은 CloudFormation에 씁니다.

비용과 운영에 미치는 영향

웜 스탠바이가 만드는 비용·운영 항목 — 금액이 아니라 항목의 성격입니다
항목 성격 줄이는 방법
대상 리전의 상시 컴퓨팅 축소 규모만큼 지속 발생 규모를 최소로 유지하고 장애 시 확장에 의존
교차 리전 복제 데이터 전송 복제하는 양에 비례 복제 대상을 접두사·태그로 한정, 옮기기 전에 압축
대상 리전의 스토리지 사본 한 벌만큼 대상 버킷의 스토리지 클래스를 낮춰 설정
교차 리전 읽기 전용 복제본 인스턴스 한 벌 인스턴스 크기를 작게 두고 장애 시 확대(다만 RTO가 늘어난다)
DR 훈련 일회성 비용과 사람 시간 줄이지 않는다. 훈련하지 않은 계획은 계획이 아니다
운영 복잡도 두 리전의 구성이 어긋나면 전환이 실패한다 템플릿으로 정의하고 드리프트를 감지

DR 문항의 비용 축은 평상시 켜 두는 자원의 양입니다. 같은 RTO를 만족하는 두 안이 있다면 평상시에 덜 켜 두는 쪽이 정답입니다. 반대로 비용만 보고 RTO 요구를 위반하는 안을 고르면 오답입니다. 명시된 요구를 위반하는 선택지는 아무리 싸도 소거합니다.

RTO와 RPO를 뒤바꿔 읽는 실수가 잦습니다. RTO는 시간(언제 다시 켜지는가), RPO는 데이터(얼마나 잃는가)입니다. "마지막 백업 이후의 데이터를 잃어도 되는가"를 묻는 문장은 RPO이고, "얼마나 빨리 서비스를 재개해야 하는가"는 RTO입니다.

공식 문서 출처

  • Amazon S3 사용 설명서 — 객체 복제 — 버전 관리 전제, 규칙 생성 이전 객체가 복제되지 않는다는 제약, 대상 스토리지 클래스 지정
  • Amazon S3 API 레퍼런스 — PutBucketReplication — 복제 규칙의 요소와 삭제 마커 복제 설정
  • Amazon RDS 사용 설명서 — 읽기 전용 복제본 사용 — 비동기 복제, 교차 리전 생성, 승격이 별도의 작업이라는 서술
  • Amazon RDS API 레퍼런스 — CreateDBInstanceReadReplica — 원본을 ARN으로 지정해 다른 리전에 복제본을 만드는 방법
  • Amazon DynamoDB 개발자 안내서 — 글로벌 테이블 — 다중 리전 복제의 동작과 일관성 모드
  • Amazon Route 53 개발자 안내서 — DNS 장애 조치 구성 — 기본·보조 레코드와 상태 확인의 연동
  • Amazon Route 53 개발자 안내서 — 엔드포인트 상태 판정 — 상태 확인이 정상·비정상을 확정하는 방식
  • Amazon Route 53 개발자 안내서 — 라우팅 정책 선택 — 장애 조치 · 가중치 기반 등 정책별 용도
  • AWS Backup 개발자 안내서 — 복구 지점 복사 — 리전 간 백업 복사 동작
