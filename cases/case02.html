읽기 부하로 데이터베이스가 죽었다

시험이 가장 집요하게 노리는 혼동 쌍이 여기에 있습니다 — Multi-AZ는 가용성을 위한 것이고, 읽기 전용 복제본은 읽기 확장을 위한 것입니다. 둘은 서로를 대체하지 않습니다. 이 케이스는 같은 장애에 네 가지 처방을 대 보고, 어느 것이 실제로 부하를 덜어 주는지 판정합니다.

주 도메인: 복원력 있는 아키텍처 설계(26%) · 고성능 아키텍처 설계(24%)

학습 목표

  • Multi-AZ 배포가 읽기 부하를 덜어 주지 않는 이유를 복제 방식과 엔드포인트로 설명할 수 있습니다.
  • 읽기 전용 복제본과 캐시 계층 중 어느 것이 근본 처방인지 쿼리 패턴으로 판단할 수 있습니다.
  • 복제 지연과 캐시 신선도가 허용되는 쿼리와 허용되지 않는 쿼리를 구분해 경로를 나눌 수 있습니다.
  • 연결 수 고갈이 원인일 때 처방이 달라진다는 점을 설명할 수 있습니다.
  • 시험 문항에서 "가용성" 신호와 "읽기 성능" 신호를 구분해 선택지를 소거할 수 있습니다.

상황

전자상거래 서비스의 상품 상세 페이지가 Amazon RDS for MySQL 단일 인스턴스를 씁니다. Multi-AZ는 켜져 있지 않고, 읽기 전용 복제본도 없습니다. 애플리케이션 서버는 데이터베이스 엔드포인트 하나만 알고 있으며, 모든 쿼리가 그 엔드포인트로 갑니다.

지난 금요일 프로모션이 시작되자 다음 순서로 장애가 진행됐습니다.

  1. 상품 상세 페이지 조회가 평소의 여러 배로 늘었습니다.
  2. 데이터베이스 CPU 사용률이 100%에 붙고 쿼리 지연이 올라갔습니다.
  3. 애플리케이션의 커넥션 풀이 반환되지 않은 연결로 가득 찼습니다.
  4. 새 요청이 연결을 얻지 못해 쓰기 경로(주문 생성)까지 함께 실패했습니다.

쿼리 로그를 보면 읽기가 전체 요청의 대부분이고, 그중에서도 같은 상품 몇 백 건에 대한 동일한 조회가 반복됩니다. 쓰기는 주문과 재고 차감 정도이며 양이 많지 않습니다.

장애 보고서에 "데이터베이스가 죽었다"고 쓰면 처방을 고르지 못합니다. 무엇이 포화됐는지를 먼저 나눠야 합니다.

CPU가 포화됐다면 쿼리 자체를 줄이는 처방(캐시, 복제본, 인덱스)이 맞고, 연결 수가 포화됐다면 연결을 재사용하는 처방(연결 풀링, RDS Proxy)이 맞습니다. 이 케이스는 CPU 포화가 먼저 오고 연결 고갈이 뒤따른 경우입니다.

표에서 한 줄만 외운다면 이것입니다 — 표준 Multi-AZ 인스턴스 배포의 대기 인스턴스는 읽기 트래픽을 받지 않습니다. 그래서 "읽기가 많아 느리다"는 문제문에 Multi-AZ를 답으로 고르면 틀립니다. 반대로 "가용 영역 장애를 견뎌야 한다"에 읽기 전용 복제본을 고르는 것도 틀립니다.

한 가지 예외를 알아 두면 함정을 피할 수 있습니다. Multi-AZ DB 클러스터 배포는 읽기 가능한 대기 인스턴스를 두는 별개의 아키텍처입니다. 문제문이 "Multi-AZ DB 클러스터"라고 명시하지 않았다면 표준 Multi-AZ 인스턴스 배포로 읽습니다.

B + C + D를 서로 다른 요구에 각각 배정합니다. 하나로 다 해결하려는 시도가 이 케이스에서 가장 흔한 오답입니다.

쿼리를 두 갈래로 나눈다

제약 1과 제약 2가 이 설계의 핵심입니다. 모든 읽기를 복제본으로 보내면 안 됩니다. 읽기 전용 복제본은 비동기로 복제되므로 프라이머리보다 뒤처진 데이터를 반환할 수 있습니다.

"쓰기 직후 같은 데이터를 읽는" 경로는 복제본에서 가장 자주 사고가 납니다. 주문을 만들고 곧바로 주문 상세로 이동하는 화면이 대표적입니다. 세션 안에서 방금 쓴 데이터를 읽는 요청은 프라이머리로 고정하는 것이 가장 단순하고 확실한 규칙입니다.

1단계 · Multi-AZ 활성화

엔드포인트 주소는 바뀌지 않습니다. 장애 조치가 일어나면 같은 이름이 대기 인스턴스를 가리키도록 DNS가 전환됩니다. 그래서 애플리케이션 설정을 고칠 필요가 없습니다.

2단계 · 읽기 전용 복제본

복제본 개수에는 상한이 있습니다. MySQL · MariaDB · PostgreSQL은 인스턴스당 최대 15개, Oracle과 SQL Server는 5개, Db2는 3개입니다. 복제본은 다른 가용 영역이나 다른 리전에도 만들 수 있어 재해 복구 구성의 재료로도 쓰입니다 (케이스 8 · 리전 장애에 대비한 DR을 설계하라).

복제 지연은 지표로 관측할 수 있습니다. Amazon CloudWatch의 복제 지연 지표에 알람을 걸어 두면 "복제본이 얼마나 뒤처져 있는지"를 감으로 판단하지 않아도 됩니다. 지연이 커지면 읽기 경로를 일시적으로 프라이머리로 되돌리는 것도 선택지입니다.

3단계 · 캐시 계층

반복 조회가 지배적이라는 관측이 캐시를 근본 처방으로 만듭니다. 같은 상품 한 건을 1초에 수백 번 조회한다면, 복제본을 몇 개 붙이든 같은 결과를 매번 다시 계산하고 있는 셈입니다.

엔진 선택 기준은 단순합니다. 복제 · 자동 장애 조치 · 스냅샷이 필요하면 복제 그룹을 만들 수 있는 엔진(Valkey 또는 Redis OSS)을 고릅니다. Memcached는 다중 스레드로 단순한 키-값 캐시를 처리하지만 복제 그룹과 자동 장애 조치를 제공하지 않습니다. 시험에서 "캐시가 죽어도 데이터가 남아야 한다"거나 "정렬된 자료 구조가 필요하다"는 신호가 있으면 Memcached는 소거 대상입니다.

캐시 채우기 전략과 무효화

지연 로딩과 라이트 스루의 차이
전략 동작 장점 단점
지연 로딩(lazy loading) 캐시에 없으면 데이터베이스에서 읽어 캐시에 넣는다 실제로 요청된 데이터만 캐시에 남는다 첫 요청은 항상 느리고, 캐시가 비면 부하가 한꺼번에 몰린다
라이트 스루(write-through) 쓰기 시점에 데이터베이스와 캐시를 함께 갱신한다 캐시가 항상 최신이다 읽히지 않는 데이터까지 캐시에 쌓이고, 쓰기 경로가 느려진다
TTL 병행 두 전략 어느 쪽이든 만료 시간을 함께 둔다 무효화를 놓쳐도 언젠가 정정된다 TTL 동안은 낡은 값이 보인다

이 케이스에서는 상품 정보에 지연 로딩과 짧은 TTL을 함께 쓰고, 가격 변경처럼 즉시 반영이 필요한 쓰기에서만 해당 키를 명시적으로 삭제합니다. 재고 수량은 캐시에 넣지 않습니다 — 제약 2 때문입니다.

비용과 운영에 미치는 영향

각 처방이 추가하는 비용 항목과 운영 항목 — 금액이 아니라 항목의 성격입니다
처방 추가되는 비용 항목 추가되는 운영 항목 얻는 것
인스턴스 클래스 확대 더 큰 인스턴스 요금으로 대체 변경 시 재시작 계획 일시적 여유. 상한은 그대로
Multi-AZ 대기 인스턴스와 가용 영역 간 복제 트래픽 장애 조치 시나리오 점검 가용성. 읽기 처리량은 그대로
읽기 전용 복제본 복제본 인스턴스 수만큼. 교차 리전이면 리전 간 전송 복제 지연 감시, 승격 절차 문서화 읽기 처리량 분산
ElastiCache 캐시 노드 무효화 설계, 캐시 적중률 감시, 콜드 스타트 대비 가장 큰 부하 경감과 가장 낮은 응답 지연
RDS Proxy 프록시 사용 항목 연결 고정(pinning) 여부 확인 연결 수 병목 완화, 장애 조치 시 연결 전환 단축

비용 한정어(MOST cost-effective)가 붙은 문항에서 같은 결과를 내는 두 안 중 캐시 쪽이 유리한 경우가 많습니다. 읽기 전용 복제본은 데이터베이스 인스턴스를 통째로 하나 더 띄우는 반면, 캐시는 반복 조회를 흡수해 원본 조회 자체를 줄이기 때문입니다.

다만 반복 조회가 없는 워크로드에서는 캐시 적중률이 낮아 비용만 늘고 효과가 없습니다. 문제문에 "동일한 쿼리가 반복된다", "읽기 대 쓰기 비율이 매우 높다"는 신호가 있는지 먼저 확인합니다.

읽기 전용 복제본으로 재해 복구를 구성했다면 장애 시 자동 승격이 일어나지 않는다는 점을 기억합니다. 복제본을 독립 인스턴스로 승격하는 작업은 별도의 조치이며, 승격 후에는 원래의 복제 관계가 끊깁니다. "자동으로 장애 조치되어야 한다"는 요구에는 Multi-AZ 또는 Aurora 구성이 답입니다.

공식 문서 출처

  • Amazon RDS 사용 설명서 — 단일 대기 인스턴스를 사용하는 Multi-AZ 배포 — 대기 복제본으로 동기식 복제한다는 서술
  • Amazon RDS 사용 설명서 — 읽기 전용 복제본 사용 — 비동기식 복제, 별도 엔드포인트, 승격 동작
  • Amazon RDS API 레퍼런스 — CreateDBInstanceReadReplica — 엔진별 읽기 전용 복제본 개수 상한(기본 15개, Oracle · SQL Server 5개, Db2 3개)과 지원 엔진 목록
  • Amazon RDS API 레퍼런스 — ModifyDBInstance — MultiAZ 설정과 즉시 적용 옵션
  • Amazon RDS 사용 설명서 — Amazon RDS Proxy — 연결 풀링과 장애 조치 시 연결 전환에 대한 설명
  • Amazon ElastiCache API 레퍼런스 — CreateReplicationGroup — 복제 그룹의 자동 장애 조치와 Multi-AZ 설정, 지원 엔진
  • Amazon ElastiCache 개발자 안내서 — 자동 장애 조치 — 프라이머리 장애 시 읽기 전용 복제본이 승격되는 조건
  • Amazon ElastiCache 개발자 안내서 — 엔진 선택 — 복제와 스냅샷을 지원하는 엔진과 Memcached의 차이
  • Amazon RDS 사용 설명서 — 모범 사례 — 연결 수와 인스턴스 크기, 모니터링 지표에 대한 권고
