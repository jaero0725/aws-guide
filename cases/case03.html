S3 비용이 매달 늘어난다

Amazon S3 요금이 늘어나는 이유는 대개 셋 중 하나입니다 — 지운 줄 알았던 이전 버전, 완료되지 않은 멀티파트 업로드, 접근하지 않는데도 S3 Standard에 남아 있는 객체. 셋은 원인도 처방도 다르므로, 먼저 무엇이 용량을 차지하는지 나누고 시작합니다.

주 도메인: 비용 최적화 아키텍처 설계(20%) · 과제 진술 4.1 비용 최적화 스토리지

학습 목표

  • 버킷 저장 용량이 줄지 않는 원인을 이전 버전·미완료 업로드·클래스 방치로 나눠 진단할 수 있습니다.
  • 스토리지 클래스별 최소 저장 기간과 최소 청구 크기가 수명 주기 설계를 어떻게 제약하는지 설명할 수 있습니다.
  • 접근 패턴을 모르는 데이터에 S3 Intelligent-Tiering을 고르는 근거를 댈 수 있습니다.
  • 완료되지 않은 멀티파트 업로드를 수명 주기 규칙으로 정리할 수 있습니다.
  • 시험 문항에서 "접근 패턴을 예측할 수 없다"와 "거의 접근하지 않는다"를 구분해 다른 클래스를 고를 수 있습니다.

상황

미디어 서비스가 원본 영상과 변환 결과, 그리고 일일 로그를 하나의 S3 버킷에 저장합니다. 운영을 시작한 지 2년이 지났고, 저장 용량과 요금이 매달 단조 증가합니다. 팀은 "오래된 파일은 지우는 배치가 돌고 있다"고 알고 있었지만, 실제 버킷 크기는 줄어든 적이 없습니다.

조사해 보니 다음 네 가지가 겹쳐 있었습니다.

버킷 용량이 줄지 않는 네 가지 원인
원인 무슨 일이 일어났는가 왜 눈에 띄지 않았는가
버전 관리 + 삭제 배치 버전 관리가 켜진 버킷에서 객체를 삭제하면 삭제 마커가 생기고 이전 버전은 남는다 목록 조회에서는 사라진 것처럼 보인다. 용량은 그대로다
완료되지 않은 멀티파트 업로드 대용량 업로드가 중간에 실패하면 이미 올라간 파트가 버킷에 남아 요금이 발생한다 객체 목록에 나타나지 않는다. 전용 API로만 보인다
클래스 방치 2년 전 로그가 아직 S3 Standard에 있다 동작에는 아무 문제가 없으므로 아무도 보지 않는다
접근 패턴 미상 데이터 변환 결과는 어떤 것은 매일 읽히고 어떤 것은 1년째 안 읽힌다 객체 단위로 판단할 방법이 없어 전부 Standard에 둔다

이 케이스에는 금액이 나오지 않습니다. 요금은 리전과 시점에 따라 달라지므로 학습 자료에 고정할 값이 아닙니다. 비용 판단은 언제나 구조로 합니다 — 무엇이 용량을 차지하는가, 어떤 방향으로 데이터가 움직이는가, 어떤 요금 항목이 새로 생기는가.

배경 개념은 8장 S3와 오브젝트 스토리지에 있습니다. 스토리지 클래스 전체 목록과 최소 저장 기간 표를 먼저 확인하면 아래 판단이 빨라집니다.

먼저 무엇이 용량을 차지하는지 나눈다

처방을 고르기 전에 원인을 분리합니다. 원인을 나누지 않으면 수명 주기 규칙을 붙여도 용량이 줄지 않고, "S3 수명 주기는 효과가 없다"는 잘못된 결론에 도달합니다.

버전 관리가 켜진 버킷에서 DELETE는 데이터를 지우지 않습니다. 삭제 마커를 새 버전으로 얹을 뿐이고, 이전 버전은 그대로 남아 요금이 계속됩니다. 실제로 지우려면 버전 ID를 지정한 삭제가 필요합니다.

그래서 "삭제 배치가 돌고 있는데 용량이 줄지 않는다"는 보고는 거의 언제나 이 문제입니다. 수동으로 지우는 대신 비현재 버전 만료 규칙을 걸어 자동화하는 것이 정답입니다.

버전 관리 자체는 신규 버킷에서 기본 비활성화입니다. 최근 바뀐 S3 기본값(퍼블릭 액세스 차단 켜짐, ACL 비활성, 신규 객체 자동 암호화)과 섞어 "기본값이 다 켜졌다"고 기억하면 틀립니다.

후보 설계안 비교

데이터 종류가 셋(원본 영상 · 변환 결과 · 로그)이므로, 후보도 "전부 하나로 처리하는 안"과 "종류별로 다르게 처리하는 안"으로 갈립니다.

One Zone-IA를 함부로 고르지 않는 이유

S3 One Zone-IA는 이름 그대로 가용 영역 하나에만 데이터를 둡니다. 저장 비용은 Standard-IA보다 낮지만, 그 가용 영역이 소실되면 데이터가 함께 사라집니다. 그래서 다시 만들 수 있는 데이터(썸네일, 재생성 가능한 변환 결과)에는 적합하고, 원본에는 적합하지 않습니다. 시험에서 "재생성할 수 있다", "2차 사본이다"라는 문장이 One Zone-IA의 신호입니다.

선택과 근거

C를 골격으로 삼고, 변환 결과 접두사에만 B(Intelligent-Tiering)를 적용합니다. 접두사별로 요구가 다르므로 규칙도 접두사별로 갈라지는 것이 자연스럽습니다.

접두사별 처방
접두사 요구 처방
originals/ 영구 보관, 수 시간 내 검색 허용 일정 기간 후 Glacier Deep Archive로 전환. 만료 없음
derived/ 접근 패턴 예측 불가 Intelligent-Tiering으로 전환하고 자동 계층화에 맡긴다

클래스 선택을 제약하는 확정 수치

수명 주기 규칙의 일수는 마음대로 정할 수 없습니다. 클래스마다 최소 저장 기간이 있어서, 그 기간을 채우기 전에 옮기거나 지우면 남은 기간만큼 요금이 청구됩니다. 규칙을 설계하기 전에 아래 값을 먼저 확인합니다.

스토리지 클래스별 최소 저장 기간과 최소 청구 크기, 가용 영역 수
클래스 최소 저장 기간 최소 청구 크기 가용 영역
S3 Standard 없음 없음 3 이상
S3 Standard-IA 30일 128 KB 3 이상
S3 One Zone-IA 30일 128 KB 1
S3 Glacier Instant Retrieval 90일 128 KB 3 이상
S3 Glacier Flexible Retrieval 90일 40 KB 3 이상
S3 Glacier Deep Archive 180일 40 KB 3 이상
S3 Intelligent-Tiering 없음 없음 3 이상

수명 주기 전환에는 추가 제약이 둘 더 있습니다.

  • S3 Standard-IA 또는 One Zone-IA로 전환하려면 객체가 최소 30일 이상 저장되어 있어야 합니다. "업로드 즉시 IA로 보낸다"는 규칙은 동작하지 않습니다.
  • 128 KB 미만 객체는 전환되지 않습니다. 작은 파일이 수백만 개인 버킷에서 수명 주기 규칙을 걸어도 용량이 그대로인 흔한 이유입니다.

그 대신 필터의 ObjectSizeGreaterThan으로 전환 대상을 크기로 한정해 규칙의 의도를 명시할 수 있습니다.

수명 주기 규칙 구성

네 번째 규칙이 이 케이스의 핵심입니다.

  • NoncurrentVersionExpiration — 이전 버전을 30일 뒤 만료시킵니다. 제약 3(30일 복구)을 만족시키면서 그 이상은 쌓이지 않게 합니다.
  • ExpiredObjectDeleteMarker — 뒤에 아무 버전도 남지 않은 삭제 마커를 정리합니다. 목록 조회 성능에도 도움이 됩니다.
  • AbortIncompleteMultipartUpload — 시작된 지 7일이 지나도 완료되지 않은 멀티파트 업로드를 중단하고 파트를 정리합니다.

AbortIncompleteMultipartUpload 규칙은 모든 버킷에 기본으로 넣어 두는 것이 좋습니다. 비용이 새는 경로 중에서 원인을 찾기가 가장 어렵고, 규칙 하나로 영구히 해결되기 때문입니다. 멀티파트 업로드는 5 GB를 넘는 객체를 올릴 때 필수이므로 대용량 워크로드에서는 반드시 발생합니다.

Intelligent-Tiering을 고르는 근거

S3 Intelligent-Tiering은 객체의 접근 여부를 모니터링해 자동으로 계층을 옮깁니다. 최소 저장 기간과 검색 요금이 없는 대신 객체당 모니터링·자동화 요금 항목이 생깁니다.

선택 기준은 명확합니다 — 접근 패턴을 알면 고정 클래스가 낫고, 모르면 Intelligent-Tiering이 낫습니다. 아카이브 티어를 켜면 90일 미접근 시 Archive Access, 180일 미접근 시 Deep Archive Access로 자동 이동합니다. 다만 아카이브 티어에 들어간 객체는 즉시 읽을 수 없으므로, 지연을 허용할 수 있을 때만 켭니다.

비용과 운영에 미치는 영향

처방별로 늘고 주는 요금 항목 — 금액이 아니라 항목의 성격입니다
처방 줄어드는 항목 새로 생기거나 늘어나는 항목
아카이브 클래스로 전환 GB당 저장 요금 전환 요청 요금, 나중에 꺼낼 때의 검색 요금
Intelligent-Tiering 안 읽히는 객체의 저장 요금 객체당 모니터링·자동화 요금
비현재 버전 만료 이전 버전이 차지하던 저장 요금 없음 (복구 가능 기간이 짧아지는 것이 대가)
미완료 업로드 정리 보이지 않던 저장 요금 없음
로그 만료 저장 요금이 상한에 고정된다 없음 (보관 기간을 규정과 맞춰야 한다)

작은 객체를 아카이브 클래스로 옮기면 오히려 손해가 날 수 있습니다. 최소 청구 크기(Standard-IA · Glacier Instant Retrieval은 128 KB, Glacier Flexible Retrieval · Deep Archive는 40 KB)와 최소 저장 기간(30 · 90 · 180일)이 함께 걸리기 때문입니다. 수많은 작은 로그 파일을 그대로 옮기는 대신, 모아서 큰 파일로 만든 뒤 옮기는 것이 구조적으로 옳습니다.

운영 측면에서는 사람이 하던 삭제 배치가 사라집니다. 수명 주기 규칙은 S3가 실행하므로 실패한 배치를 재실행할 일이 없고, 규칙이 곧 보관 정책의 문서 역할을 합니다.

관련 시험 포인트

스토리지 클래스 문항은 두 문장만 구분하면 대부분 풀립니다.

  • "접근 패턴을 예측할 수 없다" · "접근 빈도가 변한다" → S3 Intelligent-Tiering
  • "거의 접근하지 않는다" + 명시된 검색 요구 → 검색 시간 요구에 맞는 Glacier 계열(즉시 필요하면 Instant Retrieval, 수 시간 허용이면 Flexible Retrieval, 하루 정도 허용이면 Deep Archive)

"가장 저렴한 클래스"를 무조건 고르는 것은 함정입니다. 검색 시간 요구를 위반하는 선택지는 아무리 싸도 오답입니다.
