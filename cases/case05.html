아키텍처 케이스 · 5

단일 AZ 설계가 장애로 전면 중단됐다

인스턴스를 여러 대 띄웠는데도 서비스가 통째로 멈췄습니다. 원인은 대수가 아니라 장애 도메인이었습니다 — 전부 같은 가용 영역(Availability Zone, AZ)에 있었기 때문입니다. 이 케이스는 가용 영역 하나가 손상됐을 때 무엇이 어떤 순서로 끊기는지 추적하고, 다중 가용 영역 · Auto Scaling · 상태 비저장 세 가지로 구성을 바꿉니다.

주 도메인: 복원력 있는 아키텍처 설계(26%) · 과제 진술 2.2 고가용성·내결함성 아키텍처 설계

학습 목표

  • 같은 가용 영역에 인스턴스를 늘리는 것이 왜 고가용성이 아닌지 설명할 수 있습니다.
  • 가용 영역 장애 시 끊기는 구성 요소를 계층별로 열거하고 각각의 처방을 배정할 수 있습니다.
  • 세션 상태를 외부화해야 자동 교체가 성립한다는 점을 설명할 수 있습니다.
  • Auto Scaling 그룹의 상태 확인 유형 차이와 교차 영역 로드 밸런싱 기본값을 구분할 수 있습니다.
  • 시험 문항에서 "가장 가용성이 높은" 한정어가 붙었을 때 확인 순서를 적용할 수 있습니다.

상황

사내 예약 서비스가 다음과 같이 구성되어 있습니다.

  • Application Load Balancer 하나. 등록된 서브넷은 가용 영역 하나뿐입니다.
  • 애플리케이션 인스턴스 4대. Auto Scaling 그룹에 들어 있지만 VPCZoneIdentifier에 서브넷이 하나만 지정되어 있습니다.
  • Amazon RDS 단일 인스턴스. Multi-AZ가 꺼져 있습니다.
  • NAT 게이트웨이 하나. 프라이빗 라우팅 테이블 전부가 이 하나를 가리킵니다.
  • 세션 정보는 각 인스턴스의 로컬 디스크에 저장됩니다.
  • 업로드된 첨부 파일도 인스턴스의 EBS 볼륨에 저장됩니다.

해당 가용 영역에 문제가 생기자 다음 순서로 장애가 확산됐습니다.

  1. 인스턴스 4대가 동시에 응답하지 않게 되고, 로드 밸런서의 상태 확인이 전부 실패했습니다.
  2. Auto Scaling 그룹이 교체 인스턴스를 시작하려 했지만, 지정된 서브넷이 그 가용 영역에만 있어 시작이 실패했습니다.
  3. 로드 밸런서 자체도 그 가용 영역에만 등록되어 있어 요청을 받을 곳이 없었습니다.
  4. 데이터베이스도 같은 가용 영역이라 접속이 끊겼습니다.
  5. NAT 게이트웨이가 그 가용 영역에 있어, 다른 가용 영역에 무언가 띄웠더라도 외부 호출이 불가능했습니다.
  6. 복구 후에도 로컬 디스크에 있던 세션과 첨부 파일을 되살리지 못했습니다.

인스턴스 4대는 고가용성이 아닙니다. 가용 영역은 독립된 전원과 냉각, 물리 보안을 갖춘 장애 격리 단위이고, 장애는 그 단위로 발생합니다. 같은 가용 영역 안에서 대수를 늘리는 것은 인스턴스 한 대의 고장에는 대비가 되지만 가용 영역 손상에는 아무 대비가 되지 않습니다.

"가용성을 높이자"는 합의는 쉽지만, 무엇을 얼마나 바꿀지에서 갈립니다. 네 가지 수준의 안을 놓고 비교합니다.

MOST highly available이 보이면 확인 순서는 이렇습니다.

  1. 가용 영역이 몇 개인가 — 하나면 그 선택지는 소거입니다.
  2. 모든 계층이 다중인가 — 로드 밸런서 · 컴퓨팅 · 데이터베이스 · NAT 중 하나라도 단일이면 그 지점이 전체의 가용성을 결정합니다.
  3. 복구가 자동인가 — 사람이 전환해야 하는 안은 같은 조건에서 더 낮게 평가됩니다.

선택과 근거

D안을 고릅니다. C안까지만 하면 요구 1·2는 만족하지만 요구 3·4가 남습니다. 그리고 요구 3·4를 해결하지 않으면 자동 교체가 사용자에게 장애로 보입니다. 인스턴스가 바뀔 때마다 로그인이 풀리고 첨부 파일이 사라지면, 가용성을 높인 대가로 신뢰를 잃습니다.

Auto Scaling 그룹을 여러 가용 영역으로

상태 확인 유형은 EC2, EBS, ELB, VPC_LATTICE가 있고 EC2는 기본이며 끌 수 없습니다. EC2만 쓰면 인스턴스는 살아 있는데 애플리케이션이 죽은 상태를 감지하지 못합니다. 로드 밸런서 뒤에 있는 워크로드라면 ELB를 함께 켜서 애플리케이션 수준의 실패도 교체 대상이 되게 합니다.

유예 기간(HealthCheckGracePeriod)은 새 인스턴스가 준비되기 전에 비정상으로 표시돼 교체가 반복되는 것을 막습니다. 부팅과 초기화가 오래 걸리는 애플리케이션에서 이 값이 너무 작으면 기동과 종료가 무한히 반복됩니다.

최소 용량을 어떻게 잡는가

가용 영역 두 곳에 인스턴스를 나누기만 하면 되는 것이 아닙니다. 한 가용 영역이 사라졌을 때 남은 쪽이 전체 부하를 감당할 수 있어야 합니다.

  • 필요 용량이 4대이고 가용 영역이 2개라면, 각 가용 영역에 4대씩 총 8대를 두는 것이 가장 안전합니다(N+N).
  • 가용 영역을 3개로 늘리면 필요 용량의 절반만 여유로 두어도 됩니다(N+1 성격). 가용 영역 수를 늘릴수록 필요한 여유 비율이 줄어듭니다.
  • Auto Scaling이 남은 가용 영역에서 즉시 인스턴스를 시작하더라도 기동 시간 동안은 용량이 부족합니다. 이 지연을 감수할 수 있는지가 여유 용량을 정하는 기준입니다.

교차 영역 로드 밸런싱 기본값 차이

가용 영역마다 대상 수가 다를 때 트래픽 분포가 균등하지 않은 현상은 교차 영역 로드 밸런싱 설정에서 나옵니다.

로드 밸런서별 교차 영역 로드 밸런싱 기본값
로드 밸런서 기본값 변경 가능 여부
Application Load Balancer 켜짐 끌 수 없다
Network Load Balancer 꺼짐 변경 가능
Gateway Load Balancer 꺼짐 변경 가능

시험 관점에서 중요한 것은 "ALB는 기본이 켜짐"보다 "ALB는 끌 수 없다"는 사실입니다. Network Load Balancer를 다중 가용 영역에 두고 가용 영역마다 대상 수가 다르면 기본 설정에서는 트래픽이 고르게 분배되지 않습니다.

상태 비저장으로 만들기

세션을 인스턴스 로컬 디스크에 저장하고, 로드 밸런서의 고정 세션으로 같은 인스턴스에 붙입니다. 인스턴스가 교체되면 그 인스턴스에 붙어 있던 사용자의 세션이 사라집니다. 가용 영역이 사라지면 그 가용 영역 사용자 전체의 세션이 사라집니다.

세션을 외부 저장소에 두고, 어떤 인스턴스가 요청을 받아도 같은 세션을 읽게 합니다. 인스턴스는 언제든 교체할 수 있는 부품이 되고, Auto Scaling의 축소·확대가 사용자에게 보이지 않습니다.

인스턴스에 묶인 상태를 어디로 옮기는가
상태 옮길 곳 고르는 이유
사용자 세션 Amazon ElastiCache 또는 Amazon DynamoDB 짧은 수명, 매우 잦은 읽기·쓰기. 만료(TTL) 처리가 필요하다
업로드 파일 (신규 개발) Amazon S3 내구성이 높고 용량 상한을 신경 쓰지 않는다

제약 1(코드 변경 최소) 때문에 이 케이스에서는 업로드 파일을 Amazon EFS로 옮깁니다. 기존 코드가 파일 경로로 읽고 쓰는 구조라면 마운트 지점만 바꾸면 되기 때문입니다. 새로 설계한다면 S3가 더 나은 기본값입니다.

EBS 볼륨은 가용 영역 하나에 묶입니다. 다른 가용 영역의 인스턴스에 그대로 붙일 수 없고, 스냅샷을 거쳐 새 볼륨을 만들어야 합니다. "여러 가용 영역의 인스턴스가 같은 파일을 공유해야 한다"는 요구에 EBS는 답이 되지 않습니다.

비용과 운영에 미치는 영향

다중 가용 영역화가 만드는 비용·운영 항목의 변화
항목 변화 설명
컴퓨팅 여유 용량만큼 늘어난다 한 가용 영역이 빠져도 견디려면 평상시 여유가 필요하다. 이것이 가용성의 값이다
데이터베이스 대기 인스턴스가 추가된다 Multi-AZ는 읽기 처리량을 늘리지 않는다. 사는 것은 가용성이다
NAT 게이트웨이 가용 영역 수만큼 늘어난다 대신 가용 영역을 넘는 전송이 사라져 전송 요금이 줄어드는 상쇄가 있다
가용 영역 간 데이터 전송 늘어난다 계층 사이 통신이 가용 영역을 넘는 경우가 생긴다. 트래픽이 큰 구간은 배치를 고려한다

장애 대응 줄어든다 가용 영역 손상이 전면 중단에서 용량 감소로 격하된다

"가용성을 높이면 비용이 오른다"는 것 자체는 함정이 아닙니다. 시험이 노리는 것은 불필요하게 오르는 구성입니다 — 예를 들어 NAT 게이트웨이를 하나만 두고 다중 가용 영역을 구성하면 가용성은 확보되지 않으면서 가용 영역 간 전송 요금만 늘어납니다. 가용성과 비용이 동시에 나빠지는 구성이므로 항상 오답입니다.

여러 인스턴스가 같은 파일을 공유해야 한다 Amazon EFS(코드 변경 최소) 또는 Amazon S3 EBS 볼륨 공유(가용 영역에 묶인다)
애플리케이션은 살아 있는데 응답만 못 한다 Auto Scaling 상태 확인에 ELB 추가 EC2 상태 확인만 쓰는 안
가용 영역마다 대상 수가 달라 분배가 고르지 않다 교차 영역 로드 밸런싱 활성화(NLB의 경우) ALB에서 이 설정을 바꾸려는 안(끌 수 없다)
새 인스턴스가 뜨자마자 비정상으로 교체된다 상태 확인 유예 기간 확대 상태 확인을 끄는 안

내결함성(fault tolerance)과 고가용성(high availability)을 구분하는 문항이 있습니다. 고가용성은 장애가 나도 짧은 중단 뒤 서비스가 계속되는 것이고, 내결함성은 구성 요소가 고장 나도 중단 없이 동작하는 것입니다. "중단이 전혀 없어야 한다"는 문장이 있으면 여유 용량을 상시 확보한 구성을 고릅니다.

공식 문서 출처

  • Amazon EC2 Auto Scaling API 레퍼런스 — UpdateAutoScalingGroup — 상태 확인 유형(EC2 · EBS · ELB · VPC_LATTICE)과 EC2가 기본이며 끌 수 없다는 서술, VPCZoneIdentifier와 가용 영역의 관계
  • Elastic Load Balancing API 레퍼런스 — ModifyLoadBalancerAttributes — load_balancing.cross_zone.enabled의 기본값이 로드 밸런서 유형마다 다르고 Application Load Balancer에서는 변경할 수 없다는 서술
  • Amazon RDS 사용 설명서 — 단일 대기 인스턴스를 사용하는 Multi-AZ 배포 — 동기식 복제와 자동 장애 조치의 동작
  • Amazon VPC 사용 설명서 — NAT 게이트웨이 — NAT 게이트웨이가 지정한 서브넷에 만들어진다는 점(따라서 가용 영역에 묶인다)
  • Amazon EC2 사용 설명서 — 리전과 가용 영역 — 가용 영역이 독립된 장애 격리 단위라는 정의
  • Amazon EC2 API 레퍼런스 — CreateVolume — EBS 볼륨이 특정 가용 영역에 생성된다는 제약
