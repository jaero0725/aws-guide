IAM과 자격 증명

AWS에서 일어나는 모든 API 호출은 누가 호출했는가와 그 호출이 허용되는가 두 질문을 통과합니다. IAM은 그 두 질문에 답하는 시스템이고, SAA에서 가장 배점이 큰 도메인의 중심입니다. 이 장은 정책 문서의 문법부터 시작해 여러 종류의 정책이 하나의 결정으로 합쳐지는 규칙까지 내려갑니다. 이 규칙을 모르면 IAM 문항은 찍는 문제가 됩니다.

이 장은 보안 아키텍처 설계(30%)의 과제 진술 1.1 "AWS 리소스에 대한 보안 액세스 설계"를 정면으로 다룹니다. 18장 가운데 시험 문항 밀도가 가장 높은 장입니다.

학습 목표

  • IAM 사용자 · 그룹 · 역할의 차이를 자격 증명의 수명 관점에서 설명할 수 있습니다.
  • 정책 문서의 Effect · Action · Resource · Condition · Principal 요소를 읽고, 자격 증명 기반 정책과 리소스 기반 정책을 구분할 수 있습니다.
  • 명시적 거부 > 명시적 허용 > 암묵적 거부 순서로 최종 결정이 나오는 과정을 설명할 수 있습니다.
  • 합집합으로 합쳐지는 정책 조합과 교집합으로 합쳐지는 정책 조합을 구분할 수 있습니다.
  • EC2 인스턴스에서 AWS API를 호출할 때 액세스 키가 아니라 IAM 역할을 써야 하는 이유를 근거를 들어 설명할 수 있습니다.
  • SCP와 권한 경계가 각각 무엇의 상한을 정하는지 구분하고, 페더레이션 방식을 요구사항에 맞게 고를 수 있습니다.

IAM의 구성요소 — 자격 증명과 정책

IAM은 두 종류의 대상을 다룹니다. 요청을 보내는 주체인 자격 증명(identity)과, 그 주체가 무엇을 할 수 있는지 적어 둔 정책(policy)입니다. 자격 증명에는 사용자 · 그룹 · 역할이 있고, 정책은 네 자리에 붙을 수 있습니다 — 자격 증명에, 리소스에, 권한 경계로, 그리고 세션에. 시험 문항이 어려워지는 지점은 언제나 이 네 자리에 붙은 정책이 하나의 결정으로 합쳐지는 규칙입니다.

사용자와 그룹 — 장기 자격 증명이 있는 쪽

IAM 사용자는 사람이나 애플리케이션에 대응하는 자격 증명이며, 콘솔 비밀번호와 액세스 키 같은 장기 자격 증명을 가질 수 있습니다. 장기라는 말은 만료되지 않는다는 뜻이고, 만료되지 않는 자격 증명은 유출되었을 때 우리가 직접 회수하기 전까지 계속 유효합니다. 이 한 문장이 이 장 전체의 방향을 결정합니다.

사용자 그룹은 권한을 묶어 관리하기 위한 장치입니다. 그룹에 자격 증명 기반 정책을 붙이면 그 그룹의 모든 사용자가 권한을 받습니다. 다만 그룹에는 시험이 노리는 제약이 세 개 있습니다.

  • 그룹은 중첩할 수 없습니다. 그룹 안에는 사용자만 넣을 수 있고 다른 그룹은 넣을 수 없습니다.
  • 그룹은 정책의 Principal이 될 수 없습니다. IAM 사용 설명서는 "그룹은 인증이 아니라 권한에 관한 것이고 Principal은 인증된 IAM 엔터티"이기 때문이라고 설명합니다. 따라서 S3 버킷 정책에서 그룹을 지정할 수 없습니다.
  • 계정의 모든 사용자를 자동으로 포함하는 기본 그룹은 없습니다. 필요하면 직접 만들어야 합니다.

역할 — 장기 자격 증명이 없는 쪽

IAM 역할도 권한 정책을 가진 자격 증명이지만, 사용자와 결정적으로 다른 점이 있습니다. IAM 사용 설명서는 역할에 대해 "한 사람에게 고유하게 묶이는 대신 필요한 누구든 맡을 수 있도록 만들어졌고, 비밀번호나 액세스 키 같은 표준 장기 자격 증명이 없다"고 정의합니다. 역할을 맡으면 그 자리에서 만료 시각이 있는 임시 자격 증명이 발급됩니다.

역할은 두 개의 정책으로 이루어집니다. 이 이원 구조가 역할 문항의 핵심입니다.

역할을 구성하는 두 정책
정책 무엇을 정하는가 성격
신뢰 정책(trust policy) 누가 이 역할을 맡을 수 있는가. Principal에 계정 · 사용자 · 역할 · AWS 서비스를 적는다 역할에 붙는 필수 리소스 기반 정책. 신뢰 정책에는 Principal에 와일드카드(*)를 쓸 수 없다
권한 정책(permissions policy) 이 역할이 무엇을 할 수 있는가. Action과 Resource를 적는다 자격 증명 기반 정책. 관리형 또는 인라인

"역할을 만들었는데 접근이 안 된다"는 상황은 대부분 둘 중 하나만 고친 경우입니다. 권한 정책만 넓히면 맡을 수 없고, 신뢰 정책만 넓히면 맡은 뒤에 아무것도 못 합니다.

서비스 역할은 AWS 서비스가 우리를 대신해 행동하려고 맡는 역할이고, 서비스 연결 역할(service-linked role)은 특정 서비스에 묶여 그 서비스가 소유하는 역할입니다. 서비스 연결 역할은 관리자도 권한을 볼 수는 있지만 편집할 수 없습니다. 계정에 낯선 역할이 생겼다면 서비스 연결 역할일 가능성이 높고, 임의로 지우면 안 됩니다.

EC2에서 API를 호출한다 — 액세스 키인가 역할인가 SAA 빈출

이 절은 이 장에서 가장 자주 출제되는 판단 하나만 다룹니다. EC2 인스턴스 위의 애플리케이션이 Amazon S3나 Amazon DynamoDB를 호출해야 할 때 무엇을 쓰는가. 정답은 거의 언제나 IAM 역할이고, 액세스 키를 인스턴스에 심는 선택지는 오답 유도로 가장 많이 쓰이는 패턴입니다.

액세스 키가 오답인 이유

이유를 "보안상 좋지 않아서"로 외우면 응용이 안 됩니다. IAM 사용 설명서가 임시 자격 증명의 장점으로 드는 항목이 그대로 근거입니다.

인스턴스에 심은 액세스 키와 IAM 역할의 임시 자격 증명 비교
항목 액세스 키를 인스턴스에 심는다 인스턴스 프로파일로 IAM 역할을 연결한다
배포물에 들어가는 것 장기 자격 증명이 AMI · 사용자 데이터 · 환경 변수 · 소스 저장소에 남는다 아무 자격 증명도 배포물에 넣지 않는다
만료 없음 — 지울 때까지 유효 있음 — 만료되면 재사용 불가
교체(rotation) 사람이 주기적으로 수행해야 한다 AWS가 자동으로 갱신한다
유출 시 대응 전 인스턴스에서 키를 찾아 회수·재배포 역할 정책만 고치면 되고, 이미 나간 자격 증명도 곧 만료된다
감사 여러 인스턴스가 같은 키를 쓰면 CloudTrail에서 구분되지 않는다 역할 세션 단위로 기록된다
권한 변경 키를 다시 발급하거나 사용자 정책을 고쳐야 한다 역할 정책을 고치면 재배포 없이 즉시 반영된다

IAM 사용자를 만들어 액세스 키를 발급하고, 그 값을 인스턴스의 환경 변수나 자격 증명 파일에 써 둡니다. 이 키는 만료되지 않으므로, 인스턴스 이미지나 로그에 한 번이라도 새어 나가면 우리가 회수할 때까지 계속 쓸 수 있습니다.

역할을 만들어 인스턴스 프로파일로 연결하면 자격 증명을 코드에 넣지 않습니다. SDK와 CLI가 기본 자격 증명 체인으로 임시 자격 증명을 알아서 찾아 씁니다.

인스턴스 프로파일 — 역할을 인스턴스에 붙이는 그릇

EC2 인스턴스에는 역할을 직접 붙이지 않고 인스턴스 프로파일(instance profile)이라는 그릇을 통해 붙입니다. 인스턴스 프로파일 하나에는 역할 하나가 들어갑니다. 콘솔에서 역할을 만들면 같은 이름의 인스턴스 프로파일이 함께 만들어져서 이 계층이 잘 보이지 않지만, CLI나 CloudFormation으로 만들 때는 직접 만들어야 합니다.

Principal이 사람이나 계정이 아니라 서비스라는 점을 눈여겨봅니다. "이 역할은 EC2 서비스가 맡을 수 있다"는 선언이며, 이 문장이 없으면 인스턴스 프로파일에 넣어도 자격 증명이 나오지 않습니다.

애플리케이션은 어떻게 자격 증명을 찾는가

SDK와 AWS CLI는 정해진 순서로 자격 증명을 탐색합니다. 환경 변수와 자격 증명 파일이 앞쪽에 있고, 인스턴스 메타데이터가 뒤쪽에 있습니다. 그래서 액세스 키를 환경 변수에 남겨 두면 역할을 붙여도 그 키가 먼저 쓰입니다. 역할로 전환할 때는 옛 키를 지우는 것까지가 한 작업입니다.

문항에 "EC2 인스턴스의 애플리케이션이 S3에 접근해야 한다"가 나오고 선택지에 IAM 사용자를 만들어 액세스 키를 인스턴스에 저장한다가 있으면 그 자리에서 소거합니다. 액세스 키를 AWS Secrets Manager에 넣어 인스턴스가 꺼내 쓴다도 같은 이유로 오답입니다 — 장기 자격 증명이 여전히 존재하기 때문입니다.

같은 판단이 Lambda 함수(실행 역할), ECS 태스크(태스크 역할), EKS 파드에도 그대로 적용됩니다. AWS 안에서 실행되는 컴퓨팅은 전부 역할로 권한을 받습니다. 컨테이너의 역할 분리는 13장 컨테이너에서 다룹니다.

인스턴스에 역할을 붙였다고 해서 인스턴스 안의 모든 프로세스가 안전해지는 것은 아닙니다. 역할의 임시 자격 증명은 인스턴스 메타데이터 서비스에서 꺼내 오므로, 서버 측 요청 위조(SSRF) 취약점이 있으면 외부에서 그 자격 증명을 훔칠 수 있습니다. 그래서 메타데이터 접근을 토큰 기반으로 강제하는 IMDSv2가 함께 나옵니다. IMDSv2의 동작과 홉 제한은 5장 EC2와 컴퓨트에서 다룹니다.

실제로 이 구성을 잘못 만든 사고의 전개는 케이스 1 · EC2에 액세스 키를 심어 배포했다에서 따라갑니다.

정책 문서의 구조

IAM 정책은 JSON 문서입니다. 요소의 순서는 의미가 없지만 어떤 요소가 있고 없느냐가 정책의 종류를 결정합니다. 특히 Principal의 유무가 자격 증명 기반 정책과 리소스 기반 정책을 가릅니다.

요소별 역할

IAM JSON 정책의 주요 요소
요소 역할 주의
Version 정책 언어 버전. 현행 값은 2012-10-17 날짜처럼 보이지만 버전 식별자다. 정책을 만든 날짜가 아니다
Statement 실제 규칙을 담는 블록. 배열로 여러 개를 넣는다 문장 하나하나가 독립적으로 평가된다
Sid 문장 식별자. 사람이 읽기 위한 이름표 선택 사항이지만 붙여 두면 감사와 디버깅이 쉬워진다
Effect Allow 또는 Deny Deny는 다른 모든 Allow를 이긴다
Principal 누구에게 적용되는가. 계정 · 사용자 · 역할 · AWS 서비스를 지정한다 리소스 기반 정책(역할 신뢰 정책 포함)에만 있다. 자격 증명 기반 정책에는 쓰지 않는다
Action 대상 API 작업. s3:GetObject처럼 서비스:작업 형식 NotAction과 같은 문장에 함께 쓸 수 없다
Resource 대상 리소스의 ARN NotResource와 함께 쓸 수 없다. 버킷과 객체는 서로 다른 ARN이다
Condition 추가 조건. 조건 키와 연산자로 적용 범위를 좁힌다 없으면 항상 적용된다. 조건이 거짓이면 그 문장은 적용되지 않는다

두 문장이 나뉜 이유가 곧 시험 포인트입니다. s3:ListBucket은 버킷에 대한 작업이라 대상이 arn:aws:s3:::버킷이름이고, s3:GetObject는 객체에 대한 작업이라 대상이 arn:aws:s3:::버킷이름/키입니다. 하나의 ARN으로 둘 다 처리하려다 "목록은 되는데 읽기가 안 된다"가 나옵니다.

Condition — 최소 권한을 만드는 도구

조건은 "누가 무엇을"에 "어떤 상황에서"를 더합니다. 전역 조건 키는 어느 서비스에서나 쓸 수 있고, 서비스별 조건 키도 있습니다.

두 문장 모두 Effect가 Deny라는 점이 중요합니다. "TLS를 쓸 때만 허용"을 Allow + 조건으로 쓰면 다른 정책의 Allow를 막지 못합니다. 강제하고 싶은 규칙은 조건부 Deny로 씁니다.

관리형 정책과 인라인 정책

관리형 정책과 인라인 정책의 차이
구분 성격 언제 쓰는가
AWS 관리형 정책 AWS가 만들고 유지한다. 여러 계정에서 같은 이름으로 쓸 수 있다 표준적인 역할을 빠르게 세울 때. 다만 대체로 필요보다 넓다
고객 관리형 정책 우리가 만들고 버전을 관리한다. 여러 자격 증명에 재사용된다 기본 선택. 최소 권한을 직접 설계할 때
인라인 정책 자격 증명 하나에 파묻힌다. 그 자격 증명이 지워지면 함께 사라진다 정책과 자격 증명의 일대일 관계를 강제하고 싶을 때

리소스 기반 정책은 관리형이 될 수 없고 항상 인라인입니다. S3 버킷 정책이나 KMS 키 정책을 "관리형 정책으로 만들어 여러 버킷에 붙인다"는 서술은 성립하지 않습니다.

정책 평가 로직 — 최종 결정이 나오는 순서 SAA 빈출

여러 정책이 동시에 적용될 때 AWS가 결정을 내리는 절차는 정해져 있습니다. IAM 사용 설명서의 서술을 그대로 옮기면 기본은 암묵적 거부이고, 어떤 정책에서든 명시적 거부가 하나라도 있으면 즉시 거부이며, 명시적 허용만이 기본 거부를 뒤집습니다.

세 단계로 요약한 우선순위

  1. 암묵적 거부(implicit deny) — 아무 정책도 언급하지 않은 작업은 거부됩니다. 이것이 기본값이며, 계정 루트 사용자만 예외입니다.
  2. 명시적 허용(explicit allow) — 자격 증명 기반 정책이나 리소스 기반 정책에 Allow가 있으면 기본 거부를 덮습니다.
  3. 명시적 거부(explicit deny) — 어느 정책에 있든 Deny가 하나라도 있으면 앞의 모든 허용을 이깁니다. 거부는 되돌릴 수 없습니다.

따라서 우선순위는 명시적 거부 > 명시적 허용 > 암묵적 거부입니다. 실무에서 이 성질이 유용한 이유는, "무슨 일이 있어도 막아야 하는 것"을 딱 한 군데에 Deny로 적으면 아래쪽에서 실수로 허용해도 뚫리지 않기 때문입니다.

합집합인가 교집합인가

평가 순서보다 자주 틀리는 것이 결합 규칙입니다. 조합에 따라 "둘 중 하나만 허용해도 통과"와 "둘 다 허용해야 통과"가 갈립니다.

정책 유형별 결합 규칙
조합 결합 의미
자격 증명 기반 + 리소스 기반 (같은 계정) 합집합 둘 중 하나만 허용해도 통과한다
자격 증명 기반 + 리소스 기반 (교차 계정) 양쪽 모두 필요 호출자 계정과 리소스 계정이 둘 다 허용해야 한다
자격 증명 기반 + 권한 경계 교집합 경계가 허용하지 않는 작업은 정책이 허용해도 못 한다
자격 증명 기반 + SCP 교집합 SCP가 상한이며 SCP만으로는 권한이 생기지 않는다
자격 증명 기반 + 세션 정책 교집합 세션 정책은 역할의 권한을 줄이기만 한다
SCP + 권한 경계 + 자격 증명 기반 셋 다 허용해야 함 하나라도 빠지면 거부된다

규칙을 하나로 압축하면 이렇습니다. 권한을 주는 정책끼리는 합쳐지고, 상한을 정하는 정책은 곱해집니다. 여기에 "명시적 거부는 어느 정책에 있든 전부를 이긴다"를 얹으면 평가 로직이 끝납니다.

"사용자에게 AdministratorAccess가 붙어 있는데 특정 작업이 실패한다"는 시나리오는 거의 언제나 상한 쪽을 묻습니다. 확인 순서는 (1) 어딘가에 명시적 Deny가 있는가, (2) SCP가 막고 있는가, (3) 권한 경계가 좁은가, (4) 세션 정책이 좁은가입니다.

반대로 "권한을 넓혀야 한다"는 시나리오에서 "SCP에 Allow를 추가한다"는 선택지는 오답입니다. SCP는 권한을 부여하지 않습니다.

자격 증명 기반 정책과 리소스 기반 정책

같은 접근을 허용하는 방법이 두 가지 있습니다. 주체 쪽에 "너는 저기에 갈 수 있다"고 적거나, 리소스 쪽에 "저 사람은 들어와도 된다"고 적는 것입니다. 어느 쪽에 적느냐가 관리 방식과 교차 계정 동작을 바꿉니다.

리소스 기반 정책을 지원하는 대표 리소스

모든 서비스가 리소스 기반 정책을 지원하지는 않습니다. IAM 사용 설명서는 예로 Amazon S3 버킷, Amazon SQS 큐, VPC 엔드포인트, AWS KMS 키를 듭니다. 여기에 IAM 역할의 신뢰 정책도 리소스 기반 정책이라는 사실을 더하면 시험 범위가 거의 덮입니다.

항목 자격 증명 기반 정책 리소스 기반 정책

교차 계정 접근 — 양쪽이 모두 허용해야 한다

계정 경계를 넘는 순간 규칙이 바뀝니다. IAM 사용 설명서는 이 점을 명시적으로 강조합니다 — 계정 A의 호출자는 계정 B의 리소스를 부를 수 있는 자격 증명 기반 정책을 가져야 하고, 동시에 계정 B의 리소스 기반 정책이 계정 A의 호출자를 허용해야 합니다. 양쪽에 정책이 없으면 요청은 실패합니다.

구현 방법은 두 갈래이고, 무엇을 공유하느냐로 갈립니다.

교차 계정 접근의 두 가지 구현
방식 동작 고르는 기준
역할 수임(AssumeRole) 리소스 계정에 역할을 만들고 신뢰 정책에 상대 계정을 적는다. 호출자는 역할을 맡아 리소스 계정의 주체가 되어 행동한다 기본 선택. 여러 서비스에 접근해야 하거나, 리소스 기반 정책을 지원하지 않는 서비스가 섞여 있을 때

"다른 계정의 팀에게 우리 버킷 접근을 준다"는 문항에서 한쪽만 고친 선택지는 오답입니다. 선택지에 "버킷 정책만 수정한다"와 "양쪽 계정에 정책을 구성한다"가 함께 있으면 후자입니다.

그리고 계정 간 접근에 IAM 사용자와 액세스 키를 상대에게 준다는 선택지는 언제나 오답입니다. 정답은 역할과 신뢰 정책입니다.

AWS STS와 역할 수임

AWS Security Token Service(STS)는 임시 보안 자격 증명을 발급하는 서비스입니다. 발급된 자격 증명은 액세스 키 ID · 비밀 액세스 키 · 세션 토큰 세 값으로 이루어지고, 만료 시각이 있습니다. IAM 사용 설명서는 임시 자격 증명의 장점으로 "장기 자격 증명을 애플리케이션에 배포하거나 심을 필요가 없다"와 "수명이 제한되어 있으므로 교체하거나 명시적으로 폐기할 필요가 없다"를 듭니다.

상황에 따라 다른 API

임시 자격 증명을 발급하는 STS 작업
작업 언제 쓰는가 특징
AssumeRole 같은 계정 안의 권한 전환, 교차 계정 접근 호출자가 이미 AWS 자격 증명을 가지고 있어야 한다
AssumeRoleWithSAML 기업 디렉터리 페더레이션 (SAML 2.0 기반) 기업 ID 저장소를 AWS 역할에 연결한다. 사용자별 AWS 자격 증명이 필요 없다
AssumeRoleWithWebIdentity 웹 · 모바일 앱의 외부 IdP 로그인 (OIDC 호환) 호출에 AWS 자격 증명이 필요 없다. 모바일 앱에는 Amazon Cognito가 권장된다

신뢰 정책과 외부 ID

역할을 만드는 쪽(신뢰하는 계정, 리소스 소유자)이 신뢰 정책에 상대 계정(신뢰받는 계정)을 적습니다. 문제는 상대 계정이 우리와 같은 조직이 아닐 때입니다. 상대 계정 전체를 신뢰하면 그 계정의 모든 주체가 역할을 맡을 수 있게 됩니다.

외부 ID(external ID)는 이때 쓰는 장치입니다. STS API 문서는 "교차 계정 역할은 보통 한 계정 전체를 신뢰하도록 설정되므로, 신뢰하는 계정의 관리자가 외부 ID를 발급해 그 ID를 아는 사람만 역할을 맡게 한다"고 설명합니다. 서드파티 서비스에 우리 계정 접근을 위임할 때의 표준 구성입니다.

세션 길이와 역할 연쇄

세션 길이는 무한정 늘릴 수 없습니다. STS API 문서에서 확인되는 값은 다음과 같습니다.

STS 세션 길이 관련 확인된 값
항목 값 근거
AssumeRole의 DurationSeconds 최소 900초(15분)부터 역할에 설정된 최대 세션 길이까지 역할의 최대 세션 길이는 1시간에서 12시간 사이로 설정할 수 있다
역할 연쇄(role chaining) 세션이 최대 1시간으로 제한된다 1시간을 넘는 DurationSeconds를 주면 작업이 실패한다
GetSessionToken IAM 사용자 기준 900초(15분)–129,600초(36시간), 기본 43,200초(12시간) STS API 문서 본문에 명시
세션 정책 길이 인라인과 관리형 정책 ARN을 합쳐 평문 2,048자까지, 관리형 정책 ARN은 최대 10개 STS API 문서 본문에 명시

역할 연쇄란 역할로 받은 임시 자격 증명으로 또 다른 역할을 맡는 것입니다. 여기서 자주 나오는 함정이 하나 있습니다 — EC2 인스턴스가 인스턴스 프로파일의 역할로 API를 호출하는 것은 역할 연쇄가 아닙니다. 따라서 1시간 제한도 적용되지 않습니다.

페더레이션 문항에서 API 이름을 고르는 기준은 ID가 어디에 있는가입니다. 기업 Active Directory나 SAML IdP면 AssumeRoleWithSAML, 소셜 로그인이나 OIDC 제공자면 AssumeRoleWithWebIdentity, 이미 AWS 자격 증명이 있는 주체면 AssumeRole입니다.

서드파티에 우리 계정 접근을 준다는 문항에서 외부 ID가 선택지에 있으면 그것이 정답 신호입니다. IAM 사용자를 만들어 키를 넘기는 선택지는 언제나 소거합니다.

상한을 정하는 정책 — SCP와 권한 경계

지금까지의 정책은 권한을 주는 쪽이었습니다. 여기서 다루는 두 가지는 권한을 주지 않고 상한만 정합니다. 둘을 구분하는 것이 도메인 1에서 반복적으로 요구됩니다.

서비스 제어 정책(SCP) — 계정 전체의 상한

SCP는 AWS Organizations의 정책이며, 조직 루트 · OU · 개별 계정 중 어디에나 붙습니다. 성질은 두 문장으로 요약됩니다.

  • SCP는 권한을 부여하지 않습니다. 조직이나 OU의 최대 권한만 정합니다. 실제 허용은 여전히 IAM 정책이 해야 하고, SCP는 그 위에 씌우는 뚜껑입니다.
  • SCP는 멤버 계정의 루트 사용자에게도 적용됩니다. IAM 정책으로는 루트를 제한할 수 없으므로, 루트를 통제하는 유일한 수단이 SCP입니다.

조직을 전체 기능으로 만들어야 SCP를 쓸 수 있습니다. 통합 결제 전용으로 만든 조직에서는 어떤 정책 유형도 활성화되지 않습니다 (1장 AWS Organizations).

권한 경계 — 엔터티 하나의 상한

권한 경계는 관리형 정책을 IAM 사용자나 역할 하나에 상한으로 붙이는 기능입니다. IAM 사용 설명서의 표현으로는 "자격 증명 기반 정책이 그 엔터티에 부여할 수 있는 최대 권한을 설정"하며, "권한을 제한할 뿐 그 자체로는 권한을 주지 않습니다." 실효 권한은 자격 증명 기반 정책과 권한 경계의 교집합입니다.

가장 중요한 용도는 권한 관리 업무의 위임입니다. 개발팀장에게 "사용자와 역할을 만들 수 있는 권한"을 주고 싶은데 그대로 주면 관리자 권한을 가진 사용자를 만들어 버릴 수 있습니다. 새로 만드는 엔터티에 특정 권한 경계를 반드시 붙이도록 조건을 걸면 위임하면서도 상한을 유지할 수 있습니다.

SCP와 권한 경계는 무엇이 다른가

문항이 "조직의 모든 계정에서"로 시작하면 SCP, "이 개발자가 만드는 역할이 넘지 않도록"이면 권한 경계입니다. 범위의 단위가 계정인지 엔터티인지가 유일한 구분 기준입니다.

"루트 사용자도 특정 작업을 못 하게 하라"는 요구가 나오면 답은 SCP뿐입니다. IAM 정책이나 권한 경계로 루트를 막는 선택지는 전부 오답입니다.

AWS IAM Identity Center와 페더레이션 선택

계정이 늘어나면 계정마다 IAM 사용자를 만드는 방식이 무너집니다. 입사자가 오면 계정 수만큼 사용자를 만들어야 하고, 퇴사자가 나가면 계정 수만큼 지워야 하며, 하나라도 빠뜨리면 접근이 남습니다. 이 문제를 푸는 것이 페더레이션이고, AWS의 표준 답이 AWS IAM Identity Center입니다.

이 서비스는 2022년에 AWS IAM Identity Center로 이름이 바뀌었습니다. 예전 자료에 나오는 옛 이름은 같은 서비스를 가리키며, 시험과 이 사이트에서는 현재 이름을 씁니다.

권한 집합이 하는 일

IAM Identity Center는 사용자와 그룹을 한 곳에서 관리하고, 권한 집합(permission set)을 만들어 "어느 그룹이 어느 계정에서 무엇을 할 수 있는가"를 정의합니다. 권한 집합을 계정에 할당하면 그 계정 안에 대응하는 역할이 자동으로 만들어지고, 사용자는 로그인 포털에서 계정과 역할을 골라 임시 자격 증명을 받습니다.

결과적으로 얻는 것은 세 가지입니다.

  • 자격 증명이 한 곳에만 존재하므로 퇴사 처리가 한 번이면 끝납니다.
  • 계정마다 IAM 사용자를 만들지 않으므로 장기 자격 증명이 생기지 않습니다.
  • 권한 집합을 고치면 할당된 모든 계정에 반영됩니다.

무엇을 고를 것인가 — 페더레이션 판단 기준

시험은 서비스를 설명하게 하지 않고 고르게 합니다. 기준은 누구에게 접근을 주는가 하나입니다.

대상별 페더레이션 선택 기준
누구에게 무엇을 고르는가 신호가 되는 표현
사내 직원에게 여러 AWS 계정 접근을 준다 AWS IAM Identity Center "여러 계정", "중앙에서 관리", "직원이 입퇴사한다", "단일 로그인"
기존 SAML IdP를 계정 하나에 직접 연결한다 IAM의 SAML 2.0 자격 증명 공급자 + 역할 "기존 IdP를 그대로", "계정이 하나뿐"
모바일 · 웹 앱의 최종 사용자에게 준다 Amazon Cognito (자격 증명 풀) "모바일 앱 사용자 수백만", "소셜 로그인", "게스트 접근"
EC2 인스턴스에 Active Directory 도메인 참여가 필요하다 AWS Directory Service "도메인 조인", "Windows 파일 서버", "그룹 정책"
AWS 안에서 실행되는 워크로드에 준다 IAM 역할 (사람이 개입하지 않는다) "인스턴스에서", "Lambda 함수가", "태스크가"

Amazon Cognito와 AWS Directory Service의 세부 동작은 16장 보안·암호화·거버넌스에서 다룹니다. 여기서는 사람 대 직원이면 Identity Center, 사람 대 앱 사용자면 Cognito, 사람이 아니면 역할이라는 세 갈래만 확실히 해 둡니다.

"수백 개 계정의 직원 접근을 중앙에서 관리"는 IAM Identity Center이고, "모바일 앱의 익명 사용자에게 S3 업로드를 허용"은 Amazon Cognito입니다. 이 둘을 바꿔 놓는 것이 전형적인 오답 배치입니다.

어느 쪽이든 "IAM 사용자를 계정마다 만든다"는 선택지는 운영 부담 한정어와 보안 한정어 양쪽에서 동시에 밀립니다.

흔한 오해

"SCP를 붙이면 그 계정에 권한이 생긴다" — SCP는 상한만 정하고 권한을 부여하지 않습니다. SCP에 Allow를 써도 IAM 정책이 허용하지 않으면 아무 일도 일어나지 않습니다. SCP의 Allow는 "여기까지는 허용해도 된다"는 필터이지 부여가 아닙니다. 반대 방향은 강력합니다 — SCP의 Deny는 계정 안의 어떤 IAM 정책도 뚫을 수 없고, 멤버 계정의 루트 사용자에게까지 적용됩니다.

"AdministratorAccess가 붙어 있으면 뭐든 할 수 있다" — 자격 증명 기반 정책은 여러 관문 중 하나일 뿐입니다. 어딘가에 명시적 Deny가 있거나, SCP가 그 작업을 상한 밖에 두었거나, 권한 경계가 좁거나, 세션 정책이 좁으면 관리자 정책을 가지고도 거부됩니다. 권한을 주는 정책끼리는 합쳐지고, 상한을 정하는 정책은 곱해집니다. 곱셈에서는 0이 하나만 있어도 결과가 0입니다.

"교차 계정 접근은 버킷 정책만 고치면 된다" — 계정 경계를 넘는 요청은 양쪽이 모두 허용해야 통과합니다. 호출자 계정에는 그 리소스를 부를 수 있는 자격 증명 기반 정책이 있어야 하고, 리소스 계정에는 그 호출자를 허용하는 리소스 기반 정책이 있어야 합니다. 같은 계정 안에서는 둘 중 하나만 있어도 통과하기 때문에, 같은 계정에서 되던 구성이 계정을 나누는 순간 깨집니다.

시험 포인트 정리

이 장의 주제는 전부 보안 아키텍처 설계(30%)에 속합니다. 아래 표의 함정 열이 실제 오답 선택지가 만들어지는 자리입니다.

2장 핵심 암기 항목과 함정
항목 사실 함정
EC2에서의 API 호출 IAM 역할을 인스턴스 프로파일로 연결한다 액세스 키를 인스턴스나 비밀 저장소에 두는 선택지 — 장기 자격 증명이 남는다

SCP의 성질 권한을 부여하지 않고 상한만 정한다. 멤버 계정 루트에도 적용 "SCP로 권한을 준다", "루트는 SCP도 못 막는다"
SCP 전제 조건 조직이 전체 기능이어야 정책을 쓸 수 있다 통합 결제 전용 조직에서 SCP를 쓰려 함
권한 경계 IAM 사용자와 역할의 최대 권한. 권한 관리 위임에 쓴다 그룹에 붙일 수 있다고 생각. 루트에도 적용된다고 생각
역할의 두 정책 신뢰 정책(누가 맡는가) + 권한 정책(무엇을 하는가) 한쪽만 고치고 "역할이 동작하지 않는다"고 판단
신뢰 정책의 제약 역할에 붙는 리소스 기반 정책이며 Principal에 와일드카드를 쓸 수 없다 신뢰 정책을 자격 증명 기반 정책으로 취급
Principal의 위치 리소스 기반 정책에만 있다 자격 증명 기반 정책에 Principal을 넣어 문법 오류
그룹의 제약 중첩 불가, Principal이 될 수 없다 버킷 정책에서 IAM 그룹을 지정하려 함
S3 정책의 ARN 버킷 작업은 arn:aws:s3:::버킷, 객체 작업은 arn:aws:s3:::버킷/* 하나만 써서 목록은 되는데 읽기가 안 되는 구성
강제 규칙의 작성법 반드시 막아야 하는 규칙은 조건부 Deny로 쓴다 조건부 Allow로 써서 다른 정책의 허용을 막지 못함
리소스 기반 정책의 형태 항상 인라인이다. 관리형이 될 수 없다 버킷 정책을 관리형 정책으로 재사용하려 함
STS API 선택 SAML IdP는 AssumeRoleWithSAML, OIDC는 AssumeRoleWithWebIdentity 모든 페더레이션에 AssumeRole을 답으로 고름
외부 ID 서드파티에 계정 접근을 위임할 때 신뢰 정책 조건으로 쓴다 서드파티에 IAM 사용자와 액세스 키를 발급
역할 연쇄 세션이 최대 1시간. EC2 인스턴스 역할 사용은 연쇄가 아니다 인스턴스 역할에도 1시간 제한이 있다고 답함
페더레이션 선택 직원·다중 계정은 IAM Identity Center, 앱 사용자는 Amazon Cognito 둘을 바꿔 고르거나 계정마다 IAM 사용자를 만드는 안을 고름
루트 사용자 제한 IAM 정책으로는 못 줄인다. SCP만 멤버 계정 루트에 상한을 건다 루트에 거부 정책을 붙이는 선택지

한정어 MOST secure가 붙으면 판단 순서는 (1) 장기 자격 증명을 없애는 선택지, (2) 권한 범위를 좁히는 선택지, (3) 네트워크 경로를 비공개로 만드는 선택지입니다. IAM 역할, 최소 권한 정책, VPC 엔드포인트가 각 단계의 대표 답입니다.

한편 LEAST operational overhead가 함께 붙으면 자동으로 교체되는 자격 증명이 결정적 근거가 됩니다. 역할과 IAM Identity Center가 여기서도 앞섭니다 — 사람이 키를 돌릴 일이 없기 때문입니다.
