RDS와 관계형 데이터베이스

이 장의 무게중심은 하나입니다. Multi-AZ 배포와 읽기 전용 복제본은 다른 문제를 푼다는 것. 하나는 가용성을, 다른 하나는 읽기 확장을 삽니다. 시험은 이 둘을 바꿔 놓은 선택지를 거의 매번 섞어 넣고, 여기서 흔들리면 가중치 26%짜리 도메인을 통째로 잃습니다. 나머지 절들은 이 판단을 둘러싼 배경 — Amazon Aurora의 구조, 백업과 복구, 연결 관리, 암호화 — 입니다.

주 도메인은 복원력 있는 아키텍처 설계(26%)이며, Aurora와 RDS Proxy는 고성능 아키텍처 설계(24%)에도 걸칩니다.

학습 목표

  • Amazon RDS가 관리하는 범위와 고객이 남겨 받는 범위를 책임 공유 모델 위에서 구분할 수 있습니다.
  • Multi-AZ 배포와 읽기 전용 복제본을 복제 방식 · 목적 · 엔드포인트 · 읽기 처리 네 가지 축으로 구분할 수 있습니다.
  • 표준 Multi-AZ 인스턴스 배포와 Multi-AZ DB 클러스터 배포가 별개 아키텍처라는 사실을 근거를 들어 설명할 수 있습니다.
  • Amazon Aurora의 공유 클러스터 볼륨과 엔드포인트 구조가 RDS의 인스턴스별 스토리지 모델과 어떻게 다른지 설명할 수 있습니다.
  • 자동 백업 · 특정 시점 복구 · 수동 스냅샷 · 스냅샷 복사와 공유를 요구사항에 맞게 고를 수 있습니다.
  • 저장 시 암호화가 생성 시점에 결정된다는 제약을 근거로 기존 데이터베이스를 암호화하는 절차를 설계할 수 있습니다.

Amazon RDS — 무엇까지 AWS가 하는가

Amazon RDS는 관계형 데이터베이스 엔진을 대신 운영해 주는 서비스입니다. 직접 EC2에 데이터베이스를 설치하는 것과 비교하면, 운영체제와 엔진 설치 · 패치 · 백업 · 장애 조치 · 복제 설정이 AWS 쪽으로 넘어갑니다. 반대로 스키마 · 인덱스 · 쿼리 · 데이터베이스 사용자 · 네트워크 배치 · 암호화 선택은 여전히 우리 몫입니다.

시험에서 LEAST operational overhead라는 한정어가 붙으면 이 경계선이 그대로 정답의 근거가 됩니다. "EC2에 직접 데이터베이스를 설치하고 스크립트로 백업한다"는 선택지는 같은 결과를 내더라도 운영 부담이 더 크므로 소거 대상입니다.

"데이터베이스 운영 부담을 줄이고 싶다"는 요구는 단계로 읽습니다. EC2 자체 관리 → Amazon RDS → Amazon Aurora → Aurora Serverless v2 순으로 우리가 손댈 것이 줄어듭니다. 문제문이 LEAST operational overhead를 말하면 오른쪽으로, 엔진을 세밀하게 통제해야 한다거나 RDS가 지원하지 않는 엔진이라는 제약이 붙으면 왼쪽으로 이동합니다.

Multi-AZ와 읽기 전용 복제본 SAA 빈출

Multi-AZ는 가용성, 읽기 전용 복제본은 읽기 확장입니다. 이 한 문장이 이 장에서 가장 많은 문항을 가릅니다. 요구가 둘 다면 둘 다 구성하는 선택지가 정답이고, 둘을 바꿔 놓은 선택지는 그 자리에서 소거합니다.

같은 결론을 도메인 2 해설에서 이미 요약해 두었습니다. 여기서는 그 표 아래로 한 층 더 내려가 왜 그렇게 되는지를 복제 방식에서부터 따라갑니다.

Multi-AZ 배포 — 동기 복제로 가용성을 산다

Multi-AZ DB 인스턴스 배포는 다른 가용 영역에 동기식(synchronous) 대기 복제본을 두고 유지합니다. RDS 사용 설명서는 프라이머리가 "가용 영역을 가로질러 대기 복제본으로 동기적으로 복제된다"고 서술합니다. 커밋은 대기 쪽 스토리지에 기록이 반영된 뒤에 완료되므로, 장애 조치가 일어나도 커밋된 트랜잭션이 유실되지 않습니다.

대가는 지연 시간입니다. 같은 문서가 "동기 복제 때문에 단일 가용 영역 배포보다 쓰기와 커밋 지연이 늘어날 수 있다"고 명시합니다. Multi-AZ는 쓰기 지연을 조금 내주고 가용성을 사는 거래입니다.

결정적인 제약은 이것입니다. RDS 사용 설명서는 Multi-AZ에 대해 "고가용성 옵션은 읽기 전용 시나리오를 위한 확장 솔루션이 아니며, 대기 복제본으로 읽기 트래픽을 처리할 수 없다"고 못 박습니다. 대기 인스턴스는 평소에 놀고 있는 것처럼 보이지만, 애플리케이션이 접근할 수 있는 엔드포인트가 없습니다.

읽기 전용 복제본 — 비동기 복제로 읽기를 늘린다

읽기 전용 복제본은 소스 인스턴스의 변경을 비동기(asynchronous)로 따라갑니다. 비동기이므로 소스의 쓰기 성능이 복제본 수에 크게 좌우되지 않지만, 대신 복제 지연(replica lag)이 존재합니다. 방금 쓴 값을 곧바로 복제본에서 읽으면 이전 값이 보일 수 있습니다.

복제본은 자기 엔드포인트를 갖습니다. 그래서 읽기 부하를 나누려면 애플리케이션이 읽기 쿼리를 그 엔드포인트로 보내도록 수정해야 합니다. 문제문에 without changing application code가 붙어 있으면 읽기 전용 복제본만으로는 요구를 만족시키지 못한다는 뜻이 됩니다.

복제본에는 몇 가지 조건이 따라붙습니다. RDS API 문서 기준으로 정리하면 다음과 같습니다.

  • 소스 인스턴스는 자동 백업이 켜져 있어야 합니다. 보존 기간이 0이면 복제본을 만들 수 없습니다.
  • 복제본은 백업이 꺼진 상태로 생성됩니다. 필요하면 따로 켭니다.
  • 개수 상한은 엔진에 따라 다릅니다. 대부분의 엔진은 인스턴스당 15개이고, Oracle과 SQL Server는 5개, Db2는 3개입니다.
  • 복제본을 독립 인스턴스로 승격(PromoteReadReplica)할 수 있지만, 이것은 자동으로 일어나지 않습니다. 사람이나 자동화가 호출해야 합니다.
  • 복제본 자체를 Multi-AZ로 만들 수도 있습니다. 소스가 Multi-AZ인지와는 무관한 별개 설정입니다.

읽기 전용 복제본은 자동 장애 조치 수단이 아닙니다. 프라이머리가 죽어도 복제본이 스스로 승격하지 않고, 쓰기는 계속 실패합니다. "가용성을 높여야 한다"는 요구에 복제본을 답으로 고르면 틀립니다.

반대로 교차 리전 복제본은 재해 복구 자산이 됩니다. 리전 장애 시 다른 리전의 복제본을 승격해 서비스를 재개할 수 있기 때문입니다. 다만 승격은 수동 조작이므로 복구 시간 목표(RTO)가 0에 가까운 요구에는 부족합니다.

장애 조치는 어떻게 일어나는가

Multi-AZ 장애 조치의 핵심 기제는 DNS 레코드 전환입니다. RDS 사용 설명서는 "장애 조치 메커니즘이 DB 인스턴스의 DNS 레코드를 대기 인스턴스를 가리키도록 자동으로 바꾼다"고 설명하며, 그 결과 기존 연결은 다시 맺어야 한다고 덧붙입니다. 엔드포인트 문자열이 바뀌지 않으므로 애플리케이션 설정은 그대로 두어도 됩니다.

소요 시간은 같은 문서 기준 대체로 60~120초이며, 큰 트랜잭션이나 긴 복구 과정이 있으면 더 걸릴 수 있습니다. 장애 조치를 유발하는 사유도 문서에 표로 정리되어 있습니다.

Multi-AZ DB 클러스터 — 이름이 비슷한 별개 아키텍처

여기가 이 장에서 가장 조심할 지점입니다. Multi-AZ DB 인스턴스 배포와 Multi-AZ DB 클러스터 배포는 이름이 두 글자 차이지만 구조가 다릅니다. RDS 사용 설명서는 Multi-AZ DB 클러스터를 이렇게 정의합니다.

  • 읽기 가능한 대기 인스턴스 2개를 두는 배포 모드입니다. 쓰기 인스턴스 1개와 읽기 인스턴스 2개가 같은 리전의 서로 다른 세 가용 영역에 놓입니다.
  • 복제는 동기가 아니라 반동기(semisynchronous)입니다. 변경을 커밋하려면 읽기 인스턴스 중 최소 하나의 확인이 필요하며, 모든 복제본에서 완전히 실행·커밋될 것까지 요구하지는 않습니다.
  • 읽기 인스턴스는 자동 장애 조치 대상이면서 동시에 읽기 트래픽을 처리합니다.
  • Multi-AZ DB 인스턴스 배포보다 쓰기 지연이 낮은 편이라고 문서가 명시합니다.
  • 클러스터를 만들려면 DBClusterInstanceClass · AllocatedStorage · Iops · StorageType을 함께 지정해야 하고, 프로비저닝된 IOPS 스토리지만 지원합니다.

그리고 RDS 사용 설명서는 별도의 경고 상자로 "Multi-AZ DB 클러스터는 Aurora DB 클러스터와 같은 것이 아니다"라고 적어 둡니다. 이름에 모두 "클러스터"가 들어가지만 세 가지는 전부 다른 것입니다.

이름이 비슷한 세 가지 배포 형태 구분
항목 Multi-AZ DB 인스턴스 배포 Multi-AZ DB 클러스터 배포 Aurora DB 클러스터
대기 인스턴스 1개 2개 Aurora 복제본(읽기 인스턴스)
대기 인스턴스로 읽기 불가 가능 가능
복제 방식 동기 반동기 — 읽기 인스턴스 중 최소 하나의 확인 공유 클러스터 볼륨 — 인스턴스 간 데이터 복제가 아님
스토리지 인스턴스마다 자기 볼륨 인스턴스마다 자기 볼륨 (프로비저닝된 IOPS 전용) 모든 인스턴스가 하나의 클러스터 볼륨을 공유
가용 영역 수 2 3 클러스터 볼륨이 3개 가용 영역에 복제됨

"Multi-AZ 대기 인스턴스에서 읽기를 처리해 부하를 분산한다"는 서술은 표준 Multi-AZ 인스턴스 배포에서 틀립니다. 읽기 가능한 대기 인스턴스를 두는 Multi-AZ DB 클러스터 배포는 별개의 아키텍처이므로, 문제문이 어느 쪽을 말하는지 확인하고 답합니다.

판별 단서는 문제문의 어휘입니다. 대기 인스턴스가 1개이거나 가용 영역이 2개라고 쓰여 있으면 인스턴스 배포이고, 읽기 가능한 대기 2개 또는 가용 영역 3개가 나오면 DB 클러스터 배포입니다.

요구사항을 다음 순서로 읽으면 거의 실수하지 않습니다.

  • "가용 영역 장애를 견뎌야 한다" · "다운타임 최소화" · "자동 장애 조치" → Multi-AZ
  • "읽기 쿼리가 많다" · "보고서·분석 쿼리가 운영에 영향을 준다" → 읽기 전용 복제본
  • 둘 다 요구 → Multi-AZ 와 읽기 전용 복제본을 함께 구성
  • "애플리케이션 코드를 바꾸지 않고 읽기를 분산" → 복제본만으로는 부족합니다. Aurora의 리더 엔드포인트나 캐시 계층을 검토합니다 (11장 캐시 계층 선택)

Amazon Aurora — 스토리지를 컴퓨트에서 떼어 냈다

Aurora는 MySQL과 PostgreSQL 호환 엔진이지만, 스토리지 계층을 다시 설계한 것이 본질입니다. RDS에서는 인스턴스마다 자기 볼륨이 있고 복제란 곧 데이터를 한 번 더 쓰는 일이었지만, Aurora에서는 모든 인스턴스가 하나의 클러스터 볼륨을 함께 봅니다.

클러스터 볼륨 — 데이터가 인스턴스와 독립이다

Aurora 사용 설명서는 클러스터 볼륨을 "한 AWS 리전 안의 세 가용 영역에 걸쳐 데이터 사본을 두는 단일 가상 볼륨"이라고 정의합니다. 중요한 문장은 그다음입니다 — "복제의 양은 클러스터 안의 DB 인스턴스 개수와 무관하다." 인스턴스를 몇 개 두든 데이터의 내구성은 스토리지 계층이 알아서 확보합니다.

이 구조에서 따라오는 결과가 실무와 시험 양쪽에서 자주 나옵니다.

  • 인스턴스를 빠르게 추가할 수 있습니다. 테이블 데이터를 새로 복사하지 않고 이미 존재하는 공유 볼륨에 연결하기만 하면 됩니다.
  • 인스턴스를 제거해도 데이터는 남습니다. 클러스터 전체를 삭제해야 데이터가 지워집니다.
  • 스토리지는 데이터가 늘어나면 자동으로 커집니다. 용량을 미리 프로비저닝하지 않습니다.

Aurora 복제본과 엔드포인트

클러스터에 두 번째 이후의 인스턴스를 만들면 그것이 Aurora 복제본(Aurora Replica) 또는 리더 인스턴스입니다. Aurora 사용 설명서는 복제본의 목적이 두 가지라고 명시합니다 — 읽기 확장과 가용성입니다. 라이터가 사용 불가 상태가 되면 Aurora가 리더 중 하나를 새 라이터로 자동 승격합니다.

여기가 RDS 읽기 전용 복제본과 갈리는 지점입니다. RDS 복제본은 자동 승격이 없고, Aurora 복제본은 장애 조치 대상입니다. Aurora에서는 "읽기 확장을 위한 인스턴스"와 "장애 조치 대상"이 같은 것입니다.

접속은 엔드포인트를 통해 이루어지고, 종류가 나뉩니다.

Amazon Aurora 엔드포인트의 종류와 용도
엔드포인트 가리키는 대상 언제 쓰는가
클러스터 엔드포인트 (라이터) 현재 프라이머리 인스턴스 하나 모든 쓰기와 DDL. 장애 조치가 일어나면 새 프라이머리로 자동으로 따라갑니다
리더 엔드포인트 Aurora 복제본들 — 연결 단위로 부하 분산 읽기 전용 쿼리. 복제본을 추가하면 별도 설정 없이 분산 대상에 들어갑니다
사용자 지정 엔드포인트 우리가 고른 인스턴스 부분집합 분석용으로 큰 인스턴스만 따로 묶는 것처럼, 용도별로 나눌 때
인스턴스 엔드포인트 특정 인스턴스 하나 진단과 튜닝. 애플리케이션이 상시로 쓰기에는 적합하지 않습니다

리더 엔드포인트가 있다는 사실이 판단을 바꿉니다. RDS 읽기 전용 복제본은 복제본마다 엔드포인트가 따로라서 복제본을 늘릴 때 애플리케이션 쪽 분산 로직이 필요하지만, Aurora는 리더 엔드포인트 하나만 바라보면 됩니다. "읽기 확장이 필요한데 운영 부담은 늘리기 싫다"는 요구가 Aurora로 수렴하는 이유입니다.

다만 클러스터에 복제본이 하나도 없으면 리더 엔드포인트는 프라이머리에 연결됩니다. 복제본을 만들지 않으면 읽기 확장도 장애 조치 대상도 없습니다.

Aurora 글로벌 데이터베이스 — 리전을 넘는다

Aurora 글로벌 데이터베이스는 쓰기를 받는 주 리전의 클러스터 하나와 읽기 전용 보조 리전 클러스터들로 구성됩니다. 복제는 애플리케이션이나 엔진이 아니라 Aurora 스토리지 하위 시스템의 전용 인프라가 수행합니다.

용도는 둘입니다. 전 세계 사용자에게 낮은 지연의 읽기를 제공하는 것과, 리전 전체 장애로부터 빠르게 복구하는 것입니다. 시험에서 "여러 대륙의 사용자가 읽기를 하고, 쓰기는 한 곳에서만 일어난다"는 문장이 나오면 이 기능이 후보에 들어옵니다.

보조 리전은 기본적으로 읽기 전용이지만, 쓰기 전달(write forwarding)을 켜면 보조 클러스터가 받은 쓰기를 주 클러스터로 넘기고 그 결과가 다시 복제되어 돌아옵니다. API 파라미터 이름은 EnableGlobalWriteForwarding입니다.

리전 단위 요구가 나오면 후보를 이렇게 가릅니다.

  • Aurora를 쓰고 있고 리전 간 낮은 지연 읽기와 빠른 복구가 필요 → Aurora 글로벌 데이터베이스
  • RDS(비 Aurora)이고 다른 리전에 읽기와 DR 자산이 필요 → 교차 리전 읽기 전용 복제본
  • 백업만 다른 리전에 두면 되고 복구 시간이 여유롭다 → 스냅샷 교차 리전 복사 또는 자동 백업 복제

같은 판단을 재해 복구 전략의 언어로 다시 정리한 것이 도메인 2의 DR 4전략입니다.

Aurora Serverless v2 — 용량을 자동으로 조절한다

Aurora Serverless v2는 온디맨드 자동 확장 구성입니다. 인스턴스 클래스를 고르는 대신 Aurora 용량 단위(Aurora Capacity Unit, ACU)의 최소값과 최대값을 정해 두면, 워크로드에 맞춰 그 범위 안에서 용량이 오르내립니다.

v2의 특징은 조절 단위가 작다는 점입니다. Aurora 사용 설명서는 프로비저닝된 클러스터에서 확장하려면 인스턴스를 통째로 추가해야 하는 반면 v2는 0.5 ACU 단위로 더하고 뺄 수 있다고 설명합니다. API의 MinCapacity·MaxCapacity도 0.5 단위 값을 받습니다.

고르는 기준은 부하의 예측 가능성입니다.

Aurora 프로비저닝 구성과 Aurora Serverless v2의 선택 기준
상황 더 나은 선택 근거
부하가 일정하고 예측 가능 프로비저닝된 인스턴스 용량을 고정해 두는 편이 단순하고, 약정 할인 대상이 됩니다
급증이 갑작스럽고 예측 불가 Aurora Serverless v2 최대 용량만 정해 두면 되고, 쓰지 않는 용량에는 과금되지 않습니다
개발 · 테스트처럼 유휴 시간이 김 Aurora Serverless v2 유휴 구간에서 용량이 내려갑니다. 지원 버전에서는 자동 일시 중지도 가능합니다
필요한 인스턴스 크기를 아직 모름 Aurora Serverless v2 실제 확장 폭을 관찰해 적정 용량을 찾을 수 있습니다
테넌트가 많고 각자 사용 시간대가 다름 Aurora Serverless v2 테넌트별로 클러스터를 두고도 유휴 클러스터의 비용이 낮게 유지됩니다

Aurora Serverless v1은 지원이 종료되었습니다. 2025년 1월 8일부터 신규 생성이 불가능해졌고 2025년 3월 31일에 수명이 끝났습니다. 시중 자료에 남아 있는 "Aurora Serverless는 0으로 축소되고 초 단위로 과금된다"는 설명은 v1 기준이므로 지금은 맞지 않습니다. 이 사이트에서 "Aurora Serverless"라고 쓰면 언제나 v2를 뜻합니다.

MOST cost-effective와 "트래픽이 불규칙하다"가 함께 나오면 Aurora Serverless v2가 유력 후보입니다. 반대로 "부하가 일정하다" 또는 "1년 이상 계속 운영한다"가 붙으면 프로비저닝된 인스턴스와 약정이 더 쌉니다. 서버리스가 언제나 싸지는 않다는 것이 이 문항군의 요지입니다 (5장 구매 옵션과 같은 논리입니다).

백업 — 자동 백업, 특정 시점 복구, 스냅샷

RDS의 백업은 두 갈래입니다. 자동 백업은 보존 기간 안에서 임의의 시점으로 되돌리기 위한 것이고, 수동 스냅샷은 특정 순간을 기한 없이 보관하기 위한 것입니다. 둘은 대체재가 아니라 역할이 다릅니다.

자동 백업과 특정 시점 복구

자동 백업은 매일 백업 기간에 스토리지 볼륨 스냅샷을 만들고, 여기에 트랜잭션 로그를 더해 특정 시점 복구(Point-In-Time Recovery, PITR)를 가능하게 합니다. RDS 사용 설명서는 트랜잭션 로그가 5분마다 Amazon S3로 업로드된다고 명시합니다. 복구 가능한 가장 최근 시각은 LatestRestorableTime으로 확인합니다.

자동 백업의 보존 기간과 기본값
항목 값 주의
DB 인스턴스 보존 기간 0 ~ 35일 0으로 두면 자동 백업이 꺼집니다. 읽기 전용 복제본의 소스로는 0을 쓸 수 없습니다
Multi-AZ DB 클러스터 보존 기간 1 ~ 35일 클러스터에서는 0을 지정할 수 없습니다
기본 보존 기간 API·CLI로 만들면 1일, 콘솔로 만들면 7일 같은 서비스인데 만든 경로에 따라 기본값이 다릅니다
백업 기간(backup window) 지정하지 않으면 30분 창이 자동 배정 유지 관리 기간과 겹칠 수 없습니다
보존 기간 0 ↔ 0이 아닌 값 전환 중단이 발생합니다 운영 중에 무심코 바꾸면 짧은 다운타임이 생깁니다

Multi-AZ 배포에서는 백업이 대기 인스턴스 쪽에서 수행됩니다. RDS 사용 설명서는 MariaDB · MySQL · Oracle · PostgreSQL의 Multi-AZ 배포에서 프라이머리의 I/O가 백업 중에 중단되지 않는다고 서술합니다. SQL Server는 예외로, 단일 가용 영역이든 Multi-AZ든 프라이머리에서 백업을 받기 때문에 I/O가 잠시 멈춥니다. Multi-AZ는 가용성만이 아니라 백업 영향도 줄입니다.

수동 스냅샷 — 보존 기간과 무관하게 남는다

수동 스냅샷은 우리가 명시적으로 만드는 것이고, 데이터베이스를 삭제해도 남습니다. 자동 백업은 인스턴스를 지우면서 함께 사라지지만(보존 옵션을 고르지 않은 경우), 수동 스냅샷은 우리가 지우기 전까지 유지됩니다. 규정 준수 요구로 특정 시점의 데이터를 오래 보관해야 한다면 이쪽입니다.

스냅샷은 증분입니다. RDS 사용 설명서는 첫 스냅샷이 전체 데이터를 담고 이후 스냅샷은 마지막 스냅샷 이후 변경된 데이터만 저장한다고 설명합니다. 수동 스냅샷은 리전당 100개까지 보관할 수 있으며, 이 상한은 자동 백업에는 적용되지 않습니다.

복구에서 반드시 기억할 사실이 하나 있습니다. 스냅샷 복원도 PITR도 기존 인스턴스를 되돌리는 것이 아니라 새 DB 인스턴스를 만드는 작업입니다. 엔드포인트가 새로 생기므로 애플리케이션이 가리키는 주소를 바꾸거나 원래 인스턴스의 이름을 바꿔 자리를 넘겨주어야 합니다. 게다가 새 인스턴스는 기본 보안 그룹 · 기본 파라미터 그룹 · 단일 가용 영역으로 만들어지므로, 복원 후 설정을 다시 맞춰야 합니다.

스냅샷 복사와 공유

스냅샷은 다른 리전으로 복사할 수 있고 다른 계정과 공유할 수 있습니다. 두 동작의 규칙이 다릅니다.

스냅샷 복사와 공유의 규칙
동작 규칙
리전 간 복사 복사 API를 호출한 리전이 대상 리전이 됩니다. 암호화된 스냅샷을 다른 리전으로 복사하려면 대상 리전의 KMS 키를 반드시 지정해야 합니다. KMS 키는 리전에 묶여 있기 때문입니다

암호화된 스냅샷의 공유 공유는 가능하지만 계정 ID를 명시하는 방식만 허용됩니다. all을 쓸 수 없습니다. 대상 계정에는 KMS 키 사용 권한도 함께 주어야 합니다
자동 백업 자체를 리전 간 복제 별도 기능이 있습니다. 스냅샷을 일일이 복사하지 않고 자동 백업을 다른 리전으로 계속 복제해 그 리전에서 PITR을 가능하게 합니다

백업 문항은 복구 지점 목표(RPO)와 보관 기간으로 갈립니다.

  • "최근 며칠 안의 임의 시점으로 되돌려야 한다" → 자동 백업과 PITR
  • "수년간 보관해야 한다" · "규정 준수 감사" → 수동 스냅샷 (35일 상한과 무관)
  • "다른 리전에서도 복구할 수 있어야 한다" → 스냅샷 교차 리전 복사 또는 자동 백업 복제
  • "다른 계정의 감사 팀에 데이터를 넘겨야 한다" → 수동 스냅샷 공유 + KMS 키 권한

RDS Proxy — 연결이 폭주할 때

관계형 데이터베이스는 연결 하나마다 메모리와 CPU를 씁니다. 그런데 AWS Lambda나 컨테이너 기반 애플리케이션은 순간적으로 수백 개의 실행 환경이 동시에 살아납니다. 각자 연결을 열면 데이터베이스가 연결 수 상한에 부딪히거나 연결 생성 비용만으로 무너집니다.

RDS Proxy는 데이터베이스 연결 풀을 만들어 두고 재사용합니다. RDS 사용 설명서가 정리하는 효과는 네 가지입니다.

RDS Proxy가 해결하는 문제
효과 내용
연결 풀링 연결을 매번 새로 여는 메모리·CPU 비용을 없애고, 데이터베이스가 받을 연결 수를 통제합니다
과부하 완충 즉시 처리할 수 없는 연결 요청을 대기시키거나 조절합니다. 지연은 늘 수 있지만 데이터베이스가 갑자기 쓰러지지 않습니다
장애 조치 시 복원력 대기 인스턴스로 자동으로 다시 연결하면서 애플리케이션 연결은 유지합니다. 장애 조치 체감 시간이 줄어듭니다
자격 증명 관리 자격 증명을 AWS Secrets Manager에 두고 프록시가 IAM 역할로 가져다 씁니다. IAM 데이터베이스 인증도 강제할 수 있습니다

시험에서 결정적인 문장은 이것입니다 — "대부분의 애플리케이션에서 코드 변경 없이 RDS Proxy를 활성화할 수 있다." without changing application code라는 한정어와 연결 고갈이 함께 나오면 RDS Proxy가 곧바로 유력 후보가 됩니다.

프록시는 VPC 안의 서브넷에 놓이고, 엔진 계열(MYSQL · POSTGRESQL · SQLSERVER)을 지정해 만듭니다. RequireTLS로 프록시 연결에 전송 중 암호화를 강제할 수도 있습니다.

"Lambda 함수가 늘어나자 데이터베이스가 too many connections로 실패한다"는 시나리오의 정답은 거의 언제나 RDS Proxy입니다. 같은 문항에서 오답으로 자주 나오는 것이 인스턴스 클래스를 키운다(비용만 늘고 근본 원인이 그대로)와 읽기 전용 복제본을 추가한다(읽기 부하 문제가 아니라 연결 수 문제)입니다.

Lambda 쪽의 동시성 제어는 12장 서버리스와 애플리케이션 통합에서 다룹니다.

암호화 — 생성 시점에 결정된다

RDS의 저장 시 암호화는 AWS KMS 키로 이루어지며, 켜 두면 기반 스토리지 · 자동 백업 · 읽기 전용 복제본 · 스냅샷이 모두 암호화됩니다. 복호화는 투명하게 처리되므로 클라이언트 애플리케이션을 고칠 필요가 없습니다.

가장 중요한 제약

RDS 사용 설명서는 암호화된 DB 인스턴스의 제약을 목록으로 정리해 두었고, 그 첫 줄이 시험이 노리는 지점입니다.

Amazon RDS 저장 시 암호화의 제약
제약 함의
DB 인스턴스는 생성할 때만 암호화할 수 있습니다 이미 운영 중인 평문 데이터베이스를 설정 변경만으로 암호화할 수 없습니다
암호화를 끌 수 없습니다 한 번 켜면 되돌리는 설정이 없습니다. 평문으로 되돌리려면 데이터를 내보내 새 인스턴스로 옮겨야 합니다
KMS 키를 바꿀 수 없습니다 생성 후에는 그 인스턴스가 쓰는 키가 고정됩니다. 키 정책을 미리 정해야 합니다
평문 인스턴스의 암호화된 스냅샷을 만들 수 없습니다 스냅샷은 원본의 암호화 상태를 따라갑니다
평문 백업·스냅샷을 암호화된 인스턴스로 복원할 수 없습니다 복원 경로로 암호화를 끼워 넣을 수 없습니다
암호화 상태가 다른 복제본을 만들 수 없습니다 평문 소스에 암호화된 복제본, 암호화된 소스에 평문 복제본 모두 불가입니다

그렇다면 이미 운영 중인 평문 데이터베이스는 어떻게 암호화할까요. 같은 문서가 우회 경로를 함께 알려 줍니다 — 스냅샷을 만들고, 그 스냅샷의 암호화된 사본을 만든 뒤, 그 사본으로 복원합니다. 평문 스냅샷의 복사본에는 암호화를 걸 수 있기 때문입니다.

전송 중 암호화는 별개 계층입니다. RDS 사용 설명서는 암호화 여부와 무관하게 소스와 읽기 전용 복제본 사이의 전송 데이터는 암호화되며, 리전을 넘어 복제할 때도 그렇다고 명시합니다. 클라이언트와 데이터베이스 사이의 TLS는 엔진 설정으로 강제하거나 RDS Proxy의 RequireTLS로 강제합니다. KMS 키의 종류와 키 정책은 16장 보안·암호화·거버넌스에서 다룹니다.

"운영 중인 RDS 데이터베이스를 암호화하라"는 문항의 정답은 스냅샷 → 암호화된 복사본 → 복원입니다. "인스턴스를 수정해 암호화를 켠다"는 선택지는 존재하지 않는 동작이므로 오답이고, "새 파라미터 그룹을 적용한다"도 마찬가지입니다. 같은 패턴이 EBS 볼륨에서도 반복되므로 6장의 기존 볼륨 암호화와 함께 외워 두면 좋습니다.

유지 관리 기간과 패치 책임

RDS는 운영체제와 데이터베이스 엔진 패치를 유지 관리 기간(maintenance window)에 수행합니다. 지정하지 않으면 AWS가 리전마다 정해진 8시간 블록 안에서 임의의 요일 · 임의의 30분 창을 골라 배정합니다. 형식은 ddd:hh24:mi-ddd:hh24:mi이고 협정 세계시(UTC) 기준이며 최소 30분이어야 합니다.

규칙이 하나 더 있습니다. 유지 관리 기간과 백업 기간은 겹칠 수 없습니다. 두 창을 같은 시간대로 잡으려 하면 API가 거부합니다.

유지 관리 관련 설정과 기본 동작

흔한 오해

"Multi-AZ로 바꾸면 읽기 성능도 좋아진다" — 표준 Multi-AZ 인스턴스 배포의 대기 인스턴스는 읽기 트래픽을 받지 않습니다. 접근할 엔드포인트가 아예 없습니다. 오히려 동기 복제 때문에 쓰기 지연은 늘어날 수 있습니다. 읽기가 느린 것이 문제라면 읽기 전용 복제본이나 캐시가 답입니다. 읽기 가능한 대기 인스턴스를 두는 Multi-AZ DB 클러스터는 별개 아키텍처이므로, 문제문이 어느 쪽을 말하는지부터 확인합니다.

"읽기 전용 복제본이 있으면 프라이머리가 죽어도 자동으로 넘어간다" — RDS 읽기 전용 복제본은 스스로 승격하지 않습니다. 프라이머리가 사라지면 쓰기는 계속 실패하고, 누군가 승격 작업을 호출해야 서비스가 재개됩니다. Amazon Aurora는 다릅니다 — 라이터가 실패하면 Aurora가 리더 중 하나를 자동으로 승격합니다. "복제본이 있으니 고가용성"이라는 일반화가 RDS에서는 성립하지 않습니다.

"암호화는 나중에 켜면 된다" — RDS의 저장 시 암호화는 인스턴스를 만들 때만 결정할 수 있고, 이미 만들어진 평문 인스턴스를 수정해서 켤 수 없습니다. 우회 경로는 스냅샷을 만들고 그 사본을 암호화한 뒤 복원하는 것뿐이며, 이 과정에서 새 엔드포인트가 생기므로 전환 계획이 필요합니다. "나중에 켜면 된다"고 미룬 결정이 나중에 다운타임을 요구하게 됩니다.

공식 문서 출처

이 장의 개념 서술과 API 동작은 모두 아래 문서에서 확인했습니다.

  • Amazon RDS 사용 설명서 — Multi-AZ DB 인스턴스 배포 — 동기 복제 대기 복제본, 대기 인스턴스로 읽기를 처리할 수 없다는 명시, 장애 조치가 DNS 레코드를 전환한다는 설명, 소요 시간 60~120초, 장애 조치 사유 표
  • Amazon RDS 사용 설명서 — Multi-AZ DB 클러스터 배포 — 읽기 가능한 대기 2개, 3개 가용 영역, 반동기 복제, 프로비저닝된 IOPS 전용, Aurora DB 클러스터와 다르다는 경고
  • Amazon RDS 사용 설명서 — 읽기 전용 복제본 사용 — 비동기 복제와 별도 읽기 엔드포인트
  • Amazon RDS API 레퍼런스 — CreateDBInstanceReadReplica — 엔진별 복제본 개수 상한(대부분 15, Oracle·SQL Server 5, Db2 3), 소스에 자동 백업이 필요하다는 조건, Aurora가 이 작업을 지원하지 않는다는 서술
  • Amazon RDS API 레퍼런스 — CreateDBInstance — 지원 엔진 목록, MultiAZ와 AvailabilityZone을 함께 쓸 수 없다는 제약, 보존 기간 0~35일, 마이너 버전 자동 업그레이드 기본값, 유지 관리 기간 형식
  • Amazon RDS API 레퍼런스 — CreateDBCluster — Multi-AZ DB 클러스터의 필수 설정, 클러스터 보존 기간 1~35일, Aurora Serverless v2 확장 구성
  • Amazon RDS API 레퍼런스 — FailoverDBCluster — Aurora는 복제본을 승격하고 Multi-AZ DB 클러스터는 읽기 가능한 대기를 승격한다는 구분
  • Amazon RDS 사용 설명서 — 백업 작업 — 보존 기간 범위와 기본값, 스냅샷의 증분 성격, 리전당 수동 스냅샷 100개, 백업 기간이 유지 관리 기간과 겹칠 수 없다는 규칙, Multi-AZ에서 백업이 대기 쪽에서 수행된다는 서술
  • Amazon RDS 사용 설명서 — 지정한 시간으로 DB 인스턴스 복원 — 트랜잭션 로그가 5분마다 Amazon S3로 업로드된다는 설명, 복원 결과가 새 인스턴스라는 점
  • Amazon RDS API 레퍼런스 — CopyDBSnapshot — 복사를 호출한 리전이 대상 리전이 된다는 규칙
  • Amazon RDS API 레퍼런스 — ModifyDBSnapshotAttribute — 수동 스냅샷만 공유할 수 있다는 점, restore 속성과 all 값의 의미, 암호화된 스냅샷은 계정 ID 지정만 가능하다는 제약
  • Amazon RDS 사용 설명서 — Amazon RDS 리소스 암호화 — 생성 시점에만 암호화할 수 있다는 제약 목록, 스냅샷 사본을 통한 우회 경로, 복제본 전송 데이터가 암호화된다는 서술
  • Amazon RDS 사용 설명서 — Amazon RDS Proxy 사용 — 연결 풀링과 과부하 완충, 대기 인스턴스로 자동 재연결하며 애플리케이션 연결을 유지한다는 설명, 대개 코드 변경이 필요 없다는 서술
  • Amazon RDS API 레퍼런스 — CreateDBProxy — 엔진 계열 값, Secrets Manager 접근용 IAM 역할, RequireTLS
  • Amazon Aurora 사용 설명서 — Aurora 스토리지와 안정성 — 클러스터 볼륨이 3개 가용 영역에 사본을 두며 복제량이 인스턴스 개수와 무관하다는 서술, 자동 확장
  • Amazon Aurora 사용 설명서 — Aurora 복제 — Aurora 복제본이 읽기 확장과 가용성을 겸하며 라이터 실패 시 자동 승격된다는 설명
  • Amazon Aurora 사용 설명서 — Aurora 연결 관리 — 클러스터 · 리더 · 사용자 지정 · 인스턴스 엔드포인트의 역할과 리더 엔드포인트의 부하 분산
  • Amazon Aurora 사용 설명서 — Aurora 글로벌 데이터베이스 — 주 리전에서만 쓰기, 읽기 전용 보조 리전, 스토리지 하위 시스템의 전용 인프라를 통한 복제
  • Amazon Aurora 사용 설명서 — Aurora Serverless v2 사용 — 온디맨드 자동 확장 구성, 0.5 ACU 단위 조절, 적합한 워크로드 유형
