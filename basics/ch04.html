VPC 연결과 하이브리드

3장에서 VPC 하나를 만들었으니 이제 밖과 잇습니다. VPC끼리, 온프레미스와, 그리고 AWS 서비스와 잇는 방법이 각각 다르고 선택 기준도 다릅니다. 이 장에서 반드시 가져가야 할 판단은 하나입니다 — 문제문에 "데이터가 인터넷을 거치면 안 된다"는 한정어가 붙었을 때 무엇을 고르는가. 답은 VPC 엔드포인트이고, 그 이유를 라우팅 수준에서 설명할 수 있어야 합니다.

이 장은 보안 아키텍처 설계(30%)와 비용 최적화 아키텍처 설계(20%)에 함께 걸칩니다. 같은 VPC 엔드포인트가 보안 문항에서도 비용 문항에서도 정답이 되는 드문 주제입니다.

학습 목표

  • VPC 피어링이 전이 라우팅을 지원하지 않는다는 사실과, 그 제약이 규모에 따라 어떤 문제를 만드는지 설명할 수 있습니다.
  • 피어링과 Transit Gateway 중 무엇을 고를지 연결 개수와 운영 부담을 기준으로 판단할 수 있습니다.
  • 게이트웨이 엔드포인트와 인터페이스 엔드포인트를 구현 위치와 지원 서비스로 구분할 수 있습니다.
  • "인터넷을 거치면 안 된다"는 요구사항이 나왔을 때 후보 경로 중 조건을 만족하는 것을 골라낼 수 있습니다.
  • NAT 게이트웨이를 지나던 Amazon S3 트래픽을 게이트웨이 엔드포인트로 옮기는 비용 판단을 설명할 수 있습니다.
  • Site-to-Site VPN과 AWS Direct Connect의 특성 차이를 설명하고, 두 가지를 함께 쓰는 이유를 말할 수 있습니다.

VPC 피어링 — 두 VPC를 일대일로 잇는다

VPC 피어링 연결은 두 VPC 사이의 네트워킹 연결이며, 연결된 VPC의 리소스는 같은 네트워크 안에 있는 것처럼 통신합니다. VPC 사용 설명서는 두 가지를 명시합니다 — "피어링된 VPC 사이의 트래픽은 퍼블릭 인터넷을 절대 거치지 않는다"는 것과, 피어링이 게이트웨이나 VPN 연결이 아니라 기존 VPC 인프라를 사용하므로 "통신의 단일 장애점이나 대역폭 병목이 없다"는 것입니다.

연결 대상은 내 VPC끼리, 다른 계정의 VPC와, 다른 리전의 VPC와 모두 가능합니다. 요청자 VPC 소유자가 요청을 보내고 수락자 VPC 소유자가 수락해야 활성화되며, 요청은 7일 뒤 만료됩니다.

전이 라우팅이 되지 않는다

이것이 피어링의 결정적 제약입니다. VPC 피어링 안내서의 서술을 그대로 옮기면 "VPC 피어링 연결은 두 VPC 사이의 일대일 관계"이고 "전이적 피어링 관계는 지원되지 않는다", 그리고 "직접 피어링되지 않은 VPC와는 어떤 피어링 관계도 갖지 않는다"입니다.

구체적인 예도 문서가 들어 줍니다 — VPC A와 VPC B가 피어링되어 있고 VPC A와 VPC C도 피어링되어 있어도, VPC B에서 VPC A를 거쳐 VPC C로 트래픽을 보낼 수 없습니다. VPC B와 VPC C를 통신시키려면 그 둘 사이에 별도의 피어링 연결을 만들어야 합니다.

결과적으로 VPC가 N개일 때 모두를 잇는 데 필요한 연결은 N(N-1)/2개가 됩니다. 4개면 6개, 10개면 45개입니다. 연결마다 양쪽 라우팅 테이블에 경로를 넣어야 하므로 관리 대상은 그보다 더 빠르게 늘어납니다.

엣지 투 엣지 라우팅도 되지 않는다

전이성 제약은 게이트웨이에도 그대로 적용됩니다. VPC 피어링 안내서가 나열하는 항목은 다음과 같습니다.

피어링 상대의 게이트웨이를 빌려 쓸 수 없다
VPC A가 가진 것 VPC B가 그것을 쓸 수 있는가
인터넷 게이트웨이 불가 — VPC B는 VPC A의 인터넷 게이트웨이로 인터넷에 나갈 수 없다
NAT 장치 불가 — VPC B는 VPC A의 NAT 장치를 쓸 수 없다
Site-to-Site VPN 연결 불가 — VPC B는 그 VPN으로 사내 네트워크와 통신할 수 없다
AWS Direct Connect 연결 불가 — 위와 같다
Amazon S3 게이트웨이 엔드포인트 불가 — VPC B는 VPC A의 게이트웨이 엔드포인트로 S3에 접근할 수 없다

"공용 서비스 VPC에 NAT 게이트웨이 하나를 두고 다른 VPC들이 피어링으로 공유한다"는 설계는 성립하지 않습니다. 이 요구를 실제로 푸는 것이 Transit Gateway입니다.

그 밖의 제약

  • CIDR이 겹치면 피어링을 만들 수 없습니다. IPv4든 IPv6든 일치하거나 겹치면 안 되고, CIDR 블록이 여러 개일 때 그중 하나라도 겹치면 겹치지 않는 블록만 쓸 생각이어도 만들 수 없습니다.
  • 두 VPC 사이에 동시에 두 개 이상의 피어링 연결을 둘 수 없습니다.
  • 피어 VPC의 Amazon DNS 서버에 질의할 수 없습니다.
  • 리전 간 피어링에서는 피어 VPC의 보안 그룹을 참조하는 규칙을 만들 수 없고, MTU가 1,500바이트로 제한되어 점보 프레임을 쓸 수 없습니다. 같은 리전 안의 피어링은 점보 프레임을 지원합니다.

"VPC 세 개 이상을 서로 통신시켜야 한다"는 문항에서 "중간 VPC를 경유해 라우팅한다"는 선택지는 언제나 오답입니다. 피어링은 전이적이지 않습니다.

"인수한 회사의 VPC와 연결하라"는 시나리오에서 CIDR이 겹친다는 조건이 붙으면 피어링도 Transit Gateway 연결도 그대로는 성립하지 않습니다. 이때는 주소 재설계나 프라이빗 NAT를 통한 주소 변환이 필요하며, "CIDR이 겹쳐도 피어링하면 된다"는 선택지는 소거 대상입니다.

AWS Transit Gateway — 허브로 바꾼다

Transit Gateway는 VPC와 온프레미스 네트워크를 상호 연결하는 허브입니다. 각 네트워크는 Transit Gateway에 연결(attachment)을 하나씩 만들고, Transit Gateway가 그 사이의 라우팅을 담당합니다. 연결이 N개면 관리 대상도 N개입니다 — 피어링의 N(N-1)/2와 대비되는 지점이 여기입니다.

연결 유형

VPC, Site-to-Site VPN, Direct Connect 게이트웨이, 다른 Transit Gateway와의 피어링, 그리고 Connect 연결을 붙일 수 있습니다. VPN을 붙이려면 고객 게이트웨이를 만들고 VPN 연결을 만들 때 Transit Gateway를 지정합니다.

라우팅 테이블 — 연결과 전파

Transit Gateway를 만들면 기본 라우팅 테이블이 함께 만들어지고, 그것이 기본 연결(association) 라우팅 테이블이자 기본 전파(propagation) 라우팅 테이블이 됩니다. 두 용어의 의미가 다릅니다.

Transit Gateway 라우팅의 두 축
개념 의미
연결(association) 각 연결은 라우팅 테이블 하나에 연결된다. 그 라우팅 테이블이 그 연결에서 들어온 트래픽의 다음 홉을 결정한다
전파(propagation) 연결의 경로가 대상 라우팅 테이블로 전파된다. 어느 테이블로 전파할지를 따로 정할 수 있다

라우팅 테이블을 여러 개 만들면 네트워크를 분리(세그먼트)할 수 있습니다. 개발 VPC들을 한 라우팅 테이블에, 운영 VPC들을 다른 라우팅 테이블에 연결하면 같은 Transit Gateway를 쓰면서도 두 환경이 서로 도달하지 못하게 만들 수 있습니다. 피어링으로는 이런 정책 계층을 만들 수 없습니다.

Transit Gateway끼리도 피어링할 수 있고, 이때는 정적 경로만 지원됩니다. 리전을 넘는 대규모 구성에서 쓰입니다.

판단 기준은 연결 관계의 개수와 성장 방향입니다. "VPC 두세 개를 잇는다"면 피어링이 단순하고, "수십 개 VPC와 온프레미스를 함께", "앞으로 계속 늘어난다", "운영 부담을 줄여라"면 Transit Gateway입니다.

문제문에 "중앙에서 라우팅을 관리"나 "모든 VPC가 공유 서비스 VPC에 접근"이 보이면 Transit Gateway 신호입니다. 피어링으로는 공유가 성립하지 않기 때문입니다.

VPC 엔드포인트 — 게이트웨이와 인터페이스 SAA 빈출

VPC 엔드포인트는 VPC와 AWS 서비스 사이에 프라이빗 연결을 만드는 장치입니다. Amazon S3나 Amazon DynamoDB 같은 서비스는 VPC 밖에 있으므로 기본 경로로는 인터넷 게이트웨이나 NAT 게이트웨이를 거쳐야 하는데, 엔드포인트를 만들면 그 경로를 쓰지 않고 AWS 네트워크 안에서 처리됩니다.

유형은 두 가지이고, 구현 위치가 근본적으로 다릅니다.

게이트웨이 엔드포인트 — 라우팅 테이블에 붙는다

게이트웨이 엔드포인트는 Amazon S3와 Amazon DynamoDB만 지원합니다. VPC 엔드포인트를 만들 때 라우팅 테이블 ID를 지정하면, 선택한 각 라우팅 테이블에 AWS가 소유한 서비스 접두사 목록(prefix list)을 대상으로, 게이트웨이 엔드포인트를 타깃으로 하는 경로가 자동으로 추가됩니다. 하나의 라우팅 테이블에 S3용 경로와 DynamoDB용 경로를 함께 둘 수 있습니다.

AWS PrivateLink 문서는 게이트웨이 엔드포인트에 추가 요금이 없다고 명시합니다 — 시간당 요금도 데이터 처리 요금도 붙지 않습니다. 그리고 게이트웨이 엔드포인트는 AWS PrivateLink를 사용하지 않습니다. PrivateLink는 인터페이스 엔드포인트 쪽의 기술입니다.

인터페이스 엔드포인트 — 서브넷 안에 ENI를 만든다

인터페이스 엔드포인트는 AWS PrivateLink로 동작합니다. 지정한 서브넷마다 엔드포인트 네트워크 인터페이스가 만들어지고 그 서브넷의 주소 범위에서 프라이빗 IP 주소를 받습니다. 이 네트워크 인터페이스는 요청자 관리형이어서 계정에서 볼 수는 있지만 직접 관리하지는 않습니다.

여기서 게이트웨이 엔드포인트와 갈리는 두 가지가 나옵니다.

  • 보안 그룹을 붙일 수 있습니다. 엔드포인트 네트워크 인터페이스에 보안 그룹을 연결하며, 지정하지 않으면 VPC의 기본 보안 그룹이 붙습니다. 엔드포인트가 VPC 안의 실제 네트워크 인터페이스이기 때문에 가능한 일입니다.
  • 프라이빗 DNS로 이름을 가로챌 수 있습니다. 프라이빗 DNS 이름을 켜면 프라이빗 호스팅 영역이 만들어지고, 그 서비스의 기본 퍼블릭 DNS 이름이 엔드포인트 네트워크 인터페이스의 프라이빗 IP로 해석됩니다. 애플리케이션 코드나 SDK 설정을 바꾸지 않아도 경로가 바뀌는 이유가 이것입니다. 다만 VPC의 DNS 호스트 이름과 DNS 확인이 모두 켜져 있어야 하고, 만들어지는 DNS 레코드는 프라이빗이라 외부에서는 해석되지 않습니다.

인터페이스 엔드포인트는 대부분의 AWS 서비스를 지원하고, 다른 계정이 제공하는 서비스에도 연결할 수 있습니다. 서비스 제공자는 Network Load Balancer 앞에 엔드포인트 서비스를 만들고 소비자가 인터페이스 엔드포인트로 접속하는 구조입니다. Gateway Load Balancer 앞에 만들면 소비자는 Gateway Load Balancer 엔드포인트로 접속합니다.

엔드포인트 정책

두 유형 모두 엔드포인트 정책을 붙일 수 있습니다. 이것은 리소스 기반 정책이며, 지정하지 않으면 서비스에 대한 전체 접근을 허용하는 기본 정책이 붙습니다. "엔드포인트를 만들었으니 안전하다"가 성립하지 않는 이유가 여기 있습니다.

반대 방향도 있습니다. 버킷 정책에서 aws:SourceVpce 조건 키로 특정 엔드포인트를 통한 요청만 허용하면, 같은 버킷에 인터넷 경로로 들어오는 요청을 차단할 수 있습니다. 데이터 유출 통제(data perimeter)를 세울 때 쓰는 조합입니다.

"데이터가 인터넷을 거치면 안 된다" SAA 빈출

이 한정어는 SAA에서 정답을 결정하는 대표적인 신호입니다. 프라이빗 서브넷의 인스턴스가 Amazon S3에 접근한다고 할 때 후보 경로는 셋인데, 조건을 만족하는 것과 만족하지 않는 것이 갈립니다.

둘 다 조건을 만족한다면 무엇으로 가를까요. 추가 조건을 보고 고릅니다.

  • 대상이 S3나 DynamoDB뿐이고 VPC 안에서만 접근한다면 게이트웨이 엔드포인트가 단순하고 추가 요금이 없습니다.
  • 온프레미스나 다른 VPC에서도 그 서비스에 프라이빗하게 닿아야 한다면 인터페이스 엔드포인트입니다. 게이트웨이 엔드포인트는 VPC 라우팅 테이블에만 붙으므로 VPC 밖에서는 쓸 수 없습니다.
  • 대상이 S3와 DynamoDB가 아닌 다른 AWS 서비스라면 선택지는 인터페이스 엔드포인트뿐입니다.

"S3 버킷을 퍼블릭 액세스 차단으로 두면 인터넷을 거치지 않는다"는 서술도 오답입니다. 퍼블릭 액세스 차단은 누가 접근할 수 있는지를 정하는 것이고, 엔드포인트는 트래픽이 어느 경로로 가는지를 정하는 것입니다. 다른 층의 통제입니다.

NAT 게이트웨이 비용을 엔드포인트로 줄인다

같은 변경이 비용 문항에서도 정답이 됩니다. VPC 사용 설명서의 요금 페이지는 NAT 게이트웨이에 대해 프로비저닝되어 사용 가능한 시간마다 요금이 부과되고, 트래픽의 출발지나 목적지와 무관하게 게이트웨이를 통과한 데이터 양에 따라 데이터 처리 요금이 부과된다고 설명합니다.

그런데 프라이빗 서브넷의 워크로드가 만드는 아웃바운드 트래픽 중 상당 부분은 인터넷이 아니라 Amazon S3나 DynamoDB로 갑니다 — 로그 업로드, 아티팩트 내려받기, 백업이 전부 그렇습니다. 이 트래픽을 게이트웨이 엔드포인트로 옮기면 NAT 게이트웨이를 통과하는 데이터 자체가 사라지고, 게이트웨이 엔드포인트에는 추가 요금이 붙지 않습니다.

프라이빗 서브넷의 애플리케이션이 로그와 백업을 S3에 올립니다. 모든 트래픽이 NAT 게이트웨이를 지나므로 데이터 양에 비례해 처리 요금이 붙고, NAT 게이트웨이가 다른 가용 영역에 있으면 가용 영역 간 전송 요금까지 더해집니다.

S3 게이트웨이 엔드포인트를 만들고 프라이빗 라우팅 테이블에 연결합니다. S3로 가는 트래픽은 NAT 게이트웨이를 지나지 않게 되고, 남은 인터넷 트래픽만 NAT 게이트웨이를 씁니다. 보안과 비용이 같은 방향으로 개선되는 흔치 않은 변경입니다.

"NAT 게이트웨이 요금이 예상보다 많다"는 시나리오에서 가장 먼저 확인할 것은 그 트래픽이 정말 인터넷으로 가는가입니다. S3나 DynamoDB로 가는 트래픽이면 게이트웨이 엔드포인트가 답이고, 다른 AWS 서비스로 가는 트래픽이면 인터페이스 엔드포인트가 후보입니다.

"NAT 게이트웨이를 더 큰 것으로 바꾼다"는 선택지는 존재하지 않는 조작입니다. "NAT 인스턴스로 바꿔 비용을 줄인다"는 선택지는 운영 부담 한정어가 함께 붙어 있으면 밀립니다. 데이터 전송 요금의 전체 지도는 18장 비용 최적화·마이그레이션·재해 복구에서 다룹니다.

온프레미스와 잇기 — VPN과 Direct Connect

Site-to-Site VPN — 인터넷 위의 암호화 터널

Site-to-Site VPN은 온프레미스 네트워크와 VPC를 IPsec 터널로 잇습니다. 구성 요소는 세 가지입니다.

Site-to-Site VPN의 구성 요소
구성 요소 역할
고객 게이트웨이(customer gateway) 온프레미스 쪽 장비의 정보를 AWS에 알려 주는 리소스. 외부 인터페이스의 고정 IP 주소가 필요하고, BGP를 쓴다면 ASN도 알려 준다
가상 프라이빗 게이트웨이(virtual private gateway) AWS 쪽 VPN 종단점. VPC 하나에 연결된다
VPN 연결 둘을 잇는 연결. 각 VPN 연결은 터널 두 개를 포함하며 동시에 사용해 가용성을 높일 수 있다

가상 프라이빗 게이트웨이 대신 Transit Gateway에 붙일 수도 있습니다. VPC가 여러 개인 환경에서는 이쪽이 표준입니다 — VPC마다 VPN을 따로 만들지 않아도 되기 때문입니다.

라우팅은 두 가지 중에서 고릅니다. 고객 게이트웨이 장비가 BGP를 지원하면 동적 라우팅을 쓰고, 지원하지 않으면 정적 라우팅을 쓰면서 우리 네트워크의 IP 접두사를 직접 입력합니다. AWS 문서는 BGP가 견고한 활성 상태 감지를 제공하므로 첫 터널이 끊겼을 때 두 번째 터널로의 장애 조치를 돕는다고 설명합니다 — 동적 라우팅을 권하는 근거가 이것입니다.

AWS Direct Connect — 전용 회선

Direct Connect는 온프레미스와 AWS를 전용 네트워크 연결로 잇습니다. 인터넷을 거치지 않으므로 대역폭이 일정하고 지연이 예측 가능합니다. 회선 위에는 가상 인터페이스(virtual interface, VIF)를 만들어 씁니다.

Direct Connect 가상 인터페이스 세 종류
유형 무엇에 접근하는가 주소
프라이빗 VIF Amazon VPC 프라이빗 IP 주소
퍼블릭 VIF 모든 AWS 퍼블릭 서비스 (예: Amazon S3) 퍼블릭 IP 주소
전송(transit) VIF Direct Connect 게이트웨이에 연결된 하나 이상의 Transit Gateway 프라이빗 IP 주소

Direct Connect 게이트웨이는 전역 리소스이며, 여러 리전이나 여러 계정의 VPC 또는 Transit Gateway에 하나의 연결로 도달할 수 있게 해 줍니다. "리전마다 회선을 따로 끌어야 하는가"라는 질문의 답이 여기 있습니다.

AWS Direct Connect는 기본적으로 암호화되지 않습니다. 전용 회선이라 인터넷을 거치지 않을 뿐, 그 자체가 암호화를 제공하지는 않습니다. 암호화가 규정 요구사항이라면 두 가지 방법이 있습니다 — 10 Gbps 또는 100 Gbps 전용 연결에서는 MACsec을 쓰고, 1 Gbps 이하 연결에서는 Direct Connect 위에 VPN 터널을 얹습니다.

둘은 배타적이지 않습니다. Direct Connect를 주 경로로 두고 Site-to-Site VPN을 백업으로 두는 조합이 표준 구성입니다 — 회선 장애가 났을 때 즉시 인터넷 경로로 넘어갈 수 있기 때문입니다. 문제문에 "Direct Connect 장애에 대비"가 보이면 이 조합이 답입니다.

Direct Connect와 관련해 가장 자주 나오는 함정 두 가지를 정리합니다. (1) "Direct Connect는 암호화된다"는 서술은 틀렸습니다. 암호화 요구가 있으면 VPN이나 MACsec을 얹어야 합니다. (2) "Direct Connect 하나로 고가용성이 된다"는 서술도 틀렸습니다. 회선 자체가 단일 장애점이므로 두 번째 연결이나 VPN 백업이 필요합니다.

퍼블릭 VIF와 프라이빗 VIF의 구분도 자주 나옵니다. VPC 안의 리소스에 프라이빗 IP로 닿아야 하면 프라이빗 VIF, Amazon S3 같은 퍼블릭 서비스에 전용 회선으로 닿아야 하면 퍼블릭 VIF입니다.

AWS Outposts — AWS를 데이터센터 안으로

AWS Outposts는 AWS가 관리하는 인프라를 고객의 시설에 설치해 같은 API와 도구로 운영할 수 있게 합니다. 폼 팩터는 두 가지입니다 — 서버와 스위치, 전원 선반을 포함한 랙(rack) 형태와, 표준 랙에 장착하는 서버(server) 형태입니다. 공간이나 용량 요구가 작은 현장에는 서버 형태를 씁니다.

Outposts는 항상 홈 리전(부모 리전)에 연결됩니다. 그 연결을 서비스 링크라고 하며, Outpost가 홈 리전과 통신할 때 사용하는 암호화된 VPN 연결의 집합입니다. 온프레미스 네트워크와의 통신은 랙 형태에서 제공되는 로컬 게이트웨이(local gateway)가 담당합니다.

고르는 기준은 단순합니다. "온프레미스에 남아야 하는 요구(지연, 데이터 레지던시, 로컬 시스템 의존)가 있는데 AWS API와 운영 방식은 그대로 쓰고 싶다"면 Outposts입니다. 단지 온프레미스와 연결만 하면 되는 경우에는 Direct Connect나 VPN이 맞고, Outposts는 과합니다.

같은 계열의 선택지로 특정 대도시권의 지연을 줄이는 AWS Local Zones와 통신 사업자 네트워크 안의 AWS Wavelength가 있습니다. 셋의 구분은 1장 로컬 존과 Wavelength 존에 정리해 두었습니다.

흔한 오해

"VPC A가 B와, B가 C와 피어링되어 있으면 A와 C도 통신한다" — VPC 피어링은 전이적이지 않습니다. 직접 피어링되지 않은 VPC와는 어떤 관계도 없습니다. 같은 제약이 게이트웨이에도 적용됩니다 — 피어 VPC의 인터넷 게이트웨이, NAT 장치, VPN 연결, Direct Connect 연결, 그리고 게이트웨이 엔드포인트를 빌려 쓸 수 없습니다. "공유 VPC에 NAT를 하나 두고 전부 피어링으로 나간다"는 설계는 성립하지 않으며, 이 요구를 푸는 것은 Transit Gateway입니다.

"VPC 엔드포인트는 다 같은 것이다" — 구현 위치가 다릅니다. 게이트웨이 엔드포인트는 라우팅 테이블에 붙는 경로 항목이라 보안 그룹을 붙일 수 없고 VPC 밖에서는 쓸 수 없으며 Amazon S3와 DynamoDB만 지원합니다. 인터페이스 엔드포인트는 서브넷 안의 네트워크 인터페이스라 보안 그룹을 붙일 수 있고 온프레미스나 다른 VPC에서도 프라이빗 IP로 도달할 수 있습니다. "온프레미스에서 S3에 프라이빗하게 접근하라"는 요구에 게이트웨이 엔드포인트를 답으로 고르는 것이 대표적인 오답입니다.

"Direct Connect는 전용 회선이니까 암호화되어 있다" — Direct Connect는 기본적으로 암호화되지 않습니다. 인터넷을 거치지 않는 것과 암호화되는 것은 다른 이야기입니다. 전송 중 암호화가 규정 요구사항이면 10/100 Gbps 전용 연결에서는 MACsec을 쓰거나 Direct Connect 위에 VPN 터널을 얹어야 합니다. 덧붙여 Direct Connect 연결 하나는 그 자체가 단일 장애점이므로, 고가용성이 요구되면 연결을 이중화하거나 VPN을 백업으로 둡니다.

피어링의 범위 다른 계정·다른 리전과도 가능하다. 트래픽은 퍼블릭 인터넷을 거치지 않는다 같은 계정·같은 리전에서만 된다고 답함
리전 간 피어링 피어 VPC의 보안 그룹을 참조할 수 없고 MTU가 1,500바이트다 같은 리전 피어링과 동일하다고 가정
Transit Gateway 허브 앤 스포크. 연결 개수가 N으로 늘고 전이 라우팅을 지원한다 VPC가 많은데 피어링을 답으로 고름
TGW 라우팅 테이블 연결은 트래픽의 다음 홉을, 전파는 경로의 학습을 정한다. 여러 개를 만들어 세그먼트를 나눈다 둘을 같은 것으로 취급
TGW 피어링 정적 경로만 지원한다 BGP로 자동 전파된다고 가정
게이트웨이 엔드포인트 대상 Amazon S3와 Amazon DynamoDB만 다른 서비스도 게이트웨이 엔드포인트로 된다고 답함
게이트웨이 엔드포인트 구현 라우팅 테이블에 서비스 접두사 목록 경로가 자동 추가된다 서브넷과 보안 그룹을 지정하려 함
게이트웨이 엔드포인트 요금 추가 요금 없음 — 시간당·데이터 처리 요금이 없다 인터페이스 엔드포인트와 같은 요금 구조라고 가정
인터페이스 엔드포인트 구현 서브넷 안에 네트워크 인터페이스가 만들어지고 프라이빗 IP를 받는다. 보안 그룹을 붙일 수 있다 게이트웨이 엔드포인트에도 보안 그룹을 붙일 수 있다고 답함
프라이빗 DNS 서비스의 기본 퍼블릭 DNS 이름이 엔드포인트의 프라이빗 IP로 해석된다. VPC의 DNS 호스트 이름과 DNS 확인이 켜져 있어야 한다 애플리케이션 엔드포인트 설정을 바꿔야 한다고 답함
온프레미스에서의 프라이빗 접근 인터페이스 엔드포인트만 가능하다 게이트웨이 엔드포인트를 답으로 고름
엔드포인트 정책 지정하지 않으면 전체 접근을 허용하는 기본 정책이 붙는다 엔드포인트를 만들면 자동으로 좁아진다고 가정
인터넷 비경유 한정어 답은 VPC 엔드포인트 · PrivateLink · Direct Connect NAT 게이트웨이를 답으로 고름 — NAT는 인터넷으로 나가는 장치다
NAT 요금 구조 프로비저닝 시간당 요금 + 통과한 데이터 양에 따른 처리 요금 인터넷으로 가지 않는 트래픽에는 요금이 없다고 가정
NAT 비용 최적화 S3·DynamoDB 트래픽을 게이트웨이 엔드포인트로 옮긴다 NAT 게이트웨이 크기를 바꾸려 함 (그런 설정은 없다)
Site-to-Site VPN 연결마다 터널 2개. 가상 프라이빗 게이트웨이는 VPC 하나에 붙는다 터널이 하나라고 알고 이중화를 따로 설계
VPN 라우팅 고객 게이트웨이가 BGP를 지원하면 동적, 아니면 정적 항상 정적으로 설정
Direct Connect 암호화 기본적으로 암호화되지 않는다. MACsec 또는 VPN 병행 전용 회선이니 암호화된다고 답함
Direct Connect VIF 프라이빗 VIF는 VPC, 퍼블릭 VIF는 AWS 퍼블릭 서비스, 전송 VIF는 Transit Gateway 모든 접근에 프라이빗 VIF를 고름
Direct Connect 게이트웨이 전역 리소스. 여러 리전·여러 계정의 VPC나 Transit Gateway에 도달한다 리전마다 회선을 새로 끌어야 한다고 답함
하이브리드 이중화 Direct Connect + VPN 백업이 표준 조합 Direct Connect 하나로 고가용성이 된다고 답함
AWS Outposts AWS 인프라를 고객 시설에 설치. 서비스 링크로 홈 리전과 연결되고, 랙은 로컬 게이트웨이로 온프레미스와 통신한다 단순 연결 요구에 Outposts를 고름 (VPN·Direct Connect가 맞다)

  • Amazon EC2 API 레퍼런스 — CreateTransitGateway — 기본 라우팅 테이블이 기본 연결·전파 라우팅 테이블이 된다는 서술
  • AWS PrivateLink — 게이트웨이 엔드포인트 — 게이트웨이 엔드포인트가 Amazon S3와 DynamoDB에 대한 연결을 제공한다는 점, 서비스 접두사 목록을 대상으로 하는 경로가 선택한 라우팅 테이블에 자동 추가된다는 점, 추가 요금이 없다는 점, 게이트웨이 엔드포인트는 AWS PrivateLink를 사용하지 않는다는 점
  • AWS PrivateLink — Amazon S3용 게이트웨이 엔드포인트 — S3 게이트웨이 엔드포인트의 구성과 라우팅
  • AWS PrivateLink — Amazon DynamoDB용 게이트웨이 엔드포인트 — DynamoDB 게이트웨이 엔드포인트의 구성
  • AWS PrivateLink — 인터페이스 VPC 엔드포인트로 AWS 서비스 접근 — 지정한 서브넷마다 엔드포인트 네트워크 인터페이스가 만들어지고 서브넷 주소 범위의 프라이빗 IP를 받는다는 점, 요청자 관리형이라는 점, 보안 그룹을 지정하지 않으면 VPC 기본 보안 그룹이 붙는다는 점, 프라이빗 DNS 이름을 쓰려면 VPC의 DNS 호스트 이름과 DNS 확인을 켜야 한다는 점
  • AWS PrivateLink — 인터페이스 엔드포인트 구성 — 프라이빗 DNS 이름이 퍼블릭 서비스 엔드포인트로 향하는 요청을 VPC 엔드포인트로 해석시킨다는 서술
  • Amazon VPC 사용 설명서 — AWS 관리형 접두사 목록 — 게이트웨이 엔드포인트 경로의 대상이 되는 AWS 소유 접두사 목록
  • Amazon EC2 API 레퍼런스 — CreateVpcEndpoint — 엔드포인트 유형의 기본값이 Gateway라는 점, 게이트웨이 엔드포인트는 라우팅 테이블 ID를, 인터페이스 엔드포인트는 서브넷 ID와 보안 그룹을 받는다는 점, 정책을 지정하지 않으면 전체 접근을 허용하는 기본 정책이 붙는다는 점, 프라이빗 DNS가 프라이빗 호스팅 영역을 만든다는 점
  • Amazon EC2 API 레퍼런스 — CreateVpcEndpointServiceConfiguration — 엔드포인트 서비스를 Network Load Balancer 또는 Gateway Load Balancer 앞에 만든다는 점
  • Amazon VPC 사용 설명서 — NAT 게이트웨이 요금 — 프로비저닝된 시간마다, 그리고 트래픽의 출발지·목적지와 무관하게 통과한 데이터 양에 따라 요금이 부과된다는 서술
  • AWS Site-to-Site VPN 사용 설명서 — 개요 — 각 VPN 연결이 터널 두 개를 포함하며 동시에 사용해 가용성을 높일 수 있다는 점, 고객 게이트웨이와 가상 프라이빗 게이트웨이의 역할
  • AWS Site-to-Site VPN 사용 설명서 — 정적 라우팅과 동적 라우팅 — BGP 지원 여부로 동적과 정적을 고른다는 점, BGP의 활성 상태 감지가 두 번째 터널로의 장애 조치를 돕는다는 점
  • Amazon EC2 API 레퍼런스 — CreateCustomerGateway — 고객 게이트웨이 장비의 외부 인터페이스에 고정 IP가 필요하다는 점과 BGP ASN
  • AWS Direct Connect 사용 설명서 — 가상 인터페이스 — 프라이빗 VIF는 프라이빗 IP로 VPC에, 퍼블릭 VIF는 퍼블릭 IP로 AWS 퍼블릭 서비스에, 전송 VIF는 Direct Connect 게이트웨이에 연결된 Transit Gateway에 접근한다는 서술
  • AWS Direct Connect 사용 설명서 — MACsec — 전용 연결에서의 MAC 보안 암호화 옵션
  • Amazon VPC 연결 옵션 백서 — AWS Direct Connect — Direct Connect가 기본적으로 암호화되지 않는다는 점, 10/100 Gbps 전용 연결에서는 MACsec을 쓰고 1 Gbps 이하에서는 VPN 터널을 얹는다는 점, Direct Connect 게이트웨이가 여러 리전·계정의 VPC나 Transit Gateway에 도달하는 전역 리소스라는 점
  • AWS Outposts 사용 설명서 — Outposts란 — 랙과 서버 두 폼 팩터, AWS 인프라를 고객 시설에서 운영한다는 개념
  • AWS Outposts 사용 설명서 — 동작 방식 — 서비스 링크가 홈 리전과의 암호화된 VPN 연결 집합이라는 서술, 로컬 게이트웨이가 온프레미스 네트워크와의 통신을 담당한다는 서술
