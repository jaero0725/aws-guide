컨테이너

컨테이너 문항은 "컨테이너를 어떻게 만드는가"를 묻지 않습니다. 어디까지를 우리가 운영하고 어디부터를 AWS에 맡기는가를 묻습니다. 같은 컨테이너를 EC2 인스턴스 위에서 돌릴 수도, AWS Fargate 위에서 돌릴 수도 있고, 오케스트레이션을 Amazon ECS가 할 수도 Amazon EKS가 할 수도 있습니다. 이 장은 그 경계선을 긋는 기준을 정리합니다.

이 장은 복원력 있는 아키텍처 설계(26%)와 고성능 아키텍처 설계(24%)에 걸쳐 있습니다. 가장 자주 나오는 두 지점은 EC2 시작 유형과 Fargate의 선택, 그리고 태스크 역할과 태스크 실행 역할의 구분입니다.

학습 목표

  • Amazon ECS의 클러스터 · 태스크 정의 · 태스크 · 서비스가 어떤 포함 관계인지 설명할 수 있습니다.
  • EC2 시작 유형과 AWS Fargate를 운영 부담과 제어 수준을 기준으로 구분해 고를 수 있습니다.
  • 태스크 역할과 태스크 실행 역할이 서로 다른 주체의 권한이라는 점을 설명하고, 권한 오류를 어느 쪽 문제인지 판별할 수 있습니다.
  • 서비스 오토스케일링과 Application Load Balancer 연동으로 컨테이너 워크로드를 확장할 수 있습니다.
  • ECS 대신 EKS를 고르는 근거와, 컨테이너 대신 AWS Lambda를 고르는 근거를 구분해 설명할 수 있습니다.

컨테이너가 해결하는 문제

컨테이너는 애플리케이션과 그 실행에 필요한 라이브러리를 하나의 이미지로 묶습니다. 같은 이미지가 개발 노트북에서도 운영 환경에서도 같은 방식으로 실행되므로, "내 환경에서는 되는데"라는 문제가 배포 단계에서 사라집니다.

그러나 이미지를 만드는 것과 수십 개의 컨테이너를 여러 서버에 배치하고 상태를 유지하는 것은 전혀 다른 일입니다. 어느 서버에 몇 개를 띄울지, 죽으면 어디에 다시 띄울지, 새 버전을 어떻게 무중단으로 교체할지를 관리하는 것이 오케스트레이션이고, AWS에서 그 역할을 하는 서비스가 Amazon ECS와 Amazon EKS입니다.

컨테이너 관련 AWS 서비스의 역할 분담
서비스 역할 한 문장 요약
Amazon ECR 이미지 저장소(레지스트리) 컨테이너 이미지를 보관하고 배포합니다
Amazon ECS 오케스트레이션(AWS 고유) AWS에 맞춰 설계된 오케스트레이터입니다. 개념이 적고 통합이 깊습니다
Amazon EKS 오케스트레이션(Kubernetes) 관리형 Kubernetes 컨트롤 플레인을 제공합니다
AWS Fargate 서버리스 컴퓨팅 엔진 오케스트레이터가 아닙니다. ECS와 EKS가 컨테이너를 올릴 대상입니다

Fargate는 ECS나 EKS의 경쟁 상대가 아닙니다. Fargate는 "컨테이너를 어디에 올릴 것인가"에 대한 답이고, ECS와 EKS는 "무엇이 배치를 관리할 것인가"에 대한 답입니다. 그래서 ECS on Fargate, ECS on EC2, EKS on Fargate, EKS on EC2가 모두 성립합니다. "ECS와 Fargate 중 무엇을 고를까"라는 질문 자체가 두 축을 섞은 것입니다.

EC2 시작 유형과 AWS Fargate SAA 빈출

같은 태스크 정의를 두 방식으로 실행할 수 있습니다. AWS API 문서는 EC2 시작 유형이 "클러스터에 등록된 Amazon EC2 인스턴스에서 태스크를 실행"하고, Fargate 시작 유형이 "Fargate 온디맨드 인프라에서 태스크를 실행"한다고 설명합니다. 차이는 기능이 아니라 누가 인스턴스를 책임지는가입니다.

Amazon ECS 시작 유형 비교 — 판단 기준은 운영 부담과 제어 수준입니다

고르는 신호 "기존 EC2 자산을 활용", "GPU가 필요", "인스턴스 수준 튜닝이 필요", "높은 밀도로 비용을 낮춘다" "운영 부담을 최소화", "서버를 관리하고 싶지 않다", "부하가 들쭉날쭉하다"

"운영 부담이 가장 적은(LEAST operational overhead)"이 붙으면 컨테이너 문항의 답은 거의 언제나 AWS Fargate입니다. "EC2 인스턴스를 Auto Scaling 그룹으로 관리한다"는 선택지는 기능적으로는 맞지만 한정어에 지므로 소거 대상입니다.

반대로 "GPU가 필요하다", "호스트에 에이전트를 설치해야 한다", "이미 보유한 예약 인스턴스를 활용해야 한다"는 제약이 명시되면 그 순간 Fargate는 후보에서 빠지고 EC2 시작 유형이 답이 됩니다. 명시된 제약이 한정어보다 먼저입니다.

네트워크 모드

태스크 정의의 networkMode가 컨테이너의 네트워크 방식을 정합니다. AWS API 문서는 지정하지 않으면 기본값이 bridge이며, Fargate에서는 awsvpc가 필수라고 명시합니다.

Amazon ECS 태스크의 네트워크 모드

awsvpc 태스크마다 탄력적 네트워크 인터페이스가 할당되고 VPC의 IP 주소를 받습니다 태스크 단위로 보안 그룹을 붙일 수 있습니다. Fargate에서는 이 모드만 씁니다

awsvpc 모드의 태스크는 VPC 안의 리소스와 같은 방식으로 통신하므로 보안 그룹과 서브넷 설계가 3장 VPC 네트워킹 기초의 규칙을 그대로 따릅니다. 프라이빗 서브넷에 둔 태스크가 인터넷으로 나가야 하면 NAT 게이트웨이가, AWS 서비스에만 접근하면 되면 VPC 엔드포인트가 필요합니다.

서비스 스케줄링 전략

서비스에는 두 가지 스케줄링 전략이 있습니다.

  • REPLICA — 원하는 개수만큼의 태스크를 클러스터 전체에 배치하고 유지합니다. AWS 문서는 기본적으로 가용 영역에 걸쳐 태스크를 분산한다고 명시합니다. 다중 가용 영역 배치가 기본 동작이라는 뜻이며, 이것이 컨테이너 워크로드의 고가용성 기반입니다.
  • DAEMON — 배치 제약을 만족하는 모든 컨테이너 인스턴스에 정확히 하나씩 배포합니다. 로그 수집이나 모니터링 에이전트처럼 노드마다 하나가 필요한 워크로드에 씁니다. 원하는 개수를 지정하지 않고, 서비스 오토스케일링도 쓰지 않습니다.

--health-check-grace-period-seconds는 태스크가 처음 시작된 뒤 로드 밸런서와 컨테이너 상태 확인 실패를 무시하는 기간입니다. 지정하지 않으면 기본값은 0이므로, 부팅이 느린 애플리케이션은 준비되기도 전에 비정상으로 판정되어 반복해서 교체될 수 있습니다.

태스크 역할과 태스크 실행 역할 SAA 빈출

이름이 비슷해서 가장 많이 혼동되는 지점이고, 그래서 시험이 자주 노립니다. 두 역할은 서로 다른 주체가 서로 다른 시점에 씁니다.

태스크 역할과 태스크 실행 역할의 비교
항목 태스크 역할(taskRoleArn) 태스크 실행 역할(executionRoleArn)
누가 쓰는가 컨테이너 안의 애플리케이션 코드 Amazon ECS 컨테이너 에이전트(우리 코드가 아닙니다)
언제 쓰는가 태스크가 실행되는 동안, 코드가 AWS API를 호출할 때 태스크를 시작하기 전과 실행 중, 인프라 작업을 할 때
대표 권한 S3 객체 읽기, DynamoDB 테이블 쓰기, SQS 메시지 수신 ECR에서 이미지 가져오기, CloudWatch Logs에 로그 쓰기, Secrets Manager에서 값 주입
AWS 문서의 정의 "이 태스크의 컨테이너가 맡을 수 있는 IAM 역할. 이 태스크의 모든 컨테이너에 이 역할의 권한이 부여됩니다" "ECS 컨테이너 에이전트가 사용자를 대신해 AWS API를 호출하도록 허용하는 태스크 실행 역할"
없거나 잘못되면 태스크는 뜨지만 애플리케이션이 권한 오류를 냅니다 태스크가 아예 시작되지 않습니다(이미지를 못 받거나 로그를 못 씀)

증상으로 역할을 판별합니다. "태스크가 시작되지 못하고 이미지를 가져올 수 없다"면 태스크 실행 역할 문제이고, "컨테이너는 떴는데 S3 접근이 거부된다"면 태스크 역할 문제입니다.

그리고 컨테이너에 액세스 키를 환경 변수로 넣는 선택지는 오답입니다. EC2 인스턴스에서 액세스 키를 쓰지 않는 것과 정확히 같은 이유입니다 (2장 IAM과 자격 증명). 컨테이너 안의 코드는 태스크 역할로 임시 자격 증명을 받습니다.

EC2 시작 유형에는 컨테이너 인스턴스의 IAM 역할이 하나 더 있습니다. EC2 인스턴스가 클러스터에 등록하고 상태를 보고할 때 쓰는 역할이며, 위의 두 역할과는 또 다른 것입니다. 인스턴스 역할의 권한이 컨테이너에도 상속된다고 가정하지 않습니다. 애플리케이션 권한은 태스크 역할로 따로 주는 것이 최소 권한 원칙에 맞습니다.

Amazon ECR — 이미지 레지스트리

Amazon Elastic Container Registry(ECR)는 컨테이너 이미지를 저장하는 관리형 레지스트리입니다. ECS · EKS와 같은 계정 · 리전 안에 있으므로 이미지를 받아오는 경로가 짧고, 접근 제어를 IAM으로 통일할 수 있습니다.

Amazon ECR에서 시험 관점으로 알아 둘 것
기능 무엇을 하는가 언제 답이 되는가
리포지토리 정책 리소스 기반 정책으로 다른 계정에 풀 권한을 줍니다 "조직의 여러 계정이 같은 이미지를 써야 한다"
이미지 스캔 이미지의 취약점을 검사합니다 "배포 전 취약점을 확인해야 한다"
수명 주기 정책 오래되거나 태그 없는 이미지를 자동으로 정리합니다 "레지스트리 저장 비용이 계속 늘어난다"
태그 변경 불가 설정 같은 태그를 덮어쓰지 못하게 막습니다 "배포된 이미지가 바뀌면 안 된다"
교차 리전 복제 레지스트리 설정으로 다른 리전 · 계정에 이미지를 복제합니다 "다중 리전 배포에서 이미지 다운로드가 느리다", 리전 장애 대비
저장 시 암호화 이미지를 암호화해 저장하며 KMS 키를 지정할 수 있습니다 "고객 관리형 키로 암호화해야 한다"

"프라이빗 서브넷의 태스크가 이미지를 가져오지 못한다"는 시나리오는 ECR 권한 문제가 아니라 네트워크 경로 문제인 경우가 많습니다. NAT 게이트웨이가 없거나, ECR과 Amazon S3용 VPC 엔드포인트가 없는 것이 원인입니다. "인터넷을 거치면 안 된다"는 제약이 함께 있으면 답은 VPC 엔드포인트입니다.

레지스트리 저장 비용이 늘어나는 문제는 수명 주기 정책으로 답합니다. Amazon S3의 수명 주기 규칙과 같은 성격의 도구입니다.

서비스 오토스케일링과 로드 밸런서 연동

서비스 오토스케일링

ECS 서비스의 태스크 개수는 Application Auto Scaling이 조절합니다. 조절 대상(확장 가능 차원)은 ecs:service:DesiredCount이며, 정책 유형은 대상 추적 · 단계별 · 예측이 있습니다. Auto Scaling 그룹과 개념이 같으므로 7장 로드 밸런싱과 오토스케일링에서 배운 판단이 그대로 적용됩니다.

여기서 EC2 시작 유형에는 확장 축이 두 개라는 점이 중요합니다.

  • 태스크 개수 — 서비스 오토스케일링이 조절합니다.
  • 컨테이너 인스턴스 개수 — Auto Scaling 그룹이나 용량 공급자가 조절합니다. 태스크를 늘리려 해도 인스턴스에 빈 자리가 없으면 태스크는 대기 상태로 남습니다.

Fargate에는 두 번째 축이 없습니다. 태스크 개수만 조절하면 끝입니다. 이것이 "운영 부담이 적다"는 말의 구체적인 내용입니다.

Application Load Balancer 연동

서비스에 로드 밸런서를 붙이면 태스크가 뜨고 질 때마다 대상 그룹에 자동으로 등록되고 해제됩니다. AWS 문서는 로드 밸런서를 쓰는 서비스의 태스크는 실행 중이면서 로드 밸런서가 정상으로 보고할 때만 정상으로 간주된다고 명시합니다.

컨테이너 워크로드에서 로드 밸런서 선택
요구 선택 근거
경로나 호스트로 여러 서비스에 나눠 보낸다 Application Load Balancer L7 리스너 규칙으로 경로 기반 라우팅을 합니다. 마이크로서비스의 기본 선택입니다

로드 밸런서 세 종류의 계층과 프로토콜 차이는 7장에서 정리했습니다.

컨테이너 워크로드의 고가용성도 결론은 같습니다 — 가용 영역이 몇 개인가입니다. 서비스의 REPLICA 전략은 기본적으로 가용 영역에 걸쳐 태스크를 분산하지만, 서브넷을 한 가용 영역에만 지정하면 분산할 곳이 없습니다. 네트워크 구성에 여러 가용 영역의 서브넷을 넣는 것이 전제입니다.

Amazon EKS — 관리형 Kubernetes

컨트롤 플레인과 노드

EKS는 Kubernetes 컨트롤 플레인을 관리형으로 제공합니다. AWS API 문서는 컨트롤 플레인이 AWS가 관리하는 계정에서 실행되고, 여러 가용 영역에 걸쳐 프로비저닝되며 Network Load Balancer가 앞에 놓인다고 설명합니다. 노드는 우리 계정에서 실행되며 컨트롤 플레인에 연결됩니다.

즉 EKS에서도 컴퓨팅 계층의 선택은 남아 있습니다. 관리형 노드 그룹으로 EC2 인스턴스를 쓰거나, Fargate 프로파일을 만들어 파드를 Fargate에서 실행합니다. Fargate 프로파일은 선택기(selector)로 어떤 파드를 Fargate에서 실행할지 선언하며, AWS 문서는 프로파일마다 선택기를 최대 5개까지 둘 수 있고 각 선택기에 네임스페이스가 필수라고 명시합니다.

두 경우 모두 명시된 제약이 한정어를 이깁니다. 제약을 먼저 읽고 후보를 지운 다음, 남은 것 중에서 한정어로 고릅니다. 이 독해 순서는 시험 당일 전략에 정리되어 있습니다.

흔한 오해

"Fargate는 ECS의 대안이다" — Fargate는 오케스트레이터가 아니라 컨테이너를 실행하는 컴퓨팅 엔진입니다. 배치와 복구, 서비스 유지는 여전히 ECS나 EKS가 합니다. 그래서 ECS on Fargate와 EKS on Fargate가 모두 성립하고, "ECS냐 Fargate냐"라는 대립은 성립하지 않습니다. 문항의 선택지에서 두 축을 분리해 읽는 습관이 필요합니다.

"태스크 실행 역할이 있으니 컨테이너가 S3를 읽을 수 있다" — 태스크 실행 역할은 ECS 에이전트가 이미지를 받고 로그를 보낼 때 쓰는 권한입니다. 컨테이너 안의 애플리케이션 코드가 AWS API를 호출할 때 쓰는 것은 태스크 역할입니다. 두 역할은 주체가 다르므로 권한이 상속되지도 않습니다. "태스크는 뜨는데 애플리케이션이 권한 오류"라면 실행 역할이 아니라 태스크 역할을 봐야 합니다.

"EKS는 관리형이니 ECS보다 운영이 편하다" — EKS가 관리해 주는 것은 컨트롤 플레인입니다. 클러스터 버전 업그레이드, 애드온 호환성, 매니페스트와 노드 관리는 여전히 우리 몫입니다. 운영 부담만 놓고 보면 ECS on Fargate가 가장 낮습니다. EKS를 고르는 근거는 편의성이 아니라 Kubernetes 생태계와 이식성입니다.

공식 문서 출처

이 장의 동작 서술은 모두 아래 문서에서 확인했습니다.

  • Amazon ECS 개발자 안내서 — 애플리케이션 아키텍처 — 클러스터 · 태스크 정의 · 태스크 · 서비스의 관계
  • Amazon ECS 개발자 안내서 — 시작 유형 — EC2 시작 유형과 Fargate 시작 유형의 차이
  • Amazon ECS 개발자 안내서 — AWS Fargate — Fargate가 서버리스 컴퓨팅 엔진이라는 정의
  • Amazon ECS 개발자 안내서 — Fargate 용량 공급자 — Fargate Spot을 쓰려면 용량 공급자 전략이 필요하다는 서술
  • Amazon ECS API 레퍼런스 — CreateService — REPLICA 전략이 기본적으로 가용 영역에 걸쳐 분산한다는 서술, DAEMON 전략의 동작, 상태 확인 유예 기간의 기본값 0
  • Amazon ECS API 레퍼런스 — RegisterTaskDefinition — taskRoleArn과 executionRoleArn의 정의, networkMode의 기본값과 Fargate의 awsvpc 요구
  • Amazon ECS 개발자 안내서 — 태스크의 IAM 역할 — 컨테이너 안의 코드가 쓰는 권한이라는 점
  • Amazon ECS 개발자 안내서 — 태스크 실행 IAM 역할 — ECS 에이전트가 이미지를 받고 로그를 보낼 때 쓰는 권한이라는 점
  • Amazon ECS 개발자 안내서 — 태스크 네트워킹 — awsvpc 모드에서 태스크마다 네트워크 인터페이스가 할당된다는 서술
  • Amazon ECS 개발자 안내서 — 서비스 로드 밸런싱 — 대상 그룹 등록과 로드 밸런서 상태 확인이 태스크의 정상 판정에 쓰인다는 서술
  • Amazon ECS 개발자 안내서 — 서비스 오토스케일링 — Application Auto Scaling이 서비스의 원하는 태스크 개수를 조절한다는 서술
  • Amazon ECR 사용 설명서 — 리포지토리 — 이미지 저장 단위와 접근 제어
  • Amazon ECR 사용 설명서 — 수명 주기 정책 — 오래되거나 태그 없는 이미지를 자동으로 정리하는 규칙
  • Amazon ECR 사용 설명서 — 이미지 스캔 — 취약점 검사 동작
  • Amazon ECR 사용 설명서 — 리포지토리 정책 — 다른 계정에 풀 권한을 부여하는 리소스 기반 정책
  • Amazon EKS 사용 설명서 — 클러스터 기능 — 컨트롤 플레인이 AWS 관리 계정에서 여러 가용 영역에 걸쳐 실행되고 노드는 고객 계정에서 실행된다는 구조
  • Amazon EKS 사용 설명서 — Fargate 프로파일 — 선택기로 파드를 Fargate에 배치하는 방식과 파드 실행 역할
  • Amazon EKS 사용 설명서 — 관리형 노드 그룹 — 노드를 EC2 인스턴스로 운영하는 방식
