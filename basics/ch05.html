EC2와 컴퓨트

Amazon EC2 문항은 "EC2가 무엇인가"를 묻지 않습니다. 같은 워크로드를 두고 어떤 구매 옵션으로 사느냐, 어떤 배치로 두느냐, 메타데이터를 어떻게 잠그느냐를 묻습니다. 특히 구매 옵션 판단은 비용 최적화 도메인의 중심이고, 여기서 잘못 고르면 다른 설계가 아무리 좋아도 오답이 됩니다.

이 장은 고성능 아키텍처 설계(24%)와 비용 최적화 아키텍처 설계(20%)에 함께 걸칩니다. IMDSv2 부분은 보안 아키텍처 설계(30%)로 이어집니다.

학습 목표

  • 인스턴스 타입 이름에서 패밀리 · 세대 · 부가 기능 · 크기를 읽어 내고, 워크로드에 맞는 패밀리를 고를 수 있습니다.
  • 구매 옵션 다섯 가지의 약정 대상과 유연성 차이를 구분하고, 워크로드 특성으로 하나를 지목할 수 있습니다.
  • 중단 가능한 워크로드에 스팟을, 상시 기저 부하에 Savings Plans를 배정하는 판단을 근거를 들어 설명할 수 있습니다.
  • AMI와 사용자 데이터로 인스턴스 기동 시간을 줄이는 방법과 그 경계를 설명할 수 있습니다.
  • 배치 그룹 세 가지가 각각 무엇을 최적화하는지 구분하고, 성능과 장애 격리가 반대 방향임을 설명할 수 있습니다.
  • IMDSv2의 두 단계 요청 구조와 홉 제한이 서버 측 요청 위조를 어떻게 막는지 설명할 수 있습니다.

인스턴스 패밀리와 명명 규칙

인스턴스 타입 이름은 네 부분으로 이루어집니다 — 패밀리 · 세대 · 부가 기능 · 크기입니다. 예를 들어 c5n.xlarge는 컴퓨팅 최적화 패밀리(c)의 5세대(5)이며 네트워크가 최적화되어 있고(n) 크기는 xlarge라는 뜻입니다. 점 뒤가 크기이고, 베어메탈은 metal로 표기합니다.

SAA에서 자주 쓰이는 인스턴스 패밀리 문자와 의미
문자 의미 대표 워크로드
M Most scenarios — 범용 웹 · 애플리케이션 서버, 중소형 데이터베이스
T Turbo — 버스트 가능 성능 평소 부하가 낮고 가끔 튀는 개발 · 소규모 서비스
C Compute — 컴퓨팅 최적화 배치 처리, 미디어 인코딩, 고성능 웹 서버
R Random access memory — 메모리 최적화 인메모리 캐시, 대용량 인메모리 데이터베이스
X · U Extra-large memory · Ultra-high memory 인메모리 데이터베이스, 대규모 분석
I · D I/O · Dense storage — 스토리지 최적화 NoSQL, 데이터 웨어하우스, 분산 파일 시스템
P · G · Inf · Trn GPU · AWS Inferentia · AWS Trainium — 가속 컴퓨팅 머신러닝 학습과 추론, 그래픽 워크로드
Hpc High performance computing 노드 간 통신이 잦은 병렬 시뮬레이션

패밀리 문자 뒤에 붙는 부가 기능 문자도 문항의 힌트가 됩니다 — a는 AMD, g는 AWS Graviton, i는 Intel 프로세서, d는 인스턴스 스토어 볼륨, n은 네트워크 최적화, b는 블록 스토리지 최적화, e는 추가 스토리지나 메모리, z는 고클럭입니다. d가 붙은 타입은 인스턴스 스토어를 포함하므로 6장의 인스턴스 스토어 휘발성이 그대로 적용됩니다.

인스턴스 타입 목록은 계속 늘어나므로 개별 타입의 vCPU 수와 메모리 크기를 외우지 않습니다. 시험이 요구하는 것은 "메모리가 많이 필요하다 → R 계열", "컴퓨팅이 필요하다 → C 계열" 수준의 매핑입니다. 실제 설계에서는 조회해서 씁니다.

인스턴스를 키울 것인가, 늘릴 것인가

인스턴스 타입을 더 큰 것으로 바꾸는 것이 수직 확장이고, 같은 인스턴스를 여러 대로 늘리는 것이 수평 확장입니다. EC2에서 타입 변경은 인스턴스를 중지한 상태에서만 할 수 있으므로 중단이 따라옵니다. 게다가 인스턴스가 한 대인 이상 단일 장애점은 그대로 남습니다.

그래서 탄력성 · 확장성 · 고가용성이 요구되면 답은 수평 확장이고, 그 장치가 7장의 Auto Scaling 그룹입니다. 수직 확장이 정답이 되는 경우는 수평으로 나눌 수 없는 워크로드일 때입니다.

구매 옵션 5종 — 무엇을 약정하는가 SAA 빈출

구매 옵션은 결국 무엇을 얼마나 약속하고 그 대가로 무엇을 포기하느냐의 문제입니다. 아무것도 약속하지 않으면 온디맨드이고, 금액을 약속하면 Savings Plans, 구성을 약속하면 예약 인스턴스, 중단을 감수하면 스팟, 물리 호스트를 통째로 쓰면 전용 호스트입니다.

EC2 구매 옵션 다섯 가지의 약정 대상과 성격
옵션 무엇을 약정하는가 중단 가능성 언제 고르는가
온디맨드 없음. 실행한 초 단위로 지불 없음 부하를 예측할 수 없는 초기 단계, 단기 실험, 스파이크 대응
Savings Plans 시간당 사용 금액을 1년 또는 3년 약정 없음 상시 기저 부하가 있고, 인스턴스 구성을 바꿀 여지를 남기고 싶을 때
예약 인스턴스(RI) 인스턴스 구성(타입 · 리전 등)을 1년 또는 3년 약정 없음 구성이 고정되어 있고, 특정 가용 영역의 용량 확보가 필요할 때
스팟 인스턴스 없음. 대신 AWS가 용량을 회수할 수 있음 있음 — 2분 전 통지 후 중단 중단되어도 되는 배치 · 분석 · 렌더링 · 백그라운드 처리
전용 호스트 · 전용 인스턴스 물리 서버 단위(호스트) 또는 단일 테넌트 하드웨어(인스턴스) 없음 소켓 · 코어 단위 라이선스를 가져와야 하거나 물리적 격리가 규정인 경우

온디맨드 — 기준선

약정이 없고 실행한 만큼 지불합니다. 다른 옵션의 절감 효과는 언제나 온디맨드 요율을 기준으로 설명됩니다. 시험에서 온디맨드가 정답이 되는 경우는 기간이 짧거나 부하를 아직 모를 때입니다. "1년 약정" 같은 조건이 문제에 없는데 예약 인스턴스를 고르는 것은 과잉 설계입니다.

예약 인스턴스 — 구성을 약정한다

예약 인스턴스는 인스턴스 타입과 리전을 포함한 구성을 1년 또는 3년 약정하고 온디맨드보다 낮은 요율을 적용받습니다. 선택할 것이 세 가지 있습니다.

예약 인스턴스의 세 가지 선택 축
축 값 차이
범위(scope) Region / Availability Zone 리전 범위는 용량을 예약하지 않지만 가용 영역과 인스턴스 크기 유연성이 있고, 가용 영역 범위는 해당 가용 영역의 용량을 예약하지만 유연성이 없다
제공 클래스 standard / convertible 표준은 절감 폭이 크고, 컨버터블은 기간 중 다른 인스턴스 구성으로 교환할 수 있다
결제 방식 All Upfront / Partial Upfront / No Upfront 선결제 비중이 클수록 절감 폭이 커진다

시험에서 "특정 가용 영역에 용량을 확보해야 한다"는 조건이 붙으면 리전 범위 예약 인스턴스나 Savings Plans는 답이 아닙니다. 용량 예약이 필요하면 가용 영역 범위 예약 인스턴스 또는 온디맨드 용량 예약(On-Demand Capacity Reservations)입니다.

Savings Plans — 금액을 약정한다

Savings Plans는 인스턴스 구성이 아니라 시간당 사용 금액을 1년 또는 3년 약정합니다. 약정한 금액까지는 할인 요율이 적용되고, 초과분은 온디맨드 요율로 청구됩니다. 결제 방식은 예약 인스턴스와 같이 세 가지입니다. SAA 범위에서 구분해야 할 유형은 두 가지입니다.

Savings Plans 두 유형의 적용 범위
유형 API 값 적용 범위
Compute Savings Plans Compute 인스턴스 패밀리 · 크기 · 리전 · 운영체제 · 테넌시를 바꿔도 적용되고, AWS Fargate와 AWS Lambda 사용량에도 적용된다. 가장 유연하다
EC2 Instance Savings Plans EC2Instance 특정 리전의 특정 인스턴스 패밀리에 한정된다. 유연성을 포기하는 대신 Compute 유형보다 절감 폭이 크다

스팟 인스턴스 — 중단을 감수한다

스팟 인스턴스는 남는 EC2 용량을 온디맨드보다 낮은 가격에 쓰는 방식입니다. AWS가 용량이 필요해지면 인스턴스를 회수하며, 이때 2분 전에 중단 통지(interruption notice)가 인스턴스 메타데이터로 전달됩니다. 더 이른 신호로 재조정 권장(rebalance recommendation)이 있어 중단 위험이 높아졌을 때 미리 워크로드를 옮길 기회를 줍니다.

중단 시 동작은 종료 · 중지 · 최대 절전(terminate · stop · hibernate) 중에서 고를 수 있고, 요청은 일회성(one-time)과 지속(persistent)이 있습니다. 지속 요청은 중단된 뒤 용량이 생기면 자동으로 다시 제출됩니다.

스팟이 답이 되는 신호는 명확합니다 — "중단되어도 된다", "내결함성이 있다", "언제 실행되든 상관없다", "배치 작업"입니다. 반대로 상태를 로컬에 유지하는 서버, 즉시 응답해야 하는 사용자 요청 처리, 중단이 곧 데이터 손실인 워크로드에는 쓰지 않습니다.

전용 호스트와 전용 인스턴스

테넌시(Tenancy) 값은 default · dedicated · host 세 가지입니다. 전용 인스턴스(dedicated)는 단일 테넌트 하드웨어에서 실행되지만 물리 서버 자체를 우리가 지정하지는 않습니다. 전용 호스트(host)는 물리 서버를 통째로 배정받아 소켓 · 코어 · VM 단위 라이선스를 가져와 쓸 수 있고 소켓과 코어 수를 볼 수 있습니다.

따라서 시험의 갈림길은 이렇습니다 — "기존 서버 바인딩 라이선스를 가져와야 한다"면 전용 호스트, "다른 고객과 하드웨어를 공유하지 않아야 한다"는 규정만 있으면 전용 인스턴스로 충분합니다.

핵심 판단 — 스팟인가 Savings Plans인가

도메인 4에서 가장 자주 나오는 판단입니다. 기준은 단 하나, 워크로드가 중단을 견디는가입니다.

워크로드 특성에 따른 구매 옵션 배정
워크로드 특성 배정 근거
24시간 상시 실행되는 기저 부하 Savings Plans (또는 예약 인스턴스) 어차피 계속 쓸 용량이므로 약정으로 단가를 낮추는 것이 순이익이다
중단되어도 되는 배치 · 분석 · 렌더링 스팟 인스턴스 중단 비용이 낮으므로 남는 용량을 쓰는 대가를 감당할 수 있다
예측 불가능한 단기 스파이크 온디맨드 약정 기간보다 짧게 쓰면 약정이 오히려 손해다
구성이 고정되고 용량 확보까지 필요 가용 영역 범위 예약 인스턴스 Savings Plans는 용량을 예약하지 않는다
서버 바인딩 라이선스 · 물리적 격리 규정 전용 호스트 · 전용 인스턴스 비용이 아니라 라이선스와 규정이 결정 기준이다

실무와 시험 모두에서 흔한 정답 형태는 혼합입니다. Auto Scaling 그룹의 기저 대수는 Savings Plans로 덮고, 그 위로 늘어나는 변동분은 스팟으로 채우는 구성입니다. 이때도 전제는 상태 비저장 설계입니다 — 스팟 인스턴스가 2분 뒤 사라져도 서비스가 계속되어야 하기 때문입니다.

MOST cost-effective 한정어가 붙은 컴퓨팅 문항의 판단 순서입니다.

  • 중단을 견디는가 — 견딘다면 스팟이 거의 언제나 답입니다.
  • 상시 부하인가 — 그렇다면 Savings Plans 또는 예약 인스턴스입니다.
  • 구성이 고정되어 있고 용량 확보가 필요한가 — 그렇다면 가용 영역 범위 예약 인스턴스입니다.
  • 그 밖의 단기 · 예측 불가 — 온디맨드입니다.

이 사이트는 할인율 수치를 쓰지 않습니다. 요금과 할인율은 리전과 시점에 따라 달라져서 확인된 값으로 고정할 수 없기 때문입니다. 시험도 금액 계산을 요구하지 않고 구조적으로 더 싼 안을 고르게 합니다. 비용 최적화 전반은 18장과 비용 빠른참조에서 이어집니다.

예약 인스턴스와 Savings Plans는 청구 할인이지 용량 보장이 아닙니다. 리전 범위 예약 인스턴스는 용량을 예약하지 않는다고 문서가 명시합니다. "약정했으니 항상 인스턴스를 띄울 수 있다"는 가정으로 설계하면 용량 부족 오류를 만났을 때 대응할 방법이 없습니다. 용량이 필요하면 용량 예약을 별도로 확보합니다.

AMI와 사용자 데이터 — 무엇을 굽고 무엇을 실행할 것인가

Amazon Machine Image

AMI는 인스턴스를 시작할 때 쓰는 템플릿이며, 루트 볼륨의 스냅샷과 블록 디바이스 매핑, 시작 권한을 담습니다. EBS 기반 인스턴스에서 AMI를 만들면 연결된 EBS 볼륨의 스냅샷이 함께 생성되고, 그 AMI로 시작한 인스턴스는 같은 볼륨 구성을 그대로 갖습니다. AMI와 스냅샷의 관계는 6장에서 자세히 다룹니다.

AMI는 리전 단위 리소스입니다. 다른 리전에서 쓰려면 복사해야 하고, 복사 작업은 대상 리전에서 시작합니다. 재해 복구용으로 다른 리전에 골든 이미지를 미리 복사해 두는 구성이 여기서 나옵니다.

인스턴스 스토어 볼륨의 데이터는 AMI에 보존되지 않습니다. AMI로 시작한 새 인스턴스의 인스턴스 스토어는 비어 있습니다.

사용자 데이터 — 시작 시 실행되는 스크립트

사용자 데이터(user data)는 인스턴스를 시작할 때 전달하는 셸 스크립트 또는 cloud-init 지시문입니다. API로 넘길 때는 base64로 인코딩해야 하며, CLI와 SDK는 이 인코딩을 대신 해 주기도 합니다. 패키지 설치, 설정 파일 배치, 서비스 기동 같은 초기화를 여기서 처리합니다.

사용자 데이터는 편하지만 기동 시간을 늘립니다. Auto Scaling 그룹이 새 인스턴스를 띄우는 상황에서는 이 시간이 곧 스케일아웃 지연이 됩니다. 그래서 실무 표준은 변하지 않는 부분은 AMI에 미리 굽고(golden AMI), 환경마다 달라지는 값만 사용자 데이터로 주입하는 것입니다.

사용자 데이터에 액세스 키나 비밀번호를 넣지 않습니다. 사용자 데이터는 인스턴스 메타데이터로 조회할 수 있으므로, 인스턴스에 침입한 공격자나 잘못 설정된 프록시가 그대로 읽을 수 있습니다. AWS API 호출 자격 증명은 IAM 역할(인스턴스 프로파일)로, 비밀 값은 AWS Secrets Manager나 AWS Systems Manager Parameter Store로 처리합니다 (16장 보안·암호화·거버넌스).

배치 그룹 3종 — 성능과 장애 격리는 반대 방향

기본적으로 EC2는 인스턴스를 서로 다른 하드웨어에 흩어 놓으려 합니다. 배치 그룹은 그 배치에 개입해 더 가깝게 또는 더 멀리 두게 만드는 장치입니다. API의 배치 전략 값에는 cluster · partition · spread가 있습니다.

배치 그룹 세 가지의 배치 방식과 제약
전략 배치 방식 주요 제약 언제 고르는가
클러스터 cluster 단일 가용 영역 안에 인스턴스를 밀집 배치한다. 같은 고대역폭 네트워크 구간에 놓인다 여러 가용 영역에 걸칠 수 없다. 같은 타입으로 한 번에 시작하지 않으면 용량 부족 오류가 나기 쉽다 노드 간 통신이 잦은 HPC, 낮은 지연과 높은 처리량이 목표일 때
파티션 partition 인스턴스를 논리 파티션으로 나누고, 파티션끼리는 랙을 공유하지 않게 배치한다 가용 영역당 파티션 최대 7개. 전용 인스턴스를 쓰면 파티션 2개까지 HDFS · HBase · Cassandra처럼 복제본을 랙 단위로 흩어야 하는 대규모 분산 시스템

파티션 배치 그룹과 분산 배치 그룹은 같은 리전의 여러 가용 영역에 걸칠 수 있지만, 클러스터 배치 그룹은 단일 가용 영역을 벗어나지 못합니다. 여기서 시험이 노리는 충돌이 생깁니다 — "가용 영역 간 지연을 최소화하라"와 "다중 가용 영역으로 고가용성을 확보하라"는 동시에 만족시킬 수 없습니다. 문제문이 어느 쪽을 우선하는지 읽어야 합니다.

그 밖의 공통 제약도 함께 봅니다. 인스턴스는 한 번에 하나의 배치 그룹에만 속하고, 배치 그룹을 병합할 수 없으며, 전용 호스트에는 배치 그룹을 쓸 수 없습니다. 배치 그룹 생성 자체에는 요금이 붙지 않습니다.

배치 그룹 문항은 키워드 하나로 갈립니다.

  • "노드 간 지연 최소화", "HPC", "높은 네트워크 처리량" → 클러스터
  • "랙 단위 장애 격리", "Hadoop · Cassandra · Kafka 같은 분산 복제" → 파티션
  • "소수의 중요 인스턴스를 서로 떨어뜨림" → 분산

그리고 클러스터는 단일 가용 영역이라는 사실이 함정으로 쓰입니다. "다중 가용 영역 고가용성"이 요구된 문항에서 클러스터 배치 그룹 선택지는 소거 대상입니다.

인스턴스 메타데이터와 IMDSv2 SAA 빈출

인스턴스 메타데이터 서비스(Instance Metadata Service, IMDS)는 인스턴스 안에서 링크 로컬 주소 169.254.169.254로 호출하는 로컬 엔드포인트입니다. 인스턴스 ID, AMI ID, 사용자 데이터, 그리고 연결된 IAM 역할의 임시 자격 증명을 여기서 얻습니다. SDK가 자격 증명을 자동으로 찾는 것도 이 경로 덕분입니다.

문제는 임시 자격 증명이 여기 있다는 사실 자체입니다. 애플리케이션에 서버 측 요청 위조(Server-Side Request Forgery, SSRF) 취약점이 있으면, 공격자가 애플리케이션에 169.254.169.254로 요청을 보내게 만들어 자격 증명을 훔칠 수 있습니다. IMDSv2는 이 공격 경로를 막기 위해 설계되었습니다.

두 단계 요청 구조

IMDSv2는 세션 지향 방식입니다. 먼저 PUT으로 세션 토큰을 발급받고, 이후 모든 GET 요청 헤더에 그 토큰을 실어야 응답을 받습니다. 토큰의 유효 시간은 최소 1초에서 최대 6시간(21,600초)이며, 토큰 사용이 required인 인스턴스에서 토큰 없이 호출하면 401 Unauthorized가 반환됩니다. 토큰은 발급된 인스턴스에서만 유효해서 다른 인스턴스로 가져가 쓸 수 없습니다.

여기에 홉 제한(HttpPutResponseHopLimit)이 더해집니다. PUT 응답의 기본 홉 제한은 1이고 1에서 64 사이로 조정합니다. 홉 제한이 1이면 응답이 인스턴스를 벗어나지 못하므로 역방향 프록시나 컨테이너 네트워크를 한 번 더 거치는 요청은 토큰을 받을 수 없습니다. 컨테이너에서 메타데이터를 써야 한다면 이 값을 올려야 하지만, 올리는 만큼 노출 범위도 넓어진다는 것을 함께 알아야 합니다. 또한 PUT 요청에 X-Forwarded-For 헤더가 있으면 거부됩니다 — 프록시를 경유한 요청을 걸러 내기 위한 장치입니다.

2024년 이후의 기본값 정책

예전에는 인스턴스가 IMDSv1과 IMDSv2를 둘 다 받아들이는 것이 일반적이었고, IMDSv2 강제는 인스턴스마다 따로 켜야 했습니다. 2024년 3월부터는 계정과 리전 수준에서 신규 인스턴스 시작의 기본값을 지정할 수 있습니다. ModifyInstanceMetadataDefaults로 HttpTokens를 required로 정해 두면 그 이후 시작되는 인스턴스는 별도 지정이 없는 한 IMDSv2 전용으로 뜹니다. 또한 AMI에 ImdsSupport가 v2.0으로 표시된 경우와 최근에 출시된 인스턴스 타입은 IMDSv2를 전제로 동작합니다.

따라서 "IMDSv1이 기본이다"라고 서술하는 자료는 현행이 아닙니다. 설계 질문에서는 계정 수준 기본값을 required로 두고, IMDSv1이 필요한 오래된 소프트웨어만 예외로 관리하는 것이 표준 답입니다.

메타데이터 관련 문항의 정답 패턴은 두 가지로 수렴합니다.

  • "EC2에서 AWS API를 호출해야 한다" → 액세스 키가 아니라 IAM 역할입니다. 액세스 키를 인스턴스에 심는 선택지는 거의 항상 오답입니다 (2장 IAM과 자격 증명).
  • "메타데이터를 통한 자격 증명 탈취를 막아야 한다" → IMDSv2를 required로 강제하고 홉 제한을 최소로 둡니다.

메타데이터 엔드포인트를 아예 끄는 것(HttpEndpoint=disabled)도 가능하지만, 그러면 인스턴스 프로파일로 자격 증명을 받을 수 없게 되므로 IAM 역할을 쓰는 워크로드에는 답이 되지 않습니다.

인스턴스 수명주기와 상태별 과금

인스턴스 상태와 인스턴스 사용 요금 과금 여부
상태 의미 인스턴스 사용 요금
pending 시작 준비 중. 시작 직후 또는 중지 상태에서 다시 시작할 때 거친다 과금 안 됨
running 실행 중이며 사용 가능 과금됨
stopping 중지 준비 중 과금 안 됨 (최대 절전으로 중지할 때는 이 구간도 과금됨)
stopped 종료되지 않았고 언제든 다시 시작할 수 있다 과금 안 됨
shutting-down 종료 준비 중 과금 안 됨
terminated 영구 삭제되어 다시 시작할 수 없다 과금 안 됨 (예약 인스턴스 약정은 기간까지 계속 청구됨)

표는 인스턴스 사용 요금만 다룹니다. 중지된 인스턴스라도 연결된 EBS 볼륨과 Elastic IP 요금은 계속 발생합니다. "인스턴스를 껐는데 왜 요금이 나오는가"의 답이 여기 있습니다.

중지와 시작이 바꾸는 것들

  • 인스턴스가 다른 호스트로 옮겨질 수 있습니다. 그래서 인스턴스 스토어 볼륨의 데이터는 사라집니다 (6장).
  • 프라이빗 IPv4 주소와 IPv6 주소는 유지됩니다. 프라이빗 주소에 연결된 Elastic IP도 그대로 남습니다.
  • 중지 상태에서만 인스턴스 타입 같은 일부 속성을 변경할 수 있습니다.
  • 재부팅은 새 과금 주기를 시작하지 않습니다. 재부팅 동안 인스턴스는 계속 running 상태이고, 인스턴스 스토어 데이터도 남습니다.
  • 최대 절전(hibernate)은 메모리 내용을 EBS 루트 볼륨에 저장했다가 다시 불러옵니다. 그래서 루트 볼륨이 EBS인 인스턴스에서만 가능합니다.

운영체제 안에서 종료 명령을 실행했을 때의 동작은 InstanceInitiatedShutdownBehavior가 정하며 기본값은 stop입니다. 이 값을 terminate로 두면 인스턴스 안에서의 실수 한 번이 인스턴스 삭제로 이어집니다.

수명주기 문항에서 자주 묻는 것은 두 가지입니다. (1) 중지해도 계속 나가는 비용은 무엇인가 — EBS 볼륨과 Elastic IP입니다. (2) 중지하면 무엇을 잃는가 — 인스턴스 스토어 데이터입니다. 퍼블릭 IPv4 주소가 필요한데 중지와 시작을 반복하는 인스턴스라면 Elastic IP를 붙여 주소를 고정하는 것이 정답 방향입니다.

흔한 오해

"예약 인스턴스나 Savings Plans를 사면 용량이 보장된다" — Savings Plans와 리전 범위 예약 인스턴스는 청구 할인일 뿐 용량을 예약하지 않습니다. 문서가 "리전 예약 인스턴스는 용량을 예약하지 않는다"고 명시합니다. 특정 가용 영역의 용량 확보가 필요하면 가용 영역 범위 예약 인스턴스나 온디맨드 용량 예약을 별도로 구성해야 합니다. "약정했으니 언제든 띄울 수 있다"는 가정은 대규모 장애 상황에서 그대로 깨집니다.

"배치 그룹을 쓰면 성능도 좋아지고 가용성도 올라간다" — 세 전략은 서로 반대 방향을 최적화합니다. 클러스터는 인스턴스를 가깝게 두어 지연을 줄이는 대신 단일 가용 영역을 벗어날 수 없어 장애 도메인이 하나로 묶입니다. 반대로 분산은 인스턴스를 멀리 떨어뜨려 장애를 격리하지만 네트워크 지연은 줄지 않습니다. "저지연"과 "다중 가용 영역 고가용성"을 한 배치 그룹으로 동시에 얻으려는 선택지는 성립하지 않습니다.

"인스턴스를 중지하면 아무 요금도 나가지 않는다" — 멈추는 것은 인스턴스 사용 요금이고, EBS 볼륨과 연결되지 않은 Elastic IP 요금은 계속 발생합니다. 더 중요한 것은 인스턴스 스토어 데이터가 사라진다는 점입니다. 중지와 시작 과정에서 인스턴스가 다른 호스트로 옮겨질 수 있기 때문입니다. 재부팅은 이와 달라서 데이터가 남고 과금 주기도 새로 시작되지 않습니다.

Compute와 EC2 Instance Savings Plans Compute는 패밀리·리전·Fargate·Lambda까지 적용, EC2 Instance는 리전 안 특정 패밀리 한정 서버리스까지 덮어야 하는데 EC2 Instance 유형을 고름

AMI의 범위 리전 단위 리소스. 복사는 대상 리전에서 시작한다 다른 리전에서 AMI ID를 그대로 쓰려고 함
