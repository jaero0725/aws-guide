기본개념 · 16장

보안·암호화·거버넌스

2장과 3장이 누가 들어올 수 있는가를 다뤘다면, 이 장은 들어온 뒤에 데이터를 어떻게 보호하고 이상을 어떻게 알아채는가를 다룹니다. 암호화 키를 누가 쥐는지, 인증서를 어디에 붙이는지, 비밀을 어디에 두는지, 위협을 어느 서비스가 찾아내는지가 전부 이 장의 주제입니다.

이 장은 보안 아키텍처 설계(30%)의 나머지 절반입니다. 특히 과제 진술 1.2 보안 워크로드·애플리케이션 설계와 1.3 적절한 데이터 보안 제어 결정이 이 장에 몰려 있습니다.

학습 목표

  • AWS KMS 키의 세 종류를 구분하고, 고객 관리형 키를 골라야 하는 조건을 근거를 들어 말할 수 있습니다.
  • 봉투 암호화(envelope encryption)에서 데이터 키가 만들어지고 쓰이는 순서를 설명할 수 있습니다.
  • 키 정책과 IAM 정책이 함께 평가된다는 사실로 "권한은 줬는데 복호화가 안 된다"는 상황을 진단할 수 있습니다.
  • AWS Certificate Manager 인증서를 어디에 붙일 수 있는지와 Amazon CloudFront의 리전 제약을 설명할 수 있습니다.
  • AWS Secrets Manager와 Parameter Store 중 하나를 자동 교체 요구 여부로 선택할 수 있습니다.
  • GuardDuty · Inspector · Macie · Security Hub와 AWS WAF · AWS Shield를 시나리오의 요구 문장으로 구분해 고를 수 있습니다.

AWS KMS — 키를 누가 쥐는가 SAA 빈출

AWS Key Management Service(KMS)는 암호화 키를 만들고 보관하고 사용을 통제하는 서비스입니다. SAA에서 KMS가 중요한 이유는 암호 알고리즘 때문이 아닙니다. 키에 대한 접근 권한이 곧 데이터에 대한 접근 권한이 되므로, KMS 키 하나가 버킷 정책이나 보안 그룹과 같은 수준의 접근 통제 장치가 되기 때문입니다.

키 종류 세 가지

KMS API는 키의 관리 주체를 KeyManager 값으로 AWS와 CUSTOMER 두 가지로만 표현합니다. 실무와 시험에서 쓰는 구분은 여기에 AWS 소유 키를 더한 세 가지입니다. 차이는 하나입니다 — 키 정책을 우리가 편집할 수 있는가입니다.

키 종류 누가 만드는가 우리가 할 수 있는 것 고르는 신호

문제문에 "키에 대한 접근을 우리가 직접 통제해야 한다", "다른 계정과 키를 공유해야 한다", "규정이 정한 주기로 키를 교체해야 한다" 중 하나라도 있으면 고객 관리형 키입니다. "암호화만 되면 된다"는 요구에는 AWS 관리형 키로 충분하고, 이때 고객 관리형 키를 고르는 것은 과잉 설계로 취급됩니다.

봉투 암호화와 데이터 키

KMS는 큰 데이터를 직접 암호화하지 않습니다. KMS의 Encrypt 작업은 API 문서에 명시된 대로 최대 4,096바이트까지만 처리합니다. 데이터베이스 비밀번호나 식별자 정도가 그 크기입니다.

그래서 실제 암호화는 두 겹으로 이뤄집니다. KMS에게 데이터 키(data key)를 만들어 달라고 하면 GenerateDataKey가 평문 데이터 키와 KMS 키로 암호화된 데이터 키를 함께 돌려줍니다. 애플리케이션은 평문 데이터 키로 데이터를 암호화한 뒤 평문 키를 메모리에서 지우고 암호문 키를 데이터 옆에 저장합니다. 이 구조가 봉투 암호화(envelope encryption)입니다.

예제의 --encryption-context는 암호화할 때 지정한 값과 대소문자까지 정확히 같은 값을 복호화할 때 다시 줘야 합니다. 다르면 요청이 거부됩니다. 키 정책의 조건 키로도 쓸 수 있어서 "이 컨텍스트로만 복호화를 허용한다"는 통제를 만들 수 있습니다.

봉투 암호화 문항의 결론은 "대용량 데이터가 KMS를 왕복하지 않는다"입니다. "수 TB의 파일을 KMS로 보내 암호화한다"는 선택지는 크기 제한 때문에도, 성능 때문에도 오답입니다. 같은 이유로 Amazon S3의 SSE-KMS는 객체마다 KMS를 호출하지만, S3 버킷 키를 켜면 그 호출 횟수를 줄일 수 있습니다 (8장 S3와 오브젝트 스토리지).

키 정책과 IAM 정책 — 두 개가 함께 결정한다

KMS 키에는 키 정책(key policy)이라는 리소스 기반 정책이 반드시 하나 붙어 있습니다. 여기가 2장에서 다룬 리소스 기반 정책과 다른 점이 하나 있습니다. 키 정책이 비어 있으면 IAM 정책만으로는 키를 쓸 수 없습니다. 키 정책이 먼저 계정이나 주체에게 권한 위임을 열어 줘야 IAM 정책이 의미를 갖습니다.

접근을 결정하는 장치는 실제로 세 겹입니다.

  • 키 정책 — 키에 붙는 정본. 누가 이 키를 쓸 수 있는지의 출발점입니다.
  • IAM 정책 — 키 정책이 계정에 위임한 범위 안에서 주체별로 좁힙니다.
  • 권한 부여(grant) — API 문서가 "키 정책 · IAM 정책과 함께 고려된다"고 명시하는 임시 권한 수단입니다. AWS 서비스가 우리 대신 키를 쓸 때 주로 만들어지며, 만들고 쓰고 지우는 동안 키 정책을 건드리지 않아도 됩니다.

첫 번째 문장이 계정 루트를 주체로 쓰는 것은 루트 사용자에게 권한을 준다는 뜻이 아니라, 이 계정의 IAM 정책이 키에 대해 발언권을 갖도록 위임한다는 관용 표현입니다. 이 문장을 빼면 키를 만든 사람 외에는 아무도 키를 관리할 수 없게 되고, 키 정책을 잘못 저장하면 되돌릴 방법이 사라집니다.

"IAM 정책에 kms:Decrypt를 넣었는데 AccessDenied가 납니다." 거의 항상 키 정책이 그 주체를 허용하지 않은 경우입니다. 교차 계정이라면 조건은 더 늘어납니다 — 키 소유 계정의 키 정책이 상대 계정을 허용하고, 상대 계정의 IAM 정책이 그 키 ARN을 허용해야 비로소 성립합니다. 한쪽만 열어 두는 것이 교차 계정 문항의 전형적인 오답 배치입니다.

키 교체

KMS의 자동 교체는 키 재료(key material)를 새로 만들고 이전 재료를 보관하는 방식입니다. 키 ID와 ARN, 별칭은 그대로이므로 애플리케이션은 아무것도 바꾸지 않아도 되고, 예전 재료로 암호화된 데이터도 계속 복호화됩니다.

키 종류별 자동 교체 동작 (KMS API 문서 기준)
키 종류 자동 교체 주기
고객 관리형 키 켜고 끌 수 있습니다 켜면 기본적으로 활성화 시점으로부터 1년(약 365일) 뒤 교체되고 이후 매년 반복됩니다. RotationPeriodInDays로 다른 주기를 지정할 수 있습니다
AWS 관리형 키 켜고 끌 수 없습니다 KMS가 매년 자동으로 교체합니다
AWS 소유 키 해당 없음 키를 소유한 AWS 서비스가 관리합니다

자동 교체에는 범위 제한이 있습니다. API 문서는 대칭 암호화 KMS 키에서만 지원되며 비대칭 키 · HMAC 키 · 키 재료를 가져온(imported) 키 · 사용자 지정 키 스토어의 키에는 자동 교체를 켤 수 없다고 명시합니다. 키 재료를 직접 가져온 키는 새 재료를 다시 가져오는 방식으로 교체합니다.

AWS 관리형 키의 교체 주기는 2022년 5월에 3년에서 1년으로 바뀌었습니다. "AWS 관리형 키는 3년마다 교체된다"고 적힌 자료가 아직 많으니 주의합니다. 고객 관리형 키의 자동 교체 주기도 이제 고정값이 아니라 RotationPeriodInDays로 지정할 수 있습니다.

키 삭제는 되돌릴 수 없다

ScheduleKeyDeletion은 즉시 삭제하지 않고 대기 기간을 둡니다. API 문서 기준으로 기본 30일이며 7일에서 30일 사이로 지정할 수 있습니다. 대기 중에는 키 상태가 PendingDeletion이 되어 어떤 암호화 작업에도 쓸 수 없고, 기간이 끝나기 전이면 취소할 수 있습니다.

기간이 지나 실제로 삭제되면 그 키로 암호화된 데이터는 복구할 수 없습니다. 그래서 "키를 지워 데이터를 무력화한다"는 것이 규정 준수 시나리오의 정답이 되기도 하고, 반대로 사고의 원인이 되기도 합니다. 단순히 쓰지 못하게 막는 것이 목적이라면 삭제가 아니라 DisableKey가 맞습니다.

다중 리전 키와 별칭

기본적으로 KMS 키는 단일 리전 자원이며 리전 밖으로 나가지 않습니다. 그래서 리전 A에서 암호화한 데이터를 리전 B에서 읽으려면 보통 복호화 후 재암호화가 필요합니다. 다중 리전 키(multi-Region key)는 이 왕복을 없애기 위한 예외입니다.

  • 기본 키를 MultiRegion=true로 만들고 ReplicateKey로 다른 리전에 복제본을 만듭니다. 같은 파티션 안에서만 복제됩니다.
  • 기본 키와 복제본은 키 ID와 키 재료가 같습니다. 그래서 한 리전에서 암호화한 데이터를 재암호화나 리전 간 호출 없이 다른 리전에서 복호화할 수 있습니다.
  • 키 정책은 리전마다 따로 둘 수 있습니다. 공유되는 것은 키 ID · 키 재료 · 키 스펙 · 용도 · 재료 출처 · 자동 교체 상태입니다.
  • 이 값은 생성 후 바꿀 수 없습니다. 단일 리전 키를 나중에 다중 리전 키로 승격할 수 없습니다.

별칭(alias)은 키에 붙이는 사람이 읽을 수 있는 이름입니다. 계정과 리전 안에서 고유하고, 키 하나에 여러 별칭을 붙일 수 있으며, 별칭이 가리키는 키를 나중에 바꿀 수도 있습니다. 코드에 키 ID 대신 alias/app-data를 쓰면 키를 교체해도 코드를 고치지 않아도 됩니다.

"암호화된 데이터를 다른 리전으로 복제해 재해 복구에 쓴다"는 시나리오에서 다중 리전 키가 답이 되는 경우가 많습니다. 단일 리전 키만 쓰면 대상 리전에서 데이터를 읽을 수 없으므로 복제는 되는데 복구가 안 되는 구성이 나옵니다. Amazon S3 교차 리전 복제로 SSE-KMS 객체를 복제할 때 특히 자주 걸립니다 (18장).

AWS CloudHSM과의 차이

AWS CloudHSM은 전용 하드웨어 보안 모듈을 우리 VPC 안에 배치하는 서비스입니다. KMS와 겹쳐 보이지만 판단 기준은 명확합니다 — 규정이 "단독 점유 HSM"이나 "AWS도 접근할 수 없는 키"를 요구하는가입니다.

AWS KMS와 AWS CloudHSM 비교
항목 AWS KMS AWS CloudHSM
형태 완전 관리형 · 멀티테넌트 고객 전용 HSM 클러스터 · VPC 안에 배치
운영 부담 낮음 — 가용성과 백업을 AWS가 처리 높음 — 클러스터 구성 · 사용자 관리 · 백업을 직접
AWS 서비스 통합 S3 · EBS · RDS 등 광범위 직접 통합은 제한적. KMS의 사용자 지정 키 스토어로 연결해서 씁니다
고르는 신호 "저장 데이터를 암호화하고 키 사용을 감사한다" "전용 HSM", "FIPS 검증 하드웨어를 단독으로", "AWS가 키에 접근할 수 없어야 한다"

KMS 키의 재료 출처(Origin)에 AWS_CLOUDHSM과 EXTERNAL_KEY_STORE가 있는 것이 이 연결 관계를 보여 줍니다. 즉 둘은 대체재라기보다, CloudHSM을 KMS 뒤에 두는 조합이 실제 구성입니다.

저장 데이터 암호화 — 서비스별 선택지

"저장 데이터를 암호화한다"는 요구는 거의 모든 서비스에서 만족시킬 수 있습니다. 그래서 문항은 암호화 여부가 아니라 어떤 방식으로 암호화하는가를 갈림길로 씁니다. 기준은 두 가지입니다 — 키를 누가 쥐는가와 키 사용 증적이 남는가입니다.

2023년 1월부터 모든 신규 객체가 SSE-S3로 자동 암호화됩니다. 따라서 "S3에 저장되는 데이터를 암호화해야 한다"는 요구만으로는 추가 작업이 필요하지 않습니다. 문항이 키 통제나 감사를 요구할 때만 SSE-KMS로 올라갑니다. "기본 암호화를 활성화해야 한다"는 선택지는 현행 기준에서 이미 되어 있는 일입니다.

암호화 문항에서 반복되는 두 가지 패턴을 기억합니다.

첫째, "이미 만들어 둔 리소스를 암호화하라"는 요구는 EBS와 RDS에서 스냅샷을 거치는 경로가 정답입니다. "설정에서 암호화를 켠다"는 선택지는 그 자리에서 소거합니다.

둘째, "암호화 키 사용 기록을 감사해야 한다"는 요구는 서비스 관리형 키가 아니라 KMS 키를 지목합니다. KMS 호출은 CloudTrail에 남지만 서비스가 내부에서 쓰는 소유 키는 그렇지 않기 때문입니다.

AWS Certificate Manager — 인증서를 어디에 붙이는가

AWS Certificate Manager(ACM)는 퍼블릭 TLS 인증서를 발급하고 자동으로 갱신합니다. SAA에서 ACM이 나오는 자리는 거의 언제나 전송 중 암호화와 TLS 종료 지점입니다.

발급과 검증

퍼블릭 인증서를 요청하면 도메인 소유를 증명해야 합니다. API 문서가 인정하는 방법은 DNS 검증과 이메일 검증이며, AWS는 DNS 검증을 권장합니다. DNS 검증은 지정된 CNAME 레코드를 도메인에 한 번 넣어 두면 이후 갱신도 자동으로 이뤄지기 때문입니다. Amazon Route 53을 쓰면 레코드 생성까지 콘솔에서 처리됩니다. 프라이빗 CA로 발급하는 프라이빗 인증서는 도메인 검증이 필요하지 않습니다.

TLS 종료 지점과 CloudFront의 리전 제약

인증서는 요청을 받는 지점에 붙습니다. 이 지점에서 TLS가 종료되고, 그 뒤 구간은 별도로 설계합니다.

ACM 인증서를 연결하는 지점과 제약

Application Load Balancer HTTPS 리스너에서 TLS를 종료하고 뒤쪽 대상에는 HTTP 또는 HTTPS로 전달합니다 인증서는 로드 밸런서와 같은 리전에 있어야 합니다
Network Load Balancer TLS 리스너를 쓰면 로드 밸런서에서 종료하고, TCP 리스너를 쓰면 종료하지 않고 그대로 넘깁니다 종료 여부가 리스너 프로토콜 선택으로 갈립니다(7장)

CloudFront에 붙일 인증서는 us-east-1에서 발급해야 합니다. CloudFront API 문서가 "CloudFront는 US East (N. Virginia) 리전의 ACM 인증서만 지원한다"고 명시합니다. 같은 제약이 AWS WAF의 CloudFront 범위 웹 ACL에도 걸립니다. "서울 리전에서 인증서를 발급해 CloudFront에 연결한다"는 선택지는 그 자리에서 소거 대상입니다.

반대로 ALB용 인증서는 ALB와 같은 리전이어야 합니다. 두 규칙을 섞어 놓는 것이 전형적인 오답 배치입니다.

오래된 자료는 "ACM 퍼블릭 인증서는 내보낼 수 없으므로 EC2에 설치할 수 없다"고 단정합니다. 그러나 ACM API 문서 기준으로 ExportCertificate가 퍼블릭 인증서 내보내기를 지원하며, 2025년 6월 17일 이전에 만들어진 퍼블릭 인증서만 내보낼 수 없다고 명시합니다. 따라서 "내보낼 수 없다"를 근거로 삼는 판단은 현행 기준에서 성립하지 않습니다. 시험에서는 인증서를 어디에 붙이는가로 판단하는 편이 안전합니다.

Secrets Manager와 Parameter Store — 자동 교체가 기준이다

두 서비스는 겹치는 부분이 넓습니다. 둘 다 값을 KMS로 암호화해 저장하고, 둘 다 IAM으로 접근을 통제하며, 둘 다 애플리케이션이 런타임에 값을 가져오게 합니다. 그래서 시험은 겹치지 않는 지점 하나로 갈림길을 만듭니다.

둘 다 아닌 세 번째 선택지도 기억합니다. "애플리케이션 설정 파일이나 환경 변수에 비밀번호를 넣는다"는 어떤 한정어에서도 정답이 되지 않습니다.

네 서비스 모두 AWS Organizations와 연동해 조직 전체에 한 번에 켤 수 있습니다. "수십 개 계정에 일일이 켜야 한다"는 선택지가 보이면 위임된 관리자 계정에서 조직 단위로 활성화하는 안이 더 낫습니다.

AWS WAF와 AWS Shield — 규칙인가 디도스인가

둘 다 "웹을 보호한다"고 설명되지만 막는 대상이 다릅니다. AWS WAF는 요청 하나하나의 내용을 보고, AWS Shield는 트래픽의 양과 형태를 봅니다.

요청의 내용으로 막는 것은 전부 WAF입니다. 3장에서 정리했듯 보안 그룹에는 거부 규칙이 없고, 네트워크 ACL은 IP와 포트까지만 봅니다. "특정 URL 패턴을 차단한다", "국가별로 차단한다"는 요구는 보안 그룹이나 네트워크 ACL로 만들 수 없으므로 WAF가 답입니다.

WAF 웹 ACL은 범위(scope)가 둘로 나뉩니다. CloudFront에 붙일 웹 ACL은 CLOUDFRONT 범위로 만들고 us-east-1 엔드포인트로 호출해야 하며, ALB나 API Gateway에 붙일 웹 ACL은 REGIONAL 범위로 해당 리소스와 같은 리전에 만듭니다. ACM 인증서의 리전 제약과 같은 모양이라 함께 외워 두면 좋습니다.

WAF와 CloudFront·Route 53을 엮은 엣지 계층 전체 구성은 14장 엣지와 DNS에서 다룹니다. 이 장에서는 어느 계층의 무엇을 막는 장치인가만 확실히 해 둡니다.

애플리케이션 사용자와 디렉터리

2장에서 정리한 세 갈래 — 직원이면 AWS IAM Identity Center, 앱 사용자면 Amazon Cognito, 사람이 아니면 IAM 역할 — 중 두 번째와 그 주변을 여기서 마무리합니다.

Cognito는 이름이 하나지만 서로 다른 일을 하는 두 개의 구성 요소입니다. 이 둘을 뭉뚱그려 이해하면 문항에서 반드시 걸립니다.

"모바일 앱 사용자 수백만 명이 각자의 S3 접두사에만 업로드할 수 있어야 한다"는 Cognito 자격 증명 풀입니다. 사용자마다 IAM 사용자를 만드는 선택지는 운영 부담과 확장성 양쪽에서 밀립니다.

반대로 "앱에 회원 가입과 소셜 로그인을 붙여야 한다"만 있고 AWS API 직접 호출이 없으면 사용자 풀만으로 끝납니다. AWS 자격 증명이 필요하지 않은데 자격 증명 풀을 고르는 것은 과잉 설계입니다.

유형 무엇인가 고르는 신호
AWS Managed Microsoft AD AWS가 운영하는 실제 Active Directory. 온프레미스 AD와 신뢰 관계를 맺을 수 있습니다 "AWS 안에서 도메인 조인", "그룹 정책", "Amazon FSx for Windows File Server와 연동"
AD Connector 디렉터리 정보를 복제하지 않고 온프레미스 AD로 요청을 전달하는 프록시 "기존 온프레미스 AD를 그대로 쓰고 사용자를 복제하지 않는다"
Simple AD 기본적인 디렉터리 기능만 제공하는 저비용 선택지 "소규모", "고급 AD 기능이 필요 없다"

여기서 갈림길은 사용자를 어디에 두는가입니다. AWS 안에 디렉터리를 두면 Managed Microsoft AD, 온프레미스에 그대로 두고 참조만 하면 AD Connector입니다.

흔한 오해

"IAM 정책에 권한을 주면 KMS 키를 쓸 수 있다" — KMS 키에는 키 정책이 따로 있고, 키 정책이 먼저 열어 주지 않으면 IAM 정책이 아무리 넓어도 거부됩니다. 2장에서 다룬 "자격 증명 기반 + 리소스 기반은 합집합"이라는 일반 규칙이 KMS에서는 그대로 적용되지 않습니다. 교차 계정이라면 양쪽 계정이 모두 허용해야 성립합니다.

"KMS가 데이터를 암호화해 준다" — KMS의 Encrypt는 최대 4,096바이트까지만 처리합니다. 실제 데이터는 봉투 암호화로 처리됩니다. KMS는 데이터 키를 만들어 주고, 데이터를 암호화하는 일은 Amazon S3 같은 서비스나 애플리케이션이 로컬에서 합니다. 이 사실을 모르면 "대용량 파일을 KMS로 보낸다"는 선택지를 고르게 됩니다.

"GuardDuty를 켜면 취약점도 찾아 준다" — 네 서비스는 입력이 다르므로 서로를 대신하지 못합니다. GuardDuty는 로그와 네트워크 신호를 읽어 이상 행위를 찾고, 패치되지 않은 소프트웨어를 찾는 것은 Inspector, S3 안의 민감 데이터를 찾는 것은 Macie입니다. Security Hub는 이들을 모아 볼 뿐 스스로 탐지하지 않습니다.

시험 포인트 정리

이 장의 주제는 전부 보안 아키텍처 설계(30%)에 속합니다.

항목 사실 함정
KMS 키 종류 AWS 소유 / AWS 관리형 / 고객 관리형. 키 정책을 편집할 수 있는 것은 고객 관리형뿐 키 통제 요구가 없는데 고객 관리형 키를 골라 과잉 설계가 됨

자동 키 교체 고객 관리형 키는 켜면 기본 1년 주기이고 주기 지정 가능. AWS 관리형 키는 매년 자동이며 끌 수 없음 AWS 관리형 키를 "3년마다"로 외우거나 비대칭 키에 자동 교체를 켤 수 있다고 답함
키 삭제 대기 기간 7~30일(기본 30일). 삭제되면 그 키로 암호화한 데이터는 복구 불가 일시적으로 못 쓰게 하려는데 삭제를 예약함(정답은 DisableKey)
다중 리전 키 같은 키 ID와 키 재료를 여러 리전에서 공유. 생성 시에만 지정 가능 단일 리전 키로 리전 간 복제를 구성해 대상 리전에서 복호화가 막힘
CloudHSM 전용 HSM. 규정이 단독 점유 하드웨어를 요구할 때 일반적인 저장 데이터 암호화에 CloudHSM을 고름
S3 암호화 방식 SSE-S3 기본 / SSE-KMS는 감사와 키 정책 / DSSE-KMS는 이중 / SSE-C는 키를 맡길 수 없을 때 "암호화해야 한다"만 보고 SSE-KMS를 고름(신규 객체는 이미 SSE-S3)
기존 리소스 암호화 EBS·RDS는 제자리 변경 불가. 스냅샷을 암호화해 복원 "설정에서 암호화를 켠다"는 선택지를 고름
ACM 검증 DNS 검증과 이메일 검증. DNS 검증이 권장되고 갱신이 자동 이메일 검증을 기본으로 가정해 자동 갱신 요구를 놓침
ACM과 CloudFront CloudFront용 인증서는 us-east-1에서 발급 배포 리전에서 발급해 연결하려 함
WAF 웹 ACL 범위 CloudFront는 CLOUDFRONT 범위 + us-east-1, ALB·API Gateway는 REGIONAL 범위 + 같은 리전 범위를 반대로 만들어 연결이 되지 않음
Secrets Manager 대 Parameter Store 기준은 자동 교체 요구 하나 "비밀이니까 Secrets Manager"로 단정해 비용 한정어를 놓침
GuardDuty 로그·네트워크 신호로 이상 행위를 탐지 취약점 스캔까지 한다고 이해
Inspector EC2 · ECR 이미지 · Lambda의 취약점 평가 네트워크 침입 탐지 도구로 이해
Macie Amazon S3의 민감 데이터 발견과 분류 모든 데이터 저장소를 스캔한다고 이해
Security Hub 여러 소스의 결과를 집계하고 표준에 대조 Security Hub만 켜면 탐지가 시작된다고 이해
WAF 대 Shield 요청 내용 기반 규칙은 WAF, 디도스 대응은 Shield 디도스 요구에 WAF만 고르거나, SQL 삽입 요구에 Shield를 고름
Cognito 2단 구조 사용자 풀은 인증, 자격 증명 풀은 임시 AWS 자격 증명 교환 둘을 하나로 보고 "사용자 풀로 S3에 직접 업로드"라고 답함
