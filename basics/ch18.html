기본개념 · 18장

비용 최적화·마이그레이션·재해 복구

비용 문항은 계산 문제가 아닙니다. SAA는 계산기를 요구하지 않고 구조적으로 더 싼 안을 고르게 합니다. 그래서 이 장은 금액을 외우게 하지 않고 무엇이 과금 대상인가, 어느 방향의 트래픽에 요금이 붙는가, 어떤 레버가 어떤 요금 항목을 줄이는가를 다룹니다. 같은 사고방식이 재해 복구와 마이그레이션 판단에도 그대로 쓰입니다.

이 장은 비용 최적화 아키텍처 설계(20%) 전체와 복원력 있는 아키텍처 설계(26%)의 재해 복구 부분을 담당합니다.

학습 목표

  • 데이터 전송 요금이 방향에 따라 달라진다는 사실을 근거로 비용 문항의 오답을 소거할 수 있습니다.
  • NAT 게이트웨이 트래픽을 VPC 엔드포인트로, 오리진 송신을 CloudFront로 줄이는 판단을 설명할 수 있습니다.
  • Savings Plans · 예약 인스턴스 · 스팟 인스턴스를 워크로드 특성에 맞춰 조합할 수 있습니다.
  • Cost Explorer · AWS Budgets · Cost and Usage Report의 역할을 구분해 요구에 맞는 도구를 고를 수 있습니다.
  • RTO · RPO 요구가 주어졌을 때 DR 4전략 중 하나를 근거를 들어 고를 수 있습니다.
  • 6R 마이그레이션 전략을 구분하고, 대용량 데이터 전송 수단을 대역폭과 기간으로 선택할 수 있습니다.

이 장의 서술 원칙 — 금액 대신 구조

이 사이트는 구체적인 금액을 싣지 않습니다. 요금은 리전과 시점에 따라 달라져서 학습 자료에 고정해 둘 값이 아니고, 시험도 금액을 묻지 않기 때문입니다. 비용은 언제나 과금 여부 · 과금 축 · 상대 비교 세 가지로만 설명합니다. 실제 금액이 필요하면 AWS 요금 페이지와 AWS Pricing Calculator에서 확인하고, 이미 쓰고 있는 계정의 실제 값은 Cost Explorer와 Cost and Usage Report에서 봅니다.

먼저 볼 것 — 무엇이 과금 축인가

금액을 몰라도 판단할 수 있는 이유는, AWS 요금이 서비스마다 정해진 몇 개의 축으로만 매겨지기 때문입니다. 어떤 설계 변경이 어느 축을 건드리는지 알면 방향은 결정됩니다.

대표적인 과금 축과 그 축을 줄이는 설계 행동
과금 축 대표 예 이 축을 줄이는 행동
가동 시간 EC2 인스턴스 시간, NAT 게이트웨이 시간, 인터페이스 엔드포인트 시간, RDS 인스턴스 시간 쓰지 않을 때 끄기, 항상 켜 둘 필요가 없는 구성 요소를 없애기, 서버리스로 대체하기

데이터 전송 인터넷 송신, 가용 영역 간, 리전 간 배치 조정, 캐싱, 압축, 경로 변경
프로비저닝된 용량 프로비저닝된 IOPS, DynamoDB 프로비저닝 용량, 예약된 동시성 실사용에 맞춰 라이트사이징하거나 온디맨드 모드로 전환

비용 문항에서 가장 먼저 찾을 것은 "항상 켜져 있는데 거의 안 쓰는 것"입니다. 유휴 NAT 게이트웨이, 연결되지 않은 EBS 볼륨과 탄력적 IP, 트래픽이 없는 로드 밸런서, 개발 환경의 야간 가동이 전형적인 대상입니다.

그다음이 "경로를 바꿔서 지나가지 않게 하는 것", 마지막이 "약정으로 단가를 낮추는 것"입니다. 순서가 중요합니다 — 쓰지 않아도 될 자원을 약정으로 싸게 사는 것은 절감이 아닙니다.

데이터 전송 요금의 방향성 SAA 빈출

데이터 전송은 양이 아니라 방향으로 요금이 정해집니다. 이 비대칭 하나가 비용 도메인 문항의 상당수를 설명합니다. 1장에서 개요를 봤고, 여기서는 설계 판단까지 내려갑니다.

데이터 전송 방향별 과금 여부와 설계 함의 — 금액이 아니라 방향만 다룹니다
방향 과금 설계에 주는 함의
인터넷에서 AWS로 (수신) 대체로 무료 데이터를 올리는 것은 대체로 비용 요인이 아닙니다. 마이그레이션 방향이 유리한 이유입니다
AWS에서 인터넷으로 (송신) 과금 가장 큰 전송 비용 항목입니다. 송신량 자체를 줄이거나 CloudFront로 캐시해 오리진 송신을 줄입니다
같은 가용 영역, 프라이빗 IP 가장 저렴한 경로 퍼블릭 IP나 인터넷 경유로 우회하지 않도록 프라이빗 주소로 통신하게 합니다
같은 리전, 가용 영역 간 과금 다중 가용 영역은 가용성을 사지만 전송 비용을 함께 부릅니다. 대량 트래픽이 불필요하게 가용 영역을 넘지 않도록 배치합니다
리전 간 과금 교차 리전 복제, 리전 간 백업, 다중 리전 DR은 언제나 전송 비용을 동반합니다
NAT 게이트웨이 경유 시간 요금 + 처리 데이터 요금 목적지가 어디든 통과한 모든 기가바이트에 처리 요금이 붙습니다. 지나지 않게 만드는 것이 유일한 절감입니다

비용 문항에서 데이터 전송이 나오면 확인 순서는 이렇습니다.

(1) 트래픽이 인터넷으로 나가는가 — CloudFront 캐싱으로 오리진 송신을 줄입니다. (2) 가용 영역이나 리전을 넘는가 — 넘지 않아도 되는 트래픽이면 배치를 고칩니다. (3) NAT 게이트웨이를 지나는가 — AWS 서비스가 목적지라면 VPC 엔드포인트로 경로를 바꿉니다.

반대로 "업로드 비용을 줄인다"는 선택지는 대체로 무의미합니다. 수신은 대체로 무료이기 때문입니다.

NAT 게이트웨이 비용을 VPC 엔드포인트로 줄인다

NAT 게이트웨이는 두 축으로 과금됩니다. VPC 사용 설명서는 게이트웨이가 사용 가능한 매 시간과 처리한 매 기가바이트에 요금이 부과되며, 처리 데이터 요금은 트래픽의 출발지와 목적지가 어디든 상관없이 적용된다고 명시합니다.

여기서 흔한 사고가 나옵니다. 프라이빗 서브넷의 인스턴스가 Amazon S3에서 대용량 객체를 읽으면, 그 트래픽은 같은 리전 안에 머무는데도 NAT 게이트웨이를 통과하면서 처리 요금이 붙습니다. 해결은 게이트웨이 엔드포인트로 경로를 바꾸는 것입니다.

VPC 엔드포인트 두 유형과 요금 구조
유형 대상 서비스 동작 방식 요금 구조
게이트웨이 엔드포인트 Amazon S3, Amazon DynamoDB 두 가지 라우팅 테이블에 경로를 추가합니다 사용에 대한 추가 요금이 없습니다
인터페이스 엔드포인트 (AWS PrivateLink) 대부분의 AWS 서비스와 파트너·타 계정 서비스 서브넷에 네트워크 인터페이스를 만듭니다 시간 요금 + 처리 데이터 요금

따라서 판단은 두 단계입니다. S3나 DynamoDB 트래픽이면 게이트웨이 엔드포인트가 거의 언제나 이깁니다 — 보안(인터넷 비경유)과 비용이 같은 답을 가리킵니다. 다른 서비스라면 인터페이스 엔드포인트를 쓰되, NAT 처리 요금과 엔드포인트 요금 중 어느 쪽이 큰지가 실제 판단 기준이 됩니다. 엔드포인트 자체의 동작은 4장 VPC 연결과 하이브리드에서 다룹니다.

게이트웨이 엔드포인트는 온프레미스 네트워크, 다른 리전의 피어링된 VPC, Transit Gateway를 통한 접근에는 쓸 수 없습니다. 그런 요구가 문제문에 있으면 답은 인터페이스 엔드포인트입니다. "게이트웨이 엔드포인트가 항상 더 싸니까 항상 정답"이라고 외우면 여기서 틀립니다.

CloudFront로 오리진 송신을 줄인다

Amazon CloudFront는 성능 도구로 먼저 배우지만, 비용 도메인에서도 자주 정답입니다. 이유는 단순합니다. 엣지 캐시에서 응답한 요청은 오리진까지 가지 않으므로 오리진의 인터넷 송신량 자체가 줄어듭니다.

  • 정적 자산 비중이 높고 캐시 적중률을 올릴 수 있는 워크로드일수록 효과가 큽니다.
  • Amazon S3를 오리진으로 두면 버킷에서 인터넷으로 직접 나가던 트래픽이 CloudFront 뒤로 들어갑니다.
  • 오리진 액세스 제어(OAC)로 버킷을 비공개로 유지하면 보안과 비용이 같은 방향이 됩니다.

다만 캐시할 수 없는 완전 동적 응답만 오가는 워크로드에서는 절감 효과를 기대하기 어렵습니다. "모든 트래픽에 CloudFront를 붙이면 싸진다"고 일반화하지 않습니다. CloudFront의 캐시 정책과 오리진 보호는 14장 엣지와 DNS에서 다룹니다.

컴퓨팅 약정 — 무엇을 얼마나 오래 쓸 것인가

컴퓨팅 비용을 줄이는 레버는 세 가지입니다. 덜 쓰기(라이트사이징·끄기), 싸게 사기(약정·스팟), 다른 모델로 바꾸기(서버리스·컨테이너)입니다. 이 절은 두 번째를 다룹니다.

스팟인가 약정인가 — 판단은 중단 허용 여부

둘은 경쟁 관계가 아니라 서로 다른 부분을 덮는 도구입니다. 판단 기준은 하나로 정리됩니다.

  • 중단되면 안 되는 상시 부하는 Savings Plans나 예약 인스턴스로 덮습니다. 약정은 할인을 주지만 중단으로부터 보호해 주지는 않고, 애초에 중단이 없습니다.
  • 중단되어도 되는 부분은 스팟으로 처리합니다. 스팟 인스턴스는 AWS가 용량을 회수할 수 있으므로, 중단 시 재시도되거나 다른 인스턴스가 이어받는 구조여야 합니다.
  • 실제 설계는 둘을 겹쳐 씁니다. 기저 부하는 약정으로, 급증분은 스팟과 온디맨드로 받습니다.

문제문의 단어가 곧 답입니다. "중단을 허용할 수 있다", "언제든 재시작할 수 있다", "내결함성 있는 배치 작업"이면 스팟입니다. "항상 실행되어야 한다", "지난 1년간 사용량이 일정했다"면 Savings Plans 또는 예약 인스턴스입니다.

자주 나오는 오답 두 가지를 기억합니다. 운영 데이터베이스를 스팟에 올리는 선택지는 중단 가능성 때문에 소거하고, 일회성 실험 워크로드에 3년 약정을 거는 선택지는 약정 기간 때문에 소거합니다.

"인스턴스 종류를 앞으로 바꿀 수도 있다"거나 "컨테이너와 함수까지 함께 덮고 싶다"면 Compute Savings Plans입니다. "특정 가용 영역에 용량을 확보해 두어야 한다"는 요구가 있으면 Savings Plans로는 만족시킬 수 없고 영역 예약 인스턴스 또는 온디맨드 용량 예약이 답입니다. 할인율 수치를 외우려 하지 말고 약정의 대상이 금액인가 구성인가로 구분합니다.

서버리스는 언제 싸고 언제 비싼가

"서버리스가 더 싸다"는 말은 절반만 맞습니다. 서버리스의 요금은 실행한 만큼이고, EC2의 요금은 켜 둔 만큼입니다. 그래서 두 곡선은 어딘가에서 교차합니다.

서버리스가 유리한 조건과 불리한 조건
조건 유리한가 이유
트래픽이 간헐적이고 편차가 크다 유리 요청이 없는 시간에는 요금이 발생하지 않습니다. 피크에 맞춘 상시 용량이 필요 없습니다
이벤트에 반응하는 짧은 처리 유리 실행 시간 단위로 과금되고 확장이 자동입니다
운영 인력이 적다 유리 패치·확장·가용성 관리 부담이 줄어 총소유비용이 내려갑니다
부하가 일정하고 높다 불리할 수 있음 상시 가동에 가까우면 약정 할인을 받는 EC2나 컨테이너가 오히려 저렴할 수 있습니다
실행이 길고 메모리를 많이 쓴다 불리할 수 있음 실행 시간과 메모리에 비례해 과금되므로 장시간 작업에는 맞지 않습니다. AWS Lambda의 최대 실행 시간은 900초입니다

시험이 서버리스를 정답으로 지목하는 신호는 대체로 두 가지입니다. LEAST operational overhead와 "트래픽이 예측할 수 없이 변한다"입니다. 반대로 "24시간 일정한 고부하"가 명시되면 서버리스가 자동 정답이 아니며, 약정을 건 컴퓨팅이 더 저렴한 안이 될 수 있습니다.

같은 논리가 데이터베이스에도 적용됩니다. 사용량이 급변하거나 유휴 시간이 긴 워크로드는 Amazon Aurora Serverless v2가 유리하고, 꾸준한 부하는 프로비저닝된 인스턴스에 약정을 거는 편이 낫습니다 (10장 RDS와 관계형 데이터베이스).

비용 가시성 — 세 도구의 역할이 다르다

비용 도구 문항은 이름을 외우는 문제가 아니라 "보는 것인가, 알리는 것인가, 원본 데이터를 내려받는 것인가"를 구분하는 문제입니다.

AWS Cost Explorer · AWS Budgets · Cost and Usage Report의 역할 구분
도구 무엇을 하는가 고르는 신호
AWS Cost Explorer 비용과 사용량을 시각화하고 서비스·태그·계정 등으로 나눠 봅니다. 과거 추세를 바탕으로 예측도 제공합니다 "어느 서비스에서 비용이 늘었는지 분석한다", "지난 몇 달 추이를 본다"
AWS Budgets 예산을 정하고 초과하거나 초과가 예상되면 알립니다. 비용 · 사용량 · 예약 사용률과 커버리지 · Savings Plans 사용률과 커버리지 유형이 있습니다 "임계값을 넘으면 알림을 받아야 한다", "월 예산을 초과하지 않도록 감시"
Cost and Usage Report (CUR) 가장 상세한 원본 청구 데이터를 Amazon S3에 파일로 내보냅니다. 시간·일·월 단위 granularity와 CSV 또는 Parquet 형식을 고를 수 있습니다 "자체 분석 도구나 데이터 웨어하우스로 가져간다", "가장 세밀한 라인 아이템이 필요하다"

한 문장으로 갈립니다. 보고 분석하면 Cost Explorer, 알림을 받으면 Budgets, 원본 데이터를 파일로 받으면 CUR입니다.

"예산을 초과하면 자동으로 리소스를 끈다"는 요구가 나오면 Budgets 알림을 Amazon SNS로 보내고 그것으로 동작을 트리거하는 구성이 정답 구조입니다. Budgets 자체가 리소스를 끄는 것이 아니라 알림을 발생시키는 지점이라는 점을 구분합니다.

비용을 조직 단위로 나눠 보려면 비용 할당 태그가 전제입니다. 태그가 없으면 어떤 도구를 써도 팀별 비용이 나오지 않습니다. 계정을 나누면 태그 없이도 계정 단위 집계가 되는데, 이것이 다중 계정 전략의 청구 분리 이유입니다.

라이트사이징 — Compute Optimizer와 Trusted Advisor

가장 확실한 절감은 실제로 쓰지 않는 용량을 줄이는 것입니다. 추측 대신 지표로 판단하게 해 주는 도구가 둘 있습니다.

AWS Compute Optimizer와 AWS Trusted Advisor의 역할
도구 무엇을 보는가 결과
AWS Compute Optimizer Amazon EC2 인스턴스, Auto Scaling 그룹, Amazon EBS 볼륨, AWS Lambda 함수, Fargate의 Amazon ECS 서비스, Amazon RDS 인스턴스 등의 구성과 사용률 지표 리소스를 Optimized · Overprovisioned · Underprovisioned 등으로 분류하고 대안 구성을 제안합니다
AWS Trusted Advisor 계정 전반을 모범 사례 점검 항목으로 검사합니다 — 비용 최적화 · 성능 · 보안 · 내결함성 · 서비스 한도 · 운영 우수성 여섯 범주 유휴 리소스, 낮은 사용률, 한도 접근 같은 항목을 경고합니다

Trusted Advisor는 지원 플랜에 따라 볼 수 있는 점검 항목이 달라집니다. 기본 플랜에서는 서비스 한도 범주 전체와 보안·내결함성의 일부 점검만 제공되고, 전체 점검은 상위 지원 플랜에서 열립니다. "전체 점검 결과가 보이지 않는다"는 시나리오의 원인이 대개 여기입니다.

"인스턴스 크기가 적절한지 지표로 판단해 달라"는 Compute Optimizer, "계정 전반에서 낭비와 위험을 훑어 달라"는 Trusted Advisor입니다. 두 도구 모두 제안만 하고 자동으로 바꾸지는 않습니다. "자동으로 인스턴스를 축소한다"는 선택지가 있으면 그 부분을 확인합니다.

재해 복구 4전략과 RTO · RPO SAA 빈출

재해 복구(Disaster Recovery, DR) 설계는 두 개의 요구값에서 출발합니다.

  • RTO(Recovery Time Objective, 복구 목표 시간) — 장애 발생 후 얼마나 빨리 서비스를 되살려야 하는가.
  • RPO(Recovery Point Objective, 복구 목표 시점) — 되살렸을 때 얼마만큼의 데이터 손실까지 허용되는가.

네 전략은 이 두 값과 평상시 상시 가동 비용을 맞바꾼 결과입니다. 더 짧은 RTO·RPO를 원할수록 대상 리전에 켜 두어야 하는 것이 늘어나고, 그만큼 비용이 올라갑니다.

DR 4전략의 구성과 교환 관계 — 값이 아니라 상대 순서입니다
전략 평소에 무엇이 켜져 있는가 RTO · RPO 상시 비용
백업 및 복원 백업만 다른 리전에 보관합니다. 인프라는 없습니다 가장 깁니다 가장 낮음
파일럿 라이트 데이터 복제는 계속되고, 데이터베이스 같은 핵심 코어만 최소 규모로 켜 둡니다. 애플리케이션 계층은 꺼져 있습니다 백업·복원보다 짧습니다 낮음
웜 스탠바이 전체 스택이 축소된 규모로 항상 떠 있습니다. 트래픽만 받지 않습니다 파일럿 라이트보다 짧습니다 높음
다중 사이트 액티브-액티브 양쪽이 모두 운영 트래픽을 처리합니다 가장 짧습니다 가장 높음

요구가 주어졌을 때 어떻게 고르는가

표에 숫자를 넣지 않은 이유가 있습니다. 각 전략의 RTO·RPO는 구성과 데이터 크기에 따라 달라지므로 고정된 값이 없습니다. 시험도 "파일럿 라이트의 RTO는 몇 분인가"를 묻지 않고, 주어진 요구를 만족하는 전략이 무엇인가를 묻습니다.

판단 절차는 두 단계입니다.

  • (1) 요구를 만족하지 못하는 전략을 먼저 버립니다. "거의 즉시 전환되어야 한다"면 백업 및 복원은 후보에서 빠집니다.
  • (2) 남은 것 중 가장 단순하고 저렴한 것을 고릅니다. "몇 시간까지 허용된다"는데 액티브-액티브를 고르면 과잉 설계입니다.

RPO는 데이터 복제 방식이, RTO는 무엇이 켜져 있는가가 결정합니다. 두 값이 서로 다른 레버로 조절된다는 점을 구분하면 문항이 훨씬 쉬워집니다.

DR 문항의 대부분은 비용과의 교환으로 출제됩니다. 요구를 만족하는 것 중 가장 저렴한 것이 정답이라는 순서를 지킵니다.

자주 나오는 함정이 하나 있습니다. Amazon RDS의 Multi-AZ는 DR 전략이 아닙니다. Multi-AZ는 같은 리전 안의 가용 영역 장애에 대응하는 고가용성 구성이고, 리전 전체 장애가 문제문의 전제라면 리전 간 복제나 스냅샷 복사가 필요합니다 (10장).

AWS Backup — 백업을 정책으로 중앙화한다

서비스마다 백업 기능이 따로 있으면 보존 기간과 실행 여부를 한곳에서 확인할 수 없습니다. AWS Backup은 여러 서비스의 백업을 하나의 정책과 하나의 저장소로 모읍니다.

  • 백업 계획(backup plan) — 일정과 보존 기간을 담은 규칙 문서입니다. 여기에 리소스를 태그나 리소스 유형으로 배정합니다.
  • 백업 볼트(backup vault) — 복구 지점을 담는 논리 컨테이너이며 KMS 키를 지정합니다.
  • 복사 작업 — 복구 지점을 다른 리전이나 다른 계정의 볼트로 복사합니다. DR에서 이 기능이 핵심입니다.

"여러 서비스의 백업을 중앙에서 정책으로 관리하고 규정 준수를 증명해야 한다"는 AWS Backup입니다. 서비스마다 스냅샷 자동화를 따로 만드는 선택지는 운영 부담 한정어에서 밀립니다. "백업을 다른 리전에도 두어야 한다"는 요구에는 백업 계획의 복사 작업이 답이 됩니다.

S3 복제를 DR에 쓰는 판단

S3 교차 리전 복제와 동일 리전 복제의 용도 구분
유형 대상 쓰는 이유
교차 리전 복제(CRR) 다른 리전의 버킷 리전 장애 대비, 지리적으로 먼 사용자에게 지연 감소, 데이터 레지던시 요구를 만족하는 사본 유지
동일 리전 복제(SRR) 같은 리전의 다른 버킷 로그 집계, 계정 분리(운영 계정에서 감사 계정으로), 운영 환경과 테스트 환경의 데이터 동기화

복제를 켜려면 원본과 대상 버킷 모두 버전 관리가 활성화되어 있어야 하고, Amazon S3가 대신 복제할 수 있도록 IAM 역할을 지정해야 합니다. 기본적으로 규칙을 켠 뒤에 들어온 객체만 복제되며, 이미 있던 객체는 배치 복제로 따로 처리합니다. SSE-KMS로 암호화된 객체를 리전 간 복제할 때는 대상 리전에서 복호화할 수 있는 키가 있어야 합니다. 복제 규칙의 세부 동작은 8장 S3와 오브젝트 스토리지에서 다룹니다.

마이그레이션 — 전략과 도구

6R 전략

온프레미스 워크로드를 클라우드로 옮길 때 선택지는 여섯 가지로 정리됩니다. 코드 변경량과 얻는 것이 서로 반대 방향으로 움직인다는 것이 핵심입니다.

6R 마이그레이션 전략과 선택 신호
전략 무엇을 하는가 선택 신호
Rehost (리호스트) 애플리케이션을 그대로 옮깁니다. 리프트 앤 시프트 "최소한의 변경으로", "빠르게 데이터센터를 비워야 한다", "다운타임 최소화"
Replatform (리플랫폼) 핵심 구조는 두고 일부를 관리형으로 바꿉니다. 자체 관리 DB를 Amazon RDS로 옮기는 식 "코드는 크게 바꾸지 않으면서 운영 부담을 줄인다"
Repurchase (리퍼처스) 기존 제품을 버리고 다른 제품이나 SaaS로 갈아탑니다 "라이선스를 종료하고 구독형으로 전환한다"
Refactor (리팩터) 아키텍처를 다시 설계합니다. 서버리스·마이크로서비스로 재작성 "확장성과 기능 추가 속도가 지금 구조로는 안 나온다"
Retire (리타이어) 더 이상 필요 없는 시스템을 없앱니다 "조사해 보니 아무도 쓰지 않는다"
Retain (리테인) 지금은 옮기지 않고 그대로 둡니다 "규제나 의존성 때문에 아직 옮길 수 없다"

시험은 여섯 개를 다 묻지 않고 주로 앞의 네 개를 구분하게 합니다. minimal downtime과 "변경 없이"가 붙으면 Rehost, "운영 부담을 줄이되 재작성은 하지 않는다"면 Replatform, "서버리스로 다시 만든다"면 Refactor입니다.

Retire를 잊지 않는 것도 중요합니다. "옮기기 전에 사용 현황을 조사한다"는 선택지가 보이면, 그것이 가장 큰 비용 절감이 되는 경우가 실제로 많습니다.

AWS DMS와 AWS Application Migration Service

마이그레이션 도구 두 가지의 대상과 용도
도구 무엇을 옮기는가 특징
AWS Database Migration Service (DMS) 데이터베이스 Oracle · PostgreSQL · SQL Server · MySQL · MariaDB · Amazon Aurora · Amazon Redshift 등을 지원하며, 같은 엔진 간 동종 마이그레이션과 다른 엔진으로의 이기종 마이그레이션을 모두 처리합니다. 원본을 계속 운영하면서 변경분을 따라잡을 수 있어 전환 다운타임을 줄입니다
AWS Application Migration Service (MGN) 서버 전체 물리·가상 서버를 블록 수준으로 복제해 Amazon EC2 인스턴스로 전환합니다. 대표적인 Rehost 도구입니다

AWS Server Migration Service(SMS)는 AWS Application Migration Service(MGN)로 대체되었습니다. 옛 자료에서 서버 마이그레이션 도구로 SMS를 소개하는 경우가 있는데, 현재 기준의 이름은 Application Migration Service입니다.

이기종 데이터베이스 마이그레이션에서 스키마와 코드를 변환하는 도구는 현재 DMS 안의 스키마 변환 기능으로 제공됩니다. 별도 제품이던 시절의 이름으로 외우지 않습니다.

대용량 데이터 전송 — 대역폭과 기간이 기준이다

"수백 테라바이트를 어떻게 옮길 것인가"는 SAA의 단골 시나리오입니다. 판단 축은 두 개뿐입니다 — 가용 대역폭과 허용 기간, 그리고 그 전송이 일회성인지 지속적인지입니다.

대용량 전송 수단의 선택 기준
수단 성격 고르는 신호
AWS Snow Family 물리 장치를 배송받아 데이터를 담아 되돌려 보내는 오프라인 전송입니다. AWS Snowcone과 AWS Snowball Edge가 있고, 일부 장치는 현장에서 컴퓨팅도 수행합니다 "네트워크 대역폭이 부족하다", "회선으로는 몇 달이 걸린다", "네트워크가 불안정하거나 없는 현장"
AWS DataSync 네트워크를 통해 파일·객체 데이터를 온라인으로 옮기고 동기화합니다 "쓸 만한 대역폭이 있다", "주기적으로 동기화해야 한다", "온프레미스 NFS·SMB에서 Amazon S3·EFS·FSx로"
AWS Direct Connect 온프레미스와 AWS를 잇는 전용 회선입니다. 전송 도구가 아니라 경로입니다 "지속적으로 대량을 주고받는다", "일관된 네트워크 성능이 필요하다", "인터넷을 거치면 안 된다"

세 가지는 대체재가 아니라 층이 다릅니다. Direct Connect는 회선이고 DataSync는 그 위를 흐르는 전송 도구이며, Snow Family는 회선을 쓰지 않는 대안입니다. 실제 설계에서 Direct Connect 위에서 DataSync를 돌리는 조합이 흔합니다.

한 가지 더 기억합니다. Direct Connect는 주문하고 설치하는 데 시간이 걸립니다. "다음 주까지 옮겨야 한다"는 제약이 붙으면 Direct Connect 신규 구축은 답이 되기 어렵고, Snow Family나 기존 회선 위의 DataSync가 남습니다. 각 수단의 세부 동작은 9장 파일 스토리지와 데이터 전송과 4장 VPC 연결과 하이브리드에서 다룹니다.

흔한 오해

"데이터 전송은 양이 같으면 요금도 같다" — 요금은 방향으로 정해집니다. 같은 1테라바이트라도 인터넷에서 AWS로 들어오는 것은 대체로 무료이고, AWS에서 인터넷으로 나가는 것은 과금 대상이며, 가용 영역을 넘거나 리전을 넘으면 또 다른 항목이 붙습니다. NAT 게이트웨이를 통과하면 목적지가 같은 리전 안이라도 처리 요금이 붙습니다. 비용 문항을 풀 때 가장 먼저 그릴 것은 금액이 아니라 화살표의 방향입니다.

"서버리스로 바꾸면 항상 싸진다" — 서버리스는 실행한 만큼 과금되므로 유휴 시간이 길고 편차가 클 때 유리합니다. 반대로 24시간 일정한 고부하는 약정 할인을 받는 컴퓨팅이 더 저렴할 수 있습니다. 시험에서 "일정한 부하"가 명시되어 있는데 서버리스를 고르는 것은 한정어를 읽지 않은 선택입니다.

"Multi-AZ 구성이면 재해 복구가 된다" — Multi-AZ는 같은 리전 안의 가용 영역 장애에 대응하는 고가용성 구성입니다. 문제문이 리전 전체 장애를 전제로 하면 Multi-AZ만으로는 요구를 만족하지 못하고, 리전 간 복제나 스냅샷 복사, 그 위에 얹은 DR 전략이 필요합니다. 같은 이유로 백업만 있고 복원 절차를 시험해 본 적이 없는 구성도 DR이 아닙니다 — RTO는 복원에 걸리는 실제 시간으로 결정되기 때문입니다.

시험 포인트 정리

이 장은 비용 최적화 아키텍처 설계(20%) 전체와 복원력 있는 아키텍처 설계(26%)의 재해 복구 부분에 걸쳐 있습니다.
