기본개념 · 11장

NoSQL · 캐시 · 분석 DB

10장이 관계형 데이터베이스를 다뤘다면, 이 장은 관계형이 답이 아닐 때 무엇을 고르는가를 다룹니다. Amazon DynamoDB의 설계 판단, 캐시 계층을 어디에 둘지, 분석 질의를 어디로 보낼지가 축입니다. 시험은 서비스 이름을 묻지 않고 요구사항에서 서비스로 가는 경로를 묻습니다.

주 도메인은 고성능 아키텍처 설계(24%)이며, 용량 모드와 캐시 도입 판단은 비용 최적화 아키텍처 설계에도 걸칩니다.

학습 목표

  • DynamoDB의 파티션 키가 데이터 분포를 결정한다는 원리로 핫 파티션의 원인과 해법을 설명할 수 있습니다.
  • 로컬 보조 인덱스와 글로벌 보조 인덱스를 생성 시점 · 키 범위 · 일관성 · 용량 네 가지 축으로 구분할 수 있습니다.
  • 온디맨드 용량 모드와 프로비저닝된 용량 모드를 워크로드의 예측 가능성으로 가를 수 있습니다.
  • DynamoDB 스트림 · DAX · 글로벌 테이블 · TTL이 각각 어떤 요구사항에 대응하는지 설명할 수 있습니다.
  • ElastiCache의 Redis와 Memcached를 기능 요구로 구분하고, 캐시 계층을 어디에 둘지 고를 수 있습니다.
  • Amazon Redshift와 목적별 데이터베이스(DocumentDB · Neptune · Keyspaces · Timestream)의 용도를 한 문장으로 구분할 수 있습니다.

Amazon DynamoDB — 키로 접근하는 관리형 NoSQL

DynamoDB는 키-값과 문서 모델을 지원하는 완전 관리형 NoSQL 데이터베이스입니다. 서버를 프로비저닝하지 않고, 스토리지는 데이터가 늘어나면 알아서 커집니다. 관계형 데이터베이스와의 결정적 차이는 조인이 없다는 점이고, 그래서 접근 패턴을 먼저 정하고 그에 맞춰 키를 설계합니다.

테이블 · 항목 · 기본 키

기본 키는 두 형태 중 하나입니다. 단순 키는 파티션 키 하나이고, 복합 키는 파티션 키와 정렬 키의 조합입니다. DynamoDB API 문서는 각 키의 역할을 이렇게 정의합니다.

DynamoDB 기본 키를 구성하는 두 가지 키
키 API 값 역할
파티션 키 HASH 내부 해시 함수의 입력이 되어 항목을 파티션에 고르게 분배합니다. 해시 속성이라고도 부릅니다
정렬 키 RANGE 같은 파티션 키를 가진 항목들을 정렬 키 순서로 물리적으로 가까이 저장합니다. 범위 조회의 근거가 됩니다

이 정의 안에 이미 설계 규칙이 들어 있습니다. 파티션 키는 분배를 담당하고 정렬 키는 범위 조회를 담당합니다. "특정 사용자의 최근 주문 20건"처럼 하나의 파티션 안에서 시간순으로 잘라 오는 질의는 복합 키로 자연스럽게 풀립니다.

파티션 키 설계와 핫 파티션 SAA 빈출

DynamoDB 개발자 안내서는 원칙을 한 문장으로 정리합니다 — "테이블과 보조 인덱스의 모든 논리 파티션 키에 걸쳐 활동이 고르게 일어나도록 설계하라." 같은 문서는 고르지 못한 분배가 만드는 결과를 이렇게 설명합니다. "I/O 요청을 고르게 분배하지 못하는 파티션 키 설계는 '핫' 파티션을 만들어 스로틀링을 유발하고 프로비저닝된 용량을 비효율적으로 쓰게 한다."

무엇이 좋은 키이고 무엇이 나쁜 키인지도 같은 문서가 표로 제시합니다.

파티션 키 값의 분포 균일성 — DynamoDB 개발자 안내서의 비교
파티션 키 값 균일성 왜 그런가
사용자 ID (사용자가 많은 애플리케이션) 좋음 값의 가짓수가 많고 요청이 여러 값으로 흩어집니다

생성 일시를 일 · 시간 단위로 반올림한 값 나쁨 같은 날에 들어온 모든 신규 항목이 하나의 파티션 키 값으로 몰립니다
디바이스 ID (디바이스들이 비슷한 간격으로 접근) 좋음 가짓수가 많고 트래픽이 고릅니다
디바이스 ID (한 대가 압도적으로 인기) 나쁨 가짓수가 많아도 실제 트래픽이 한 값에 쏠리면 소용없습니다

마지막 두 줄이 시험이 좋아하는 지점입니다. 키의 가짓수가 많다는 것만으로는 충분하지 않습니다. 실제 접근이 몇 개 값에 쏠리면 그 값이 핫 파티션이 됩니다.

쓰기 샤딩 — 접미사로 흩뿌린다

날짜를 파티션 키로 쓸 수밖에 없는 구조라면 쓰기 샤딩(write sharding)을 씁니다. 파티션 키 값에 계산된 접미사를 붙여 하나의 논리 키를 여러 개로 쪼개는 방법입니다. 읽을 때는 접미사 범위를 돌며 질의를 합치면 됩니다.

생성 일자를 그대로 파티션 키로 씁니다. 그날의 모든 쓰기가 하나의 파티션 키 값으로 들어가 테이블 전체 용량을 다 쓰기 전에 스로틀링이 시작됩니다.

같은 날짜에 접미사를 붙여 쓰기를 여러 파티션 키 값으로 흩뜨립니다. 읽을 때는 접미사 0부터 N까지 질의해 결과를 합칩니다.

DynamoDB에는 적응 용량(adaptive capacity)도 있습니다. 개발자 안내서는 이 기능이 모든 테이블에서 추가 비용 없이 자동으로 켜져 있으며 불균형한 워크로드를 감당해 스로틀링을 줄인다고 설명합니다. 다만 적응 용량이 나쁜 키 설계를 대신 고쳐 주지는 않습니다. 설계가 먼저이고 적응 용량은 완충 장치입니다.

"DynamoDB 테이블에서 스로틀링이 발생한다"는 시나리오는 거의 언제나 파티션 키 설계 문항입니다. 정답 후보는 카디널리티가 높은 파티션 키로 바꾼다, 접미사로 쓰기를 분산한다, 읽기가 몰리는 소수 항목이면 DAX를 앞에 둔다입니다.

오답으로 자주 나오는 것이 프로비저닝된 용량을 크게 올린다입니다. 한 파티션에 트래픽이 몰린 상황에서는 테이블 전체 용량을 올려도 그 파티션이 감당할 수 있는 몫은 그만큼 늘지 않아 문제가 남습니다.

LSI와 GSI SAA 빈출

기본 키가 아닌 속성으로 조회해야 하면 보조 인덱스를 만듭니다. 종류는 둘이고, 이름의 "로컬"과 "글로벌"이 곧 차이의 요약입니다.

  • 로컬 보조 인덱스(Local Secondary Index, LSI) — 파티션 키가 기본 테이블과 같고 정렬 키만 다릅니다. 인덱스의 각 파티션이 같은 파티션 키 값을 갖는 기본 테이블 파티션에 묶여 있어서 "로컬"입니다.
  • 글로벌 보조 인덱스(Global Secondary Index, GSI) — 파티션 키와 정렬 키를 기본 테이블과 다르게 잡을 수 있습니다. 인덱스에 대한 질의가 기본 테이블의 모든 파티션에 걸친 데이터를 대상으로 하므로 "글로벌"입니다.
로컬 보조 인덱스와 글로벌 보조 인덱스 비교
항목 LSI (로컬 보조 인덱스) GSI (글로벌 보조 인덱스)
생성 시점 테이블을 만들 때만. 나중에 추가도 삭제도 불가 테이블 생성 시 또는 나중에 언제든 추가·삭제
파티션 키 기본 테이블과 같아야 합니다 기본 테이블과 달라도 됩니다
키 구성 반드시 복합 키 (파티션 키 + 정렬 키) 단순 키 또는 복합 키 모두 가능
읽기 일관성 최종 일관성과 강력한 일관성 중 선택 최종 일관성만. 강력한 일관성 요청 시 오류
용량 기본 테이블의 용량을 함께 씁니다 자체 용량 설정을 갖습니다
개수 상한 테이블당 5개 테이블당 20개 (기본 할당량)
크기 제약 파티션 키 값당 인덱싱된 항목 총합 10 GB 이하 크기 제약 없음
질의 범위 질의에 지정한 파티션 하나 모든 파티션에 걸친 테이블 전체
프로젝션되지 않은 속성 요청하면 DynamoDB가 테이블에서 가져다 줍니다 프로젝션된 속성만 받을 수 있습니다

표에서 가장 자주 출제되는 두 줄은 생성 시점과 읽기 일관성입니다. DynamoDB API 문서를 보면 근거가 구조에 남아 있습니다 — 기존 테이블을 바꾸는 UpdateTable 작업에는 글로벌 보조 인덱스를 추가·수정·삭제하는 파라미터만 있고 로컬 보조 인덱스를 다루는 파라미터가 없습니다. 같은 API 문서는 글로벌 보조 인덱스에 강력한 일관성 읽기를 요청하면 ValidationException을 받는다고 명시합니다.

판단 순서는 이렇습니다.

  • 이미 운영 중인 테이블에 새 조회 패턴이 필요 → GSI. LSI는 이제 만들 수 없습니다.
  • 파티션 키는 그대로 두고 다른 정렬 순서만 필요 + 강력한 일관성 필요 → LSI. 단 테이블을 만들 때 함께 만들어 두었어야 합니다.
  • 완전히 다른 속성으로 검색 → GSI. LSI는 파티션 키를 바꿀 수 없습니다.
  • 인덱스가 테이블 용량을 잠식하면 안 됨 → GSI. 자체 용량을 갖습니다.

"강력한 일관성이 필요한데 GSI를 쓴다"는 선택지는 항상 오답입니다.

용량 모드 — 온디맨드와 프로비저닝

DynamoDB의 처리량 과금 방식은 두 가지이고, API 파라미터 이름과 표시 이름이 다르므로 함께 외웁니다.

DynamoDB 용량 모드의 API 값과 성격
모드 API 값 AWS의 권장 기준
온디맨드 용량 모드 PAY_PER_REQUEST API 문서가 "대부분의 DynamoDB 워크로드에 권장"한다고 명시합니다
프로비저닝된 용량 모드 PROVISIONED "용량 요구를 신뢰성 있게 예측할 수 있는, 예측 가능한 성장세의 안정적인 워크로드"에 권장합니다

결정적인 사실이 하나 더 있습니다 — 이 설정은 나중에 바꿀 수 있습니다. API 문서가 BillingMode에 대해 "이 설정은 나중에 변경할 수 있다"고 적어 두었습니다. 따라서 "처음에는 패턴을 모르니 온디맨드로 시작하고, 패턴이 안정되면 프로비저닝으로 옮긴다"는 전략이 성립합니다.

프로비저닝된 모드에서는 Auto Scaling을 붙여 목표 사용률을 유지하도록 용량을 자동으로 조절할 수 있습니다. 다만 오토스케일링은 지표를 보고 반응하므로 수 초 만에 몇십 배로 뛰는 급증에는 늦을 수 있습니다. 그런 워크로드는 온디맨드가 맞습니다.

용량 모드 선택의 판단 기준
요구사항의 신호 선택
트래픽 패턴을 모른다 · 새 애플리케이션이다 온디맨드
급증이 갑작스럽고 예측할 수 없다 온디맨드 — 오토스케일링의 반응 지연을 피합니다
사용량이 드물고 대부분 유휴다 온디맨드 — 쓰지 않는 용량에 돈을 내지 않습니다
부하가 안정적이고 예측 가능하다 프로비저닝 + 오토스케일링
비용을 상한선 안에서 통제해야 한다 프로비저닝 — 용량 상한이 곧 비용 상한이 됩니다

MOST cost-effective가 붙었다고 반사적으로 한쪽을 고르지 않습니다. "예측할 수 없는" · "산발적인" · "새로운"이면 온디맨드, "일정한" · "예측 가능한" · "상시"면 프로비저닝입니다. 이것은 5장 EC2 구매 옵션의 판단 축과 정확히 같은 구조입니다.

읽기 일관성 옵션

DynamoDB의 읽기는 기본이 최종 일관성(eventually consistent)이고, 요청마다 ConsistentRead를 true로 주면 강력한 일관성(strongly consistent) 읽기가 됩니다.

DynamoDB 읽기 일관성 선택
항목 최종 일관성 읽기 (기본) 강력한 일관성 읽기
방금 쓴 값 이전 값이 보일 수 있습니다 최신 값이 보장됩니다
소비 용량 더 적습니다 더 많습니다
GSI에서 사용 가능 사용 불가 — 요청하면 오류가 반환됩니다
DAX를 거칠 때 캐시에서 응답합니다 캐시를 쓰지 못하고 DynamoDB로 전달됩니다

시험에서는 "읽은 값이 최신임이 보장되어야 한다"는 문장이 신호입니다. 이 조건이 붙으면 GSI로 조회하는 선택지와 DAX로 가속하는 선택지가 함께 소거됩니다. 강력한 일관성 요구는 캐시와 GSI를 동시에 무력화한다는 것이 요점입니다.

DynamoDB 스트림 — 변경을 이벤트로 바꾼다

스트림을 켜면 항목이 추가 · 수정 · 삭제될 때마다 변경 레코드가 시간 순서대로 쌓입니다. AWS Lambda를 붙이면 변경에 반응하는 처리를 이벤트 기반으로 만들 수 있습니다 — 집계 테이블 갱신, 알림 발송, 검색 색인 갱신이 전형적인 용도입니다.

스트림에 무엇을 담을지는 뷰 타입으로 정합니다. 네 가지입니다.

DynamoDB 스트림의 뷰 타입
뷰 타입 스트림에 담기는 것 언제 고르는가
KEYS_ONLY 변경된 항목의 키 속성만 무엇이 바뀌었는지만 알면 되고, 본문은 다시 읽어도 될 때
NEW_IMAGE 변경 후의 항목 전체 바뀐 결과만 필요할 때
OLD_IMAGE 변경 전의 항목 전체 삭제된 항목을 보존하거나 이전 값을 감사할 때
NEW_AND_OLD_IMAGES 변경 전과 후 모두 차이를 계산해야 할 때. 재고 증감 같은 집계가 대표적입니다

DAX — DynamoDB 전용 인메모리 캐시

Amazon DynamoDB Accelerator(DAX)는 DynamoDB API와 호환되는 캐싱 서비스입니다. DynamoDB 개발자 안내서가 정리한 성격은 세 가지입니다.

  • 최종 일관성 읽기의 응답 시간을 한 자릿수 밀리초에서 마이크로초 수준으로 낮춥니다.
  • DynamoDB와 API 호환이므로 기존 애플리케이션에 최소한의 기능 변경만으로 붙습니다.
  • 읽기가 많거나 폭발적인 워크로드에서 읽기 용량을 과잉 프로비저닝할 필요를 줄입니다.

내부에는 두 개의 캐시가 있습니다. 항목 캐시는 GetItem·BatchGetItem의 결과를 기본 키로 저장하고, 질의 캐시는 Query·Scan의 결과 집합을 파라미터 값으로 저장합니다. 둘 다 TTL과 LRU 축출이 함께 동작하며, TTL은 클러스터를 만들 때 지정합니다.

같은 문서는 DAX가 적합하지 않은 경우도 명시합니다. 이 목록이 사실상 오답 소거 기준입니다.

  • 강력한 일관성 읽기가 필요한 애플리케이션. DAX가 제공하는 것은 최종 일관성 데이터입니다.
  • 마이크로초 수준의 응답이 필요 없거나, 반복 읽기를 덜어낼 필요가 없는 경우.
  • 쓰기 위주이거나 읽기가 거의 없는 워크로드.
  • 이미 다른 캐싱 솔루션을 클라이언트 로직으로 쓰고 있는 경우.

고가용성을 위해서는 여러 노드로 클러스터를 구성합니다. DAX API 문서는 노드 수가 1이면 복제본 없는 단일 노드 클러스터가 되고, 내결함성이 필요하면 프라이머리 1대와 읽기 복제본을 둔 다중 노드로 만들라고 안내합니다.

"DynamoDB 읽기 지연을 마이크로초 수준으로 줄여라" + "애플리케이션 코드 변경을 최소화하라" → DAX입니다.

같은 문항에서 Amazon ElastiCache가 오답으로 나오는 이유는 캐시 채우기와 무효화 로직을 애플리케이션이 직접 짜야 하기 때문입니다. 반대로 문제문에 "강력한 일관성"이 들어 있으면 DAX 자체가 소거 대상이 됩니다.

글로벌 테이블 — 다중 리전 다중 활성

글로벌 테이블은 여러 리전에 같은 이름의 테이블을 두고 서로 복제하는 구성입니다. 각 리전의 복제본이 읽기와 쓰기를 모두 받는다는 점에서 주 리전에서만 쓰기를 받는 Aurora 글로벌 데이터베이스와 다릅니다.

복제본으로 추가하려면 조건이 있습니다. API 문서 기준으로 같은 테이블 이름 · 같은 기본 키 · 스트림 활성화가 필요합니다. 복제가 스트림 위에서 동작하기 때문입니다.

글로벌 테이블에는 버전이 두 가지이며, API 문서는 현재 버전인 2019.11.21을 쓰라고 권장하고 레거시인 2017.11.29는 신규 구성에서 피하라고 명시합니다. 현재 버전이 유연성과 효율이 낫고 쓰기 용량도 덜 씁니다. 옛 자료에서 "글로벌 테이블은 리전마다 별도 테이블을 만들어 묶는다"고 설명한다면 레거시 버전 기준입니다.

TTL — 만료된 항목을 지운다

TTL(Time to Live)은 항목에 담긴 만료 시각 속성을 기준으로 지난 항목을 자동으로 삭제하는 기능입니다. 속성 값은 에포크 시간(초)이어야 하며, 현재 시각보다 작으면 만료로 표시됩니다.

중요한 성질이 두 가지입니다. 첫째, 삭제는 최선 노력(best-effort)입니다. API 문서는 다른 데이터 작업의 처리량을 보장하기 위해 최선 노력으로 삭제하며 대체로 만료 후 이틀 안에 지운다고 명시합니다. 정확한 시각에 사라지지 않습니다. 둘째, TTL 삭제는 쓰기 용량을 소비하지 않습니다.

세션 데이터, 임시 토큰, 로그처럼 수명이 정해진 데이터를 비용 없이 정리하는 것이 용도입니다. "오래된 항목을 지우는 배치 작업을 매일 돌린다"는 선택지가 있으면 TTL이 더 나은 답입니다.

Amazon ElastiCache — Redis와 Memcached

ElastiCache는 인메모리 캐시를 관리형으로 제공합니다. DAX가 DynamoDB 앞에만 붙는 전용 캐시인 것과 달리, ElastiCache는 어떤 데이터 소스 앞에도 놓을 수 있는 범용 캐시입니다. 대신 무엇을 캐시하고 언제 무효화할지는 애플리케이션이 책임집니다.

선택 기준 — 기능이 필요한가, 단순함이 필요한가

두 엔진의 차이는 API 구조에 그대로 드러납니다. Redis 쪽에는 복제 그룹 · 자동 장애 조치 · 스냅샷 · 샤드 재구성 API가 있고, Memcached 쪽에는 그런 API가 없습니다.

ElastiCache 엔진 선택 기준
요구 Redis Memcached
데이터 구조 목록 · 집합 · 정렬된 집합 · 해시 등 풍부한 자료구조 단순 키-값 문자열
복제와 읽기 확장 복제 그룹 — 프라이머리 1대와 읽기 전용 복제본들. 쓰기는 비동기로 전파 복제 없음. 노드끼리 데이터를 공유하지 않습니다
자동 장애 조치 지원 — 복제본이 프라이머리로 승격됩니다 없음. 노드가 죽으면 그 노드의 데이터가 사라집니다
백업(스냅샷) 지원 불가 — 스냅샷 API가 Redis 계열에서만 유효합니다
저장 시 암호화 · 전송 중 암호화 지원 해당 파라미터가 Redis 계열 전용입니다
수평 확장 방식 클러스터 모드에서 샤드로 나눕니다 노드를 늘려 메모리 풀을 키웁니다 (여러 가용 영역에 배치 가능)
멀티스레드 단일 스레드 중심 멀티스레드 — 단순 캐시 작업에서 코어를 더 씁니다
전형적인 용도 세션 저장소, 리더보드, 순위 계산, 지속성이 필요한 캐시, 발행·구독 단순 객체 캐시, 잃어버려도 되는 데이터, 수평으로 크게 키우는 캐시 풀

정리하면 기본값은 Redis이고, Memcached는 "가장 단순한 캐시 풀이면 충분하다"가 명시될 때 고릅니다. 시험 문항에서 지속성 · 복제 · 장애 조치 · 스냅샷 · 자료구조 중 하나라도 요구되면 Memcached는 그 자리에서 소거됩니다.

ElastiCache API의 Engine 파라미터는 오랫동안 memcached와 redis 두 값을 받아 왔고, 최근 문서는 Redis 계열을 Valkey 또는 Redis OSS로 표기합니다. 시험이 묻는 판단은 여전히 Redis 계열이냐 Memcached냐이므로, 이 장에서도 그 축으로만 다룹니다.

캐시 계층 선택 — 무엇을 언제 SAA 빈출

"읽기가 느리다"는 같은 증상에 네 가지 처방이 붙습니다. ElastiCache · DAX · 읽기 전용 복제본 · Amazon CloudFront. 이 넷을 가르는 기준은 성능 수치가 아니라 데이터가 어디에 있고, 누가 캐시 로직을 책임지며, 무엇을 캐시하는가입니다.

읽기 지연을 줄이는 네 가지 수단의 적용 조건
수단 무엇을 가속하는가 고르는 신호 한계
Amazon CloudFront 사용자와 오리진 사이의 HTTP 응답 전 세계 사용자, 정적 콘텐츠, 반복되는 동일 요청 데이터베이스 질의 자체를 줄이지는 않습니다. HTTP 계층에서만 동작합니다
Amazon ElastiCache 임의의 데이터 소스의 조회 결과 계산 비용이 큰 질의, 세션 저장소, 관계형 데이터베이스 앞의 캐시 캐시 채우기와 무효화를 애플리케이션이 구현해야 합니다
DAX DynamoDB의 읽기 DynamoDB를 쓰고 있고 코드 변경을 최소화하고 싶을 때 DynamoDB 전용이며 최종 일관성 데이터만 제공합니다
읽기 전용 복제본 관계형 데이터베이스의 읽기 처리량 읽기 질의가 다양해 캐시 적중률이 낮을 때, 분석 질의를 분리할 때 복제 지연이 있고, 읽기를 복제본으로 보내도록 애플리케이션 수정이 필요합니다

캐시를 도입하기로 했다면 채우기 전략도 함께 정해야 합니다. 전략은 크게 둘이고, 각각의 대가가 분명합니다.

캐시 채우기 전략의 교환 조건
전략 동작 대가
지연 로딩(lazy loading) 캐시에 없을 때만 원본에서 읽어 와 채웁니다 요청되지 않은 데이터는 캐시에 들어가지 않아 메모리가 절약되지만, 첫 요청은 항상 느리고 오래된 값이 남을 수 있습니다
라이트 스루(write-through) 쓰기가 일어날 때 캐시도 함께 갱신합니다 캐시가 항상 최신에 가깝지만, 읽히지 않을 데이터까지 캐시를 차지하고 쓰기 경로가 무거워집니다

둘을 TTL과 함께 섞어 쓰는 것이 실무의 기본형입니다. 지연 로딩으로 채우되 TTL을 걸어 오래된 값이 무한히 남지 않게 하는 방식입니다.

캐시 문항은 데이터 소스로 먼저 가르면 절반이 정리됩니다.

  • 소스가 DynamoDB이고 코드 변경 최소화 → DAX
  • 소스가 RDS나 Aurora이고 같은 질의가 반복 → ElastiCache
  • 소스가 RDS나 Aurora인데 질의가 제각각 → 읽기 전용 복제본
  • 소스가 S3나 웹 오리진이고 사용자가 전 세계 → CloudFront
  • 강력한 일관성이 요구된다 → 캐시 계열은 전부 소거

엣지 캐싱의 동작은 14장 엣지와 DNS에서, 읽기 전용 복제본의 성질은 10장에서 다룹니다.

Amazon Redshift — 데이터 웨어하우스

Redshift는 열 지향 저장과 대규모 병렬 처리를 쓰는 데이터 웨어하우스입니다. 운영 데이터베이스가 한 건을 빠르게 읽고 쓰는 일(OLTP)에 최적화되어 있다면, Redshift는 수억 건을 스캔해 집계하는 일(OLAP)에 최적화되어 있습니다. 같은 데이터를 다루더라도 목적이 다릅니다.

운영 데이터베이스와 Amazon Redshift의 성격 차이
항목 Amazon RDS · Aurora (OLTP) Amazon Redshift (OLAP)
전형적인 질의 키로 몇 건을 읽고 쓰는 트랜잭션 넓은 범위를 스캔해 집계하는 분석 질의
저장 방식 행 지향 열 지향 — 필요한 열만 읽어 스캔량을 줄입니다
확장 구조 인스턴스 크기와 복제본 리더 노드와 여러 컴퓨트 노드로 질의를 병렬 처리합니다
클러스터 구성 해당 없음 API의 ClusterType이 single-node 또는 multi-node입니다
저장 시 암호화 생성 시점에 결정 API의 Encrypted 기본값이 참이며 거짓으로 두려는 요청은 실패합니다

시험에서 Redshift와 자주 붙는 오답이 Amazon Athena입니다. 경계는 이렇습니다 — S3에 있는 데이터를 그때그때 SQL로 조회하면 Athena, 여러 소스를 정기적으로 적재해 두고 반복적으로 분석하면 Redshift입니다. 분석 파이프라인 전체는 15장 데이터 분석 파이프라인에서 다룹니다.

목적별 데이터베이스 — 한 줄 정의

아래 네 가지는 깊이 파고들 대상이 아닙니다. 시험에서는 데이터 모델을 묘사한 문장에서 서비스 이름을 떠올릴 수 있는지만 물어봅니다. 정의 한 줄과 신호 단어를 짝지어 외우면 충분합니다.

목적별 데이터베이스의 용도와 문제문의 신호
서비스 한 줄 정의 문제문의 신호
Amazon DocumentDB MongoDB 호환 문서 데이터베이스 "MongoDB로 만든 애플리케이션을 관리형으로 옮기고 싶다"
Amazon Neptune 그래프 데이터베이스 "소셜 네트워크", "추천", "사기 탐지", "관계를 여러 단계로 따라가는 질의"
Amazon Keyspaces Apache Cassandra 호환 와이드 컬럼 데이터베이스 "Cassandra 워크로드를 서버 관리 없이 운영하고 싶다", "CQL"
Amazon Timestream 시계열 데이터베이스 "IoT 센서 측정값", "시간 순서로 쌓이는 지표를 기간별로 집계"

이 네 서비스가 정답인 문항은 데이터 모델을 그대로 말해 줍니다. "관계를 탐색한다"고 쓰여 있으면 그래프, "센서가 시간마다 값을 보낸다"면 시계열입니다. 반대로 모델이 명시되지 않은 채 "확장 가능한 NoSQL"만 나오면 DynamoDB가 기본값입니다. 호환성 요구(MongoDB · Cassandra)가 명시될 때만 DocumentDB와 Keyspaces가 답이 됩니다.

흔한 오해

"LSI와 GSI는 이름만 다르고 나중에 아무거나 추가하면 된다" — 로컬 보조 인덱스는 테이블을 만들 때만 생성할 수 있고, 이후에는 추가도 삭제도 할 수 없습니다. 이미 운영 중인 테이블에 새 조회 패턴이 필요하다면 선택지는 GSI뿐입니다. 거꾸로 강력한 일관성 읽기는 LSI에서만 가능하므로, 그 요구가 나중에 생기면 테이블을 다시 만드는 것 외에 방법이 없습니다. 인덱스 설계는 테이블을 만들기 전에 끝내야 합니다.

"프로비저닝된 용량을 올리면 스로틀링이 사라진다" — 트래픽이 한 파티션 키 값에 몰려 있으면 테이블 전체 용량을 올려도 그 파티션이 받는 몫은 비례해서 늘지 않습니다. 적응 용량이 어느 정도 완충해 주지만 나쁜 키 설계를 대신 고쳐 주지는 않습니다. 해법은 카디널리티가 높은 파티션 키, 접미사를 이용한 쓰기 분산, 그리고 읽기가 몰릴 때의 DAX입니다.

"캐시를 붙이면 언제나 빨라진다" — 캐시는 같은 데이터를 반복해서 읽을 때만 효과가 있습니다. 질의가 매번 달라 적중률이 낮으면 캐시는 지연 한 겹을 더할 뿐입니다. 그리고 강력한 일관성이 요구되면 캐시는 답이 될 수 없습니다 — DAX는 최종 일관성 데이터만 제공하고, 강력한 일관성 읽기는 캐시를 지나쳐 DynamoDB로 전달됩니다. 질의가 다양한 읽기 부하는 캐시가 아니라 읽기 전용 복제본이 맞는 처방입니다.

시험 포인트 정리

이 장의 주제는 대부분 고성능 아키텍처 설계(24%)에 속하며, 용량 모드와 캐시 도입 판단은 비용 최적화 아키텍처 설계에도 걸칩니다.

LSI의 읽기 일관성 최종 일관성과 강력한 일관성 모두 가능 모든 보조 인덱스가 최종 일관성만 지원한다고 일반화

LSI의 크기 제약 파티션 키 값당 10 GB GSI에도 같은 제약이 있다고 봄
인덱스의 용량 LSI는 테이블 용량 공유, GSI는 자체 용량 GSI 트래픽이 테이블 용량을 잡아먹는다고 판단
용량 모드 PAY_PER_REQUEST(온디맨드) / PROVISIONED. 나중에 변경 가능 한 번 정하면 못 바꾼다고 답함
용량 모드 선택 예측 불가·산발적이면 온디맨드, 안정적이면 프로비저닝 + 오토스케일링 비용 한정어만 보고 반사적으로 한쪽을 고름
읽기 일관성 기본값 최종 일관성. ConsistentRead로 강력한 일관성 선택 기본이 강력한 일관성이라고 가정

DAX의 성격 DynamoDB 전용 · API 호환 · 마이크로초 · 최종 일관성 강력한 일관성 요구 문항에서 DAX를 고름
DAX와 ElastiCache DAX는 코드 변경 최소, ElastiCache는 캐시 로직을 직접 구현 DynamoDB 앞의 캐시로 ElastiCache를 고름
글로벌 테이블 여러 리전이 모두 읽고 쓴다. 복제본에 스트림 활성화 필요 Aurora 글로벌 데이터베이스처럼 한 리전만 쓰기가 된다고 봄
TTL 에포크 초 속성 기준 · 최선 노력 · 대체로 만료 후 이틀 안 삭제 · 쓰기 용량 미소비 지정한 시각에 정확히 사라진다고 가정
DynamoDB 백업 온디맨드 백업은 개수 제한 없음, PITR은 최근 35일 PITR이 무기한 보관을 대신한다고 봄
Redis와 Memcached 복제 · 자동 장애 조치 · 스냅샷 · 자료구조가 필요하면 Redis 세션 저장이나 지속성 요구에 Memcached를 고름
Memcached의 성격 복제 없음 · 스냅샷 불가 · 멀티스레드 · 노드를 늘려 메모리 풀 확장 Memcached도 복제본으로 읽기를 확장할 수 있다고 봄
캐시 계층 선택 DynamoDB → DAX, 관계형 반복 질의 → ElastiCache, 다양한 읽기 → 읽기 전용 복제본, HTTP → CloudFront 모든 지연 문제에 CloudFront나 ElastiCache를 고름
Redshift와 Athena 정기 적재 후 반복 분석은 Redshift, S3 위 임시 SQL은 Athena 서버리스라는 이유만으로 모든 분석에 Athena를 고름
목적별 데이터베이스 문서=DocumentDB, 그래프=Neptune, 와이드 컬럼=Keyspaces, 시계열=Timestream 모델이 명시되었는데도 DynamoDB를 고름

이 장의 개념 서술과 API 동작은 모두 아래 문서에서 확인했습니다.

  • Amazon DynamoDB API 레퍼런스 — CreateTable — 파티션 키(HASH)와 정렬 키(RANGE)의 정의, 용량 모드 값과 권장 기준, 나중에 변경할 수 있다는 서술, LSI 5개·GSI 20개 상한, LSI의 파티션 키 값당 10 GB 제약, 스트림 뷰 타입 네 가지
  • Amazon DynamoDB API 레퍼런스 — UpdateTable — 기존 테이블에 대해 글로벌 보조 인덱스만 추가·수정·삭제할 수 있고 한 번에 하나씩만 가능하다는 규칙
  • Amazon DynamoDB API 레퍼런스 — Query — 글로벌 보조 인덱스에 강력한 일관성 읽기를 요청하면 ValidationException이 반환된다는 명시
  • Amazon DynamoDB 개발자 안내서 — 보조 인덱스로 데이터 액세스 개선 — LSI와 GSI의 특성 비교표(키 스키마, 크기 제약, 온라인 인덱스 작업, 질의 범위, 읽기 일관성, 처리량 소비, 프로젝션 속성)
  • Amazon DynamoDB 개발자 안내서 — 파티션 키 설계 모범 사례 — 논리 파티션 키 전반에 활동을 고르게 분산하라는 원칙, 버스트 용량, 적응 용량이 모든 테이블에 자동으로 켜져 있고 추가 비용이 없다는 설명
  • Amazon DynamoDB 개발자 안내서 — 워크로드를 고르게 분산하는 파티션 키 설계 — 파티션 키 값별 균일성 비교표와 핫 파티션이 스로틀링을 유발한다는 서술
  • Amazon DynamoDB 개발자 안내서 — 쓰기 샤딩으로 워크로드 분산 — 파티션 키 값에 접미사를 붙여 쓰기를 분산하는 방법
  • Amazon DynamoDB API 레퍼런스 — UpdateTimeToLive — 에포크 시간 기준 만료, 최선 노력 삭제, 대체로 만료 후 이틀 안에 삭제된다는 서술
  • Amazon DynamoDB API 레퍼런스 — UpdateContinuousBackups — 최근 35일 안의 임의 시점 복원, 보존 일수 1~35일, 최신 복원 지점이 대체로 현재 시각 5분 전이라는 설명
  • Amazon DynamoDB API 레퍼런스 — CreateBackup — 온디맨드 백업 개수에 제한이 없고 테이블의 프로비저닝된 처리량을 소비하지 않는다는 서술
  • Amazon DynamoDB API 레퍼런스 — CreateGlobalTable — 복제본 조건(같은 이름·같은 기본 키·스트림 활성화)과 현재 버전 2019.11.21 권장
  • Amazon DynamoDB 개발자 안내서 — DAX를 사용한 인메모리 가속 — 마이크로초 응답, API 호환으로 최소한의 변경만 필요하다는 점, DAX가 적합하지 않은 경우 목록
  • Amazon DynamoDB 개발자 안내서 — DAX 작동 방식 — 항목 캐시와 질의 캐시의 구분, TTL과 LRU 축출
  • Amazon DAX API 레퍼런스 — CreateCluster — 단일 노드와 다중 노드 클러스터 구성, 프라이머리와 읽기 복제본
  • Amazon ElastiCache API 레퍼런스 — CreateCacheCluster — 엔진 값, Memcached의 노드 수 범위와 가용 영역 배치 옵션, 스냅샷 보존이 Redis 계열에만 유효하다는 제약
  • Amazon ElastiCache API 레퍼런스 — CreateReplicationGroup — 프라이머리와 읽기 전용 복제본 구조, 쓰기가 비동기로 전파된다는 설명, 자동 장애 조치와 저장 시·전송 중 암호화 설정
  • Amazon ElastiCache API 레퍼런스 — CreateSnapshot — 스냅샷 작업이 Redis 계열에서만 유효하다는 명시
  • Amazon Redshift API 레퍼런스 — CreateCluster — ClusterType의 단일 노드와 다중 노드 구분, 저장 시 암호화 기본값
