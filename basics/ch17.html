기본개념 · 17장

모니터링·운영·계정 관리

이 장의 서비스들은 시나리오에서 서로를 대신하지 않습니다. 지금 어떤 상태인가, 누가 무엇을 호출했는가, 구성이 규칙을 지키는가는 서로 다른 질문이고, 각 질문에 답하는 서비스가 하나씩 정해져 있습니다. 시험이 이 셋을 집요하게 섞어 놓는 이유도 그래서입니다.

이 장은 보안 아키텍처 설계(30%)의 감사·거버넌스 부분과 복원력 있는 아키텍처 설계(26%)의 관측·자동 복구 부분에 걸쳐 있습니다.

학습 목표

  • CloudWatch의 지표 · 로그 · 알람이 어떻게 연결되는지 설명하고, 지표 필터와 구독 필터를 구분할 수 있습니다.
  • EC2 기본 지표에 메모리 사용률이 없다는 사실과 그 대응 방법을 설명할 수 있습니다.
  • CloudTrail · AWS Config · CloudWatch가 각각 어떤 질문에 답하는지로 시나리오에서 서비스를 고를 수 있습니다.
  • Systems Manager의 Session Manager로 SSH 없이 접속하는 구성의 이점을 설명할 수 있습니다.
  • AWS Organizations · AWS Control Tower · Trusted Advisor의 역할을 구분할 수 있습니다.
  • CloudFormation의 스택 · 변경 세트 · 드리프트 · StackSets를 구분하고, AWS CDK가 시험 범위 밖이라는 사실을 설명할 수 있습니다.

Amazon CloudWatch — 지표, 로그, 알람

CloudWatch는 세 가지를 담습니다. 지표(metric)는 시간에 따른 숫자, 로그(log)는 텍스트 이벤트, 알람(alarm)은 지표가 조건을 만족할 때 동작을 일으키는 장치입니다. 이 셋이 어떻게 연결되는지가 이 절의 전부입니다.

지표 — 해상도와 사용자 지정 지표

AWS 서비스는 지표를 자동으로 CloudWatch에 보냅니다. Amazon EC2의 경우 기본 모니터링에서는 데이터 포인트가 5분 단위로 제공되고, 세부 모니터링을 켜면 1분 단위가 됩니다. 기본 모니터링에는 추가 요금이 없고, 세부 모니터링은 전송되는 지표마다 요금이 붙습니다.

직접 올리는 사용자 지정 지표에는 해상도 선택지가 하나 더 있습니다. PutMetricData의 StorageResolution 값이 60이면 1분 해상도이고, 1로 지정하면 1초 단위까지 저장하는 고해상도 지표가 됩니다. API 문서는 고해상도가 사용자 지정 지표에서만 제공된다고 명시합니다.

EC2의 기본 지표에는 메모리 사용률과 파일 시스템 사용률이 없습니다. AWS/EC2 네임스페이스가 제공하는 것은 CPU 사용률, 네트워크 입출력, 디스크 읽기·쓰기 같은 하이퍼바이저에서 관측되는 값뿐입니다. 메모리와 파일 시스템 여유 공간은 게스트 운영체제 안의 값이라 AWS가 밖에서 볼 수 없습니다.

따라서 "메모리 사용률로 Auto Scaling을 하거나 알람을 걸어야 한다"는 요구가 나오면 정답에는 CloudWatch 에이전트 설치가 반드시 포함됩니다. 에이전트가 수집한 값은 사용자 지정 지표로 과금된다는 점도 함께 기억합니다. 이 사실을 모르면 "메모리 지표로 알람을 건다"는 선택지를 그냥 통과시킵니다.

로그 — 지표 필터와 구독 필터는 다르다

CloudWatch Logs는 로그 이벤트를 로그 그룹 아래 로그 스트림으로 담습니다. 로그 그룹에는 보존 정책을 걸 수 있고, 걸지 않으면 무기한 보관됩니다. 비용 항목이 되므로 보존 기간을 정해 두는 것이 기본입니다.

로그에서 무언가를 꺼내는 방법은 두 가지이며, 목적이 다릅니다.

지표 필터와 구독 필터의 차이
항목 지표 필터(metric filter) 구독 필터(subscription filter)
하는 일 패턴에 맞는 로그 이벤트를 세어 CloudWatch 지표로 만듭니다 로그 이벤트를 실시간 스트림으로 다른 서비스에 전달합니다
결과 지표 → 알람 → 알림·동작 Amazon Kinesis Data Streams, Amazon Data Firehose, AWS Lambda로 전달
쓰는 상황 "로그에 ERROR가 N번 넘게 나오면 알림" "로그를 실시간으로 가공해 다른 저장소로 보낸다", "여러 계정의 로그를 한 계정으로 모은다"
제약 추출된 지표는 사용자 지정 지표로 과금됩니다. 카디널리티가 높은 값을 차원으로 쓰지 않습니다 로그 그룹 하나에 구독 필터를 최대 2개까지 붙일 수 있습니다

알람 — 결측 데이터와 복합 알람

알람은 지표가 평가 기간 동안 조건을 만족하는지 보고 OK · ALARM · INSUFFICIENT_DATA 세 상태 사이를 오갑니다. 여기서 두 가지가 시험에 나옵니다.

첫째, 결측 데이터 처리입니다. TreatMissingData의 값은 breaching · notBreaching · ignore · missing 네 가지이고, 지정하지 않으면 기본값은 missing입니다. 데이터가 드문드문 들어오는 지표에 알람을 걸면 이 설정 때문에 알람이 계속 울리거나 아예 울리지 않는 일이 생깁니다.

둘째, 복합 알람입니다. 다른 알람들의 상태를 규칙식으로 조합해 만드는 알람이며, API 문서는 규칙식에 최대 100개의 하위 알람을 넣을 수 있다고 명시합니다. 여러 알람이 동시에 울려 알림이 쏟아지는 것을 줄이는 것이 목적입니다.

알람이 일으킬 수 있는 대표 동작
동작 쓰는 상황
Amazon SNS 알림 운영자에게 알리거나, 구독한 Lambda 함수로 후속 처리를 트리거합니다
Auto Scaling 정책 실행 지표 기반으로 인스턴스 수를 늘리거나 줄입니다(7장)
EC2 동작 상태 확인에 실패한 인스턴스를 재부팅하거나 복구합니다

대시보드

대시보드는 여러 리전과 계정의 지표를 한 화면에 모읍니다. 시험에서 대시보드 자체를 깊게 묻지는 않지만, "여러 계정의 운영 지표를 한곳에서 본다"는 요구가 나오면 교차 계정 대시보드가 답의 일부가 됩니다.

로그 관련 문항에서 갈림길은 대체로 하나입니다. "조건을 만족하면 알림"이면 지표 필터 + 알람, "로그를 실시간으로 다른 곳에 흘려보낸다"면 구독 필터입니다.

한 가지 더 있습니다. 로그를 장기 보관하면서 비용을 줄여야 한다는 요구에는 CloudWatch Logs에 무기한 두는 것이 답이 아닙니다. 보존 정책을 걸고, 필요한 것은 Amazon S3로 내보내 스토리지 클래스로 관리하는 구성이 정답 형태입니다.

CloudTrail · Config · CloudWatch — 세 가지 질문 SAA 빈출

이 세 서비스를 구분하는 방법은 기능을 외우는 것이 아니라 각자 답하는 질문을 하나씩 붙여 두는 것입니다. 시험은 이 구분만 반복해서 묻습니다.

CloudTrail · AWS Config · CloudWatch가 답하는 질문
서비스 답하는 질문 기록 단위 문제문의 신호
AWS CloudTrail 누가 언제 어떤 API를 호출했는가 API 호출 이벤트 "누가 삭제했는지 밝혀야 한다", "감사 추적", "API 활동 기록"
AWS Config 리소스 구성이 규칙에 맞는가, 언제 어떻게 바뀌었는가 리소스 구성 항목과 이력 "규정 준수 여부를 지속적으로 평가", "구성 변경 이력", "규칙 위반 시 자동 수정"
Amazon CloudWatch 지금 얼마나 잘 동작하고 있는가 지표와 로그 "사용률이 임계값을 넘으면", "응답 지연을 감시", "로그에서 오류를 찾아"

가장 흔한 오답 배치는 CloudTrail과 Config를 바꿔 놓는 것입니다. 기준 문장을 하나만 기억하면 됩니다.

"누가 그랬는가"는 CloudTrail, "지금 상태가 맞는가"는 Config입니다. "보안 그룹이 0.0.0.0/0으로 열려 있는지 지속적으로 확인하고 위반하면 되돌린다"는 Config 규칙과 수정 동작이고, "그 보안 그룹 규칙을 누가 추가했는지 찾는다"는 CloudTrail입니다. 두 서비스가 같은 사건의 서로 다른 면을 본다는 점이 핵심입니다.

CloudTrail — 이벤트 유형과 무결성

CloudTrail은 계정의 API 호출을 기록하고 추적(trail)을 만들면 Amazon S3 버킷으로 로그 파일을 계속 전달합니다. 기록되는 이벤트는 유형에 따라 기본 동작이 다릅니다.

CloudTrail 이벤트 유형과 기본 기록 여부
이벤트 유형 무엇을 기록하는가 기본 동작
관리 이벤트 리소스를 만들고 바꾸고 지우는 제어 평면 호출. 보안 그룹 수정, 역할 생성 등 별도 선택기를 지정하지 않으면 읽기·쓰기 관리 이벤트가 모두 기록됩니다
데이터 이벤트 객체 수준 호출. Amazon S3 객체 GetObject·PutObject, Lambda 함수 Invoke, DynamoDB 테이블 항목 작업 등 기본적으로 기록되지 않습니다 — 이벤트 선택기로 켜야 하고 양이 많아 비용이 커질 수 있습니다
인사이트 이벤트 호출량이 평소와 크게 다른 비정상 패턴 별도로 켜야 합니다

추적을 만들 때 정하는 설정 중 시험에 나오는 것은 셋입니다.

  • 다중 리전 추적 — IsMultiRegionTrail의 기본값은 false여서 만든 리전에서만 기록합니다. 모든 리전의 이벤트를 남기려면 켜야 합니다. AWS는 이를 모범 사례로 권장합니다.
  • 조직 추적 — IsOrganizationTrail을 켜면 조직의 모든 계정에 대한 추적이 됩니다. 관리 계정이나 위임된 관리자 계정에서만 만들 수 있습니다.
  • 로그 파일 무결성 검증 — 켜면 CloudTrail이 다이제스트 파일을 함께 만들어 로그가 전달 후 변조되지 않았음을 증명할 수 있게 합니다. 기본값은 꺼짐입니다.

규정 준수 시나리오에서 반복되는 조합이 있습니다. 조직 추적 + 다중 리전 + 로그 파일 무결성 검증 + 별도 로그 아카이브 계정의 S3 버킷, 그리고 그 버킷에 Object Lock과 버전 관리를 걸어 삭제를 막는 구성입니다.

함정은 로그를 워크로드 계정에 그대로 두는 선택지입니다. 침해가 일어난 계정 안에 증적을 두면 증적도 함께 지워질 수 있습니다. 계정을 분리하는 것 자체가 통제라는 것이 이 문항들의 결론입니다.

AWS Config — 규칙과 자동 수정

Config는 리소스의 구성을 계속 기록하고, 규칙(rule)으로 그 구성이 원하는 상태인지 평가합니다. 규칙에는 AWS가 미리 만들어 둔 관리형 규칙과 직접 작성하는 사용자 지정 규칙이 있습니다.

  • 구성 항목과 이력 — 리소스가 어느 시점에 어떤 구성이었는지 되짚을 수 있습니다. "언제부터 이 버킷이 공개였는가" 같은 질문에 답합니다.
  • 적합성 팩(conformance pack) — 규칙과 수정 동작의 묶음을 계정과 리전, 나아가 조직 전체에 한 번에 배포합니다.
  • 수정 동작(remediation) — 규칙을 위반한 리소스에 대해 Systems Manager 자동화 문서를 실행해 원하는 상태로 되돌립니다.

"규정을 어긴 구성을 발견하면 자동으로 되돌려야 한다"는 요구는 Config 규칙 + 수정 동작 조합입니다. CloudTrail은 기록만 남기므로 이 요구를 스스로 만족시키지 못합니다.

여러 계정에 같은 가드레일을 걸어야 한다면 계정마다 규칙을 만드는 것이 아니라 조직 단위 적합성 팩이나 AWS Control Tower의 제어가 답입니다. "계정마다 수동으로 설정한다"는 선택지는 운영 부담 한정어에서 항상 밀립니다.

AWS Systems Manager — 인스턴스를 열지 않고 운영한다

Systems Manager는 여러 기능의 묶음입니다. SAA에서 반복해서 나오는 것은 세 가지입니다.

Systems Manager의 시험 빈출 기능
기능 무엇을 하는가 고르는 신호
Session Manager 브라우저나 CLI로 인스턴스에 셸 세션을 엽니다. 인스턴스가 SSM 에이전트로 바깥으로 연결하므로 인바운드 포트를 열지 않아도 됩니다 "SSH 키를 관리하고 싶지 않다", "배스천 호스트를 없애고 싶다", "22번 포트를 열 수 없다"
Patch Manager 패치 기준선(patch baseline)과 유지 관리 기간에 따라 운영체제 패치를 자동으로 적용합니다 "수백 대 인스턴스에 패치를 일괄 적용", "패치 준수 상태를 보고"
Parameter Store 설정값과 비밀을 계층 구조로 저장합니다. 자세한 비교는 16장에 있습니다 "설정값을 코드 밖으로", "교체 요구가 없는 값"

"배스천 호스트 없이 프라이빗 서브넷의 인스턴스에 접속해야 한다"는 Session Manager입니다. 정답 구성에는 보통 두 가지가 함께 들어갑니다 — 인스턴스에 SSM 권한을 가진 IAM 역할을 붙이는 것, 그리고 인터넷을 거치지 않게 하려면 Systems Manager용 인터페이스 엔드포인트를 두는 것입니다.

함께 얻는 것도 기억합니다. Session Manager 세션은 누가 언제 접속했는지 CloudTrail에 남고, 세션 내용도 S3나 CloudWatch Logs에 기록할 수 있습니다. SSH 키를 나눠 주는 방식으로는 이 증적을 만들 수 없습니다.

계정 거버넌스 — Organizations, Control Tower, Trusted Advisor

1장에서 AWS Organizations의 계층과 2장에서 SCP의 성질을 다뤘습니다. 여기서는 그 위에 얹히는 도구들을 정리합니다.

거버넌스 도구 세 가지의 역할
도구 무엇을 하는가 고르는 신호
AWS Organizations 계정을 조직과 OU로 묶고, 서비스 제어 정책으로 권한 상한을 걸며, 결제를 통합합니다 "여러 계정을 하나로 관리", "특정 리전 사용을 막는다", "통합 결제"
AWS Control Tower 모범 사례 구성의 랜딩 존을 자동으로 세우고, 제어(가드레일)를 OU에 적용하며, 계정 발급을 표준화합니다 "다중 계정 환경을 처음부터 표준에 맞게 구축", "새 계정을 규칙에 맞게 자동 발급"
AWS Trusted Advisor 계정을 모범 사례 점검 항목으로 검사합니다 — 비용 최적화 · 성능 · 보안 · 내결함성 · 서비스 한도 · 운영 우수성 여섯 범주 "낭비와 위험을 훑어본다", "서비스 한도에 근접했는지 확인"

Control Tower는 Organizations 위에 얹힌다

둘은 경쟁 관계가 아닙니다. Control Tower는 Organizations를 바탕으로 동작하며, 조직·OU·SCP·CloudTrail·Config를 미리 정해진 모범 사례 형태로 한 번에 구성해 줍니다. 직접 하나씩 세우는 것과 같은 결과를 자동화한 것이라고 보면 됩니다.

제어(control)는 성격이 셋으로 나뉩니다 — 위반을 막는 예방 제어, 위반을 알아채는 탐지 제어, 위반이 일어나지 않게 구성 자체를 강제하는 사전 예방 제어입니다. 예방 제어는 대체로 SCP로, 탐지 제어는 대체로 Config 규칙으로 구현됩니다.

문제문의 시제가 갈림길입니다. "다중 계정 환경을 새로 구축한다"면 Control Tower, "이미 있는 조직에 특정 권한 상한을 건다"면 Organizations의 SCP입니다.

Trusted Advisor는 점검 항목이 지원 플랜에 따라 달라집니다. 기본 플랜에서는 서비스 한도 범주 전체와 보안·내결함성의 일부만 보이고, 전체 점검은 상위 지원 플랜에서 열립니다. "Trusted Advisor에서 비용 절감 항목이 안 보인다"는 시나리오의 원인이 대개 여기입니다. 비용 도구 전반은 18장에서 다룹니다.

AWS CloudFormation — 코드형 인프라

CloudFormation은 템플릿에 적힌 리소스 구성을 그대로 만들고 갱신하고 지웁니다. 만들어진 리소스 묶음이 스택(stack)이며, 스택을 지우면 그 안의 리소스가 함께 정리됩니다.

CloudFormation의 핵심 개념
개념 무엇인가 왜 필요한가
스택 템플릿 하나로 만들어진 리소스 묶음이자 관리 단위 생성·갱신·삭제를 한 단위로 다룰 수 있습니다
변경 세트(change set) 템플릿을 적용하기 전에 무엇이 생기고 바뀌는지 미리 보여 주는 목록 운영 환경에서 의도치 않은 리소스 교체를 사전에 발견합니다
드리프트 감지(drift detection) 실제 구성이 템플릿에서 정의한 기대 구성과 달라졌는지 검사합니다. 템플릿에 명시된 속성만 검사합니다 콘솔에서 손으로 바꾼 변경을 찾아냅니다. 상태가 DRIFTED · IN_SYNC 등으로 표시됩니다
StackSets 하나의 템플릿을 여러 계정과 여러 리전에 배포합니다. 조직 단위(OU)를 대상으로 지정할 수 있습니다 계정마다 같은 스택을 손으로 만들지 않아도 됩니다
롤백 생성이나 업데이트가 실패하면 이전 상태로 되돌립니다 부분적으로만 만들어진 인프라가 남는 것을 막습니다

AWS CloudFormation은 시험 범위 안이고, AWS CDK는 범위 밖입니다. 둘 다 코드형 인프라라서 실무에서는 함께 배우고 싶어지지만, AWS는 CDK를 SAA-C03의 out-of-scope 서비스로 명시했습니다. 이 사이트는 CDK를 학습 대상으로 다루지 않으며, 시험 대비에는 템플릿 구조 · 스택 · 변경 세트 · 드리프트 · StackSets까지만 익히면 충분합니다.

같은 이유로 CodeBuild · CodeDeploy · CodePipeline · CodeCommit 같은 개발자 도구도 범위 밖입니다. "배포 파이프라인을 만든다"는 시나리오가 보이면 그 도구 이름이 정답 선택지가 아닐 가능성이 높다는 점을 기억합니다. 범위 안팎 목록은 1장에 정리해 두었습니다.

CloudFormation 문항의 갈림길은 대체로 셋입니다. "적용 전에 영향을 확인해야 한다"면 변경 세트, "누가 손으로 바꾼 것이 있는지 알아야 한다"면 드리프트 감지, "여러 계정과 리전에 같은 것을 배포해야 한다"면 StackSets입니다.

한 가지 더 있습니다. 스택을 지울 때 데이터가 함께 사라지면 안 되는 리소스에는 삭제 정책(DeletionPolicy)을 Retain이나 Snapshot으로 지정합니다. "스택을 지웠더니 데이터베이스가 사라졌다"는 사고의 방지책입니다.

AWS X-Ray — 요청이 어디서 느려지는가

지표와 로그는 구성 요소 하나하나를 보여 주지만, 요청 하나가 여러 서비스를 거칠 때 어느 구간에서 시간이 걸렸는지는 알려 주지 않습니다. AWS X-Ray는 요청에 추적 정보를 붙여 서비스 맵과 구간별 지연을 만듭니다.

  • 마이크로서비스나 서버리스처럼 호출이 여러 단계로 나뉜 구조에서 가치가 큽니다.
  • AWS Lambda, Amazon API Gateway, Amazon ECS 등과 통합되어 추적을 수집합니다.
  • "어느 서비스 호출이 병목인지 찾아야 한다"는 요구에 CloudWatch 지표만으로는 답하기 어렵습니다.

"분산된 서비스 사이에서 지연의 원인을 찾아야 한다"는 X-Ray, "특정 지표가 임계값을 넘었는지 감시한다"는 CloudWatch, "어떤 API가 호출되었는지 감사한다"는 CloudTrail입니다. 셋을 한 문항에 섞어 두는 것이 전형적인 출제 형태입니다.

흔한 오해

"EC2 지표에 메모리 사용률이 있다" — AWS/EC2 네임스페이스의 기본 지표에는 메모리와 파일 시스템 사용률이 없습니다. 게스트 운영체제 안의 값이라 하이퍼바이저 밖에서는 볼 수 없기 때문입니다. 메모리로 알람이나 스케일링을 하려면 CloudWatch 에이전트를 설치해 사용자 지정 지표로 올려야 합니다. "세부 모니터링을 켜면 메모리가 보인다"는 것도 틀립니다 — 세부 모니터링은 주기를 5분에서 1분으로 줄이는 것이지 지표 종류를 늘리지 않습니다.

"CloudTrail을 켜면 S3 객체 접근도 다 기록된다" — CloudTrail이 기본으로 남기는 것은 관리 이벤트입니다. S3 객체 GetObject·PutObject 같은 데이터 이벤트는 기본적으로 기록되지 않고, 이벤트 선택기로 따로 켜야 합니다. 양이 많아 비용이 커질 수 있으므로 대상 버킷과 접두사를 좁혀 켜는 것이 실무 관행입니다. "버킷에서 누가 파일을 내려받았는지 확인하라"는 시나리오는 이 설정을 묻는 문항입니다.

"코드형 인프라니까 CloudFormation과 CDK를 같이 공부해야 한다" — AWS CloudFormation은 시험 범위 안이고 AWS CDK는 범위 밖입니다. CDK를 공부한다고 CloudFormation 문항을 더 잘 푸는 것도 아닙니다. 시험에 필요한 것은 템플릿 구조와 스택 수명주기, 변경 세트·드리프트·StackSets의 용도입니다. 범위 밖 서비스를 공부하지 않는 것도 학습 전략의 일부입니다.
