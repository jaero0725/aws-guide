S3와 오브젝트 스토리지

Amazon S3 문항은 어디에 두는가, 누가 열 수 있는가, 얼마나 오래 두는가 세 갈래로 갈립니다. 첫째는 스토리지 클래스와 수명 주기가, 둘째는 버킷 정책과 암호화가, 셋째는 버저닝과 Object Lock이 답을 정합니다. 그리고 이 장에는 시중 자료가 가장 많이 틀리는 항목이 몰려 있습니다 — 일관성 모델과 신규 버킷 기본값이 그것입니다.

이 장은 고성능 아키텍처 설계(24%)와 비용 최적화 아키텍처 설계(20%)의 중심이고, 보안 아키텍처 설계(30%)의 데이터 보안 제어에도 걸칩니다. 18장 중 출제 밀도가 가장 높은 장에 속합니다.

학습 목표

  • Amazon S3의 일관성 모델을 현행 기준으로 설명하고, 언제 무엇이 바뀌었는지 말할 수 있습니다.
  • 신규 버킷의 현행 보안 기본값 세 가지와 여전히 꺼져 있는 설정을 구분할 수 있습니다.
  • 스토리지 클래스를 접근 빈도·검색 시간·가용 영역 수로 나누고, 최소 저장 기간을 근거로 선택할 수 있습니다.
  • 수명 주기 규칙으로 전환·만료·불완전 멀티파트 업로드 정리를 설계할 수 있습니다.
  • 서버 측 암호화 네 가지를 키 관리 주체와 감사 요구를 기준으로 고를 수 있습니다.
  • 버킷 정책·프리사인 URL·퍼블릭 액세스 차단이 요청을 어떤 순서로 거르는지 설명할 수 있습니다.

객체 모델 — 버킷과 키, 그리고 폴더가 없다는 사실

Amazon S3는 파일 시스템이 아니라 객체 스토리지(object storage)입니다. 데이터는 버킷(bucket) 안에 객체(object)로 저장되고, 객체는 키(key)라는 문자열로 식별됩니다. 블록 단위로 일부만 고쳐 쓰는 동작이 없고, 객체는 통째로 올리거나 통째로 대체합니다.

logs/2026/07/app.log처럼 슬래시가 들어간 키를 콘솔이 폴더처럼 보여 주지만, S3에 디렉터리 구조는 존재하지 않습니다. 슬래시는 키 문자열의 일부일 뿐이고, 앞부분은 접두사(prefix)로 불립니다. 이 사실은 뒤의 성능 절에서 요청 분산의 근거가 됩니다.

객체에는 데이터 외에 메타데이터가 붙습니다. Content-Type 같은 시스템 메타데이터, 사용자가 붙이는 사용자 정의 메타데이터, 그리고 접근 제어와 수명 주기 규칙의 필터로 쓰이는 객체 태그가 있습니다. 메타데이터만 따로 고칠 수는 없고, 메타데이터를 바꾸려면 객체 전체를 다시 올려야 합니다.

일관성 모델 — 강력한 읽기 후 쓰기 일관성 SAA 빈출

Amazon S3는 모든 AWS 리전에서 강력한 읽기 후 쓰기 일관성(strong read-after-write consistency)을 제공합니다. 신규 객체를 올린 직후에도, 기존 객체를 덮어쓴 직후에도, 삭제한 직후에도 다음 읽기는 항상 최신 상태를 반환합니다.

  • 신규 객체 PUT · 기존 객체를 덮어쓰는 PUT · DELETE 모두 강력한 일관성
  • 객체 목록 조회(LIST)도 강력한 일관성 — 새 객체를 쓴 직후 목록을 조회하면 그 객체가 보인다
  • ACL · 객체 태그 · 객체 메타데이터 읽기도 강력한 일관성
  • 단일 키에 대한 갱신은 원자적(atomic)이다 — 동시에 읽으면 이전 데이터나 새 데이터를 받고, 부분적으로 섞인 데이터는 절대 반환되지 않는다

추가 요금도, 성능 저하도, 별도 설정도 없습니다. "쓰고 나서 잠깐 기다렸다 읽어야 한다", "재시도 루프를 넣어야 한다" 같은 설계는 이제 필요하지 않습니다.

2020년 12월까지는 달랐습니다. 그전에는 신규 객체를 올리는 경우에만 읽기 후 쓰기 일관성이 보장되었고, 덮어쓰기와 삭제는 최종적 일관성(eventual consistency)이었습니다. 그래서 당시에는 "쓴 직후 읽으면 옛 데이터가 나올 수 있다"가 맞는 서술이었고, 그 제약을 우회하려고 DynamoDB에 인덱스를 따로 두는 패턴까지 쓰였습니다.

바뀐 사실 자체를 기억하는 것이 중요합니다. 한국어 SAA 자료 상당수가 2020년 이전 기준으로 쓰여 있어서 "S3는 최종적 일관성"이라고 가르치고, 그에 맞춘 문항까지 실려 있습니다. 그 서술은 현행 기준으로 명백한 오류입니다.

"S3에 쓴 데이터를 즉시 읽어야 한다"는 요구가 나오면 그것만으로는 아무 추가 설계도 필요하지 않습니다. 일관성을 확보하려고 다른 서비스를 덧붙이는 선택지는 과잉 설계이며, 비용 한정어가 붙어 있으면 더 확실히 오답입니다.

반대로 "여러 클라이언트가 같은 키에 동시에 쓴다"는 상황에서 S3가 쓰기 순서를 정해 주지는 않습니다. 마지막에 쓰인 것이 남을 뿐이고, 순서 제어가 필요하면 12장의 큐나 조건부 요청 같은 별도 장치가 필요합니다.

신규 버킷의 현행 기본값 SAA 빈출

지금 새로 만드는 버킷은 기본적으로 닫혀 있고 기본적으로 암호화됩니다. 이 사실을 모르면 시나리오 문항에서 불필요한 조치를 정답으로 고르게 됩니다.

"기본값이 전부 안전해졌다"고 뭉뚱그리면 틀립니다. 버전 관리(Versioning)는 지금도 기본 비활성이고, 이 기본값은 바뀐 적이 없습니다. 실수로 덮어쓰거나 지운 객체를 되돌려야 한다는 요구가 나오면 버전 관리를 켜는 것이 답이며, "이미 켜져 있다"고 전제하면 안 됩니다.

객체 소유권이 BucketOwnerEnforced라는 것은 ACL이 아예 동작하지 않는다는 뜻입니다. 다른 계정이 이 버킷에 객체를 올려도 소유자는 버킷 소유자가 되고, 접근 제어는 전적으로 버킷 정책과 IAM 정책으로 합니다. AWS는 특별한 사유가 없는 한 이 상태를 유지할 것을 권장합니다.

시나리오에 "다른 계정이 올린 객체를 우리 계정이 읽지 못한다"는 문제가 나오면, 과거에는 객체 ACL로 bucket-owner-full-control을 주는 것이 정답이었습니다. 현행 기본값에서는 그 문제 자체가 발생하지 않습니다 — 버킷 소유자가 자동으로 모든 객체를 소유합니다. "객체 ACL을 조정한다"는 선택지는 이제 기본 구성에서는 동작하지 않습니다.

반대로 "버킷을 공개해야 한다"는 요구에는 퍼블릭 액세스 차단을 꺼야 한다는 점을 인지해야 합니다. 다만 대부분의 문항에서 정답은 버킷을 공개하는 것이 아니라 CloudFront와 오리진 액세스 제어(OAC)로 비공개를 유지하는 것입니다 (14장 엣지와 DNS).

스토리지 클래스 — 접근 빈도와 검색 시간이 기준

스토리지 클래스는 객체 단위 속성입니다. 같은 버킷 안에서 객체마다 다른 클래스를 쓸 수 있고, 올릴 때 지정하거나 나중에 수명 주기 규칙으로 바꿉니다. 지정하지 않으면 S3 Standard입니다.

선택 기준은 두 가지뿐입니다. 얼마나 자주 읽는가와 읽어야 할 때 얼마나 빨리 필요한가입니다. 여기에 최소 저장 기간이라는 제약이 붙어서, 자주 지우는 데이터를 차가운 클래스에 두면 오히려 손해가 나는 구간이 생깁니다.

위 표에 클래스별 설계 가용성 수치(99.99% 등)를 넣지 않았습니다. 내구성은 모든 클래스가 같은 값으로 설계되어 있지만, 가용성 수치는 이 사이트가 접근할 수 있는 1차 소스에서 현행 값으로 교차 확인하지 못했기 때문입니다. 가용 영역 수는 확인된 값이고, 실제 판단에 필요한 정보는 그쪽입니다 — One Zone-IA가 단일 가용 영역이라는 사실이 소수점 아래 숫자보다 훨씬 중요합니다.

One Zone-IA — 무엇을 내주고 싼가

S3 One Zone-IA는 데이터를 단 하나의 가용 영역에만 저장합니다. 그래서 Standard-IA보다 저렴하지만, 그 대가가 명확합니다 — 해당 가용 영역이 물리적으로 손실되면 데이터도 손실됩니다. 다른 클래스는 세 개 이상의 지리적으로 분리된 가용 영역에 저장되므로 가용 영역 하나가 사라져도 데이터가 남습니다.

따라서 One Zone-IA가 맞는 데이터는 다시 만들 수 있거나 다른 곳에 원본이 있는 데이터입니다. 원본에서 다시 생성할 수 있는 썸네일, 다른 리전에 복제본이 있는 보조 사본, 온프레미스에 원본이 남아 있는 백업의 2차 사본 같은 것들입니다.

"비용을 최소화하라"는 한정어만 보고 One Zone-IA를 고르는 것이 전형적인 오답입니다. 같은 문장 안에 "가용 영역 장애에도 견뎌야 한다", "복구할 수 없는 원본이다", "규정상 다중 가용 영역 저장이 필요하다" 같은 조건이 하나라도 있으면 One Zone-IA는 그 자리에서 소거됩니다.

거꾸로 "재생성 가능한 데이터", "이미 다른 곳에 사본이 있다"가 명시되어 있는데 Standard-IA를 고르면 비용 한정어를 놓친 것입니다. 두 방향 모두 출제됩니다.

Intelligent-Tiering — 접근 패턴을 모를 때

S3 Intelligent-Tiering은 접근 패턴을 모니터링해서 객체를 자동으로 옮기는 클래스입니다. 선택 기준은 단 하나입니다 — 접근 패턴을 모르거나 계속 변할 때 씁니다. 패턴을 이미 안다면 해당 클래스를 직접 지정하는 편이 낫습니다.

티어 이동 조건 활성화
Frequent Access 업로드·전환 직후의 기본 티어 기본

중요한 성질이 셋 있습니다. (1) 검색 요금이 없습니다 — 티어가 어디든 읽는 데 추가 검색 요금이 붙지 않습니다. (2) 최소 저장 기간이 없습니다. (3) 대신 객체당 모니터링·자동화 요금이 붙습니다 — 그래서 아주 작은 객체가 아주 많으면 오히려 불리할 수 있습니다.

기본 세 티어는 모두 밀리초 접근이지만, 선택 티어인 Archive Access와 Deep Archive Access는 비동기 접근입니다. 이 두 티어에 있는 객체는 RestoreObject로 먼저 복원해야 읽을 수 있으므로, 애플리케이션이 즉시 읽어야 한다면 켜지 않습니다.

128 KB 미만 객체는 모니터링 대상이 아니며 자동 계층화되지 않고 Frequent Access 티어에 남습니다.

문항에서 "접근 패턴을 예측할 수 없다", "접근 패턴이 시간이 지나며 바뀐다", "운영 부담 없이 비용을 최적화하라"가 함께 나오면 답은 S3 Intelligent-Tiering입니다. 수명 주기 규칙을 직접 설계하는 선택지는 패턴을 아는 경우의 답입니다.

반대로 "90일 뒤에는 거의 읽지 않는다", "7년간 보관하되 조회는 연 1회"처럼 패턴이 명시되어 있으면 Intelligent-Tiering은 모니터링 요금만 더 내는 선택입니다. 그때는 수명 주기 규칙 + 명시적 클래스 전환이 답입니다.

Glacier 계열 — 검색 시간이 클래스를 가른다

Glacier 계열 세 클래스의 차이는 저장 비용이 아니라 읽어야 할 때 얼마나 걸리는가입니다.

Glacier 계열 클래스의 접근 방식과 확인된 검색 시간
클래스 접근 방식 검색 시간
S3 Glacier Instant Retrieval 복원 없이 즉시 읽는다 밀리초
S3 Glacier Flexible Retrieval RestoreObject로 복원 후 읽는다 신속(Expedited) 1–5분 · 대량(Bulk) 5–12시간
S3 Glacier Deep Archive RestoreObject로 복원 후 읽는다 기본 검색 시간 12시간

복원 요청의 티어는 Expedited · Standard · Bulk 세 가지입니다. Flexible Retrieval에서 대량(Bulk) 검색은 무료이고, 신속 검색은 가장 빠른 대신 비쌉니다. 두 클래스 모두 복원 요청은 계정당 초당 최대 1,000 트랜잭션까지 처리됩니다.

클래스 선택 문항의 판단 순서입니다.

  • 밀리초 접근이 필요한가 — 필요하면 Glacier Flexible Retrieval과 Deep Archive는 즉시 소거됩니다. 드물게 읽지만 읽을 때는 즉시여야 하면 Glacier Instant Retrieval입니다.
  • 얼마나 오래 두는가 — 30일 이내에 지울 데이터를 Standard-IA에 두면 최소 저장 기간 때문에 손해입니다.
  • 가용 영역 하나를 잃어도 되는가 — 아니면 One Zone-IA는 소거됩니다.
  • 패턴을 아는가 — 모르면 Intelligent-Tiering, 알면 명시적 전환입니다.

"규정상 7년 보관하되 사실상 읽지 않는다"는 전형적인 Glacier Deep Archive 시나리오이고, "복구 시간 목표가 몇 시간"이면 Deep Archive의 12시간이 그 목표를 넘는지 반드시 확인해야 합니다.

API의 스토리지 클래스 열거값에는 EXPRESS_ONEZONE(S3 Express One Zone), FSX_OPENZFS, FSX_ONTAP, OUTPOSTS, REDUCED_REDUNDANCY도 있습니다. 이 중 S3 Express One Zone은 디렉터리 버킷이라는 별개의 버킷 유형을 쓰며 SAA-C03 학습 대상으로 다루지 않습니다. Reduced Redundancy는 AWS가 사용을 권장하지 않는 구세대 클래스입니다. 이 장의 선택 판단은 위 표의 일곱 클래스로 충분합니다.

수명 주기 규칙 — 전환, 만료, 그리고 비용 누수 차단

수명 주기 구성(lifecycle configuration)은 버킷에 붙이는 규칙 집합입니다. 규칙 하나는 필터(어떤 객체에), 상태(켜짐/꺼짐), 동작(무엇을)으로 이루어집니다. 필터는 키 접두사 · 객체 태그 · 객체 크기 또는 이들의 조합으로 지정할 수 있고, 한 버킷의 수명 주기 구성은 최대 1,000개 규칙까지 가질 수 있습니다.

전환 규칙의 제약

수명 주기 전환에는 시험에서 반복되는 제약이 셋 있습니다.

  • Standard-IA 또는 One Zone-IA로 전환하려면 객체가 최소 30일 저장되어 있어야 합니다. "업로드 즉시 IA로 보내 비용을 아낀다"는 규칙은 만들 수 없습니다.
  • 버전 관리 버킷의 비현재 버전도 최소 30일 비현재 상태여야 전환됩니다.
  • 128 KB 미만 객체는 전환되지 않습니다. 최소 청구 크기 때문에 작은 객체를 옮겨도 절감 효과가 없거나 오히려 손해이기 때문입니다.

만료와 비현재 버전 정리

만료(expiration) 동작은 객체를 지웁니다. 버전 관리가 켜진 버킷에서는 현재 버전의 만료가 삭제 마커를 남기는 것이고, 실제로 저장 용량을 줄이려면 비현재 버전 만료를 함께 설정해야 합니다. 만료된 삭제 마커를 정리하는 동작도 따로 있습니다.

불완전 멀티파트 업로드 정리 SAA 빈출

멀티파트 업로드를 시작하고 완료도 중단도 하지 않으면, 이미 올라간 파트가 계속 저장되고 계속 과금됩니다. 이 파트들은 객체 목록에 보이지 않습니다. 그래서 "버킷에 든 게 별로 없는데 요금이 계속 늘어난다"는 상황이 만들어집니다. 전형적인 비용 누수이고, 원인을 모르면 영원히 찾지 못합니다.

해결은 수명 주기 규칙의 AbortIncompleteMultipartUpload 동작입니다. 시작 후 지정한 일수가 지난 불완전 업로드의 파트를 S3가 자동으로 지웁니다. 신규 버킷을 만들 때 기본으로 넣어 두는 규칙이라고 생각하는 편이 좋습니다.

"S3 요금이 매달 늘어나는데 원인을 모르겠다"는 시나리오의 정답 후보는 셋입니다.

  • 불완전 멀티파트 업로드 — 목록에 보이지 않으므로 가장 자주 놓칩니다. AbortIncompleteMultipartUpload 규칙으로 해결합니다.
  • 버전 관리 버킷의 비현재 버전 — 지운 줄 알았던 객체가 이전 버전으로 남아 있습니다. 비현재 버전 만료 규칙으로 해결합니다.
  • 클래스 전환이 없는 방치 — 접근하지 않는 데이터가 Standard에 그대로 있습니다.

"수명 주기 규칙으로 즉시 IA로 보낸다"는 선택지는 30일 제약 때문에 성립하지 않습니다. 업로드 시점부터 차갑게 두려면 올릴 때 클래스를 직접 지정해야 합니다.

버저닝, 삭제 마커, MFA Delete, Object Lock

버전 관리를 켜면 같은 키에 쓸 때마다 새 버전 ID가 붙은 버전이 쌓입니다. 상태는 비활성 · Enabled · Suspended 세 가지이고, 한 번 켠 뒤에는 완전한 비활성 상태로 되돌릴 수 없습니다. 중지(Suspended)하면 새 버전이 더 생기지 않을 뿐, 이미 쌓인 버전은 그대로 남습니다.

삭제 마커 — 지운 게 아니라 가린 것

버전 관리 버킷에서 버전 ID 없이 DELETE를 호출하면 객체가 지워지는 것이 아니라 삭제 마커(delete marker)가 최신 버전으로 올라갑니다. 이후 일반 GET은 404를 반환하지만, 데이터는 이전 버전으로 그대로 남아 있고 계속 과금됩니다.

  • 복구 — 삭제 마커를 지우면 직전 버전이 다시 최신 버전이 됩니다.
  • 영구 삭제 — 버전 ID를 명시해서 DELETE를 호출해야 합니다.
  • 비용 — 정리 규칙이 없으면 버전이 무한정 쌓입니다. 비현재 버전 만료와 짝지어 쓰는 이유입니다.

MFA Delete

MFA Delete를 켜면 다음 두 작업에 MFA 장치의 인증 코드가 추가로 필요합니다.

  • 객체 버전의 영구 삭제
  • 버킷의 버전 관리 상태 변경

제약이 까다롭습니다. 버킷을 소유한 계정의 루트 사용자만 활성화할 수 있고, 콘솔로는 켤 수 없어 AWS CLI나 API를 써야 하며, 수명 주기 구성과 함께 쓸 수 없습니다. 요청은 HTTPS여야 합니다.

Object Lock — WORM 보존

S3 Object Lock은 한 번 쓰면 여러 번 읽을 수 있는(write-once-read-many, WORM) 모델로 객체 버전을 보호합니다. 규정 준수 요구를 만족시키는 장치입니다. 버전 관리가 켜져 있어야 하고, 보호는 객체 버전 단위로 적용됩니다.

Object Lock의 보존 모드와 법적 보존
방식 동작 해제
거버넌스 모드(Governance) 대부분의 사용자가 삭제·덮어쓰기를 할 수 없다 s3:BypassGovernanceRetention 권한이 있으면 우회할 수 있다
규정 준수 모드(Compliance) 계정의 루트 사용자를 포함해 누구도 삭제·덮어쓰기를 할 수 없다 불가 — 보존 모드 변경도, 보존 기간 단축도 안 된다
법적 보존(Legal hold) 기간 없이 무기한 보호한다 권한을 가진 사용자가 명시적으로 해제한다

보존 기간은 객체마다 직접 지정하거나 버킷 기본 설정으로 줄 수 있습니다. 기본 설정을 쓰면 객체가 들어올 때마다 생성 시각에 기간을 더해 보존 만료 시각이 계산됩니다. 같은 키에 새로 PUT하면 새 버전이 만들어지고 이전 버전은 원래 보존 기간을 유지합니다.

"감사 기간 동안 어떤 방법으로도 데이터를 지울 수 없어야 한다"는 요구는 Object Lock 규정 준수 모드를 지목합니다. 루트 사용자조차 지울 수 없다는 점이 다른 어떤 통제와도 구별되는 성질입니다.

"실수로 지우는 것을 막되 필요하면 관리자가 해제할 수 있어야 한다"면 거버넌스 모드입니다. 여기에 "자격 증명이 유출되어도 지워지면 안 된다"가 더해지면 MFA Delete가 후보에 들어옵니다. 세 장치가 노리는 위협이 서로 다릅니다.

복제 — CRR과 SRR은 목적이 다르다

복제(replication)는 버킷 사이에 객체를 자동으로, 비동기적으로 복사합니다. 원본과 대상 버킷은 같은 계정일 수도 다른 계정일 수도 있습니다.

복제의 전제 조건과 기본 동작

  • 원본과 대상 버킷 양쪽에 버전 관리가 켜져 있어야 합니다.
  • S3가 대신 복사할 수 있도록 IAM 역할을 지정해야 합니다.
  • 기본적으로 복제 규칙을 추가한 뒤에 생성된 객체만 복제됩니다. 이미 있던 객체를 옮기려면 S3 배치 복제(Batch Replication)를 별도로 실행합니다.
  • 원본 버킷에 Object Lock이 켜져 있으면 대상 버킷에도 켜져 있어야 합니다.
  • 대상 버킷은 Requester Pays 버킷일 수 없습니다(교차 계정 구성에서).

삭제 동작이 특히 자주 출제됩니다. 버전 ID를 명시한 삭제는 대상 버킷에 전파되지 않습니다 — 악의적·실수 삭제로부터 사본을 지키기 위한 설계입니다. 버전 ID 없이 삭제해 생긴 삭제 마커는 최신 규칙 형식에서 기본적으로 복제되지 않고, 필요하면 삭제 마커 복제를 따로 켜야 합니다.

복제로 함께 넘어가는 것과 넘어가지 않는 것도 구분해 둡니다. 객체 메타데이터·태그·ACL 갱신·Object Lock 보존 정보는 함께 복제되고, 다른 규칙이 만들어 낸 복제본은 다시 복제되지 않습니다(연쇄 복제 없음). 복제 시 대상의 스토리지 클래스를 바꾸거나 복제본 소유자를 대상 계정으로 바꿀 수 있습니다.

복제 시간이 예측 가능해야 한다면 S3 복제 시간 제어(S3 RTC)를 켭니다. 신규 객체의 99.99%를 15분 안에 복제하며 서비스 수준 계약이 뒷받침합니다. 배치 복제에는 적용되지 않습니다.

"복제를 켰는데 기존 데이터가 대상 버킷에 없다"는 시나리오의 원인은 거의 언제나 규칙 생성 이전 객체는 복제되지 않는다는 기본 동작입니다. 정답은 배치 복제이고, "복제 규칙을 다시 만든다"는 선택지는 효과가 없습니다.

"원본에서 실수로 지운 객체가 사본에서도 사라지면 안 된다"는 요구에는 삭제 마커 복제를 켜지 않는 것이 답입니다. 반대로 "두 버킷을 완전히 동일하게 유지"가 요구되면 삭제 마커 복제를 켭니다. 기본값이 "켜지지 않음"이라는 점이 핵심입니다.

암호화 — 키를 누가 쥐는가 SAA 빈출

서버 측 암호화에는 서로 배타적인 네 가지 옵션이 있습니다. 기능 차이가 아니라 키를 누가 만들고, 누가 보관하고, 사용 기록이 어디에 남는가가 다릅니다. 선택 기준도 거기서 나옵니다.

SSE-KMS aws:kms AWS KMS 키를 쓴다. 고객 관리형 키를 지정할 수 있다 키 정책으로 접근을 통제하고, 키 사용 호출을 CloudTrail로 감사하며, 교체 주기를 통제해야 한다
DSSE-KMS aws:kms:dsse KMS 키로 이중 계층 암호화를 적용한다 규정이 다중 계층 암호화를 명시적으로 요구한다
SSE-C 요청 헤더로 키 전달 고객이 키를 제공하고 S3는 저장하지 않는다 키를 AWS 밖에서 관리해야 한다. 키를 잃으면 데이터를 영원히 못 읽는다

SSE-KMS에서 키를 지정하지 않으면 AWS 관리형 키(aws/s3)가 쓰이고, 고객 관리형 키를 지정하면 키 정책·권한 부여·교체를 직접 통제할 수 있습니다. 키 사용은 KMS API 호출이므로 CloudTrail에 남고, 이것이 감사 요구가 있을 때 SSE-KMS가 답이 되는 이유입니다.

대신 객체마다 KMS 호출이 발생하므로 요청량이 많으면 KMS 요청 한도에 걸릴 수 있습니다. S3 버킷 키(S3 Bucket Key)를 켜면 KMS 호출 횟수를 줄일 수 있습니다.

SSE-C는 키를 요청마다 함께 보내고 S3는 그 키를 저장하지 않습니다. 암호화에 쓴 뒤 폐기하므로, 키를 분실하면 객체를 복호화할 방법이 없습니다. 키가 요청에 실려 가므로 HTTPS가 필수입니다.

네 가지 모두 서버 측 암호화입니다. 클라이언트 측 암호화(client-side encryption)는 별개로, 데이터를 S3에 보내기 전에 애플리케이션이 직접 암호화하는 방식입니다. "AWS가 평문을 절대 볼 수 없어야 한다"는 요구에만 씁니다.

암호화 문항은 요구 문장 하나로 답이 정해집니다.

  • "암호화되어야 한다"만 있다 — SSE-S3로 충분합니다. 신규 객체는 이미 그렇게 암호화되므로 추가 조치가 필요 없을 수도 있습니다.
  • "키 사용을 감사해야 한다", "키 접근을 정책으로 통제", "교체 주기 관리" — SSE-KMS, 그중에서도 고객 관리형 키입니다.
  • "키를 온프레미스에서 관리해야 한다", "AWS에 키를 두면 안 된다" — SSE-C 또는 클라이언트 측 암호화입니다.
  • "이중 계층 암호화가 규정 요구" — DSSE-KMS입니다.

"암호화되지 않은 업로드를 거부하라"는 요구는 암호화 방식 선택이 아니라 버킷 정책의 조건으로 푸는 문제입니다. s3:x-amz-server-side-encryption 조건 키로 Deny를 겁니다.

접근 제어 — 요청은 어디서 막히는가

버킷 정책과 ACL

접근 제어 수단은 세 가지입니다. IAM 정책(주체에 붙임), 버킷 정책(리소스에 붙임), 그리고 ACL(현행 기본값에서는 비활성)입니다.

  • 버킷 정책은 리소스 기반 정책이므로 다른 계정에 권한을 줄 수 있습니다. 교차 계정 접근의 기본 수단입니다.
  • IAM 정책은 같은 계정 안의 주체에게 권한을 줍니다. 자격 증명 기반 정책과 리소스 기반 정책은 같은 계정에서 합집합으로 동작합니다 (2장 IAM과 자격 증명).
  • ACL은 BucketOwnerEnforced에서 완전히 비활성입니다. ACL로 접근을 제어하는 설계는 더 이상 기본 구성이 아닙니다.

퍼블릭 액세스 차단은 이 모든 것보다 앞에서 동작합니다. 버킷 정책이 퍼블릭 접근을 허용하더라도 차단이 켜져 있으면 요청은 거부됩니다. 계정 수준과 버킷 수준 양쪽에서 설정할 수 있고, 어느 한쪽이라도 차단하면 차단됩니다.

프리사인 URL — 서명자의 권한을 빌린다

프리사인 URL(presigned URL)은 버킷 정책을 고치지 않고 한시적으로 객체를 내려받거나 올릴 수 있게 하는 장치입니다. 핵심 성질은 하나입니다 — URL은 그것을 만든 주체의 자격 증명과 권한으로 동작합니다. 받는 쪽은 AWS 자격 증명이 없어도 되고, 만든 쪽이 권한이 없으면 URL도 동작하지 않습니다.

프리사인 URL의 유효 기간 — 서명에 쓴 자격 증명이 상한을 정한다
서명에 쓴 자격 증명 최대 유효 기간
IAM 인스턴스 프로파일 최대 6시간
AWS STS 임시 자격 증명 영구 자격 증명으로 서명한 경우 최대 36시간
IAM 사용자 (서명 버전 4) 최대 7일

콘솔에서 만들면 1분에서 12시간 사이로 지정할 수 있고, AWS CLI나 SDK로 만들면 최대 7일까지 지정할 수 있습니다. 임시 자격 증명으로 만들었다면 URL에 적힌 만료 시각과 무관하게 자격 증명이 만료되는 순간 URL도 만료됩니다. 만료 전까지는 여러 번 재사용할 수 있습니다.

정적 웹사이트 호스팅

버킷을 정적 웹사이트로 게시할 수 있습니다. 인덱스 문서와 오류 문서를 지정하고 리다이렉션 규칙을 줄 수 있습니다. 시험에서 주의할 점은 두 가지입니다.

  • S3 웹사이트 엔드포인트는 HTTPS를 제공하지 않습니다. HTTPS가 필요하면 앞에 Amazon CloudFront를 둡니다.
  • 웹사이트 엔드포인트로 서비스하려면 객체가 공개되어야 합니다. 버킷을 비공개로 유지하면서 배포하는 방법이 CloudFront + 오리진 액세스 제어(OAC)이고, 이쪽이 대부분 문항의 정답입니다.

Requester Pays

기본적으로 버킷 소유자가 저장 요금과 데이터 전송 요금을 모두 냅니다. Requester Pays를 켜면 요청자가 요청 요금과 다운로드 요금을 내고, 소유자는 저장 요금만 냅니다. 공개 데이터셋을 배포하되 전송 비용을 떠안고 싶지 않을 때 씁니다.

  • 익명 요청을 허용하지 않습니다. 모든 요청이 인증되어야 요금을 청구할 대상을 특정할 수 있습니다.
  • 요청자는 x-amz-request-payer 헤더를 붙여 과금에 동의했음을 밝혀야 합니다. 빠뜨리면 403이 반환되고 그 요청 요금은 버킷 소유자가 냅니다.
  • 요청자가 IAM 역할을 맡아 호출하면 역할이 속한 계정이 청구 대상입니다.

"특정 사용자에게 한시적으로 파일 하나를 주고 싶다"는 요구의 답은 프리사인 URL입니다. 버킷을 공개하거나 IAM 사용자를 새로 만드는 선택지는 모두 과잉이며 보안 한정어가 붙으면 확실한 오답입니다.

"대용량 공개 데이터셋을 배포하는데 전송 요금 부담이 크다"면 Requester Pays입니다. 다만 익명 접근이 불가능해지므로 "누구나 로그인 없이 받을 수 있어야 한다"는 조건과는 양립하지 않습니다.

성능 — 접두사, 멀티파트, 전송 가속화

접두사별 요청 성능

S3는 요청률에 맞춰 자동으로 확장합니다. 확인된 기준은 파티션된 접두사 하나당 초당 최소 3,500건의 PUT·COPY·POST·DELETE와 초당 최소 5,500건의 GET·HEAD입니다. 버킷 안의 접두사 개수에는 제한이 없습니다.

그래서 읽기 성능을 늘리는 방법은 단순합니다 — 접두사를 나눠 병렬화합니다. 접두사 10개로 나누면 초당 55,000건의 읽기까지 확장할 수 있습니다. 다만 확장은 점진적이며 즉시 일어나지 않습니다. 확장이 진행되는 동안 503 Slow Down 오류가 보일 수 있고, 확장이 끝나면 사라집니다.

"키 앞에 임의의 해시를 붙여 성능을 올린다"는 조언은 옛 기준입니다. 예전에는 키 접두사의 사전 순 분포가 파티션 분할에 영향을 주어 무작위 접두사를 권장했지만, 현재 기준은 접두사를 논리적으로 나누어 병렬 요청을 분산하는 것입니다. 날짜나 테넌트 기준의 읽기 쉬운 접두사 설계로 충분합니다.

멀티파트 업로드

큰 객체는 멀티파트 업로드로 나누어 병렬 전송합니다. 처리량이 올라가고, 실패한 파트만 다시 올리면 되며, 업로드를 중간에 멈췄다 재개할 수 있습니다.

  • 파트 번호는 1부터 10,000까지입니다.
  • 각 파트는 최소 5 MB여야 합니다. 마지막 파트에는 최소 크기 제한이 없습니다.
  • 같은 파트 번호로 다시 올리면 이전 파트를 덮어씁니다.
  • 완료(CompleteMultipartUpload)하거나 중단(AbortMultipartUpload)하기 전까지 올라간 파트에 저장 요금이 계속 부과됩니다 (불완전 멀티파트 업로드 정리).

내려받을 때는 바이트 범위 요청(byte-range fetch)으로 한 객체를 여러 구간으로 나누어 병렬로 받을 수 있습니다. 앞부분만 필요할 때 앞부분만 받는 용도로도 씁니다.

Transfer Acceleration

S3 Transfer Acceleration은 버킷 단위 기능으로, Amazon CloudFront의 엣지 로케이션에 먼저 데이터를 받은 뒤 AWS 내부의 최적화된 경로로 버킷까지 전달합니다. 멀리 떨어진 클라이언트가 한 버킷으로 대용량을 올릴 때 효과가 있습니다.

  • 버킷 이름이 DNS 규칙에 맞아야 하고 마침표를 포함하면 안 됩니다.
  • 가상 호스팅 방식 요청만 지원하며 s3-accelerate 엔드포인트를 씁니다.
  • 켠 뒤 전송 속도가 올라가기까지 최대 20분이 걸릴 수 있습니다.
  • 모든 리전에서 지원하지는 않으며, 추가 데이터 전송 요금이 발생할 수 있습니다.

업로드 성능 문항의 구분입니다.

  • "파일 하나가 아주 크다" — 멀티파트 업로드입니다.
  • "전 세계 사용자가 먼 리전의 버킷으로 올린다" — Transfer Acceleration입니다.
  • "요청 수가 많아 503 Slow Down이 난다" — 접두사를 나누어 분산합니다.
  • "전 세계 사용자에게 내려주는 속도" — S3가 아니라 CloudFront의 문제입니다(14장).

Transfer Acceleration과 CloudFront를 바꿔 고르는 것이 흔한 실수입니다. 올리는 쪽이면 Transfer Acceleration, 내려주는 쪽이면 CloudFront로 기억합니다.

흔한 오해

"S3는 최종적 일관성이라 쓴 직후 읽으면 옛 데이터가 나올 수 있다" — 2020년 12월부터 모든 리전에서 강력한 읽기 후 쓰기 일관성을 제공합니다. 신규 객체 업로드뿐 아니라 덮어쓰기와 삭제, 그리고 목록 조회까지 최신 상태를 반환합니다. 이 서술이 참이었던 시기가 있었기 때문에 지금도 자료에 그대로 남아 있는 것인데, 그 자료로 공부하면 일관성을 확보하려고 불필요한 구성 요소를 덧붙이는 오답을 고르게 됩니다.

"S3 버킷은 기본적으로 열려 있으니 퍼블릭 액세스 차단을 켜고 ACL을 정리해야 한다" — 2023년 이후 신규 버킷은 퍼블릭 액세스 차단이 켜진 채로, ACL이 비활성인 채로, 신규 객체가 SSE-S3로 자동 암호화된 채로 만들어집니다. "차단을 켠다", "기본 암호화를 활성화한다", "객체 ACL을 조정한다"는 조치는 이미 되어 있거나 동작하지 않는 것들입니다. 다만 버전 관리는 여전히 꺼져 있습니다 — 여기까지 묶어서 "다 켜져 있다"고 외우면 반대로 틀립니다.

"수명 주기 규칙을 걸었으니 오래된 데이터는 알아서 정리되고 비용도 준다" — 전환 규칙에는 Standard-IA·One Zone-IA로 가려면 최소 30일이라는 하한이 있고, 128 KB 미만 객체는 아예 전환되지 않습니다. 또 버전 관리 버킷에서 현재 버전을 만료시키면 삭제 마커가 생길 뿐 데이터는 남아 비현재 버전 만료를 따로 걸어야 용량이 줄고, 불완전 멀티파트 업로드는 객체 목록에 보이지 않으면서 계속 과금됩니다. 세 가지를 함께 걸지 않으면 요금은 계속 늘어납니다.
