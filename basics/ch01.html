기본개념 · 1장

AWS 글로벌 인프라와 계정 기초

SAA 문항의 상당수는 서비스 하나를 아는지가 아니라 어디에 배치했는가와 누구의 책임인가를 묻습니다. 가용 영역(Availability Zone, AZ)을 몇 개 썼는지, 데이터가 리전 경계를 넘는지, 문제에서 깨진 것이 AWS의 몫인지 우리의 몫인지가 정답을 가릅니다. 이 장은 나머지 17장이 전부 딛고 서는 그 바닥을 깔아 둡니다.

이 장은 특정 도메인에 속하지 않고 4개 도메인 전체의 전제가 됩니다. 여기서 정리한 어휘로 2장부터의 설명이 진행됩니다.

학습 목표

  • 리전 · 가용 영역 · 로컬 존 · Wavelength 존 · 엣지 로케이션의 역할을 구분하고, 어떤 요구사항이 어느 계층을 부르는지 판단할 수 있습니다.
  • 가용 영역이 데이터센터 한 동이 아니라는 점과, 가용 영역 이름과 가용 영역 ID의 차이를 설명할 수 있습니다.
  • 리전 선택을 지연 시간 · 규정 준수 · 서비스 가용성 · 비용 네 가지 기준으로 근거를 들어 설명할 수 있습니다.
  • 책임 공유 모델의 경계가 Amazon EC2 · AWS Lambda · Amazon S3에서 각각 어디에 그어지는지 구분할 수 있습니다.
  • Well-Architected 6개 기둥을 나열하고, SAA 4개 도메인이 어느 기둥에 대응하는지 설명할 수 있습니다.
  • 루트 사용자를 일상 작업에 쓰지 않는 이유와 다중 계정 전략의 근거를 설명할 수 있습니다.
  • 데이터 전송 요금이 방향에 따라 달라진다는 사실을 근거로 비용 문항의 오답을 소거할 수 있습니다.

글로벌 인프라 — 리전, 가용 영역, 그리고 그 바깥

AWS의 물리 인프라는 세 겹으로 되어 있습니다. 리소스를 실제로 실행하는 리전과 가용 영역, 리전보다 사용자에게 더 가까이 컴퓨팅을 밀어 넣는 로컬 존과 Wavelength 존, 그리고 콘텐츠를 캐시해 응답하는 엣지 네트워크입니다. 시험 문항은 요구사항의 성격으로 이 셋 중 하나를 지목합니다.

리전 — 격리의 기본 단위

리전은 지리적으로 분리된 영역이며, 각 리전은 독립적으로 동작합니다. 기본적으로 리소스는 리전 밖으로 복제되지 않고, API 호출도 리전 엔드포인트로 나뉩니다. 리전 간 복제는 우리가 명시적으로 구성해야 일어납니다 — Amazon S3 교차 리전 복제, Amazon RDS 스냅샷 복사, Amazon DynamoDB 글로벌 테이블이 모두 그런 예입니다.

이 격리는 규정 준수 요구사항을 만족시키는 근거가 됩니다. "데이터가 국경을 넘어서는 안 된다"는 조건이 붙으면, 답은 리전을 고정하고 리전 간 복제를 켜지 않는 설계입니다.

계정 수준에서 리전은 활성화 상태를 가집니다. 오래된 리전은 기본으로 켜져 있지만 (ENABLED_BY_DEFAULT), 나중에 추가된 리전은 계정에서 옵트인해야 사용할 수 있습니다. 쓰지 않는 리전을 꺼 두는 것 자체가 공격 표면을 줄이는 통제입니다.

계정에서 어떤 리전이 켜져 있는지는 account API로 조회합니다. 조직에 속한 계정이라면 관리 계정에서 --account-id로 다른 계정의 상태도 볼 수 있습니다.

가용 영역 — 데이터센터 한 동이 아니다 SAA 빈출

가용 영역(Availability Zone, AZ)은 하나 이상의 개별 데이터센터로 구성된 논리 단위입니다. 각 가용 영역은 독립된 전원 · 냉각 · 물리 보안을 갖추고, 같은 리전의 다른 가용 영역과는 저지연 네트워크로 연결됩니다. 즉 가용 영역 하나 안에도 이미 여러 건물이 있고, 가용 영역을 나누는 이유는 건물이 아니라 장애 도메인을 나누는 것입니다.

여기서 실무와 시험 양쪽의 결론이 하나로 모입니다. 같은 가용 영역 안에서 인스턴스를 여러 대 띄우는 것은 고가용성이 아닙니다. 전원이나 네트워크 수준의 사고는 가용 영역 단위로 발생하기 때문입니다. 가용성을 올리려면 서로 다른 가용 영역에 배치해야 합니다.

가용 영역 이름과 가용 영역 ID

us-east-1a 같은 가용 영역 이름은 계정마다 다른 물리 가용 영역에 매핑됩니다. A 계정의 us-east-1a와 B 계정의 us-east-1a가 같은 곳이라는 보장이 없습니다. AWS가 계정별로 이름을 무작위로 배정해 특정 가용 영역에 부하가 몰리는 것을 막기 때문입니다.

반면 use1-az1 형태의 가용 영역 ID는 모든 계정에서 같은 물리 위치를 가리킵니다. EC2 API 문서는 AvailabilityZoneId에 대해 "계정 간에 일관된 식별자를 제공하므로 AvailabilityZone보다 이 옵션이 선호된다"고 명시합니다. 여러 계정이 VPC 서브넷을 공유하거나 계정 간 배치를 맞춰야 할 때는 이름이 아니라 ID로 이야기해야 합니다.

시나리오에 "가장 가용성이 높은(MOST highly available)"이 붙으면 가장 먼저 확인할 것은 인스턴스 대수가 아니라 가용 영역이 몇 개인가입니다. 단일 가용 영역에 인스턴스를 늘리는 선택지, 단일 가용 영역에만 NAT 게이트웨이를 두는 선택지는 그 자리에서 소거 대상입니다.

리전마다 가용 영역 개수가 다르므로 "가용 영역은 몇 개다"라고 외우지 않습니다. 설계할 때도 개수를 하드코딩하지 말고 조회해서 씁니다.

로컬 존과 Wavelength 존 — 옵트인해야 보인다

EC2 API는 존을 availability-zone, local-zone, wavelength-zone 세 가지 유형으로 구분합니다. 뒤의 두 가지는 부모 리전에 딸린 확장이며, API 호출 같은 제어 평면 작업의 일부를 부모 존이 대신 처리합니다.

존 유형별 성격과 옵트인 여부
항목 API 값 무엇인가 옵트인
가용 영역 availability-zone 리전을 구성하는 표준 장애 격리 단위. 대부분의 서비스가 여기에 배치된다 불필요 — 항상 opt-in-not-required
로컬 존 local-zone 리전에서 먼 대도시권에 컴퓨팅·스토리지를 배치해 한 자릿수 밀리초 지연이 필요한 워크로드를 담는다 필요 — 켜야 목록에 나타난다

시험에서는 표현이 갈림길이 됩니다. "특정 도시의 사용자에게 매우 낮은 지연"이면 로컬 존, "5G 이동통신 단말"이면 Wavelength, "온프레미스 데이터센터 안에서 AWS API를 그대로"면 Outposts입니다 (Outposts는 4장 VPC 연결과 하이브리드에서 다룹니다).

엣지 로케이션과 리전 엣지 캐시

엣지 로케이션은 리전 바깥에 훨씬 촘촘하게 배치된 지점으로, Amazon CloudFront가 콘텐츠를 캐시하고 Amazon Route 53이 DNS 질의에 응답하는 곳입니다. 엣지에서 캐시 미스가 나면 곧바로 오리진으로 가지 않고 리전 엣지 캐시를 한 번 더 거칠 수 있습니다. CloudFront 문서는 Origin Shield를 끄면 "여러 엣지 로케이션이나 리전 엣지 캐시에서 오리진으로 직접 요청이 갈 수 있다"고 설명합니다. 이 중간 계층이 오리진 부하를 줄여 줍니다.

정적 콘텐츠의 전송 지연이면 CloudFront(엣지 캐시), 동적·비HTTP 트래픽의 지연과 장애 조치면 AWS Global Accelerator, 특정 도시의 컴퓨팅 지연이면 로컬 존입니다. 셋을 한 문항에 섞어 놓는 것이 전형적인 출제 형태입니다. 자세한 동작은 14장 엣지와 DNS에서 다룹니다.

"가까운 곳을 고른다"는 답이 아닙니다. 실제로는 네 가지를 함께 저울질합니다.

네 기준이 충돌할 때의 우선순위는 문제문이 정해 줍니다. 규정 준수 제약이 명시되면 그것이 다른 세 가지를 이깁니다 — 명시된 제약을 위반하는 선택지는 아무리 싸고 빨라도 오답이기 때문입니다.

책임 공유 모델 — 선이 어디에 그어지는가

AWS는 보안 책임을 둘로 나눕니다. 클라우드 자체의 보안(security of the cloud)은 AWS가, 클라우드 안의 보안(security in the cloud)은 고객이 맡습니다. AWS는 하드웨어 · 물리 시설 · 리전과 가용 영역을 잇는 네트워크 · 하이퍼바이저를 책임지고, 고객은 그 위에 올린 데이터 · 자격 증명 · 권한 · 네트워크 구성 · 암호화 선택을 책임집니다.

서비스 유형에 따라 경계가 움직인다

모델을 외우기만 하면 문항을 놓칩니다. 핵심은 경계선이 고정되어 있지 않다는 점입니다. 관리형 서비스일수록 AWS가 가져가는 몫이 커지고, 고객의 몫은 위쪽으로 좁아집니다.

표의 마지막 두 줄이 핵심입니다. 데이터와 권한은 어떤 서비스를 쓰든 항상 고객 책임입니다. Amazon RDS처럼 중간에 있는 서비스도 마찬가지여서, 데이터베이스 엔진과 운영체제 패치는 AWS가 수행하지만 스키마 · 데이터베이스 사용자 · 네트워크 배치 · 암호화 여부는 고객이 정합니다.

Amazon S3 버킷이 인터넷에 노출되어 데이터가 유출된 사고는 전부 고객 책임 영역에서 일어납니다. AWS는 버킷 정책을 대신 써 주지 않습니다. 현재 신규 버킷은 퍼블릭 액세스 차단이 켜진 상태로 만들어지지만, 그 차단을 해제하는 것은 여전히 고객이 할 수 있는 선택입니다. 기본값이 안전해진 것이지 책임이 옮겨 간 것이 아닙니다 (8장 S3와 오브젝트 스토리지).

가장 자주 나오는 형태는 "다음 중 고객의 책임인 것은 무엇입니까"이고, 정답 후보는 거의 언제나 이 넷 중 하나입니다 — IAM 권한 설정 · 게스트 운영체제 패치(EC2에 한함) · 데이터 암호화 선택 · 보안 그룹과 네트워크 ACL 규칙.

반대로 물리적 데이터센터 보안 · 하드웨어 폐기 · 하이퍼바이저 패치가 선택지에 있으면 그것은 AWS의 몫입니다. 한 가지 함정은 "EC2 인스턴스의 운영체제 패치"인데, 같은 문장이 Lambda나 RDS 문맥에서는 AWS의 몫이 됩니다. 서비스 이름을 먼저 보고 경계선을 다시 그으세요.

Well-Architected Framework — 6개 기둥과 시험 도메인

AWS Well-Architected Framework는 설계를 평가하는 여섯 가지 관점입니다. SAA는 이 프레임워크를 직접 묻지는 않지만, 문항의 한정어가 곧 기둥의 이름이라 기둥을 알면 무엇이 우선인지 빨리 판단할 수 있습니다.

Well-Architected 6개 기둥과 이 사이트의 한국어 표기
기둥 영문 무엇을 묻는가
운영 우수성 Operational Excellence 변경을 안전하게 배포하고 운영에서 배우는가
보안 Security 자격 증명 · 권한 · 암호화 · 추적으로 자산을 보호하는가
안정성(Reliability, 신뢰성으로도 번역됨) Reliability 장애에서 복구하고 수요 변화에 맞춰 동작을 유지하는가
성능 효율성 Performance Efficiency 컴퓨팅 자원을 요구에 맞게 쓰고 유지하는가
비용 최적화 Cost Optimization 가장 낮은 비용으로 비즈니스 가치를 내는가
지속 가능성 Sustainability 워크로드의 환경 영향을 줄이는가

AWS 한국어 문서는 Reliability를 "안정성"과 "신뢰성"으로 혼용합니다. 이 사이트는 안정성으로 통일하며, 처음 나올 때만 안정성(Reliability, 신뢰성으로도 번역됨)으로 병기합니다. 시험에서 한국어 번역이 "신뢰성"으로 나오더라도 같은 기둥입니다.

기둥과 SAA 도메인의 대응

SAA의 4개 도메인은 기둥 2번부터 5번까지에 그대로 대응합니다. 운영 우수성과 지속 가능성은 개념 이해용으로만 다루면 충분합니다 — 이 사이트가 두 기둥에 지면을 적게 쓰는 이유도 여기에 있습니다.

계정, 루트 사용자, 그리고 AWS Organizations

AWS 계정은 청구의 단위이자 격리의 단위입니다. 계정이 다르면 리소스 이름이 겹쳐도 상관없고, 한 계정에서 권한을 잘못 준 실수가 다른 계정으로 번지지 않습니다. 이 성질이 다중 계정 전략의 출발점입니다.

루트 사용자를 쓰지 않는 이유

루트 사용자는 계정을 만들 때 생기는 이메일 주소로 로그인하는 최상위 자격 증명이며, 계정 안의 모든 리소스에 대해 제한 없는 권한을 가집니다. IAM 정책으로 루트의 권한을 줄일 수 없고, 서비스 제어 정책(SCP)만이 조직 멤버 계정의 루트에 상한을 걸 수 있습니다.

문제는 이 권한이 회수도 추적도 어렵다는 점입니다. 루트 자격 증명이 유출되면 계정 전체가 넘어가고, 누가 무엇을 했는지 구분할 수도 없습니다. 그래서 실무 표준은 다음과 같습니다.

  • 루트 사용자에 MFA를 활성화하고 자격 증명을 잠가 둡니다.
  • 루트 액세스 키를 만들지 않습니다. 이미 있다면 삭제합니다.
  • 일상 작업은 IAM 역할이나 AWS IAM Identity Center로 발급받은 임시 자격 증명으로 합니다.
  • 계정 이메일 변경, 계정 해지처럼 루트만 할 수 있는 작업일 때만 로그인합니다.

루트 사용자로 장기 액세스 키를 발급해 배포 파이프라인에 심습니다. 키가 유출되면 계정 전체가 넘어가고, 감사 로그에는 모든 작업이 "루트"로만 남습니다.

루트는 MFA를 켜고 잠가 둔 채, 배포에 필요한 권한만 가진 역할을 맡습니다. 자격 증명은 만료되고, 감사 로그에는 어떤 역할이 어떤 세션으로 호출했는지 남습니다.

"EC2 인스턴스나 CI에 액세스 키를 심는다"는 선택지는 SAA에서 거의 항상 오답입니다. 정답은 IAM 역할입니다. 역할은 임시 자격 증명을 자동으로 교체해 주므로 유출된 키를 회수할 일 자체가 생기지 않습니다. 정책 문서 구조와 평가 로직은 2장 IAM과 자격 증명에서 다룹니다.

AWS Single Sign-On은 2022년에 AWS IAM Identity Center로 이름이 바뀌었습니다. 옛 자료에 나오는 "AWS SSO"는 같은 서비스이며, 시험과 이 사이트에서는 새 이름을 씁니다.

AWS Organizations — 조직, OU, SCP

AWS Organizations는 여러 계정을 하나의 조직으로 묶습니다. 조직을 만든 계정이 관리 계정이 되고, 나머지는 멤버 계정입니다. 계정은 조직 단위(Organizational Unit, OU)로 묶어 계층을 만들며, 정책은 조직 루트 · OU · 개별 계정 중 어디에나 붙일 수 있습니다.

조직을 만들 때 기능 집합을 고릅니다. 전체 기능(ALL)으로 만들면 조직 루트에 서비스 제어 정책이 자동으로 활성화됩니다. 통합 결제 전용(CONSOLIDATED_BILLING)으로 만들면 어떤 정책 유형도 활성화되지 않고 조직 정책을 쓸 수 없습니다. 시나리오에 "여러 계정에 일괄적으로 가드레일을 걸어야 한다"가 나오면 전체 기능이 전제입니다.

서비스 제어 정책(Service Control Policy, SCP)의 성질은 두 문장으로 요약됩니다.

  • SCP는 권한을 부여하지 않습니다. 최대 권한의 상한(guardrail)만 정합니다. 실제 허용은 여전히 IAM 정책이 해야 합니다.
  • SCP는 멤버 계정의 루트 사용자에게도 적용됩니다. IAM 정책으로는 막을 수 없는 루트를 통제하는 유일한 수단입니다.

리전 개념이 없는 글로벌 서비스는 NotAction으로 빼 둡니다. 빼지 않으면 IAM 사용자 생성이나 Route 53 레코드 수정까지 함께 막혀 조직이 마비됩니다. SCP 평가가 IAM 정책과 어떻게 결합하는지는 2장 IAM과 자격 증명에서 자세히 다룹니다.

이 세 가지는 18장 비용 최적화·마이그레이션·재해 복구와 비용 빠른참조에서 수치 없이 구조로 정리합니다.

시험 범위 — 무엇을 공부하고 무엇을 버릴 것인가

AWS는 SAA-C03 시험 가이드에서 범위 안 서비스와 범위 밖 서비스를 각각 목록으로 공개합니다. 범위 밖 목록을 먼저 읽는 편이 시간을 아낍니다. 여기 있는 서비스는 문항에 정답으로 등장하지 않습니다.

범위 안 — 이 사이트가 다루는 영역

컴퓨팅(EC2 · Lambda · ECS · EKS), 스토리지(S3 · EBS · EFS · FSx), 데이터베이스(RDS · Aurora · DynamoDB · ElastiCache), 네트워킹(VPC · Route 53 · CloudFront · ELB), 보안(IAM · KMS · WAF · Shield · GuardDuty), 통합(SQS · SNS · EventBridge · Step Functions), 관리(CloudWatch · CloudTrail · Config · Systems Manager · CloudFormation). 18장 커리큘럼은 이 범위를 도메인 가중치에 맞춰 배분한 것입니다.

AWS CloudFormation은 시험 범위 안이고, AWS CDK는 범위 밖입니다. 둘 다 코드형 인프라라서 나란히 배우고 싶어지지만, 시험 대비 관점에서는 CloudFormation의 템플릿 구조 · 스택 · 변경 세트만 익히면 충분합니다. CDK는 이 사이트에서 학습 대상으로 다루지 않습니다.

Aurora DSQL, S3 Tables, S3 Vectors처럼 최근에 나온 서비스도 같은 취급입니다. 이름을 들어 본 정도면 되고, 시험 답으로 나오지 않습니다.

흔한 오해

"가용 영역은 데이터센터 한 동이다" — 가용 영역은 하나 이상의 개별 데이터센터로 이루어진 논리 단위입니다. 그래서 "가용 영역 하나에 인스턴스를 두 대 두면 건물이 두 개니까 안전하다"는 계산이 성립하지 않습니다. 가용 영역의 의미는 건물 수가 아니라 전원 · 냉각 · 네트워크가 독립된 장애 도메인이라는 데 있습니다. 가용성을 올리는 유일한 방법은 가용 영역을 여러 개 쓰는 것입니다.

"리전은 가까운 곳을 고르면 된다" — 지연 시간은 네 가지 기준 중 하나일 뿐입니다. 규정 준수 제약이 있으면 그것이 먼저이고, 필요한 서비스가 그 리전에 없으면 설계 자체가 성립하지 않습니다. 비용도 리전마다 다릅니다. 특히 시험에서 "데이터가 특정 국가를 벗어나면 안 된다"는 문장이 나오면 그 순간 리전은 고정되고, 지연 시간을 이유로 다른 리전을 고르는 선택지는 전부 오답이 됩니다.

"책임 공유 모델이니까 보안은 AWS가 해 준다" — AWS가 책임지는 것은 클라우드 자체의 보안이며, 그 위에 무엇을 올리고 누구에게 열어 줄지는 전부 고객의 몫입니다. 실제 유출 사고의 대부분은 잘못된 버킷 정책, 과도한 IAM 권한, 공개된 보안 그룹처럼 고객 책임 영역에서 일어납니다. 더 나아가 경계선은 서비스마다 다릅니다 — 같은 "운영체제 패치"가 EC2에서는 고객 책임이고 Lambda에서는 AWS 책임입니다.

엣지 계층 선택 정적 캐시는 CloudFront, 비HTTP·동적은 Global Accelerator, 도시 단위 컴퓨팅은 로컬 존 모든 지연 문제에 CloudFront를 답으로 고름

책임 공유 — AWS의 몫 물리 시설, 하드웨어, 하이퍼바이저, 리전·가용 영역 간 네트워크 "보안 그룹 설정"까지 AWS가 한다고 착각
책임 공유 — 고객의 몫 데이터, 데이터 분류와 암호화 선택, IAM 권한, 네트워크 접근 제어 서비스가 관리형이면 데이터 보호까지 위임된다고 착각
경계선의 이동 EC2는 게스트 OS가 고객, Lambda·RDS는 OS와 엔진 패치가 AWS "OS 패치는 고객 책임"을 서비스 구분 없이 일반화
Well-Architected 기둥 운영 우수성 · 보안 · 안정성 · 성능 효율성 · 비용 최적화 · 지속 가능성 6개 지속 가능성을 빼고 5개로 외움

채점 방식 보상형 — 도메인별 과락 없음, 총점만 본다. 오답 감점도 없다 "보안에서 60% 미만이면 탈락"이라는 근거 없는 규칙을 믿음

루트 사용자 IAM 정책으로 제한할 수 없고, SCP만이 멤버 계정 루트에 상한을 건다 루트에 IAM 정책을 붙여 권한을 줄일 수 있다고 답함

CloudFormation 대 CDK CloudFormation은 범위 안, CDK는 범위 밖 CDK를 정답으로 고르거나 학습 시간을 씀
