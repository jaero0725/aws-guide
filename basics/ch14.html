기본개념 · 14장

엣지와 DNS

이 장은 요청이 리전에 닿기 전에 일어나는 일을 다룹니다. 어느 IP로 응답할지 정하는 Amazon Route 53, 응답을 엣지에서 대신 돌려주는 Amazon CloudFront, 캐시가 통하지 않는 트래픽을 AWS 백본에 빨리 태우는 AWS Global Accelerator입니다. 셋은 목적이 다르고, 시험은 요구사항의 성격으로 셋 중 하나를 지목합니다.

주 도메인은 고성능 아키텍처 설계(24%)이지만, 오리진 보호와 WAF 연결 지점은 보안 아키텍처 설계(30%), 장애 조치 라우팅은 복원력 있는 아키텍처 설계(26%)에 걸칩니다. 분량 대비 출제 밀도가 높은 장입니다.

학습 목표

  • CloudFront 배포의 오리진과 캐시 동작을 구분하고, 캐시 키를 무엇이 결정하는지 설명할 수 있습니다.
  • 원본 액세스 제어(Origin Access Control, OAC)로 Amazon S3 버킷을 비공개로 유지하는 구성을 버킷 정책 수준에서 작성할 수 있습니다.
  • 서명 URL과 서명 쿠키, 지리적 제한 중 어느 것이 요구사항에 맞는지 판단할 수 있습니다.
  • Route 53 라우팅 정책 8종을 나열하고, 지연 시간 기반 · 지리적 위치 · 지리 근접의 차이를 설명할 수 있습니다.
  • 상태 확인과 장애 조치 라우팅으로 리전 장애에 대응하는 설계를 구성할 수 있습니다.
  • Global Accelerator와 CloudFront 중 무엇을 고를지 프로토콜과 캐시 가능성으로 판단할 수 있습니다.

Amazon CloudFront — 배포, 오리진, 캐시 동작

CloudFront는 배포(distribution) 단위로 구성합니다. 배포 하나는 콘텐츠를 가져올 오리진(origin) 목록과, 요청 경로에 따라 어떻게 처리할지 정하는 캐시 동작(cache behavior) 목록을 가집니다. 배포를 만들면 d111111abcdef8.cloudfront.net 형태의 도메인 이름이 생기고, 자체 도메인을 쓰려면 대체 도메인 이름(alternate domain name, CNAME)을 등록합니다.

오리진 — S3, ALB, 그리고 커스텀 오리진

CloudFront는 오리진을 두 부류로 취급합니다. S3 REST 엔드포인트를 가리키는 S3 오리진과, 그 밖의 모든 것을 가리키는 커스텀 오리진입니다. API 문서는 커스텀 오리진을 "S3 버킷이 아닌 모든 오리진, 단 한 가지 예외가 있다"고 정의하는데, 그 예외가 정적 웹사이트 호스팅으로 구성된 S3 버킷입니다. 웹사이트 엔드포인트는 S3 오리진이 아니라 커스텀 오리진으로 등록해야 합니다.

이 구분이 시험에서 중요한 이유는 OAC를 쓸 수 있는지가 여기서 갈리기 때문입니다. 웹사이트 엔드포인트로 등록한 버킷에는 OAC도 OAI도 붙일 수 없습니다. S3를 비공개로 유지하면서 CloudFront로만 노출하려면 REST 엔드포인트 + OAC 조합이어야 합니다.

오리진과의 연결 방식은 OriginProtocolPolicy가 정합니다. 값은 http-only · https-only · match-viewer 세 가지이며, 엔드투엔드 암호화가 요구되면 https-only를 씁니다. 오리진 응답 타임아웃은 기본 30초(1~120초), 연결 유지(keep-alive) 타임아웃은 기본 5초(1~120초)입니다.

오리진을 오리진 그룹(origin group)으로 묶으면 기본 오리진이 지정한 상태 코드를 반환할 때 보조 오리진으로 넘어갑니다. 이것이 CloudFront 수준의 오리진 장애 조치이며, DNS 수준의 장애 조치인 Route 53 장애 조치 라우팅과는 계층이 다릅니다.

캐시 동작과 경로 패턴

배포에는 기본 캐시 동작이 정확히 하나 있어야 하고, 경로 패턴(images/*.jpg 같은)을 가진 추가 캐시 동작을 여러 개 둘 수 있습니다. 요청 경로는 캐시 동작이 나열된 순서대로 비교되며, 처음 일치한 동작이 적용됩니다. 정적 자산과 동적 API를 한 배포에서 다루려면 이 순서를 설계해야 합니다.

캐시 동작마다 대상 오리진, ViewerProtocolPolicy(allow-all · https-only · redirect-to-https), 허용 HTTP 메서드, 압축 여부, 그리고 세 가지 정책을 붙입니다.

캐시 동작에 붙는 세 가지 정책의 역할
정책 무엇을 정하는가 잘못 쓰면

캐시 동작의 ForwardedValues · MinTTL · DefaultTTL · MaxTTL 필드는 API 모델에서 deprecated로 표시되어 있고, AWS는 캐시 정책과 오리진 요청 정책을 쓰라고 안내합니다. "헤더를 전달(forward)하면 그만큼 캐시 키가 늘어난다"는 옛 설명은 지금도 개념적으로 맞지만, 구성 위치가 캐시 정책 안으로 옮겨졌다는 점을 기억합니다.

TTL — 무엇이 우선하는가

CloudFront 개발자 안내서는 기본적으로 파일이 24시간 후 만료된다고 명시합니다. 이 기본값은 두 가지 방법으로 바꿉니다. 캐시 동작 전체에 적용하려면 캐시 정책의 MinTTL · DefaultTTL · MaxTTL을 조정하고, 개별 파일만 바꾸려면 오리진이 Cache-Control: max-age 또는 s-maxage, 혹은 Expires 헤더를 붙여 내려보냅니다.

두 헤더를 모두 보내면 CloudFront는 Cache-Control max-age만 봅니다. 반대로 뷰어가 보낸 Cache-Control이나 Pragma 헤더는 무시합니다. 클라이언트가 헤더를 붙여 오리진까지 강제로 다녀오게 만들 수는 없습니다.

"정적 콘텐츠의 캐시 적중률을 높이려면"이라는 문제의 답은 거의 항상 캐시 키를 줄이는 것입니다. 불필요한 헤더 · 쿠키 · 쿼리 문자열을 캐시 키에서 빼고, 오리진이 필요로 하는 값은 오리진 요청 정책으로 옮깁니다. "엣지 로케이션을 늘린다", "TTL을 0으로 한다" 같은 선택지는 방향이 반대입니다.

캐시 무효화 — 마지막 수단이다

만료 전에 파일을 엣지 캐시에서 없애려면 무효화(invalidation)를 요청합니다. 경로는 /images/image1.jpg처럼 개별 파일이거나 /images/*처럼 * 와일드카드로 끝날 수 있습니다. 무효화는 대소문자를 구분하고, 쿠키나 헤더로 여러 벌이 캐시된 경우에는 모든 벌이 함께 무효화됩니다. 특정 벌만 골라 지울 수는 없습니다.

AWS 문서는 자주 바뀌는 파일에는 무효화가 아니라 버전이 붙은 파일 이름 (style.v3.css 같은)을 권장합니다. 이유는 세 가지입니다. 사용자 브라우저나 회사 프록시에 남은 캐시까지는 무효화가 닿지 않고, 액세스 로그에서 버전별 결과를 구분할 수 있으며, 되돌리기가 쉽습니다. 월별 무료 한도를 넘긴 무효화 경로에는 요금이 붙는다는 점도 이유에 들어갑니다.

오리진 보호 — OAC로 S3 버킷을 비공개로 유지한다

CloudFront 뒤에 S3를 두는 구성에서 버킷을 퍼블릭으로 여는 것은 오답입니다. 버킷이 퍼블릭이면 누구나 S3 엔드포인트로 직접 접근할 수 있어 CloudFront의 서명 URL · 지리적 제한 · WAF 규칙이 전부 우회됩니다. 정답은 버킷을 비공개로 두고, CloudFront가 서명한 요청만 버킷 정책으로 허용하는 것입니다.

원본 액세스 제어(OAC)

AWS는 S3 오리진에 인증된 요청을 보내는 방법으로 OAC와 구형인 원본 액세스 ID(Origin Access Identity, OAI) 두 가지를 제공하며, 문서는 OAC를 권장합니다. OAC가 지원하는 것 중 OAI가 못 하는 것은 다음 셋입니다.

  • 2022년 12월 이후 출시된 옵트인 리전을 포함한 모든 리전의 S3 버킷
  • SSE-KMS로 암호화된 객체 (KMS 키 정책에 OAC를 허용하는 문장을 추가해야 합니다)
  • PUT · DELETE 같은 동적 요청

OAC 자체는 서명 프로토콜(sigv4)과 서명 동작(always · never · no-override)만 정의합니다. 접근을 실제로 허용하는 것은 S3 버킷 정책이며, 이 점이 시험에서 자주 갈립니다.

AWS:SourceArn 조건이 없으면 다른 계정의 아무 배포나 이 버킷을 오리진으로 삼을 수 있습니다. 조건을 빼먹은 정책은 "CloudFront만 허용했다"고 착각하기 쉬운 대표적인 잘못된 구성입니다.

"S3에 저장된 정적 콘텐츠를 CloudFront로 배포하되 버킷에 직접 접근하지 못하게 하라"는 시나리오의 정답 조합은 OAC + 퍼블릭 액세스 차단 유지 + 버킷 정책에 cloudfront.amazonaws.com 허용입니다. "버킷을 퍼블릭으로 만들고 CloudFront를 앞에 둔다", "버킷 ACL로 CloudFront에 읽기 권한을 준다"는 선택지는 그 자리에서 소거합니다. 신규 버킷은 퍼블릭 액세스 차단이 켜져 있고 ACL이 비활성이므로, ACL을 쓰는 선택지는 현행 기본값과도 어긋납니다.

서명 URL과 서명 쿠키

오리진을 감추는 것과 콘텐츠를 볼 자격이 있는 사람만 보게 하는 것은 다른 문제입니다. 후자는 서명 URL 또는 서명 쿠키로 해결합니다. 캐시 동작에 신뢰할 수 있는 키 그룹(TrustedKeyGroups)을 연결하면 그 동작에 매칭되는 모든 요청에 서명이 요구됩니다. 서명은 키 그룹에 등록된 공개 키에 대응하는 개인 키로 만듭니다.

대상 범위 개별 파일 (설치 파일 하나 내려받기 등) 여러 파일 (HLS 영상 조각 전체, 구독자 전용 영역 전체)
URL 변경 URL에 서명 파라미터가 붙습니다 현재 URL을 그대로 둘 수 있습니다

둘 다 쓸 때 서명 URL이 우선합니다. 뷰어가 서명 URL로 요청하면 CloudFront는 서명 쿠키를 보지 않습니다

서명하지 않은 기존 URL에 Expires · Policy · Signature · Key-Pair-Id 쿼리 문자열이 이미 들어 있으면 서명 URL도 서명 쿠키도 쓸 수 없습니다. CloudFront가 그 URL을 이미 서명된 것으로 간주하기 때문입니다.

지리적 제한

CloudFront의 지리적 제한 기능은 국가 단위로 동작하며, 허용 목록(allow list) 또는 차단 목록(block list) 중 하나를 씁니다. 차단된 요청에는 403 Forbidden이 반환되고, 이 오류 응답은 기본적으로 10초 동안 캐시됩니다.

중요한 제약은 지리적 제한이 배포 전체에 적용된다는 것입니다. 콘텐츠 일부에만 다른 제한을 걸어야 하면 배포를 나누거나, 도시 · 우편번호 단위처럼 국가보다 세밀한 기준이 필요하면 서드파티 지오로케이션 서비스와 서명 URL을 조합해야 합니다.

TLS 종료 지점과 ACM 인증서

CloudFront는 뷰어와의 TLS를 엣지에서 종료합니다. 대체 도메인 이름을 쓰려면 인증서가 필요한데, 여기서 리전 제약이 하나 붙습니다. CloudFront API 문서는 CloudFront가 미국 동부(버지니아 북부) 리전 us-east-1의 ACM 인증서만 지원한다고 명시합니다. 서울 리전에서 발급한 인증서를 CloudFront에 붙일 수 없다는 뜻입니다.

SSLSupportMethod는 sni-only가 권장값입니다. SNI를 지원하지 않는 뷰어까지 받으려면 vip를 쓸 수 있으나 AWS는 권장하지 않고 추가 요금이 발생한다고 안내합니다. MinimumProtocolVersion은 콘솔에서 "보안 정책"으로 표시되며, 허용할 최소 TLS 버전과 암호 스위트를 함께 정합니다.

TLS 종료 지점을 묻는 문제는 인증서를 어디에 붙이는가로 갈립니다. ACM 인증서는 CloudFront · Application Load Balancer · Amazon API Gateway에 연결하며, EC2 인스턴스에 직접 설치할 수는 없습니다. 그리고 CloudFront용 인증서만 us-east-1에서 발급해야 합니다. 자세한 내용은 16장 보안 · 암호화 · 거버넌스에서 다룹니다.

WAF와 Shield가 붙는 지점

AWS WAF의 웹 ACL은 범위(scope)가 두 가지입니다. CLOUDFRONT는 CloudFront 배포에 붙는 전역 범위이고, REGIONAL은 Application Load Balancer · Amazon API Gateway · AWS AppSync · Amazon Cognito 사용자 풀 같은 리전 리소스에 붙습니다.

연결 방법도 다릅니다. 리전 리소스는 AssociateWebACL API로 연결하지만, CloudFront는 배포 구성의 WebACLId 필드에 웹 ACL ARN을 넣어 연결합니다. 또한 CLOUDFRONT 범위의 웹 ACL은 us-east-1 엔드포인트에서 만들고 관리해야 합니다.

AWS Shield Standard는 모든 CloudFront 배포와 Route 53 호스팅 영역에 자동으로 적용됩니다. Shield Advanced는 별도 구독이며 대응 팀 지원과 공격 대응 기능이 추가됩니다. WAF는 계층 7 규칙, Shield는 DDoS 완화라는 역할 분담을 기억합니다.

엣지에서 코드 실행 — CloudFront Functions와 Lambda@Edge

요청과 응답을 엣지에서 손보는 방법은 두 가지입니다. CloudFront Functions는 CloudFront에 내장된 JavaScript 실행 환경이고, Lambda@Edge는 AWS Lambda의 확장으로 하나의 리전에 게시한 함수를 CloudFront가 전 세계에 복제합니다.

항목 CloudFront Functions Lambda@Edge
언어 JavaScript Node.js, Python
연결 가능한 이벤트 viewer-request, viewer-response 둘뿐 viewer-request, viewer-response, origin-request, origin-response 넷 전부
실행 시간 서브밀리초 뷰어 이벤트 최대 5초, 오리진 이벤트 최대 30초

판단 기준은 단순합니다. 캐시 키 정규화 · 헤더 조작 · URL 재작성 · 토큰 검증처럼 요청 하나를 짧게 손보는 일은 CloudFront Functions입니다. 외부 서비스 호출, AWS SDK 사용, 요청 본문 읽기, 무거운 처리가 필요하면 Lambda@Edge입니다. 그리고 오리진 쪽 이벤트에서 뭔가를 해야 한다면 선택의 여지가 없습니다 — CloudFront Functions는 오리진 이벤트에 붙지 않습니다.

"오리진 요청 단계에서 다른 AWS 서비스를 호출해 응답을 바꾸라"는 시나리오는 Lambda@Edge입니다. 반대로 "모든 뷰어 요청에 헤더 하나를 추가하되 지연을 최소화하라"는 CloudFront Functions입니다. 비용과 지연이 둘 다 한정어로 붙으면 가벼운 쪽이 정답입니다.

CloudFront와 비용 구조

CloudFront는 성능 서비스이면서 비용 최적화 레버이기도 합니다. 구조는 이렇습니다. 캐시가 적중하면 오리진까지 올라가는 요청이 사라지므로 오리진의 송신 트래픽과 요청 처리 부하가 함께 줄어듭니다. S3 오리진이면 GET 요청 수가 줄고, EC2나 ALB 오리진이면 인스턴스 사용량이 줄어듭니다.

비용을 다루는 문항은 금액을 계산시키지 않습니다. 구조적으로 트래픽이 줄어드는 안을 고르게 합니다. 판단 축은 셋입니다.

  • 캐시 적중률을 올린다 — 캐시 키를 줄이고 TTL을 늘립니다. 가장 큰 레버입니다.
  • 엣지 범위를 좁힌다 — PriceClass_100 · PriceClass_200 · PriceClass_All 중에서 고릅니다. 사용자가 특정 대륙에 몰려 있으면 전 세계 엣지를 살 이유가 없습니다.
  • 무효화를 남발하지 않는다 — 버전이 붙은 파일 이름으로 대체합니다.

"오리진의 데이터 전송 비용을 줄여라"는 요구에 CloudFront가 답이 되는 이유는 같은 바이트를 오리진에서 반복해 내보내지 않기 때문입니다. 데이터 전송 요금의 방향성은 1장에서 정리했고, 전체 비용 레버는 18장 비용 최적화 · 마이그레이션 · 재해 복구에서 다룹니다. 이 사이트는 요금 금액을 쓰지 않습니다. 리전과 시점에 따라 달라지는 값이라 외울 대상이 아니고, 시험도 금액을 묻지 않습니다.

Amazon Route 53 — 호스팅 영역과 레코드

Route 53은 도메인 등록 · 권한 있는 DNS · 상태 확인 세 가지를 합친 서비스입니다. DNS 레코드는 호스팅 영역(hosted zone) 안에 만듭니다.

퍼블릭 호스팅 영역과 프라이빗 호스팅 영역
항목 퍼블릭 호스팅 영역 프라이빗 호스팅 영역
응답 대상 인터넷의 모든 리졸버 연결한 VPC 안에서만
API 구성 HostedZoneConfig.PrivateZone이 false PrivateZone이 true이고 VPC를 연결
용도 공개 서비스의 도메인 내부 서비스 이름 (db.internal.example.com 등)
제약 - CloudFront 배포를 가리키는 별칭 레코드를 만들 수 없습니다

별칭 레코드와 CNAME

별칭(alias) 레코드는 Route 53 고유 기능으로, AWS 리소스를 직접 가리킵니다. API에서는 AliasTarget을 넣고 ResourceRecords와 TTL을 생략합니다. TTL은 대상 리소스의 값을 따릅니다.

별칭 레코드와 CNAME 레코드의 차이
항목 별칭(Alias) CNAME
영역 정점(example.com) 사용 가능 사용 불가 — DNS 표준이 정점에 CNAME을 금지합니다
대상 CloudFront 배포, ELB, S3 정적 웹사이트, API Gateway, VPC 인터페이스 엔드포인트, 같은 영역의 다른 레코드 임의의 도메인 이름
TTL 지정하지 않습니다 (대상의 TTL을 따릅니다) 직접 지정합니다
대상 상태 반영 EvaluateTargetHealth로 대상 리소스의 상태를 상속할 수 있습니다 불가 — 별도 상태 확인이 필요합니다

별칭 대상이 CloudFront 배포인 경우에는 EvaluateTargetHealth를 true로 설정할 수 없습니다. "CloudFront 앞에 상태 확인을 걸어 장애 조치한다"는 구성을 그리기 전에 이 제약을 확인해야 합니다.

Route 53 라우팅 정책 8종 SAA 빈출

Route 53의 라우팅 정책은 8종입니다. 시중 자료 상당수가 지리 근접과 IP 기반을 빠뜨려 6종이나 7종으로 적는데, Route 53 API의 레코드 구조에는 여덟 가지를 구분하는 멤버가 모두 있습니다. 여덟 가지를 전부 알고 있어야 "이 중 해당하지 않는 것은" 형태의 문항에서 실점하지 않습니다.

Route 53 라우팅 정책 8종 — 식별 멤버와 언제 쓰는가
라우팅 정책 레코드의 식별 멤버 언제 쓰는가
단순(Simple) 없음 대상이 하나뿐이고 조건 분기가 없을 때. 기본값이며 SetIdentifier가 필요 없는 유일한 정책입니다
가중치 기반(Weighted) Weight 트래픽을 비율로 나눌 때. 카나리 배포와 블루/그린 전환, A/B 테스트
지연 시간 기반(Latency) Region 여러 리전에 같은 서비스를 배포해 두고 가장 빠른 리전으로 보낼 때
장애 조치(Failover) Failover (PRIMARY / SECONDARY) + HealthCheckId 액티브-패시브 구성. 기본 사이트가 죽으면 대기 사이트로 넘길 때
지리적 위치(Geolocation) GeoLocation (대륙 · 국가 · 미국 주 코드) 사용자가 어디에 있는지로 콘텐츠를 나눌 때. 언어별 사이트, 저작권 · 규제 대응
지리 근접(Geoproximity) GeoProximityLocation (리전 · 로컬 존 그룹 · 좌표 + Bias) 리소스가 어디에 있는지를 기준으로 가까운 쪽에 보내되, 편향값으로 담당 영역 크기를 조절할 때
다중값 응답(Multivalue answer) MultiValueAnswer 여러 IP를 무작위에 가깝게 돌려주고 상태 확인으로 비정상 대상을 빼고 싶을 때
IP 기반(IP-based) CidrRoutingConfig (CIDR 컬렉션 + 위치 이름) 특정 클라이언트 IP 대역을 지정한 엔드포인트로 보낼 때. 통신 사업자별 경로 최적화 등

"Route 53 라우팅 정책은 6가지" 또는 "7가지"라는 서술은 지리 근접과 IP 기반이 빠진 옛 목록입니다. Route 53 레코드 구조에는 GeoProximityLocation과 CidrRoutingConfig가 별개 멤버로 존재하며, 각각 독립된 라우팅 정책에 대응합니다. 이 사이트는 8종으로 서술합니다.

단순 라우팅을 제외한 모든 정책은 SetIdentifier가 필수입니다. 같은 이름과 같은 유형을 가진 레코드가 여러 개 존재할 수 있기 때문에, 그중 무엇인지 구별하는 식별자가 있어야 합니다. SetIdentifier가 눈에 띄면 그 레코드는 단순 라우팅이 아닙니다.

지연 시간 · 지리적 위치 · 지리 근접 — 시험이 노리는 3자 구분

셋 다 "가까운 데로 보낸다"처럼 들리지만 판단 기준이 완전히 다릅니다. 문제에서 어떤 단어가 쓰였는지로 갈립니다.

지연 시간 기반 · 지리적 위치 · 지리 근접의 판단 기준
정책 무엇을 보고 결정하는가 문제에 나오는 신호
지연 시간 기반 Route 53이 측정한 사용자와 리전 사이의 실제 지연 "가장 빠른 응답", "최저 지연 시간", "성능"
지리적 위치 질의가 어디에서 왔는가 (대륙 · 국가 · 미국 주) "이 나라 사용자에게는 이 콘텐츠", "규제상 특정 국가 차단", "언어별 사이트"
지리 근접 질의 위치와 리소스 위치의 거리. Bias로 담당 영역을 넓히거나 좁힘 "트래픽을 한쪽 리전으로 점진적으로 옮기고 싶다", "특정 리소스가 더 넓은 지역을 맡게 하라"

헷갈릴 때 쓰는 규칙은 이렇습니다. 지연 시간은 네트워크 성능이 기준이라 지리적으로 가까운 리전이 답이 아닐 수도 있습니다. 지리적 위치는 성능이 아니라 규정과 콘텐츠의 문제입니다. 지리 근접은 거리 기반이면서 편향값으로 비율을 조정할 수 있는 유일한 정책입니다.

"유럽 사용자는 반드시 유럽 리전에서 처리되어야 한다(데이터 레지던시)"는 지리적 위치입니다. 지연 시간 기반은 상황에 따라 다른 리전을 고를 수 있으므로 규정 준수 요구를 보장하지 못합니다. 반대로 "전 세계 사용자에게 가장 빠른 응답"이라면 지연 시간 기반입니다. 이 한 문장 차이로 정답이 바뀝니다.

다중값 응답은 로드 밸런서의 대체재가 아닙니다. Route 53은 한 응답에 최대 8개의 정상 레코드를 돌려주고, 상태 확인을 붙이지 않은 레코드는 항상 정상으로 간주합니다. 모든 레코드가 비정상이면 비정상 레코드를 최대 8개까지 그대로 응답합니다. 또한 별칭 레코드로는 다중값 응답을 만들 수 없습니다. 부하 분산 자체가 필요하면 7장의 로드 밸런서가 맡습니다.

상태 확인과 장애 조치 라우팅

Route 53 상태 확인은 여덟 가지 유형이 있고, 크게 세 부류입니다. 엔드포인트를 직접 찔러 보는 유형, 다른 상태 확인을 집계하는 유형, 그리고 외부 신호를 읽는 유형입니다.

Route 53 상태 확인 유형
유형 판정 방식
HTTP / HTTPS TCP 연결 후 요청을 보내고 200 이상 400 미만의 상태 코드를 기다립니다
HTTP_STR_MATCH / HTTPS_STR_MATCH 응답 본문의 앞부분 5,120바이트에서 지정한 문자열을 찾습니다
TCP TCP 연결이 되는지만 봅니다. HTTP가 아닌 서비스에 씁니다
CALCULATED 하위 상태 확인들의 정상 개수를 HealthThreshold와 비교합니다
CLOUDWATCH_METRIC CloudWatch 경보 상태를 읽습니다. 프라이빗 리소스처럼 외부에서 찌를 수 없는 대상에 씁니다
RECOVERY_CONTROL Route 53 Application Recovery Controller의 라우팅 컨트롤 상태(ON/OFF)를 따릅니다

요청 간격(RequestInterval)은 10초 또는 30초이며 지정하지 않으면 30초입니다. 실패 임계값(FailureThreshold)은 기본 3회로, 연속 3회 실패해야 상태가 뒤집힙니다. 두 값 모두 생성 후에는 바꿀 수 없습니다.

장애 조치 라우팅

장애 조치 라우팅은 같은 이름과 유형의 레코드 두 개에 PRIMARY와 SECONDARY를 지정하고 HealthCheckId를 붙여 구성합니다. 동작은 다음과 같습니다.

  • 주 레코드가 정상이면 보조의 상태와 무관하게 주로 응답합니다.
  • 주가 비정상이고 보조가 정상이면 보조로 응답합니다.
  • 보조가 비정상이면 주의 상태와 무관하게 주로 응답합니다. 둘 다 죽었을 때는 주를 돌려줍니다.
  • 보조에 상태 확인을 붙이지 않으면, 주가 비정상일 때 보조 엔드포인트의 실제 상태와 관계없이 항상 보조로 응답합니다.

장애 조치 별칭 레코드를 쓸 때는 EvaluateTargetHealth를 true로 설정해야 합니다. 그러지 않으면 대상이 죽어도 Route 53이 알아채지 못합니다.

리전 전체가 죽는 시나리오에서 트래픽을 다른 리전으로 넘기는 장치는 Route 53 장애 조치 라우팅 + 상태 확인입니다. 로드 밸런서는 리전 안의 대상만 다루므로 리전 장애를 넘기지 못합니다. 그리고 DNS 장애 조치의 실제 전환 시간에는 TTL이 그대로 더해집니다. 상태 확인을 붙인 레코드에는 TTL을 60초 이하로 두라고 AWS가 권장하는 이유입니다. 이 값이 재해 복구 설계에서 RTO에 직접 반영됩니다.

AWS Global Accelerator와 CloudFront의 선택

Global Accelerator는 애니캐스트 고정 IP를 발급하고, AWS 엣지 네트워크에서 받은 트래픽을 AWS 글로벌 네트워크를 통해 최적의 엔드포인트로 보냅니다. IP 세트 하나는 최대 2개의 IP 주소를 가지며, 듀얼스택으로 만들면 IPv4 2개와 IPv6 2개를 받습니다.

핵심 차이는 캐시하지 않는다는 점입니다. Global Accelerator는 콘텐츠를 저장하지 않고 경로만 개선합니다. 리스너 프로토콜은 TCP와 UDP이며, 엔드포인트로는 Application Load Balancer, Network Load Balancer, 탄력적 IP 주소, EC2 인스턴스를 등록합니다.

판단 규칙은 두 문장으로 정리됩니다. 캐시할 수 있는 HTTP 콘텐츠라면 CloudFront입니다. 비 HTTP 프로토콜이거나, 클라이언트가 IP를 고정으로 알아야 하거나, 리전 간 장애 조치를 IP 변경 없이 하고 싶다면 Global Accelerator입니다. 게임 서버(UDP), VoIP, IoT 장비처럼 방화벽에 IP를 등록해야 하는 환경이 후자의 전형입니다.

"고정 IP"라는 단어가 나오면 후보는 둘입니다. 리전 안에서 고정 IP가 필요하면 Network Load Balancer, 전 세계에서 하나의 고정 IP가 필요하면 Global Accelerator입니다. "UDP", "게임", "IP 허용 목록"이 함께 보이면 CloudFront는 후보가 아닙니다. 반대로 "정적 파일", "이미지", "동영상 스트리밍", "캐시"가 보이면 CloudFront입니다.

흔한 오해

"Route 53 라우팅 정책은 6가지다" — 8가지입니다. 단순 · 가중치 기반 · 지연 시간 기반 · 장애 조치 · 지리적 위치 · 지리 근접 · 다중값 응답 · IP 기반입니다. 한국어 자료 상당수가 지리 근접과 IP 기반을 빠뜨린 옛 목록을 그대로 옮겨 적었습니다. Route 53 레코드 구조에는 GeoProximityLocation과 CidrRoutingConfig가 독립된 멤버로 들어 있고, 각각 별개의 라우팅 정책입니다. 개수를 묻지 않더라도, 목록에서 빠진 두 개가 정답 선택지로 등장하면 그대로 실점합니다.

"CloudFront를 앞에 두었으니 S3 버킷은 안전하다" — 버킷이 퍼블릭이면 CloudFront를 우회한 직접 접근이 그대로 열려 있습니다. 서명 URL도, 지리적 제한도, WAF 규칙도 CloudFront를 지나야 적용되기 때문에 S3 엔드포인트로 바로 요청하면 전부 무력화됩니다. 버킷은 비공개로 유지하고 OAC를 붙인 뒤, 버킷 정책에서 cloudfront.amazonaws.com 서비스 주체를 AWS:SourceArn 조건과 함께 허용하는 것이 유일한 정답 구성입니다.

"Global Accelerator는 CloudFront의 상위 호환이다" — 둘은 겹치지 않는 도구입니다. Global Accelerator는 캐시하지 않습니다. 정적 콘텐츠를 반복해서 내려받는 워크로드에 Global Accelerator를 쓰면 매 요청이 오리진까지 도달하므로 지연도 비용도 개선되지 않습니다. 반대로 UDP 트래픽이나 고정 IP 요구에 CloudFront를 쓰는 것은 애초에 불가능합니다. 캐시 가능성과 프로토콜이 두 서비스를 가르는 기준입니다.

시험 포인트 정리

항목 사실 함정
Route 53 라우팅 정책 수 8종 — 단순 · 가중치 · 지연 시간 · 장애 조치 · 지리적 위치 · 지리 근접 · 다중값 응답 · IP 기반 지리 근접과 IP 기반을 뺀 옛 목록으로 외워 선택지에서 놓침
지연 시간 대 지리적 위치 지연 시간은 측정된 성능, 지리적 위치는 질의 출발지 데이터 레지던시 요구에 지연 시간 기반을 고름
지리 근접 질의와 리소스의 거리 기준. Bias로 담당 영역 조절 지리적 위치와 같은 것으로 보고 구분하지 못함
SetIdentifier 단순 라우팅을 제외한 모든 정책에 필수 단순 라우팅에도 필요하다고 생각함
다중값 응답 한 응답에 최대 8개의 정상 레코드. 별칭 레코드로는 불가 로드 밸런서 대체재로 오해
별칭 대 CNAME 별칭은 영역 정점에 사용 가능하고 TTL을 지정하지 않음 example.com에 CNAME을 걸려 함
장애 조치 동작 주가 정상이면 주. 보조가 비정상이면 주의 상태와 무관하게 주 둘 다 비정상일 때 응답이 없다고 생각함
상태 확인 기본값 요청 간격 30초, 실패 임계값 3회. 생성 후 변경 불가 나중에 조정하면 된다고 가정
DNS 장애 조치와 TTL 전환 시간에 TTL이 더해진다. 상태 확인 연동 레코드는 TTL 60초 이하 권장 상태 확인 주기만 보고 RTO를 계산
프라이빗 호스팅 영역 연결한 VPC 안에서만 응답. CloudFront 별칭 레코드 생성 불가 내부 도메인으로 CloudFront를 가리키려 함
S3 오리진 보호 OAC + 비공개 버킷 + 버킷 정책의 cloudfront.amazonaws.com 허용 버킷을 퍼블릭으로 열거나 ACL로 권한을 줌
OAC가 OAI보다 나은 점 전 리전 지원, SSE-KMS 지원, PUT/DELETE 지원 둘이 같은 기능이라고 보고 신규 설계에 OAI를 고름
S3 웹사이트 엔드포인트 커스텀 오리진이며 OAC·OAI를 붙일 수 없음 정적 웹사이트 호스팅을 켠 채로 OAC를 쓰려 함
서명 URL 대 서명 쿠키 파일 하나면 서명 URL, 여러 파일이거나 URL을 못 바꾸면 서명 쿠키. 서명 URL이 우선 영상 조각 전체 보호에 서명 URL을 고름
지리적 제한 범위 국가 단위이며 배포 전체에 적용. 차단 시 403 경로별로 다른 국가 제한을 걸 수 있다고 가정
CloudFront용 ACM 인증서 us-east-1에서 발급한 것만 연결 가능 서비스 리전에서 발급해 붙이려 함
WAF 웹 ACL 범위 CloudFront는 CLOUDFRONT 범위(us-east-1 관리), ALB·API Gateway 등은 REGIONAL 리전 웹 ACL을 CloudFront에 붙이려 함
엣지 함수 선택 CloudFront Functions는 뷰어 이벤트만, 네트워크·본문 접근 불가. Lambda@Edge는 4개 이벤트 전부 오리진 요청 단계 작업에 CloudFront Functions를 고름
캐시 적중률 개선 캐시 키를 줄인다. 오리진이 필요한 값은 오리진 요청 정책으로 모든 헤더와 쿠키를 캐시 키에 넣어 캐시가 쪼개짐
무효화 대소문자 구분, 와일드카드 가능, 쿠키·헤더별 모든 벌이 함께 무효화 잦은 갱신을 전부 무효화로 처리 (버전 파일명이 권장)
Global Accelerator TCP/UDP, 정적 애니캐스트 IP, 캐시 없음 정적 콘텐츠 가속에 Global Accelerator를 고름
고정 IP 요구 리전 내부면 NLB, 전 세계 단일 IP면 Global Accelerator CloudFront로 고정 IP를 제공하려 함

이 장의 비용 판단은 하나로 요약됩니다. 같은 바이트를 오리진에서 두 번 내보내지 않는 안이 더 싸다. 캐시 적중률을 올리는 선택지, 엣지 범위를 필요한 만큼만 사는 선택지, 무효화 대신 버전 파일명을 쓰는 선택지가 그 방향입니다. 전체 비용 레버는 비용 빠른참조에 모아 두었습니다.

공식 문서 출처

이 장의 개념 서술과 API 동작은 모두 아래 문서에서 확인했습니다.

  • Amazon CloudFront 개발자 안내서 — CloudFront란 — 배포 · 오리진 · 엣지 로케이션의 기본 개념
  • Amazon CloudFront 개발자 안내서 — 캐시에 콘텐츠가 머무는 기간 관리 — 기본 만료 24시간, Cache-Control max-age와 Expires의 우선순위, 뷰어 요청의 캐시 헤더를 무시한다는 서술
  • Amazon CloudFront 개발자 안내서 — 파일 무효화 — 와일드카드 경로, 대소문자 구분, 버전 파일명 권장 근거
  • Amazon CloudFront 개발자 안내서 — Amazon S3 오리진에 대한 액세스 제한 — OAC 권장 이유 3가지와 버킷 정책 예시, 웹사이트 엔드포인트는 커스텀 오리진이라 OAC를 쓸 수 없다는 제약
  • Amazon CloudFront 개발자 안내서 — 서명 URL과 서명 쿠키 중 선택 — 각각의 적용 조건과 서명 URL 우선 규칙
  • Amazon CloudFront 개발자 안내서 — 콘텐츠의 지리적 배포 제한 — 국가 단위 제한, 403 응답과 기본 10초 캐시, 배포 전체 적용
  • Amazon CloudFront 개발자 안내서 — 엣지에서 함수로 사용자 지정 — CloudFront Functions와 Lambda@Edge의 비교표
  • Amazon CloudFront API 레퍼런스 — DefaultCacheBehavior — 캐시 정책 · 오리진 요청 정책 · 응답 헤더 정책, ForwardedValues와 TTL 필드가 deprecated라는 서술
  • Amazon CloudFront API 레퍼런스 — CustomOriginConfig — 커스텀 오리진의 정의, OriginProtocolPolicy, 오리진 응답 타임아웃 기본 30초와 연결 유지 5초
  • Amazon CloudFront API 레퍼런스 — ViewerCertificate — CloudFront가 us-east-1의 ACM 인증서만 지원한다는 서술, sni-only 권장
  • Amazon CloudFront API 레퍼런스 — OriginAccessControlConfig — 서명 프로토콜 sigv4와 서명 동작 3가지
  • Amazon Route 53 API 레퍼런스 — ResourceRecordSet — 라우팅 정책 8종을 구분하는 멤버(Weight, Region, Failover, GeoLocation, GeoProximityLocation, MultiValueAnswer, CidrRoutingConfig), SetIdentifier 필수 조건, 다중값 응답 최대 8개, 장애 조치 동작 규칙
  • Amazon Route 53 API 레퍼런스 — AliasTarget — 별칭 레코드에서 TTL을 생략한다는 점, EvaluateTargetHealth의 제약
  • Amazon Route 53 API 레퍼런스 — HealthCheckConfig — 상태 확인 유형 8종, 요청 간격 기본 30초, 실패 임계값 기본 3회, 문자열 검색은 앞 5,120바이트
  • Amazon Route 53 API 레퍼런스 — GeoProximityLocation — 리전 · 로컬 존 그룹 · 좌표 중 하나를 지정하며 Bias로 영역 크기를 조절한다는 서술
  • AWS Global Accelerator API 레퍼런스 — 애니캐스트 정적 IP, 표준 가속기와 사용자 지정 라우팅 가속기, API가 us-west-2에서 동작한다는 서술
  • AWS Global Accelerator API 레퍼런스 — EndpointGroup — 트래픽 다이얼, 상태 확인 간격 10초/30초와 기본 30초, 임계값 기본 3회
  • AWS WAF API 레퍼런스 — AssociateWebACL — CloudFront는 이 API가 아니라 배포 구성의 웹 ACL ARN으로 연결한다는 서술
  • AWS WAF API 레퍼런스 — CreateWebACL — CLOUDFRONT 범위와 REGIONAL 범위의 구분, CloudFront 범위는 us-east-1에서 관리
