시험 대비 · 도메인 1

보안 아키텍처 설계 (30%)

Design Secure Architectures는 가중치가 가장 큰 도메인인데 과제 진술은 셋뿐입니다. 범위가 좁고 깊다는 뜻이고, 같은 판단 지점이 시나리오를 바꿔 가며 반복된다는 뜻입니다. 여기서 실점하면 다른 도메인으로 만회하기가 가장 어렵습니다. 반대로 투입 대비 회수가 가장 큰 구간이기도 합니다.

이 페이지는 무엇을 판단해야 하는지를 정리합니다. 판단에 필요한 지식은 2장 IAM, 3장 VPC 네트워킹 기초, 16장 보안·암호화·거버넌스가 담당합니다.

학습 목표

  • 과제 진술 1.1 · 1.2 · 1.3이 각각 무엇을 묻는지 구분하고 담당 챕터를 지목할 수 있습니다.
  • IAM 정책 평가 순서와 정책 유형별 결합 규칙으로 접근 허용 여부를 판정할 수 있습니다.
  • 보안 그룹과 네트워크 ACL의 차이를 근거로 잘못된 선택지를 소거할 수 있습니다.
  • 인터넷을 거치지 않는 접근 요구에 게이트웨이 엔드포인트와 인터페이스 엔드포인트 중 무엇을 쓸지 결정할 수 있습니다.
  • 저장 데이터 암호화 방식을 키 관리 주체와 감사 요구를 기준으로 선택할 수 있습니다.
  • 이 도메인의 판단 지점 18개를 점검표로 삼아 자기 취약 지점을 찾을 수 있습니다.

과제 진술 1.1 · AWS 리소스에 대한 보안 액세스 설계

이 진술의 문항은 대부분 "이 주체가 이 리소스를 호출할 수 있게 하려면" 또는 "이 접근이 왜 거부되는가" 형태입니다. 서비스 이름을 아는 것보다 정책이 어떻게 결합되는지가 훨씬 자주 결정적입니다.

액세스 키가 아니라 IAM 역할 SAA 빈출

이 도메인에서 가장 자주 재활용되는 판단입니다. EC2 인스턴스·컨테이너·Lambda 함수가 AWS API를 호출해야 한다면 답은 IAM 역할입니다. 역할이 전달하는 자격 증명은 임시이고 자동으로 교체되므로, 유출된 키를 찾아 회수하는 문제 자체가 생기지 않습니다.

선택지에 "IAM 사용자를 만들어 액세스 키를 발급하고 인스턴스에 저장한다"가 보이면 거의 항상 오답입니다. 실행 주체별로 역할의 이름이 다를 뿐 결론은 같습니다.

정책 평가 순서와 결합 규칙

접근 허용 여부는 세 줄로 정리됩니다. 기본은 암묵적 거부이고, 어느 정책에서든 명시적 Deny가 하나라도 있으면 즉시 거부이며, 명시적 Allow가 있고 거부가 없으면 허용됩니다. 우선순위는 명시적 Deny 우선, 그다음 명시적 Allow, 마지막이 암묵적 거부입니다.

더 자주 틀리는 것은 순서가 아니라 결합 규칙입니다. 같은 계정 안에서 자격 증명 기반 정책과 리소스 기반 정책은 합집합으로 동작하지만, 권한 경계·SCP·세션 정책은 교집합으로 동작합니다.

정책 유형별 결합 규칙
조합 결과 시험에서의 의미
자격 증명 기반 + 리소스 기반 (동일 계정) 합집합 둘 중 하나만 허용해도 통과합니다
자격 증명 기반 + 권한 경계 교집합 양쪽이 모두 허용해야 통과합니다

자격 증명 기반 + 세션 정책 교집합 역할을 맡을 때 전달한 세션 정책이 상한이 됩니다
권한 경계 + SCP + 자격 증명 기반 셋 다 허용해야 통과 교차 계정 문항에서 원인을 찾을 때 순서대로 확인합니다

교차 계정 접근은 이 규칙의 대표 응용입니다. 다른 계정의 리소스에 접근하려면 호출자 쪽 자격 증명 기반 정책과 리소스 쪽 리소스 기반 정책이 둘 다 허용해야 합니다. 한쪽만 고친 선택지는 오답입니다.

SCP와 권한 경계

서비스 제어 정책(Service Control Policy, SCP)은 조직 전체에 상한을 겁니다. 두 가지 성질만 기억하면 관련 문항이 대부분 풀립니다 — SCP는 권한을 부여하지 않고, 멤버 계정의 루트 사용자에게도 적용됩니다. 루트를 통제할 수 있는 사실상 유일한 수단이라는 점이 자주 출제됩니다.

권한 경계는 개별 IAM 주체에 거는 상한입니다. 적용 범위가 조직이 아니라 주체라는 점이 SCP와의 결정적 차이이며, "개발자에게 IAM 역할을 만들 권한을 주되 자기보다 큰 권한은 못 만들게 한다"는 요구가 나오면 권한 경계가 답입니다.

접근 거부 원인을 찾는 문항은 확인 순서가 정해져 있습니다. 명시적 Deny가 어딘가에 있는가 → SCP가 그 작업을 허용하는가 → 권한 경계 안에 있는가 → 자격 증명 기반 정책이 허용하는가 → (교차 계정이면) 리소스 기반 정책이 허용하는가. 이 순서대로 선택지를 대조하면 대부분 하나만 남습니다.

과제 진술 1.2 · 보안 워크로드와 애플리케이션 설계

이 진술은 네트워크 경계를 묻습니다. 무엇을 퍼블릭 서브넷에 두고 무엇을 프라이빗 서브넷에 두는가, 어떤 계층에서 트래픽을 막는가, 그리고 트래픽이 인터넷을 지나는가가 중심입니다.

"보안 그룹으로 특정 IP를 차단한다"는 선택지는 항상 오답입니다. 보안 그룹에는 거부 규칙이 없습니다. 차단은 네트워크 ACL이나 상위 계층(AWS WAF)의 일입니다.

반대로 네트워크 ACL은 상태 비저장이므로 아웃바운드만 열고 인바운드 반환 트래픽을 허용하지 않으면 응답이 돌아오지 않습니다. "연결은 나가는데 응답이 오지 않는다"는 시나리오는 대개 여기가 원인입니다.

인터넷을 거치지 않는 경로

"트래픽이 퍼블릭 인터넷을 지나면 안 된다"는 제약이 붙으면 암호화 여부가 아니라 경로가 판단 기준이 됩니다. NAT 게이트웨이를 통해 서비스의 퍼블릭 엔드포인트로 나가는 구성은 이 제약을 만족하지 못합니다.

비공개 경로를 만드는 선택지
요구 선택 판단 기준
VPC에서 Amazon S3 · Amazon DynamoDB에 접근 게이트웨이 VPC 엔드포인트 이 두 서비스 전용입니다. 라우팅 테이블에 경로가 추가되는 방식이라 네트워크 인터페이스를 만들지 않습니다
그 밖의 AWS 서비스에 비공개 접근 인터페이스 VPC 엔드포인트(AWS PrivateLink) 서브넷에 네트워크 인터페이스가 생기고 보안 그룹을 연결할 수 있습니다
다른 VPC의 서비스에 비공개 접근 AWS PrivateLink 또는 VPC 피어링 특정 서비스만 노출하려면 PrivateLink, 네트워크를 잇는 것이 목적이면 피어링

게이트웨이 엔드포인트를 쓰면 NAT 게이트웨이를 지나는 트래픽이 줄기 때문에 보안 요구와 비용 요구가 같은 답을 가리키는 경우가 많습니다. 비용 도메인에서도 같은 판단이 나옵니다.

웹 계층 보호

AWS WAF는 HTTP 요청의 내용을 보고 규칙으로 차단합니다. SQL 삽입이나 특정 경로·헤더 패턴을 막는 요구가 나오면 WAF입니다. AWS Shield는 디도스(DDoS) 공격에 대응하며, 표준 보호는 기본 제공되고 상위 보호는 별도 구독입니다.

붙이는 위치도 함께 묻습니다. WAF는 Amazon CloudFront 배포, Application Load Balancer, Amazon API Gateway 같은 요청을 받는 지점에 연결합니다. 네트워크 계층의 광범위한 트래픽 검사가 필요하면 AWS Network Firewall이 답입니다.

NAT 게이트웨이는 지정한 서브넷의 가용 영역 안에서만 동작합니다. 고가용성이 필요하면 가용 영역마다 하나씩 만들고 각 가용 영역의 프라이빗 라우팅 테이블이 자기 가용 영역의 NAT를 가리키게 해야 합니다. 단일 NAT에 다중 가용 영역 프라이빗 서브넷을 붙인 구성은 가용 영역 장애 시 전면 중단과 가용 영역 간 데이터 전송 요금을 동시에 부릅니다. 또한 NAT 게이트웨이에는 보안 그룹을 연결할 수 없습니다.

과제 진술 1.3 · 적절한 데이터 보안 제어 결정

이 진술의 판단 축은 키를 누가 쥐는가와 증적이 남는가입니다. "암호화한다"는 선택지가 여러 개 있을 때, 문제문이 요구한 키 관리 수준으로 갈립니다.

S3 서버 측 암호화 방식과 선택 기준

신규 S3 버킷의 기본값은 2023년에 크게 바뀌었습니다. 퍼블릭 액세스 차단이 켜진 상태로 생성되고, ACL이 비활성(객체 소유권이 버킷 소유자로 강제)이며, 모든 신규 객체가 SSE-S3로 자동 암호화됩니다. 그래서 "암호화를 켜야 한다"거나 "ACL로 권한을 준다"는 서술은 더 이상 기본 구성이 아닙니다.

다만 버킷 버전 관리는 여전히 기본 비활성화입니다. "기본값이 전부 안전해졌다"고 뭉뚱그리면 이 지점에서 틀립니다.

KMS와 봉투 암호화

AWS KMS는 데이터를 직접 암호화하지 않고 데이터 키를 만들어 줍니다. 서비스는 그 데이터 키로 데이터를 암호화하고, 데이터 키 자체는 KMS 키로 암호화해 함께 저장합니다. 이 구조를 봉투 암호화(envelope encryption)라고 합니다. 큰 데이터를 KMS로 왕복시키지 않으면서도 키 통제를 KMS에 남기는 것이 목적입니다.

KMS 키 종류와 선택 기준

증적과 불변성

규정 준수 문항은 기록이 남는가와 지워지지 않는가를 묻습니다. AWS CloudTrail은 누가 어떤 API를 호출했는지를 남기고, AWS Config는 리소스 구성이 규칙에 맞는지를 지속적으로 평가합니다. 둘은 대체 관계가 아니라 질문이 다릅니다.

보관 자체가 요구일 때는 S3 버전 관리와 S3 Object Lock을 씁니다. Object Lock은 지정한 기간 동안 객체 삭제와 덮어쓰기를 막습니다. 민감 데이터가 어디에 있는지 찾아야 한다면 Amazon Macie가 답입니다.

위협 탐지 서비스는 질문이 서로 다릅니다. Amazon GuardDuty는 이상 행위와 위협을, Amazon Inspector는 워크로드의 취약점을, Amazon Macie는 민감 데이터의 위치를, AWS Security Hub는 여러 서비스의 결과를 모아 보는 것을 담당합니다. 문제문의 동사를 보고 고릅니다.

이 도메인의 함정

"보안 그룹으로 특정 IP를 차단한다" — 보안 그룹은 허용 규칙만 지원합니다. 차단은 네트워크 ACL이나 AWS WAF의 일입니다. 이 선택지는 보이는 즉시 소거합니다.

"SCP로 개발 팀에 권한을 부여한다" — SCP는 권한을 부여하지 않습니다. 상한만 정합니다. 실제 허용은 여전히 IAM 정책이 해야 하므로, "SCP만 고치면 된다"는 선택지는 요구를 절반만 충족합니다.

"암호화했으니 인터넷을 지나도 된다" — "인터넷을 경유하면 안 된다"는 제약은 경로에 대한 것입니다. TLS로 암호화한 채 NAT 게이트웨이를 지나 퍼블릭 엔드포인트로 나가는 구성은 이 제약을 만족하지 못합니다. 답은 VPC 엔드포인트 계열입니다.

"버킷 ACL로 접근을 제어한다" — 신규 버킷은 ACL이 비활성 상태로 만들어집니다. 접근 제어는 버킷 정책과 IAM 정책으로 합니다. ACL을 기본 수단으로 서술하는 선택지는 현행 기본 구성과 어긋납니다.

"IAM 정책만 열면 KMS로 암호화된 객체를 읽을 수 있다" — KMS 키에는 키 정책이 따로 있습니다. IAM 정책과 키 정책이 함께 허용해야 복호화가 됩니다. 교차 계정 접근에서는 이 지점이 특히 자주 원인이 됩니다.
