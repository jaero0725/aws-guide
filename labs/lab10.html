VPC 엔드포인트로 S3 비공개 접근

프라이빗 서브넷에서 Amazon S3를 호출하면 기본적으로 NAT 게이트웨이를 지나 인터넷 경로로 나갑니다. VPC 엔드포인트를 만들면 그 트래픽이 VPC 안에서 처리되고, 보안 요구와 비용 요구를 동시에 만족시킵니다.

관련 도메인: 보안 아키텍처 설계(30%) · 비용 최적화 아키텍처 설계(20%)

학습 목표

  • 게이트웨이 엔드포인트와 인터페이스 엔드포인트의 구현 위치 차이를 설명할 수 있습니다.
  • 게이트웨이 엔드포인트가 라우팅 테이블을 어떻게 바꾸는지 확인할 수 있습니다.
  • 엔드포인트 정책으로 접근 가능한 리소스를 제한할 수 있습니다.
  • 인터페이스 엔드포인트의 프라이빗 DNS가 무엇을 바꾸는지 설명할 수 있습니다.
  • 버킷 정책으로 특정 VPC 엔드포인트 경유만 허용할 수 있습니다.

시나리오

실습 1의 네트워크에서 프라이빗 서브넷의 워크로드가 Amazon S3와 AWS Systems Manager를 호출합니다. 요구는 이렇습니다.

  • 이 트래픽이 인터넷을 경유하면 안 됩니다.
  • NAT 게이트웨이를 지나는 데이터양을 줄여야 합니다.
  • 지정된 버킷 외에는 접근할 수 없어야 합니다.
  • 애플리케이션 코드는 바꾸지 않습니다.

아키텍처 개요

게이트웨이 엔드포인트와 인터페이스 엔드포인트 비교
항목 게이트웨이 엔드포인트 인터페이스 엔드포인트(PrivateLink)
구현 위치 라우팅 테이블의 경로 서브넷 안의 네트워크 인터페이스
대상 서비스 Amazon S3, Amazon DynamoDB 대부분의 AWS 서비스와 PrivateLink 서비스
보안 그룹 연결하지 않는다 연결한다
DNS 공용 이름 그대로, 경로만 바뀐다 프라이빗 DNS로 공용 이름을 가로챌 수 있다
온프레미스에서 사용 직접 불가 가능
접근 제어 엔드포인트 정책 엔드포인트 정책 + 보안 그룹

요구를 나누면 이렇게 배정됩니다 — Amazon S3는 게이트웨이 엔드포인트, Systems Manager는 인터페이스 엔드포인트입니다.

구성 단계

1 · 사용 가능한 엔드포인트 서비스 확인

서비스 이름은 com.amazonaws.<리전>.<서비스> 형태입니다. 게이트웨이 유형으로 제공되는 것은 Amazon S3와 Amazon DynamoDB뿐이라는 사실을 위 첫 번째 명령의 출력으로 직접 확인할 수 있습니다.

2 · S3 게이트웨이 엔드포인트

3 · 엔드포인트 정책으로 범위 제한

엔드포인트 정책은 이 엔드포인트를 통해 무엇을 할 수 있는지를 정합니다. 기본값은 전체 허용이므로, 요구 3(지정 버킷만)을 만족시키려면 좁혀야 합니다.

엔드포인트 정책은 권한을 부여하지 않습니다. IAM 정책과 버킷 정책이 이미 허용한 것 중에서 이 경로로 지나갈 수 있는 범위를 한 번 더 좁히는 상한입니다. IAM에서 허용하지 않은 동작이 엔드포인트 정책만으로 가능해지지는 않습니다.

4 · 버킷 쪽에서 경로를 강제

반대 방향의 통제도 가능합니다. 버킷 정책에 특정 엔드포인트를 지나지 않은 요청은 거부하는 조건을 넣으면, 인터넷 경유 접근 자체가 막힙니다.

이 정책은 강력한 만큼 위험합니다. 콘솔이나 사무실에서의 접근까지 전부 막히므로, 운영 도구가 이 버킷에 접근해야 한다면 함께 예외를 두어야 합니다. 적용 전에 누가 이 버킷에 접근하는지 목록을 먼저 만드세요.

5 · 인터페이스 엔드포인트

--private-dns-enabled가 요구 4(코드 무변경)의 핵심입니다. 이 옵션을 켜면 공용 서비스 이름이 VPC 안에서 엔드포인트의 사설 IP로 해석되므로, 애플리케이션은 평소와 같은 엔드포인트를 호출하면 됩니다.

프라이빗 DNS가 동작하려면 VPC의 DNS 확인과 DNS 호스트 이름이 켜져 있어야 합니다. 그리고 인터페이스 엔드포인트에는 보안 그룹이 붙으므로, 워크로드에서 이 엔드포인트로 향하는 HTTPS를 허용해야 합니다. "엔드포인트를 만들었는데 연결이 안 된다"의 가장 흔한 원인입니다.

Systems Manager로 세션 접속까지 하려면 관련 엔드포인트가 여러 개 필요합니다. 어떤 조합이 필요한지는 문서에서 확인하고 만듭니다.

검증 방법

라우팅 테이블이 실제로 바뀌었는가

게이트웨이 엔드포인트를 만들면 DestinationPrefixListId가 채워진 경로가 새로 나타나고 대상이 vpce-로 시작합니다. 이것이 게이트웨이 엔드포인트가 "라우팅 테이블에 구현된다"는 말의 실체입니다.

판단 기준은 단순합니다. S3와 DynamoDB는 게이트웨이 엔드포인트를 거의 항상 만드는 편이 낫습니다. 인터페이스 엔드포인트는 그 서비스로 가는 트래픽이 충분히 클 때 유리하며, 트래픽이 적으면 엔드포인트 항목이 NAT 절감분보다 클 수 있습니다.

프로덕션 고려사항

  • 인터페이스 엔드포인트를 가용 영역마다 둡니다. 한 가용 영역에만 두면 그 가용 영역 장애 시 호출이 끊기고, 평상시에도 가용 영역을 넘는 전송이 생깁니다.
  • 엔드포인트 정책을 기본 전체 허용으로 두지 않습니다. 경로를 좁힌 만큼 권한도 좁히는 것이 일관됩니다.
  • 버킷 정책의 aws:SourceVpce 조건은 신중하게. 적용 범위를 잘못 잡으면 배포 파이프라인이나 운영 도구가 함께 막힙니다.
  • 온프레미스에서 접근해야 하면 게이트웨이 엔드포인트로는 안 됩니다. 전용 회선이나 VPN과 인터페이스 엔드포인트를 조합합니다.
  • 엔드포인트에도 흐름 로그가 유용합니다. 인터페이스 엔드포인트의 네트워크 인터페이스에서 트래픽을 관측할 수 있습니다.
  • 서비스별로 필요한 엔드포인트 목록을 정리해 둡니다. 컨테이너 워크로드라면 ECR·로그·S3 조합이 함께 필요합니다(실습 9).

정리 — 리소스 삭제

버킷 정책에 aws:SourceVpce 조건을 남긴 채 엔드포인트를 지우면 그 버킷에 아무도 접근할 수 없게 됩니다. 엔드포인트를 지우기 전에 버킷 정책을 먼저 되돌리세요.

공식 문서 출처

  • Amazon EC2 API 레퍼런스 — CreateVpcEndpoint — 엔드포인트 유형(Gateway·Interface), 라우팅 테이블·서브넷·보안 그룹 지정, 프라이빗 DNS 옵션
  • Amazon EC2 API 레퍼런스 — ModifyVpcEndpoint — 엔드포인트 정책 변경과 라우팅 테이블 추가·제거
  • Amazon EC2 API 레퍼런스 — DescribeVpcEndpointServices — 리전에서 제공되는 서비스와 유형, 프라이빗 DNS 이름 확인
  • Amazon EC2 API 레퍼런스 — DescribeRouteTables — 접두사 목록 대상 경로의 표현
  • Amazon S3 API 레퍼런스 — PutBucketPolicy — 조건 키를 사용한 접근 제한
  • Amazon VPC 사용 설명서 — NAT 게이트웨이 — 프라이빗 서브넷의 기본 아웃바운드 경로
