EventBridge 이벤트 아키텍처

큐가 한 소비자에게 일을 넘기는 구조라면, 이벤트 버스는 일어난 사실을 알리고 관심 있는 쪽이 각자 반응하는 구조입니다. 생산자는 소비자가 몇인지 알 필요가 없고, 소비자를 늘려도 생산자를 고치지 않습니다.

관련 도메인: 복원력 있는 아키텍처 설계(26%)

학습 목표

  • 사용자 지정 이벤트 버스를 만들고 이벤트를 게시할 수 있습니다.
  • 이벤트 패턴으로 필요한 이벤트만 골라 대상에 전달할 수 있습니다.
  • 대상별 재시도 정책과 배달 못한 편지 대기열을 설정할 수 있습니다.
  • SNS 팬아웃과 EventBridge 라우팅의 구조적 차이를 설명할 수 있습니다.
  • 예약 규칙으로 주기적인 작업을 트리거할 수 있습니다.

시나리오

주문 서비스가 이벤트를 게시하고, 여러 팀이 각자 반응합니다.

  • 주문이 생성되면 알림 팀이 메일을 보냅니다.
  • 주문이 취소되면 정산 팀이 환불을 처리합니다.
  • 금액이 일정 기준을 넘는 주문은 심사 팀이 검토합니다.
  • 새 팀이 생겨도 주문 서비스 코드를 고치지 않아야 합니다.

마지막 조건이 이벤트 버스를 고르는 이유입니다. 구독자를 추가하는 일이 규칙 하나를 만드는 일로 끝납니다.

아키텍처 개요

SNS 팬아웃과 EventBridge 라우팅의 구조 차이
항목 Amazon SNS 팬아웃 Amazon EventBridge
전달 방식 주제를 구독한 모든 대상에 브로드캐스트 이벤트 패턴에 맞는 규칙의 대상에만 전달
필터링 구독 필터 정책으로 메시지 속성 기준 이벤트 본문 구조 전체를 패턴으로 매칭
대상 종류 큐·함수·HTTP·이메일 등 훨씬 다양한 AWS 서비스
AWS 서비스 이벤트 직접 받지 않는다 기본 버스로 들어온다
스키마 정의되지 않는다 스키마 레지스트리로 관리할 수 있다

이 실습은 사용자 지정 버스를 씁니다. AWS 서비스가 내보내는 이벤트는 기본 버스로 들어오므로, 애플리케이션 이벤트를 섞지 않으려면 버스를 나누는 편이 관리하기 쉽습니다.

구성 단계

1 · 사용자 지정 이벤트 버스

2 · 이벤트 형태 정하기

EventBridge 이벤트는 Source · DetailType · Detail 세 가지가 핵심입니다. 이 셋을 규칙에서 매칭하므로, 처음에 명명 규칙을 정해 두면 나중이 편합니다.

Detail은 JSON 객체를 문자열로 인코딩한 값입니다. 객체를 그대로 넣으면 게시가 실패합니다. 응답의 FailedEntryCount가 0인지 반드시 확인합니다 — 일부 항목만 실패해도 API 호출 자체는 성공으로 반환됩니다.

3 · 규칙과 대상

4 · 대상 호출 권한

실습 6과 같은 구조입니다. 대상 쪽에 "EventBridge가 호출해도 된다"는 권한이 있어야 합니다.

SQS 큐가 대상이면 큐 정책에 events.amazonaws.com의 sqs:SendMessage를 허용하고, 조건으로 규칙 ARN을 지정합니다.

5 · 예약 규칙

일정 표현식은 UTC 기준으로 해석됩니다. 위의 cron(0 18 * * ? *)은 한국 표준시로 다음 날 오전 3시입니다. 현지 시각을 그대로 적어 두면 엉뚱한 시각에 실행됩니다.

그리고 예약 규칙은 기본 이벤트 버스에서만 동작합니다. 사용자 지정 버스에 일정 표현식을 붙일 수 없습니다.

검증 방법

패턴을 먼저 시험한다

규칙을 만들기 전에 패턴이 실제 이벤트와 맞는지 확인할 수 있습니다. 이벤트가 전달되지 않는 문제의 대부분은 패턴 불일치입니다.

항목 기대 결과
일반 주문 이벤트 알림 대상만 호출된다
고액 주문 이벤트 알림과 심사 양쪽 규칙에 모두 매칭된다

이벤트가 전달되는지 눈으로 보고 싶다면 규칙의 대상으로 CloudWatch Logs 로그 그룹을 하나 추가하면 됩니다. 어떤 이벤트가 어떤 형태로 도착했는지 그대로 남으므로 디버깅에 유용합니다.

비용 고려

요금이 발생하는 항목
항목 성격
사용자 지정 이벤트 게시한 이벤트 수
AWS 서비스 이벤트 기본 버스로 들어오는 이벤트의 취급이 다르다
대상 호출 호출되는 대상 서비스(Lambda·SQS 등)의 요금이 별도로 발생한다
아카이브와 재생 보관한 이벤트 양과 재생한 이벤트 수
재시도 실패가 반복되면 대상 호출이 늘어난다

비용을 좌우하는 것은 이벤트 수입니다. 모든 상태 변화를 이벤트로 만들면 양이 빠르게 늘어납니다. "누군가 반응해야 하는 사실"만 이벤트로 만들고, 내부 상태 변화는 이벤트로 올리지 않는 편이 좋습니다.

프로덕션 고려사항

  • 이벤트 이름 규칙을 먼저 정합니다. Source는 도메인, DetailType은 과거형 사실 (OrderCreated, PaymentFailed)로 통일하면 규칙이 단순해집니다.
  • 스키마를 관리합니다. 생산자가 필드를 바꾸면 소비자가 조용히 깨집니다. 필드는 추가만 하고 제거·의미 변경은 새 DetailType으로 처리합니다.
  • 대상마다 DLQ를 붙입니다. 전달 실패는 조용히 사라지는 것이 가장 나쁩니다.
  • 아카이브와 재생을 켜 두면 소비자 버그를 고친 뒤 과거 이벤트를 다시 흘려보낼 수 있습니다.
  • 버스를 나눕니다. AWS 서비스 이벤트와 애플리케이션 이벤트를 섞지 않습니다.
  • 교차 계정 전달이 필요하면 버스 리소스 정책으로 다른 계정의 게시를 허용합니다.
  • 순서가 필요하면 이벤트 버스가 아닙니다. EventBridge는 순서를 보장하지 않습니다. 순서가 요구되면 FIFO 큐나 스트림을 씁니다.

정리 — 리소스 삭제

대상이 남아 있으면 규칙을 삭제할 수 없습니다. 대상을 먼저 제거한 뒤 규칙을 지우고, 마지막에 버스를 삭제합니다.
