DynamoDB 테이블 설계

관계형 데이터베이스는 데이터를 정규화한 뒤 질의를 짜지만, Amazon DynamoDB는 접근 패턴을 먼저 적고 그것에 맞춰 키를 정합니다. 이 실습은 주문 데이터를 예로 파티션 키와 정렬 키를 정하고, 두 번째 접근 패턴을 글로벌 보조 인덱스로 지원하는 과정을 따라갑니다.

관련 도메인: 고성능 아키텍처 설계(24%) · 비용 최적화 아키텍처 설계(20%)

학습 목표

  • 접근 패턴에서 파티션 키와 정렬 키를 도출할 수 있습니다.
  • 글로벌 보조 인덱스와 로컬 보조 인덱스의 제약 차이를 설명할 수 있습니다.
  • 온디맨드와 프로비저닝 용량 모드를 선택 기준으로 구분할 수 있습니다.
  • TTL로 오래된 항목을 자동 만료시킬 수 있습니다.
  • 핫 파티션이 생기는 키 설계를 알아보고 피할 수 있습니다.

시나리오

주문 서비스의 데이터를 DynamoDB에 담습니다. 필요한 접근 패턴은 셋입니다.

  1. 고객 한 명의 주문 목록을 최신순으로 조회한다.
  2. 주문 하나를 주문 번호로 조회한다.
  3. 상태가 PENDING인 주문을 오래된 순으로 조회한다(운영 화면).

트래픽은 프로모션 때 크게 튀고 평상시에는 낮습니다. 완료된 주문의 임시 처리 기록은 90일이 지나면 지워도 됩니다.

아키텍처 개요 — 키 설계

접근 패턴에서 도출한 키 설계
접근 패턴 사용할 키 조회 방식
1. 고객의 주문 목록(최신순) 파티션 키 customerId · 정렬 키 orderedAt 기본 테이블 Query, 내림차순
2. 주문 번호로 단건 조회 글로벌 보조 인덱스 파티션 키 orderId 인덱스 Query
3. 상태별 주문 목록 글로벌 보조 인덱스 파티션 키 status · 정렬 키 orderedAt 인덱스 Query, 오름차순
로컬 보조 인덱스와 글로벌 보조 인덱스의 제약 비교
항목 LSI (로컬 보조 인덱스) GSI (글로벌 보조 인덱스)
최대 개수 5개 20개
파티션 키 테이블과 같아야 한다 달라도 된다
크기 제약 파티션 키 값당 10 GB 없음
용량 테이블 용량을 공유 자체 용량을 가진다
나중에 추가 불가 — 테이블 생성 시에만 언제든 추가·삭제 가능

접근 패턴 2와 3의 파티션 키가 테이블과 다르므로 둘 다 GSI여야 합니다. 그리고 운영 중인 테이블에 인덱스를 추가해야 하는 상황이라면 답은 언제나 GSI입니다 — LSI를 갱신하는 API 자체가 존재하지 않습니다.

구성 단계

1 · 테이블 만들기

트래픽이 프로모션 때 크게 튀므로 온디맨드(PAY_PER_REQUEST)로 시작합니다. 용량 모드는 나중에 바꿀 수 있습니다.

--attribute-definitions에는 키로 쓰는 속성만 선언합니다. 나머지 속성은 항목마다 자유롭게 넣을 수 있습니다. 이것이 스키마를 미리 정의하는 관계형 모델과의 근본적인 차이입니다.

2 · 글로벌 보조 인덱스 추가

프로젝션 타입 3종
타입 인덱스에 복사되는 속성 고르는 기준
KEYS_ONLY 키 속성만 저장 용량을 최소화. 나머지는 테이블을 다시 읽어야 한다
INCLUDE 키 + 지정한 속성 화면에 필요한 속성만 골라 담는다. 대개 이 선택이 균형이 좋다
ALL 모든 속성 인덱스만으로 조회가 끝난다. 저장 용량과 쓰기 비용이 커진다

INCLUDE로 지정하는 비키 속성의 총합은 모든 보조 인덱스를 통틀어 100개를 넘을 수 없습니다. 같은 속성을 두 인덱스에 넣으면 2개로 계산됩니다.

3 · TTL로 오래된 항목 자동 만료

TTL 속성에는 에포크 초 단위의 숫자를 넣습니다. 문자열로 넣거나 밀리초로 넣으면 만료가 동작하지 않습니다. 삭제는 즉시가 아니라 백그라운드에서 이뤄지므로, 만료된 항목이 잠시 조회될 수 있습니다. 정확한 만료가 필요한 로직에서는 조회 시점에 한 번 더 걸러야 합니다.

4 · 항목 넣기와 조회

status는 예약어이므로 표현식에 그대로 쓸 수 없습니다. --expression-attribute-names로 별칭을 만들어 씁니다.

그리고 Scan을 습관적으로 쓰지 않습니다. Scan은 테이블 전체를 읽으므로 데이터가 늘수록 비용과 지연이 함께 커집니다. "조회 조건이 키에 없다"면 그것은 인덱스를 하나 더 만들어야 한다는 신호입니다.

비용 고려

용량 모드 선택 기준
모드 AWS 권고 고르는 상황
PAY_PER_REQUEST (온디맨드) 대부분의 워크로드에 권장 트래픽이 예측하기 어렵거나 변동이 클 때, 신규 서비스
PROVISIONED (프로비저닝) 안정적이고 예측 가능한 증가에 권장 용량을 신뢰성 있게 예측할 수 있을 때

이 밖에 비용을 좌우하는 것은 다음입니다.

  • 인덱스 수와 프로젝션. GSI는 자체 저장 공간과 쓰기 용량을 가집니다. ALL 프로젝션은 쓰기마다 인덱스에도 전체 항목을 씁니다.
  • Scan의 사용. 전체 읽기는 데이터가 늘수록 선형으로 비싸집니다.
  • 항목 크기. 읽기·쓰기 용량은 항목 크기 단위로 계산되므로 큰 속성을 굳이 항목 안에 담지 않습니다. 대용량 본문은 Amazon S3에 두고 키만 저장하는 방식이 일반적입니다.
  • TTL로 자동 삭제. 만료 항목을 배치로 지우는 대신 TTL을 쓰면 삭제에 별도의 쓰기 용량이 들지 않습니다.

프로덕션 고려사항

  • 핫 파티션을 피합니다. 날짜나 상태값처럼 값의 종류가 적은 속성을 파티션 키로 쓰면 요청이 한 파티션에 몰려 스로틀링이 납니다. 접미사를 붙여 분산하거나 복합 키로 바꿉니다.
  • 일관성 모델을 이해합니다. 기본 읽기는 최종적 일관성이고, 필요하면 강력한 일관성 읽기를 요청할 수 있습니다. 다만 GSI는 강력한 일관성 읽기를 지원하지 않습니다.
  • DynamoDB Streams로 변경 이벤트를 흘려보내면 집계나 검색 인덱스 갱신을 비동기로 처리할 수 있습니다.
  • DAX는 DynamoDB 앞에 붙는 캐시로, 읽기가 압도적으로 많은 워크로드에서 코드 변경을 거의 하지 않고 지연을 줄입니다.
  • 글로벌 테이블은 여러 리전에서 읽고 쓰는 구성입니다 (케이스 8).
  • 지정 시점 복구를 켜 두면 실수로 지운 데이터를 되돌릴 수 있습니다.
  • IAM 정책으로 항목 수준 접근 제어가 가능합니다. 조건 키로 파티션 키 값을 제한하면 테넌트 격리를 만들 수 있습니다.

정리 — 리소스 삭제

테이블을 지우면 보조 인덱스도 함께 사라집니다. 다만 별도로 만든 온디맨드 백업은 테이블과 무관하게 남으므로 확인합니다.

실수 증상 고치는 법

파티션 키에 값 종류가 적은 속성 사용 핫 파티션과 스로틀링 고유값이 많은 속성이나 복합 키를 쓴다

예약어를 표현식에 직접 사용 유효성 오류가 난다 --expression-attribute-names로 별칭을 쓴다

공식 문서 출처

  • Amazon DynamoDB API 레퍼런스 — CreateTable — 용량 모드(PAY_PER_REQUEST · PROVISIONED)와 권고, LSI 최대 5개·파티션 키 값당 10 GB 제약, GSI 최대 20개, 프로젝션 타입
  • Amazon DynamoDB API 레퍼런스 — UpdateTable — GlobalSecondaryIndexUpdates만 존재하고 LSI를 갱신하는 파라미터가 없다는 사실
  • Amazon DynamoDB API 레퍼런스 — UpdateTimeToLive — TTL 속성 지정 방식과 만료 처리의 성격
  • Amazon DynamoDB API 레퍼런스 — Query — 키 조건 표현식, 인덱스 조회, 정렬 방향과 일관성 옵션
  • Amazon DynamoDB API 레퍼런스 — Scan — 전체 테이블을 읽는 동작과 소비 용량
  • Amazon DynamoDB 개발자 안내서 — 글로벌 테이블 — 다중 리전 복제의 동작
