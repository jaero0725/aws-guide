S3 정적 사이트 + CloudFront + OAC

이 실습의 결론은 하나입니다 — 버킷을 퍼블릭으로 열지 않고도 정적 사이트를 배포할 수 있습니다. 오리진 액세스 제어(Origin Access Control, OAC)를 쓰면 CloudFront 배포만 버킷을 읽을 수 있고 직접 접근은 차단됩니다.

관련 도메인: 보안 아키텍처 설계(30%) · 고성능 아키텍처 설계(24%)

학습 목표

  • 퍼블릭 액세스가 차단된 버킷을 CloudFront 오리진으로 쓸 수 있습니다.
  • 오리진 액세스 제어와 버킷 정책이 어떻게 짝을 이루는지 설명할 수 있습니다.
  • 기본 루트 객체와 사용자 지정 오류 응답을 설정할 수 있습니다.
  • 배포 후 캐시 무효화로 변경을 반영할 수 있습니다.
  • 버킷에 직접 접근했을 때 차단되는지 검증할 수 있습니다.

시나리오

제품 소개 페이지를 정적 파일로 배포합니다. 요구는 이렇습니다.

  • 전 세계 사용자에게 낮은 지연으로 제공해야 합니다.
  • 오리진 버킷은 인터넷에 직접 노출되지 않아야 합니다.
  • HTTPS로만 접근되어야 합니다.
  • 배포 후 변경 사항이 빠르게 반영되어야 합니다.

S3의 정적 웹사이트 호스팅 기능만 쓰면 버킷을 퍼블릭으로 열어야 하고, HTTPS도 직접 제공되지 않습니다. 그래서 비공개 버킷 + CloudFront + OAC가 현재의 표준 조합입니다.

아키텍처 개요

구성 요소와 역할
구성 요소 역할 설정 요점
S3 버킷 정적 파일의 오리진 퍼블릭 액세스 차단 유지, 정적 웹사이트 호스팅은 켜지 않는다
오리진 액세스 제어(OAC) CloudFront가 서명된 요청으로 오리진에 접근 서명 프로토콜 sigv4, 서명 동작 always
버킷 정책 CloudFront 서비스 주체에게만 읽기 허용 조건으로 특정 배포 ARN만 허용
CloudFront 배포 엣지 캐시와 HTTPS 종료 뷰어 프로토콜 정책 redirect-to-https, 기본 루트 객체 지정

신규 S3 버킷은 퍼블릭 액세스 차단이 켜진 상태로 만들어지고, ACL이 비활성화되어 있으며(객체 소유권이 버킷 소유자로 강제), 신규 객체는 SSE-S3로 자동 암호화됩니다. "버킷을 만들고 퍼블릭 읽기 ACL을 붙인다"는 옛 절차는 지금 기본 구성에서 동작하지 않습니다.

다만 버전 관리는 여전히 기본 비활성화입니다. 기본값이 전부 켜졌다고 뭉뚱그리면 틀립니다.

구성 단계

1 · 비공개 버킷 만들기

us-east-1에 버킷을 만들 때는 --create-bucket-configuration을 지정하지 않습니다. 그 리전이 기본값이라 위치 제약을 함께 주면 오류가 납니다.

2 · 오리진 액세스 제어 만들기

OriginAccessControlOriginType은 s3 · mediastore · mediapackagev2 · lambda 중 하나이고, 이 실습에서는 s3입니다. 서명 프로토콜은 sigv4 하나뿐입니다.

3 · 배포 만들기

CachePolicyId에는 AWS가 제공하는 관리형 캐시 정책의 ID를 넣습니다. 정책 목록은 aws cloudfront list-cache-policies --type managed로 조회할 수 있으므로, 위 값을 그대로 쓰지 말고 조회해서 확인한 뒤 씁니다. 쿼리 문자열이나 쿠키를 캐시 키에 포함할지가 캐시 적중률을 좌우합니다.

4 · 버킷 정책으로 배포만 허용

OAC를 만들었다고 접근이 되는 것은 아닙니다. 버킷 정책이 CloudFront 서비스 주체를 허용해야 완성됩니다. 조건으로 배포 ARN을 못 박아 이 배포만 읽을 수 있게 합니다.

조건 없이 cloudfront.amazonaws.com을 허용하면 다른 계정의 배포도 이 버킷을 오리진으로 삼을 수 있습니다. AWS:SourceArn 조건을 반드시 넣습니다.

5 · 배포 후 캐시 무효화

무효화는 편리하지만 남용하면 요금 항목이 됩니다. 프로덕션에서는 파일 이름에 내용 해시를 넣어 새 경로로 배포하고, index.html처럼 이름이 고정된 소수의 파일만 무효화하는 방식이 일반적입니다.

정적 사이트에서 비용을 좌우하는 것은 캐시 적중률입니다. 캐시 키에 불필요한 쿼리 문자열이나 헤더를 넣으면 같은 콘텐츠가 여러 항목으로 나뉘어 적중률이 떨어지고 오리진 요청이 늘어납니다. 구조적 배경은 케이스 6에 있습니다.

프로덕션 고려사항

  • 사용자 지정 도메인과 인증서. CloudFront에 붙일 ACM 인증서는 us-east-1에서 발급해야 합니다. 다른 리전에서 만든 인증서는 붙지 않습니다.
  • 단일 페이지 애플리케이션의 라우팅. 존재하지 않는 경로를 index.html로 돌려주려면 사용자 지정 오류 응답을 설정합니다.
  • 보안 헤더. 응답 헤더 정책으로 콘텐츠 보안 정책 등을 붙일 수 있습니다.
  • 접근 로그. 기본이 꺼짐이므로 필요한 경우 켜고 저장 위치를 정합니다.
  • 지리적 제한. 특정 국가만 허용하거나 차단해야 한다면 배포 수준에서 설정합니다.
  • WAF 연동. 애플리케이션 계층 공격 방어가 필요하면 배포에 웹 ACL을 붙입니다.
  • 버전 관리. 실수로 덮어쓴 파일을 되돌리려면 버킷 버전 관리를 켭니다. 대신 이전 버전 만료 규칙을 함께 둡니다(케이스 3).

정리 — 리소스 삭제

CloudFront 배포는 비활성화한 뒤에야 삭제할 수 있고, 비활성화가 전 엣지에 전파되기까지 시간이 걸립니다. 삭제 요청에는 현재 ETag가 필요합니다.

버킷 버전 관리를 켰다면 rm --recursive만으로는 비워지지 않습니다. 이전 버전과 삭제 마커까지 지워야 버킷을 삭제할 수 있습니다.

공식 문서 출처

  • Amazon CloudFront API 레퍼런스 — CreateOriginAccessControl — 오리진 유형(s3 등), 서명 프로토콜 sigv4, 서명 동작 값
  • Amazon CloudFront API 레퍼런스 — CreateDistribution — 배포 구성의 필수 요소와 DefaultRootObject, 뷰어 프로토콜 정책
  • Amazon CloudFront API 레퍼런스 — CreateInvalidation — 무효화 경로 지정 방식
  • Amazon S3 API 레퍼런스 — PutPublicAccessBlock — 네 가지 차단 설정의 의미
  • Amazon S3 API 레퍼런스 — PutBucketPolicy — 버킷 정책 적용 방식
  • Amazon S3 API 레퍼런스 — CreateBucket — 퍼블릭 액세스 차단 기본 활성화와 ACL 비활성화(BucketOwnerEnforced) 기본값
  • Amazon CloudFront 개발자 안내서 — CloudFront란 — 엣지 캐시의 동작과 배포 상태의 의미
