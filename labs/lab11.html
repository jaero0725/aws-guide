KMS 고객 관리형 키로 암호화

고객 관리형 키를 쓰는 이유는 암호화 자체가 아니라 키에 대한 통제와 감사입니다. 누가 이 키를 쓸 수 있는지 정하고, 언제 누가 썼는지 남기고, 교체 주기를 정하는 일이 전부 여기서 이뤄집니다. 이 실습에서는 봉투 암호화의 흐름도 데이터 키로 직접 확인합니다.

관련 도메인: 보안 아키텍처 설계(30%) · 과제 진술 1.3 적절한 데이터 보안 제어 결정

학습 목표

  • 키 정책과 IAM 정책이 함께 작동하는 방식을 설명할 수 있습니다.
  • 봉투 암호화의 단계를 데이터 키 생성과 복호화로 확인할 수 있습니다.
  • 버킷 기본 암호화를 고객 관리형 키로 설정할 수 있습니다.
  • 버킷 키가 무엇을 줄이는지 설명할 수 있습니다.
  • 자동 교체가 적용되는 키 종류와 주기를 구분할 수 있습니다.

시나리오

규제 대상 문서를 S3 버킷에 보관합니다. 요구는 이렇습니다.

  • 객체는 고객 관리형 키로 암호화되어야 합니다.
  • 누가 언제 키를 썼는지 제시할 수 있어야 합니다.
  • 키를 사용할 수 있는 주체를 특정 역할로 한정해야 합니다.
  • 키는 주기적으로 교체되어야 합니다.

신규 S3 버킷은 이미 SSE-S3로 자동 암호화되지만, 그 키는 AWS가 소유하므로 키 정책도 사용 기록도 우리가 다룰 수 없습니다. 요구 2와 3이 고객 관리형 키를 지목합니다.

봉투 암호화의 흐름

대용량 데이터를 KMS로 직접 암호화하지는 않습니다. KMS는 데이터 키를 만들어 주고, 실제 암호화는 그 데이터 키로 로컬에서 합니다.

  1. KMS에 데이터 키를 요청하면 평문 키와 암호문 키 두 벌을 돌려줍니다.
  2. 애플리케이션이 평문 데이터 키로 데이터를 암호화합니다.
  3. 평문 데이터 키를 메모리에서 지우고, 암호문 데이터 키를 데이터와 함께 저장합니다.
  4. 복호화할 때는 암호문 데이터 키를 KMS에 보내 평문 키를 받아 씁니다.

이 구조 덕분에 대용량 데이터가 KMS를 통과하지 않습니다. KMS가 보는 것은 데이터 키뿐입니다.

구성 단계

1 · 키 정책 작성

키 정책은 키에 붙는 리소스 기반 정책입니다. 키 정책이 계정에 권한 위임을 허용하지 않으면 IAM 정책만으로는 이 키를 쓸 수 없습니다.

첫 번째 문(EnableIamPolicies)을 빼면 계정의 IAM 정책이 이 키에 대해 아무 효력을 갖지 못합니다. 키 정책에 명시된 주체만 쓸 수 있게 되고, 그 주체를 잃으면 키를 되살릴 방법이 없습니다.

KMS는 이런 잠금을 막기 위해 정책 검사를 수행하며, 이를 건너뛰는 옵션이 있지만 실습이든 운영이든 쓰지 않는 편이 안전합니다.

2 · 키 생성과 별칭

KeyManager가 CUSTOMER로 나오면 고객 관리형 키입니다. 별칭을 쓰면 코드와 정책에서 키 ID를 하드코딩하지 않아도 되고, 나중에 키를 교체할 때 별칭만 옮기면 됩니다.

3 · 자동 교체

자동 교체의 적용 범위
항목 내용

고객 관리형 키의 자동 교체 주기는 2022년 5월에 3년에서 1년으로 바뀌었습니다. "3년마다 교체된다"고 쓰인 자료는 현행 기준이 아닙니다.

4 · 버킷 기본 암호화

버킷 키를 켜면 객체마다 KMS를 호출하는 대신 버킷 수준의 키를 재사용해 KMS 호출 수가 줄어듭니다. 객체가 많은 버킷에서 비용과 스로틀링 양쪽에 도움이 됩니다.

객체 수가 많은 버킷에서 SSE-KMS를 쓸 때는 버킷 키를 켜는 것이 사실상 필수입니다. 켜지 않으면 객체마다 KMS 호출이 발생해 비용과 요청 한도 양쪽에서 문제가 됩니다.

프로덕션 고려사항

  • 키를 데이터 분류 단위로 나눕니다. 모든 데이터를 하나의 키로 암호화하면 폭발 반경이 커지고, 키 정책으로 접근을 나누기도 어렵습니다.
  • 키 관리자와 키 사용자를 분리합니다. 키를 지울 수 있는 사람과 데이터를 읽을 수 있는 사람이 같을 이유가 없습니다.
  • 삭제는 예약이며 대기 기간이 있습니다. 키를 지우면 그 키로 암호화된 데이터를 영구히 복호화할 수 없습니다. 대기 기간 안에는 취소할 수 있으므로 절차를 문서로 남깁니다.
  • 다중 리전 키는 재해 복구 구성에서 유용합니다. 다만 리전 간에 키 재료를 공유하는 것이 규정상 허용되는지 먼저 확인합니다.
  • 암호화 컨텍스트를 표준화하면 로그가 훨씬 유용해집니다.
  • 교차 계정 사용이 필요하면 키 정책에서 그 계정을 허용하고, 상대 계정에서도 IAM 정책으로 허용해야 합니다. 양쪽이 모두 필요합니다.
  • 스냅샷과 AMI의 암호화는 키를 따라갑니다. 다른 리전이나 계정으로 공유하려면 대상 쪽에서 접근할 수 있는 키로 다시 암호화해야 합니다.

정리 — 리소스 삭제

키를 삭제하면 그 키로 암호화된 모든 데이터를 복구할 수 없습니다. 삭제는 즉시 실행되지 않고 대기 기간을 거치며, 그 기간 안에는 취소할 수 있습니다. 암호화된 객체를 먼저 정리한 뒤 키 삭제를 예약하세요.

공식 문서 출처

  • AWS KMS API 레퍼런스 — CreateKey — 키 사양(SYMMETRIC_DEFAULT 등)과 키 용도, 키 정책 지정
  • AWS KMS API 레퍼런스 — EnableKeyRotation — 기본 교체 주기 365일, 대칭 암호화 키에만 적용, AWS 관리형 키의 매년 자동 교체
  • AWS KMS API 레퍼런스 — GenerateDataKey — 평문 키와 암호문 키를 함께 반환하는 봉투 암호화 동작, 암호화 컨텍스트
  • AWS KMS API 레퍼런스 — PutKeyPolicy — 키 정책이 키 접근을 통제하는 방식과 정책 잠금 검사
  • AWS KMS API 레퍼런스 — ScheduleKeyDeletion — 삭제 예약과 대기 기간, 취소 가능성
  • Amazon S3 API 레퍼런스 — PutBucketEncryption — SSEAlgorithm 값과 KMSMasterKeyID, BucketKeyEnabled
  • Amazon S3 사용 설명서 — SSE-KMS로 데이터 보호 — 버킷 키가 KMS 호출을 줄이는 방식
